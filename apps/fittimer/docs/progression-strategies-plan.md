# План: универсальная прогрессия FitTimer без усложнения тренировки

Статус: план работ, повторно проверен против текущего `main` 2026-10-02.
PR #456 уже влит в `main`: индивидуальная частота `ex.progEvery`, наследование от `p.progression`, подсчёт только полных выполнений и AI-поле `ЧАСТОТА ПРОГРЕССИИ` уже реализованы.

## 0. Цель

Сделать прогрессию FitTimer универсальной для:
- упражнений с собственным весом;
- гантелей/гирь/штанги и других нагрузок в кг;
- упражнений на время;
- резинок и других нагрузок, которые неудобно выражать килограммами;
- программ, созданных как через AI, так и полностью вручную.

При этом НЕ усложнять саму тренировку.

Во время тренировки пользователь по-прежнему должен видеть только то, что нужно сделать сейчас, и управлять тренировкой через:
- Готово;
- Пропустить;
- Дальше;
- голосовые команды.

Не добавлять обязательный ввод:
- фактических повторов после каждого подхода;
- фактического веса после каждого подхода;
- RIR;
- RPE;
- субъективной оценки каждого сета.

Главный принцип:

> Движок прогрессии становится сложнее, интерфейс тренировки — нет.

AI не должен иметь скрытых возможностей, недоступных ручному редактору. AI только автоматически заполняет ту же модель данных, которую пользователь может настроить сам.

### 1.2. Проверка прогрессии после тренировки

`70-workout.js` уже работает в правильной продуктовой модели:

- считается полное выполнение конкретного упражнения;
- пропущенное/незавершённое упражнение не двигает счётчик;
- когда счётчик достигает порога, упражнение попадает в `state.progCheck`;
- пользователь подтверждает повышение;
- упражнение, отмеченное как тяжёлое, не повышается;
- его счётчик остаётся на пороге, поэтому предложение вернётся после следующего полного выполнения.

Это сохранить.

### 1.3. Индивидуальная частота уже в main

PR #456 уже влит.

Сейчас в коде есть:
- `p.progression` — общая частота по умолчанию;
- `ex.progEvery = null` — наследовать `p.progression`;
- `ex.progEvery = 1..15` — собственная частота упражнения;
- `ex.progEvery = 0` — технически отключить прогрессию этого упражнения;
- `exerciseProgEvery(ex, program)`;
- `programHasProgression(program)`;
- подсчёт только полного выполнения конкретного упражнения;
- partial workout не мешает засчитать полностью выполненное отдельное упражнение;
- skipped/unfinished упражнение счётчик не двигает.

Эту часть повторно не реализовывать.

Важно: `p.progression = 0` уже НЕ является глобальным master-off. У упражнения может быть положительный `ex.progEvery` даже при выключенном program default. UI обязан отражать именно эту семантику.

# 2. Целевая модель

Нужно разделить три независимых понятия:

1. **Что измеряет упражнение**
2. **Какая внешняя нагрузка используется**
3. **Как оно прогрессирует**

Сейчас часть этих понятий смешана.

## 2.1. Основная метрика

Новое поле `metric` НЕ добавлять.

В репозитории уже есть каноническое:

```js
ex.type: 'reps' | 'time'
```

Этого достаточно.

UI:

- Повторения
- Время

В нормализованной runtime-модели можно называть это `metric`, но persistent source of truth остаётся `ex.type`. Это убирает второй источник истины и уменьшает миграцию.

## 2.2. Тип нагрузки

Внутри:

```js
loadType: 'none' | 'weight' | 'level'
```

Где:

- `none` — без внешней нагрузки;
- `weight` — измеримая нагрузка в кг;
- `level` — дискретное сопротивление/сложность без универсального значения в кг.

UI:

**Нагрузка**
- Без дополнительной нагрузки
- Вес
- Сопротивление

Важно: слово `level` пользователю не показывать.

## 2.3. Стратегия прогрессии

Добавить одно явное persistent-поле для новых/отредактированных упражнений:

```js
ex.progMode:
  'reps'
  | 'weight'
  | 'double_range'
  | 'time'
  | 'level'
  | 'parallel'
```

Пользовательские названия:

| Внутри | UI |
|---|---|
| `reps` | Повторы |
| `weight` | Вес |
| `double_range` | Повторы → вес |
| `time` | Время |
| `level` | Повторы → сопротивление / Сопротивление |

Технические имена пользователь не видит.

Отдельно нужен `parallel` — одновременный рост двух осей:
- повторы + вес;
- время + вес.

Причина: текущий ручной редактор уже умеет это через два положительных шага, а `advanceExerciseProgression()` реально повышает обе оси на одном подтверждении. Новый редактор не должен терять существующую возможность.

Но `parallel`:
- не является default;
- AI сам его не выбирает без явного запроса;
- в UI показывается как продвинутый вариант «Повторы и вес одновременно» / «Время и вес одновременно».

# 3. Целевая модель данных без дублирования

На первом этапе НЕ сохранять второй вложенный объект `progression.every/enabled/...` поверх уже существующих полей. Это создало бы два источника истины.

Persistent source of truth на переходном этапе:

```js
ex.type        // 'reps' | 'time' — уже существует
ex.loadType    // 'none' | 'weight' | 'level' — новое
ex.progOn      // включена ли прогрессия — уже существует
ex.progMode    // reps | weight | double_range | time | level | parallel — новое
ex.progEvery   // null | 0 | 1..15 — уже существует после PR #456

// существующие параметры шага и потолка пока сохраняем:
ex.repsStep
ex.timeStep
ex.wStep
ex.repsMax
ex.timeMax
ex.weightMax

// kg остаётся как сейчас:
ex.weight

// level V1:
ex.loadLevels  // ordered array user-visible labels
ex.loadLevel   // базовый индекс 0..N-1

// фактическое текущее состояние:
ex.ps = {
  n,
  cur: {
    reps?,
    sec?,
    kg?,
    level?     // новый текущий индекс сопротивления
  }
}
```

`p.progression` остаётся общей частотой по умолчанию и НЕ переносится внутрь упражнения.

## 3.1. Нормализованная runtime-модель

Движок получает единый вычисляемый объект:

```js
getProgressionStrategy(ex, program) => {
  enabled,
  every,
  mode,
  metric,
  loadType,
  reps: {step, max},
  time: {step, max},
  weight: {step, max},
  level: {current, max}
}
```

Этот объект не обязан храниться в JSON программы. Он собирается из новых полей и legacy-полей.

Правила приоритета:
1. `ex.type` — источник метрики.
2. Если есть `ex.loadType`, он главный; иначе adapter выводит `weight` из `trackWeight/hasWeight`, иначе `none`.
3. `ex.progOn=false` всегда выключает прогрессию.
4. Если есть `ex.progMode`, он главный; иначе mode выводится из legacy.
5. Частота берётся только через существующий `exerciseProgEvery(ex,p)`: `ex.progEvery` → fallback `p.progression`.
6. Шаги/потолки на первой версии читаются из существующих `repsStep/timeStep/wStep/*Max`.
7. Для `level` текущая фактическая ступень берётся из `ps.cur.level`, а при её отсутствии — из `ex.loadLevel`.

Это даёт единый strategy engine без большой миграции storage-схемы.

## 3.2. Примеры persistent-модели

### Повторы без веса

```js
{
  type: 'reps',
  loadType: 'none',
  progOn: true,
  progMode: 'reps',
  progEvery: null,
  value: '12-14',
  repsStep: 2,
  repsMax: 20
}
```

### Гантели, двойная прогрессия

```js
{
  type: 'reps',
  loadType: 'weight',
  trackWeight: true, // compatibility mirror на переходном этапе
  weight: 5,
  value: '8-10',
  progOn: true,
  progMode: 'double_range',
  progEvery: 2,
  repsStep: 1,
  repsMax: 14,
  wStep: 1,
  weightMax: 12
}
```

### Планка

```js
{
  type: 'time',
  loadType: 'none',
  value: 45,
  progOn: true,
  progMode: 'time',
  progEvery: null,
  timeStep: 5,
  timeMax: 60
}
```

### Резинка

```js
{
  type: 'reps',
  loadType: 'level',
  value: '12-15',
  loadLevels: [
    {key:'light'},
    {key:'medium'},
    {key:'strong'},
    {key:'veryStrong'}
  ],
  loadLevel: 1,
  progOn: true,
  progMode: 'level',
  progEvery: 2,
  repsStep: 2,
  repsMax: 18,
  ps: {n: 0, cur: {level: 1}}
}
```

# 4. Compatibility со старой моделью

Нельзя одномоментно удалить:
- `prog`;
- `progOn`;
- `trackWeight`;
- `repsStep`;
- `timeStep`;
- `wStep`;
- `repsMax`;
- `timeMax`;
- `weightMax`;
- `dualProg`.

Сначала нужен adapter.

## 4.1. Функция нормализации

Добавить:

```js
getProgressionStrategy(ex, program)
```

Она возвращает runtime-структуру из раздела 3.1.

Если `ex.progMode` есть — использовать его.

Иначе вывести mode из legacy без изменения поведения.

### Старое reps-only

```text
type=reps
repsStep > 0
weight axis отсутствует или wStep = 0
```

→ `mode = reps`

### Старый weight-only

```text
trackWeight=true
wStep > 0
repsStep = 0
dualProg=false
```

→ `mode = weight`

### Старая double progression

```text
trackWeight=true
dualProg=true
repsStep > 0
wStep > 0
```

→ `mode = double_range`

### Старое time-only

```text
type=time
timeStep > 0
weight axis отсутствует или wStep = 0
```

→ `mode = time`

### Legacy parallel — обязательно сохранить

Текущий `advanceExerciseProgression()` вне double progression умеет на одном подтверждённом шаге менять сразу две оси.

Поэтому:

```text
type=reps + trackWeight=true + dualProg=false
repsStep > 0 + wStep > 0
```

→ `mode = parallel`

и:

```text
type=time + trackWeight=true
timeStep > 0 + wStep > 0
```

→ `mode = parallel`

Adapter и migration tests обязаны воспроизводить прежний next step 1:1.

В новом ручном UI `parallel` остаётся доступен как продвинутый вариант, чтобы не потерять существующую функциональность. При этом recommended/default режимом он не является.

## 4.2. Запись новых данных

Для новых/вручную отредактированных упражнений сохранять:
- `loadType`;
- `progMode`;
- существующие step/max;
- существующий `progEvery`.

На переходном этапе:
- для `loadType='weight'` продолжать зеркалить `trackWeight=true`;
- для старых частей кода при необходимости поддерживать `dualProg = (progMode==='double_range')`;
- не вводить второй `progression.every`;
- не вводить второй `progression.enabled`.

Legacy cleanup — отдельный поздний этап после стабилизации.

# 5. Дефолты ручного редактора

Ручной редактор должен самостоятельно выбрать разумную прогрессию без AI.

Источник истины — не название упражнения.

Нельзя делать:
- увидели слово «резинка» в названии → автоматически выбрали level;
- увидели слово «планка» → автоматически выбрали time.

Для ручного редактора стратегия определяется только по явно выбранным пользователем:
- метрике;
- типу нагрузки.

## 5.1. Матрица дефолтов

```text
reps + none
→ reps

reps + weight
→ double_range

reps + level
→ level с ростом повторов перед переходом уровня

time + none
→ time

time + weight
→ time

time + level
→ time
```

Для `time + weight` пользователь может вручную выбрать weight, если хочет фиксированное время и рост веса.

Для `time + level` пользователь может вручную выбрать рост сопротивления.

# 9. Частота проверки

После PR #456 программа имеет default, упражнение может его переопределять.

## 9.1. Уровень программы

После PR #456 `p.progression` — это default frequency, а не глобальный выключатель. Поэтому program UI не должен обещать «выключить всю прогрессию».

Рекомендуемый UI:

```text
Повышение нагрузки

Обычно предлагать после
[4 выполнений упражнения ▾]
```

В select дополнительно:

```text
Не задавать общую частоту
```

Это записывает `p.progression=0`.

Подсказка:

```text
Это общая частота для упражнений без своей настройки.
Считаются только полные выполнения конкретного упражнения.
Упражнение со своей частотой продолжит работать независимо от общей настройки.
```

То есть program-level UI больше не выглядит как master ON/OFF.

Если хочется сохранить существующий `bProgOn` в первой маленькой UI-пачке, его временная подпись должна быть «Использовать общую частоту», а не «Предлагать повышение нагрузки». В конечном UI лучше один select без отдельного тумблера.

## 9.2. Уровень упражнения

Поле:

```text
Проверять повышение
[Как в программе — после 4 выполнений ▾]
```

Варианты:

- Как в программе — после N выполнений
- После 1 выполнения
- После 2 выполнений
- ...
- После 15 выполнений

Не показывать «0 — Без прогрессии» в этом select.

# 10. Унификация level / сопротивления

## 10.1. Почему не показываем «Уровень 2»

Число не объясняет человеку, что физически делать.

Плохо:

```text
Уровень 2 → Уровень 3
```

Хорошо:

```text
Среднее сопротивление → Сильное сопротивление
```

или:

```text
Красная резинка → Синяя резинка
```

## 10.2. Модель шкалы V1

На первой версии не вводить отдельную profile-библиотеку шкал и `loadScaleId`. Это слишком рано добавляет ещё один sync/reference слой.

Хранить snapshot шкалы прямо в упражнении:

```js
loadLevels: [
  { key: 'light' },
  { key: 'medium' },
  { key: 'strong' },
  { key: 'veryStrong' }
],
loadLevel: 1
```

Где `loadLevel` — базовый индекс.

Текущая прогрессированная ступень:

```js
ex.ps.cur.level
```

Алгоритм всегда показывает пользовательский label, а не индекс.

Formatter:
- если у элемента есть `label` → показывать его как пользовательский текст;
- если есть built-in `key` → брать локализованное название через i18n.

Пример custom level:

```js
{ label: 'Красная 15–25 lb' }
```

Так встроенные «Лёгкое / Среднее / Сильное» корректно переключаются RU/EN, а пользовательские цвета/номера остаются ровно такими, как их назвал человек.

В V1 переход уровня всегда на следующую соседнюю ступень. Настройка «ШАГ УРОВНЯ = 2» не нужна пользователю и не нужна движку.

Потолок уровня = последний элемент `loadLevels`. Отдельный `level.max` тоже не нужен в V1.

## 10.3. Пользовательские шкалы

Пользователь может создать свою шкалу.

Пример:

```text
Мои резинки

1. Жёлтая
2. Красная
3. Синяя
4. Чёрная
```

Или:

```text
Эспандер
3
4
5
6
7
```

UI всегда показывает label.

При выборе «Сопротивление» ручной редактор сразу показывает текущую шкалу и позволяет её переименовать. Пользователь может оставить встроенную относительную шкалу или сделать её физически конкретной: «Красная», «Чёрная», «№3», «20–30 lb», «дальше от крепления» и т.п.

Внутренне прогрессия двигается по индексу массива.

## 10.4. Где хранить шкалы

V1: embedded snapshot в упражнении.

Почему:
- программа самодостаточна при sharing/import/export;
- каталог и программа тренера не зависят от profile reference;
- sync уже переносит программу целиком;
- нет проблемы «шкала удалена из профиля, а программа на неё ссылается»;
- проще AI round-trip.

В будущем можно добавить пользовательскую библиотеку «Мои шкалы сопротивления» как convenience-функцию: она копирует выбранную шкалу в упражнение. Но runtime программы всё равно должен иметь собственный snapshot labels.

# 12. Что означает progMode=level

Нужны два пользовательских сценария внутри одного mode.

## 12.1. Только сопротивление

Если `repsStep=0`:

```text
12 повторов · Среднее
↓
12 повторов · Сильное
```

## 12.2. Повторы → сопротивление

Default для `reps + level`:

```text
12–15 · Среднее
↓
14–17 · Среднее
↓
16–18 · Среднее
↓
12–15 · Сильное
```

То есть наличие `repsStep > 0` определяет первую стадию.

Когда верх диапазона достигает `repsMax`:
- если есть следующий label в `loadLevels` → `ps.cur.level += 1`, повторы сбрасываются к базовому `ex.value`;
- если текущий level уже последний → упражнение на полном потолке.

Для `time + level`, если пользователь вручную выбрал рост сопротивления, время остаётся фиксированным, а level просто идёт на следующую ступень.

Не создавать отдельный sixth mode.

## 13.1. Где использовать preview

# 14. advanceExerciseProgression()

Переписать как dispatcher стратегий.

Концептуально:

```js
function advanceExerciseProgression(ex, program) {
  const p = getProgressionStrategy(ex, program);

  switch (p.mode) {
    case 'reps':
      return advanceReps(ex, p);

    case 'weight':
      return advanceWeight(ex, p);

    case 'double_range':
      return advanceDoubleRange(ex, p);

    case 'time':
      return advanceTime(ex, p);

    case 'level':
      return advanceLevel(ex, p);

    case 'parallel':
      return advanceParallel(ex, p);
  }
}
```

Каждая стратегия должна иметь:
- `preview`;
- `advance`;
- `atCeiling`;
- validation.

Желательно одна реализация расчёта для preview и apply:

```js
const next = computeNextProgression(ex, strategy);
```

`preview` только показывает `next`.

`apply` записывает `next` в `ps.cur`.

Не дублировать формулы.

# 15. Потолки

Каждая растущая ось имеет явный потолок.

- reps → max reps;
- time → max seconds;
- weight → max kg;
- level → последний элемент `loadLevels`.

Если достигнут полный потолок стратегии:
- счётчик больше не растёт;
- предложение повышения не появляется;
- если есть `ЗАМЕНА`, интерфейс может отдельно предложить следующий вариант упражнения.

Не смешивать «повысить нагрузку» и «заменить упражнение» в одну автоматическую операцию на первом этапе.

# 19. AI-протокол

AI должен использовать ту же модель, что ручной редактор.

Добавить/нормализовать понятия:

- тип прогрессии;
- частота упражнения;
- тип нагрузки;
- сопротивление;
- шкала сопротивления;
- текущий уровень;
- ordered шкала сопротивления.

Не обязательно сразу менять публичный plain-text протокол на полностью новую форму. Можно сначала научить parser преобразовывать новые labels в новую модель.

## 19.1. Protocol: минимально расширять существующий формат

Не добавлять `ТИП ПРОГРЕССИИ` только ради новых `reps/weight/double_range/time`: текущий протокол уже однозначно описывает их через:
- `ФОРМАТ`;
- `ШАГ / ШАГ ПОВТОРОВ / ШАГ ВРЕМЕНИ / ШАГ ВЕСА`;
- `ПРИ ПОТОЛКЕ`;
- потолки.

Parser после разбора сам выставляет `progMode`.

`ЧАСТОТА ПРОГРЕССИИ` уже существует после PR #456.

Новые protocol labels нужны только для сопротивления, которого раньше не было. Например:

```text
НАГРУЗКА: сопротивление
СОПРОТИВЛЕНИЕ: Среднее
УРОВНИ СОПРОТИВЛЕНИЯ: Лёгкое | Среднее | Сильное | Очень сильное
```

Для `level`:
- `ШАГ ПОВТОРОВ` и `ПОТОЛОК ПОВТОРОВ` продолжают описывать рост повторов;
- переход сопротивления всегда идёт на следующую ступень, отдельный `ШАГ УРОВНЯ` в V1 не нужен.

Старые программы без новых labels должны round-trip без изменения смысла.

## 19.2. AI-дефолты

AI:

- reps + none → reps;
- reps + kg → double_range в большинстве силовых упражнений;
- reps + resistance band → level;
- time + none → time;
- warmup → progression off.

`parallel` AI не выбирает сам по умолчанию. Только если пользователь явно просит одновременно повышать обе оси или редактируется существующее упражнение с таким режимом.

AI может отклоняться от default, если программа этого требует.

# 23. Валидация

Добавить единый:

```js
validateProgression(ex)
```

Примеры:

### reps

- step > 0;
- max > текущей верхней границы.

### weight

- loadType=weight;
- weight step > 0;
- max weight > current weight.

### double_range

- ex.type=reps;
- loadType=weight;
- rep step > 0;
- weight step > 0;
- rep max > starting upper bound;
- weight max > current/base weight.

### time

- ex.type=time;
- step > 0;
- max > current seconds.

### level

- loadType=level;
- loadLevels содержит минимум 2 непустых label;
- loadLevel и ps.cur.level (если есть) находятся в диапазоне loadLevels;
- если нужен следующий шаг уровня, текущий индекс не последний;
- если reps тоже растут — reps max валиден.

UI не должен позволять сохранить заведомо противоречивую комбинацию.

# 25. Синхронизация

`progMode`, `loadType`, `loadLevels`, `loadLevel` и `ps.cur.level` должны синхронизироваться вместе с программой.

Проверить:
- профильный storage;
- cloud sync;
- backup/export;
- import;
- trainer snapshots;
- catalog;
- shared programs;
- AI-edit copy;
- восстановление после переустановки.

Особенно проверить:
- старый `ps.cur` не теряется при миграции на новую стратегию;
- sanitizer в `30-progress-media.js` явно сохраняет новый `ps.cur.level` (сейчас он пересобирает `cur` только из `reps/sec/kg` и иначе level будет молча удалён);
- `exerciseLoad()` и `workoutLoadSnapshot()` расширены данными сопротивления, иначе история «было → сегодня» не сможет показать level;
- import/share sanitizer валидирует `loadLevels/loadLevel/ps.cur.level`;
- backup и cloud sync не отбрасывают новые поля.

# 26. Каталог и программы тренера

Каталог должен хранить базовую prescription-модель.

Пользовательская текущая прогрессия остаётся локальным/профильным состоянием программы пользователя через `ps`, как сейчас.

При обновлении каталожной/тренерской программы:
- не сбрасывать пользовательский progression state у совпавшего упражнения без причины;
- сопоставление делать по стабильному `ex.id`, а не по имени;
- изменение progression policy тренером должно обновлять стратегию осознанно.

# 27. Перенос изображений и AI-редактирование

Новая progression модель не должна ломать уже реализованный перенос media при AI-редактировании.

Для одинакового упражнения по `КОД`:
- сохранить media;
- сохранить текущий progression state, если новая политика совместима;
- если AI намеренно поменял диапазон/тип нагрузки/стратегию, использовать новые параметры как policy, но аккуратно нормализовать текущее состояние.

Текущая `carryExerciseProgress()` уже существует, поэтому не создавать параллельную функцию с тем же назначением. Расширить её и `progBaseKey()`.

`progBaseKey()` должен учитывать минимум:
- `ex.type`;
- `loadType`;
- базовое `value`;
- базовый weight или `loadLevel`;
- `progMode`;
- для level — snapshot `loadLevels`.

Правило:
- совместимая база/стратегия → переносить весь `ps`;
- изменилась только частота `progEvery` → `ps.cur` сохранять, `ps.n` clamp к новой частоте;
- несовместимая база/тип нагрузки/шкала → сохранить только разумный `ps.n`, а `ps.cur` очистить;
- для level никогда не переносить индекс в другую шкалу только потому, что число совпало.

Не копировать `ps.cur` вслепую между несовместимыми форматами.

# 31. Тест-план

## Unit: стратегия

Для каждого mode:
- обычный шаг;
- ровно перед потолком;
- достижение потолка;
- уже на потолке;
- invalid config;
- every inherit;
- every override;
- progression disabled.

## Double range

Обязательно:

```text
8-10
9-11
10-12
...
12-14
→ +weight
→ 8-10
```

Проверить сохранение ширины диапазона.

## Level

```text
12-15 medium
14-17 medium
16-18 medium
12-15 strong
```

Проверить последний level.

## Workout

- done всех сетов → счётчик +1;
- один skipped set → упражнение не считается полным;
- partial workout, но конкретное упражнение полностью выполнено → считается;
- hard/keep → не повышается;
- после keep вопрос возвращается после следующего выполнения.

## UI

- irrelevant fields скрыты;
- switch off;
- default strategy;
- custom strategy;
- weight → level → weight не теряет draft value;
- preview совпадает с apply.

## AI

- manual equivalent;
- roundtrip;
- level labels;
- custom scale;
- отсутствие выдуманных цветов.

## Migration

Снимки реальных старых программ:
- reps;
- time;
- weighted weight-only;
- weighted reps + weight simultaneously (parallel);
- weighted time + weight simultaneously (parallel);
- dual;
- уже прогрессированные;
- на потолке;
- legacy без `progOn`.

До и после adapter текущая нагрузка и следующий шаг должны совпадать.

Отдельно:
- `p.progression=0 + ex.progEvery>0` остаётся активным override;
- `progEvery=0` корректно отображается как выключенное упражнение;
- `ps.cur.level` переживает sanitize/save/reload/share;
- level snapshot в истории показывает правильный label.

# 32. Что НЕ делать в рамках этой задачи

Не добавлять:
- RIR;
- RPE;
- actual reps по сетам;
- actual kg по сетам;
- обязательную оценку «легко/нормально/тяжело»;
- top set/backoff;
- продвинутую periodization;
- автоматический deload;
- прогноз 1RM;
- forced progression без подтверждения пользователя.

Это отдельные продукты/режимы и противоречат текущему hands-free UX FitTimer.

# 33. Инварианты источников истины

Перед реализацией зафиксировать и не нарушать:

- метрика: только `ex.type`;
- program default frequency: только `p.progression`;
- exercise frequency override: только `ex.progEvery`;
- progression on/off упражнения: `ex.progOn`;
- новый явный strategy mode: `ex.progMode` (включая advanced `parallel`; fallback из legacy, если отсутствует);
- тип нагрузки: `ex.loadType` (fallback из legacy `trackWeight`, если отсутствует);
- текущие reps/sec/kg/level: только `ex.ps.cur`;
- базовый level: `ex.loadLevel`;
- labels level V1: embedded `ex.loadLevels`.

Не добавлять параллельные `metric`, `progression.every`, `progression.enabled` до отдельного осознанного cleanup/migration.

# 34. Критерий готовности всей задачи

Функционал считается готовым, если:

1. Старые программы продолжают работать без сброса текущей нагрузки.
2. Новую программу можно полностью собрать вручную без AI.
3. Для обычного упражнения пользователь не обязан понимать терминологию прогрессии.
4. FitTimer предлагает разумный тип прогрессии по ex.type + loadType.
5. Продвинутый пользователь может изменить стратегию вручную, включая существующий режим одновременного роста двух осей.
6. Гантели, вес тела, время и резинки работают через одну архитектуру.
7. Сопротивление всегда показывается понятным label, а не абстрактным номером.
8. Перед повышением пользователь видит точное `сейчас → будет`.
9. Ничего не повышается без подтверждения.
10. Во время тренировки не добавляется ни одного обязательного действия.
11. AI использует те же возможности, что ручной редактор.
12. Preview и реально применяемая прогрессия используют один расчёт.
13. Индивидуальная частота упражнения работает независимо от частоты программы.
14. Partial/skipped логика остаётся корректной.
15. Sync/import/catalog/trainer не теряют progression state.

# 35. Рекомендуемый конечный UX в одном примере

Пользователь вручную создаёт:

```text
Махи гантелей в стороны
Повторения: 8–10
Нагрузка: Вес
5 кг
```

FitTimer сам предлагает:

```text
Со временем сложнее
Повторы → вес
```

Внутри:

```text
Повторы: +1 до 14
Потом: +1 кг и снова 8–10
Максимальный вес: 12 кг
Проверять: как в программе — после 2 выполнений
```

Во время тренировки:

```text
Махи гантелей в стороны
8–10 повторов
5 кг
```

Никаких дополнительных вопросов.

После нужного количества выполнений:

```text
Пора немного увеличить нагрузку

Махи гантелей в стороны
8–10 × 5 кг
→ 9–11 × 5 кг

[Оставить как есть]

[Применить изменения]
```

Это и есть целевая модель: мощная прогрессия под капотом, но простой FitTimer для человека.

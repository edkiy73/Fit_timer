# План: универсальная прогрессия FitTimer без усложнения тренировки

Статус: план работ.
Сверено с текущим `main` и открытым PR #456 на 2026-10-02.

## 0. Цель

Сделать прогрессию FitTimer универсальной для:
- упражнений с собственным весом;
- гантелей/гирь/штанги и других нагрузок в кг;
- упражнений на время;
- резинок и других нагрузок, которые неудобно выражать килограммами;
- программ, созданных как через AI, так и полностью вручную.

При этом НЕ усложнять саму тренировку.

Во время тренировки пользователь по-прежнему должен видеть только то, что нужно сделать сейчас, и управлять тренировкой через:
- Готово;
- Пропустить;
- Дальше;
- голосовые команды.

Не добавлять обязательный ввод:
- фактических повторов после каждого подхода;
- фактического веса после каждого подхода;
- RIR;
- RPE;
- субъективной оценки каждого сета.

Главный принцип:

> Движок прогрессии становится сложнее, интерфейс тренировки — нет.

AI не должен иметь скрытых возможностей, недоступных ручному редактору. AI только автоматически заполняет ту же модель данных, которую пользователь может настроить сам.

# 2. Целевая модель

Нужно разделить три независимых понятия:

1. **Что измеряет упражнение**
2. **Какая внешняя нагрузка используется**
3. **Как оно прогрессирует**

Сейчас часть этих понятий смешана.

## 2.1. Основная метрика

Внутри:

```js
metric: 'reps' | 'time'
```

UI:

- Повторения
- Время

Это заменяет зависимость бизнес-логики от размытого понятия `type`, но старое `type` пока можно оставить compatibility-полем.

## 2.2. Тип нагрузки

Внутри:

```js
loadType: 'none' | 'weight' | 'level'
```

Где:

- `none` — без внешней нагрузки;
- `weight` — измеримая нагрузка в кг;
- `level` — дискретное сопротивление/сложность без универсального значения в кг.

UI:

**Нагрузка**
- Без дополнительной нагрузки
- Вес
- Сопротивление

Важно: слово `level` пользователю не показывать.

## 2.3. Стратегия прогрессии

Внутри:

```js
progression.mode:
  'reps'
  | 'weight'
  | 'double_range'
  | 'time'
  | 'level'
```

Пользовательские названия:

| Внутри | UI |
|---|---|
| `reps` | Повторы |
| `weight` | Вес |
| `double_range` | Повторы → вес |
| `time` | Время |
| `level` | Повторы → сопротивление / Сопротивление |

Не использовать технические имена в интерфейсе.

# 3. Новая структура progression

Целевая структура:

```js
progression: {
  enabled: true,

  // null = наследовать программу
  // 0 = технически выключено для compatibility/import
  // 1..15 = собственная частота
  every: null,

  mode: 'double_range',

  reps: {
    step: 1,
    max: 14
  },

  time: {
    step: 5,
    max: 60
  },

  weight: {
    step: 1,
    max: 12
  },

  level: {
    step: 1,
    max: 3
  }
}
```

Не все секции обязательны.

Примеры.

### Повторы без веса

```js
{
  metric: 'reps',
  loadType: 'none',
  progression: {
    enabled: true,
    every: null,
    mode: 'reps',
    reps: { step: 2, max: 20 }
  }
}
```

### Гантели, двойная прогрессия

```js
{
  metric: 'reps',
  loadType: 'weight',
  weight: 5,
  value: '8-10',
  progression: {
    enabled: true,
    every: 2,
    mode: 'double_range',
    reps: { step: 1, max: 14 },
    weight: { step: 1, max: 12 }
  }
}
```

### Планка

```js
{
  metric: 'time',
  loadType: 'none',
  value: 45,
  progression: {
    enabled: true,
    every: null,
    mode: 'time',
    time: { step: 5, max: 60 }
  }
}
```

### Резинка

```js
{
  metric: 'reps',
  loadType: 'level',
  value: '12-15',
  loadScaleId: 'default-resistance',
  loadLevel: 1,
  progression: {
    enabled: true,
    every: 2,
    mode: 'level',
    reps: { step: 2, max: 18 },
    level: { step: 1, max: 3 }
  }
}
```

# 4. Compatibility со старой моделью

Нельзя одномоментно удалить:
- `prog`;
- `progOn`;
- `trackWeight`;
- `repsStep`;
- `timeStep`;
- `wStep`;
- `repsMax`;
- `timeMax`;
- `weightMax`;
- `dualProg`.

Сначала нужен adapter.

## 4.1. Функция нормализации

Добавить условную:

```js
getProgressionStrategy(ex, program)
```

Она возвращает новую нормализованную структуру независимо от того, старое это упражнение или новое.

Если `ex.progression` существует — использовать её.

Иначе вывести стратегию из старых полей:

### Старое reps

```text
progOn = true
type = reps
trackWeight = false
```

→ `mode = reps`

### Старый weight-only

```text
trackWeight = true
wStep > 0
repsStep = 0
dualProg = false
```

→ `mode = weight`

### Старая double progression

```text
trackWeight = true
dualProg = true
repsStep > 0
wStep > 0
```

→ `mode = double_range`

### Старое time

→ `mode = time`

Так старые программы начинают работать через новый движок без миграции всех данных в один момент.

## 4.2. Запись новых данных

После ручного редактирования упражнения или AI-правки сохранять новую структуру.

На переходном этапе можно также зеркалить значения в старые поля, если это нужно старым частям приложения.

Удаление legacy — отдельный поздний этап после стабилизации.

# 5. Дефолты ручного редактора

Ручной редактор должен самостоятельно выбрать разумную прогрессию без AI.

Источник истины — не название упражнения.

Нельзя делать:
- увидели слово «резинка» в названии → автоматически выбрали level;
- увидели слово «планка» → автоматически выбрали time.

Для ручного редактора стратегия определяется только по явно выбранным пользователем:
- метрике;
- типу нагрузки.

## 5.1. Матрица дефолтов

```text
reps + none
→ reps

reps + weight
→ double_range

reps + level
→ level с ростом повторов перед переходом уровня

time + none
→ time

time + weight
→ time

time + level
→ time
```

Для `time + weight` пользователь может вручную выбрать weight, если хочет фиксированное время и рост веса.

Для `time + level` пользователь может вручную выбрать рост сопротивления.

# 10. Унификация level / сопротивления

## 10.1. Почему не показываем «Уровень 2»

Число не объясняет человеку, что физически делать.

Плохо:

```text
Уровень 2 → Уровень 3
```

Хорошо:

```text
Среднее сопротивление → Сильное сопротивление
```

или:

```text
Красная резинка → Синяя резинка
```

## 10.2. Модель шкалы

Добавить структуру шкалы сопротивления.

Пример:

```js
{
  id: 'default-resistance',
  name: 'Сопротивление',
  levels: [
    { id: 'light', label: 'Лёгкое' },
    { id: 'medium', label: 'Среднее' },
    { id: 'strong', label: 'Сильное' },
    { id: 'very-strong', label: 'Очень сильное' }
  ]
}
```

Упражнение хранит ссылку и текущую позицию:

```js
loadScaleId: 'default-resistance'
loadLevel: 1
```

Не привязывать алгоритм к конкретным английским id — порядок определяется массивом.

## 10.3. Пользовательские шкалы

Пользователь может создать свою шкалу.

Пример:

```text
Мои резинки

1. Жёлтая
2. Красная
3. Синяя
4. Чёрная
```

Или:

```text
Эспандер
3
4
5
6
7
```

UI всегда показывает label.

Внутренне прогрессия двигается по индексу/ID.

## 10.4. Где хранить шкалы

Предпочтительно на уровне профиля пользователя, а не внутри каждого упражнения:

```js
profile.loadScales[]
```

Причина:
- одна и та же резинка используется во многих программах;
- пользователь настраивает цвета один раз;
- AI и ручной редактор могут переиспользовать шкалу;
- изменение названия уровня не требует обходить все упражнения.

Но программа должна сохранять достаточно fallback-данных для корректной работы при импорте/шаринге.

Варианты реализации:
1. profile scale + snapshot labels в упражнении;
2. полностью embedded scale в программе.

На первом этапе проще и безопаснее embedded/snapshot, затем вынести пользовательские библиотеки отдельно.

# 13. previewNextProgression()

Добавить одну центральную функцию:

```js
previewNextProgression(ex, program)
```

Она НЕ мутирует данные.

Возвращает структурированный preview:

```js
  mode: 'double_range',

  next: {
    reps: '9-11',

  },

  changed: ['reps'],

  currentLabel: '8–10 повторов · 5 кг',
```

Для level:

Обязательно один и тот же preview используется:

- в тестах.

Это предотвращает рассинхрон: UI не должен обещать одно, а `advanceExerciseProgression()` применять другое.

# 14. advanceExerciseProgression()

Переписать как dispatcher стратегий.

Концептуально:

```js
function advanceExerciseProgression(ex, program) {
  const p = getProgressionStrategy(ex, program);

  switch (p.mode) {
    case 'reps':
      return advanceReps(ex, p);

    case 'weight':
      return advanceWeight(ex, p);

    case 'double_range':
      return advanceDoubleRange(ex, p);

    case 'time':
      return advanceTime(ex, p);

    case 'level':
      return advanceLevel(ex, p);
  }
}
```

Каждая стратегия должна иметь:
- `preview`;
- `advance`;
- `atCeiling`;
- validation.

Желательно одна реализация расчёта для preview и apply:

```js
const next = computeNextProgression(ex, strategy);
```

`preview` только показывает `next`.

`apply` записывает `next` в `ps.cur`.

Не дублировать формулы.

---

# 15. Потолки

Каждая растущая ось имеет явный потолок.

- reps → max reps;
- time → max seconds;
- weight → max kg;
- level → последний допустимый уровень.

Если достигнут полный потолок стратегии:
- счётчик больше не растёт;
- предложение повышения не появляется;
- если есть `ЗАМЕНА`, интерфейс может отдельно предложить следующий вариант упражнения.

Не смешивать «повысить нагрузку» и «заменить упражнение» в одну автоматическую операцию на первом этапе.

# 16. Финальная проверка прогрессии

Существующий `state.progCheck` сохранить концептуально.

Но UI переделать.

## 16.1. Заголовок

Вместо:

```text
Всё получилось? Нагрузку повысим
```

использовать:

```text
Пора немного увеличить нагрузку
```

Подпись:

```text
По плану готовы следующие упражнения.
Если где-то было тяжело — оставь его как есть.
```

## 16.2. Показывать не только название, но current → next

Примеры карточек:

```text
Тяга гантели
10–12 × 8 кг
→ 11–13 × 8 кг
```

```text

8–10 × 5 кг
→ 9–11 × 5 кг
```

```text

```

```text

```

## 16.3. Логика выбора

По умолчанию все карточки = будут повышены.

У каждой:

```text
Оставить как есть
```

После нажатия:

```text
Без изменений
```

Внутренне можно продолжать использовать `chk.hard`.

Пользователь не обязан понимать термин «тяжело» как состояние данных.

## 16.4. Главная кнопка

Если ничего не исключено:

```text
Применить изменения
```

Если исключено хотя бы одно — всё равно:

```text
Применить изменения
```

Не менять label динамически без необходимости.

## 16.5. После применения

Коротко:

```text
Нагрузка обновлена
Повышено: 3 · Без изменений: 1
```

Без отдельного длинного экрана.

# 17. Что происходит с упражнением «было тяжело»

Сохранить нынешнюю правильную логику:

если порог был `2/2`, пользователь оставил упражнение без изменений:
- не сбрасывать в `0/2`;
- оставить готовым к повторной проверке;
- после следующего полного выполнения снова предложить повышение.

Иначе пользователь, который честно отказался от шага, будет вынужден ждать ещё два/четыре полных цикла.

# 19. AI-протокол

AI должен использовать ту же модель, что ручной редактор.

Добавить/нормализовать понятия:

- тип прогрессии;
- частота упражнения;
- тип нагрузки;
- сопротивление;
- шкала сопротивления;
- текущий уровень;
- шаг уровня.

Не обязательно сразу менять публичный plain-text протокол на полностью новую форму. Можно сначала научить parser преобразовывать новые labels в новую модель.

## 19.1. Рекомендуемые protocol labels

Возможный вариант:

```text
НАГРУЗКА: нет | вес | сопротивление
ТИП ПРОГРЕССИИ: повторы | вес | повторы_вес | время | сопротивление
ЧАСТОТА ПРОГРЕССИИ: 0-15
СОПРОТИВЛЕНИЕ: Среднее
УРОВНИ СОПРОТИВЛЕНИЯ: Лёгкое | Среднее | Сильное | Очень сильное
ШАГ УРОВНЯ: 1
```

Но перед фиксацией labels проверить backward compatibility parser-а.

## 19.2. AI-дефолты

AI:

- reps + none → reps;
- reps + kg → double_range в большинстве силовых упражнений;
- reps + resistance band → level;
- time + none → time;
- warmup → progression off.

AI может отклоняться от default, если программа этого требует.

# 20. Ручной редактор и AI должны давать одинаковый результат

Если пользователь вручную собрал:

```text
+1 повтор
до 14

до 12 кг
```

Никаких AI-only скрытых progression полей.

# 21. Смена типа нагрузки в редакторе

Пользователь может случайно переключать:

```text

```

Не уничтожать старое значение мгновенно.

В draft хранить временно:
- lastWeight;
- lastLoadScale / lastLoadLevel.

Если пользователь вернулся на «Вес», его 8 кг должны восстановиться.

Очищать неактивные данные только при финальном normalize/save, если это действительно безопасно.

# 22. Смена формата упражнения

При смене:

```text
Повторения → Время
```

пересчитать рекомендуемый progression mode.

Но если пользователь уже вручную менял progression settings, не молча уничтожать их.

Правило:
- fresh/new exercise → применять default автоматически;
- уже настроенное упражнение → показать подходящий новый default, но сохранить старые данные до подтверждения/сохранения.

# 23. Валидация

Добавить единый:

```js
validateProgression(ex)
```

Примеры:

### reps

- step > 0;
- max > текущей верхней границы.

### weight

- loadType=weight;
- weight step > 0;
- max weight > current weight.

### double_range

- metric=reps;
- loadType=weight;
- rep step > 0;
- weight step > 0;
- rep max > starting upper bound;
- weight max > current/base weight.

### time

- metric=time;
- step > 0;
- max > current seconds.

### level

- loadType=level;
- scale существует;
- current level существует;
- следующий уровень существует;
- если reps тоже растут — reps max валиден.

UI не должен позволять сохранить заведомо противоречивую комбинацию.

# 24. История прогрессии

Не обязательно делать отдельный журнал в первой пачке.

Но при применении шага желательно сохранять минимальное событие:

```js
{
  at,
  exerciseId,
  from,
  to,
  mode
}
```

Это поможет:
- объяснять пользователю историю;
- отлаживать sync;
- анализировать прогрессию;
- в будущем понимать длительное плато.

Если это сильно расширяет первую реализацию — отложить, но предусмотреть формат.

# 25. Синхронизация

`progression`, `loadType`, `loadLevel` и шкала должны синхронизироваться вместе с программой.

Проверить:
- профильный storage;
- cloud sync;
- backup/export;
- import;
- trainer snapshots;
- catalog;
- shared programs;
- AI-edit copy;
- восстановление после переустановки.

Особенно проверить, что старый `ps.cur` не теряется при миграции на новую стратегию.

---

# 26. Каталог и программы тренера

Каталог должен хранить базовую prescription-модель.

Пользовательская текущая прогрессия остаётся локальным/профильным состоянием программы пользователя через `ps`, как сейчас.

При обновлении каталожной/тренерской программы:
- не сбрасывать пользовательский progression state у совпавшего упражнения без причины;
- сопоставление делать по стабильному `ex.id`, а не по имени;
- изменение progression policy тренером должно обновлять стратегию осознанно.

---

# 27. Перенос изображений и AI-редактирование

Новая progression модель не должна ломать уже реализованный перенос media при AI-редактировании.

Для одинакового упражнения по `КОД`:
- сохранить media;
- сохранить текущий progression state, если новая политика совместима;
- если AI намеренно поменял диапазон/тип нагрузки/стратегию, использовать новые параметры как policy, но аккуратно нормализовать текущее состояние.

Нужна отдельная функция совместимости:

```js
carryProgressionState(oldEx, newEx)
```

Не копировать `ps.cur` вслепую между несовместимыми форматами.

# 31. Тест-план

## Unit: стратегия

Для каждого mode:
- обычный шаг;
- ровно перед потолком;
- достижение потолка;
- уже на потолке;
- invalid config;
- every inherit;
- every override;
- progression disabled.

## Double range

Обязательно:

```text
8-10
9-11
10-12
...
12-14
→ +weight
→ 8-10
```

Проверить сохранение ширины диапазона.

## Level

```text
12-15 medium
14-17 medium
16-18 medium
12-15 strong
```

Проверить последний level.

## Workout

- done всех сетов → счётчик +1;
- один skipped set → упражнение не считается полным;
- partial workout, но конкретное упражнение полностью выполнено → считается;
- hard/keep → не повышается;
- после keep вопрос возвращается после следующего выполнения.

- irrelevant fields скрыты;
- switch off;
- default strategy;
- custom strategy;
- weight → level → weight не теряет draft value;
- preview совпадает с apply.

## AI

- manual equivalent;
- roundtrip;
- level labels;
- custom scale;
- отсутствие выдуманных цветов.

## Migration

Снимки реальных старых программ:
- reps;
- time;
- weighted;
- dual;
- уже прогрессированные;
- на потолке;
- legacy без `progOn`.

# 32. Что НЕ делать в рамках этой задачи

Не добавлять:
- RIR;
- RPE;

- прогноз 1RM;

# 33. Критерий готовности всей задачи

Функционал считается готовым, если:

1. Старые программы продолжают работать без сброса текущей нагрузки.
2. Новую программу можно полностью собрать вручную без AI.
3. Для обычного упражнения пользователь не обязан понимать терминологию прогрессии.
4. FitTimer предлагает разумный тип прогрессии по metric + loadType.
5. Продвинутый пользователь может изменить стратегию вручную.
6. Гантели, вес тела, время и резинки работают через одну архитектуру.
7. Сопротивление всегда показывается понятным label, а не абстрактным номером.
8. Перед повышением пользователь видит точное `сейчас → будет`.
9. Ничего не повышается без подтверждения.
10. Во время тренировки не добавляется ни одного обязательного действия.
11. AI использует те же возможности, что ручной редактор.
12. Preview и реально применяемая прогрессия используют один расчёт.
13. Индивидуальная частота упражнения работает независимо от частоты программы.
14. Partial/skipped логика остаётся корректной.
15. Sync/import/catalog/trainer не теряют progression state.

# 34. Рекомендуемый конечный UX в одном примере

Пользователь вручную создаёт:

```text
Махи гантелей в стороны
Повторения: 8–10
Нагрузка: Вес
5 кг
```

FitTimer сам предлагает:

```text
Со временем сложнее
Повторы → вес
```

Внутри:

```text
Повторы: +1 до 14
Потом: +1 кг и снова 8–10
Максимальный вес: 12 кг
Проверять: как в программе — после 2 выполнений
```

Во время тренировки:

```text
Махи гантелей в стороны
8–10 повторов
5 кг
```

Никаких дополнительных вопросов.

После нужного количества выполнений:

```text
Пора немного увеличить нагрузку

Махи гантелей в стороны
8–10 × 5 кг
→ 9–11 × 5 кг

[Оставить как есть]

[Применить изменения]
```

Это и есть целевая модель: мощная прогрессия под капотом, но простой FitTimer для человека.

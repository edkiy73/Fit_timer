# FitTimer — модель снарядов, нагрузки и прогрессии

Дата создания: 2026-10-08  
Статус: третье ревью Клода разобрано; fixed movement stages, прямой cfgKey и movementChanged внесены в основные разделы; реализация не начата  
Источник истины: этот файл должен актуализироваться после каждого завершённого этапа/PR.

## 0. Зачем этот план

Сейчас FitTimer умеет хранить вес и прогрессировать его, но одно число веса не отвечает на вопрос, что именно использует человек:

- одна гантель 10 кг;
- две гантели по 10 кг;
- штанга 40 кг;
- одна гантель в одностороннем упражнении;
- резинка с дискретным уровнем сопротивления.

Из-за этого один и тот же `ВЕС: 10` может трактоваться по-разному.

Цель — сделать модель однозначной, не усложняя тренировочный экран и не ломая уже удачное разделение FitTimer на:
- метрику упражнения: повторы / время;
- тип нагрузки: без дополнительной нагрузки / вес / сопротивление;
- стратегию прогрессии.

Старую совместимость не строим вообще: приложение стартует с чистого листа (см. 1.9). Две реальные программы — пользователя и Светы — после внедрения генерируются заново через новый AI-контракт/редактор, а не переносятся.

Также убираем бессмысленную агрегированную статистику вида «всего поднято N кг / 10 тонн». Историю нагрузки конкретного упражнения сохраняем.

## 0.1. Ревью 2026-10-07 простыми словами (для обсуждения с другим ИИ)

Этот раздел — короткое человеческое резюме. Подробности — в разделах, на которые даны ссылки. Код приложения при ревью не менялся.

### Главное решение владельца

Старые данные не нужны совсем: ни программы, ни история, ни бэкапы, ни текущий каталог. После внедрения приложение будет пустым, всё создаётся заново. Подробно — 1.9.

### Что нашли, сравнив план с кодом

**1. Настройки упражнения хранятся в нескольких местах одновременно.**
«Есть ли вес» и «как растёт нагрузка» записаны сразу в нескольких полях. Это осталось от старых версий: их держали, чтобы не сломать старые программы. Раз старые данные не нужны, этот мусор выкидываем и оставляем одно понятное место. Сейчас это бесплатно, потом будет дорого. → 2.8

**2. Ошибка в истории тренировок.**
Приложение запоминает вариант тренировки по номеру в списке («вариант №1»). Но при смене дней приложение само переставляет варианты местами — и прошлая история «переезжает» к другому варианту. Ломаются «было → сегодня», оценка длительности и отчёт тренеру. Упражнения в истории тоже ищутся по номеру и названию: переименовал — сравнение пропало.
Решение: у каждого варианта и упражнения постоянный ID («паспорт»), история запоминает по нему. → 2.6, 10

**3. Защита от старой версии приложения.**
Старая версия на чьём-то телефоне не поймёт новый формат и может испортить данные. Нужна проверка: «данные новее меня — не трогаю, прошу обновиться». → 1.9

**4. Фунты.**
Вес сейчас всегда округляется до 0,5 кг — фунты потом не сохранить правильно. Сразу храним у веса пометку единицы («кг»). Интерфейс фунтов не делаем, но и переделывать данные потом не придётся. → 2.8

**5. Мелкие уточнения модели.**
- В persistent V2 вес/уровень без load-equipment не сохраняется; незаполненный снаряд допустим только во временном UI-draft. → 2.8
- Один предмет бывает в разных ролях: резинка — сопротивление или помощь, блин — груз или платформа. → 3
- Угол тела/высота опоры/TRX не превращаются в универсальный load.level; для этого теперь есть ограниченная movement chain. → 5.3, 5.6
- Правка веса перед тренировкой — это два разных действия: «только сегодня» и «теперь это мой рабочий вес». → 5.5

**6. Порядок работ.**
В исходном плане самая большая и рискованная часть (новый способ общения с ИИ) стояла рано. Предложение: сначала то, что потом дорого менять (хранение упражнений, история, экраны), а ИИ — после. ИИ работает на сервере, его можно менять без обновления приложения. → 13

### Решения по вопросам ревью Клода

**Вопрос 1. Как ИИ будет исправлять программу — РЕШЕНО.**

Принимаем вариант А, но точнее: **target state + ссылки на неизменённые ID**.

AI возвращает целевую структуру программы после правки:
- неизменённый вариант/упражнение — короткая ссылка по ID;
- изменённый объект — ссылка + новый prescription/config;
- новый объект — полный новый объект без постоянного ID;
- удаление — только явным списком removed IDs.

Почему: перестановка, перенос, split/merge естественно выражаются структурой результата; не нужен собственный язык move/delete/insert; неизменённые упражнения не переписываются.

Каждый существующий plan.id/exercise.id обязан быть упомянут ровно один раз либо явно удалён. Иначе весь ответ отклоняется. Применение атомарное к snapshot, который ушёл в запрос. Подробно — 8.4.

**Вопрос 2. Группировать ли настройки прогрессии — РЕШЕНО: да, сразу в V2.**

Настройки собираются в один объект `progression`, а накопленное состояние — отдельно в `progressState`.

Почему: сейчас дешёво убрать россыпь wStep/repsStep/timeStep/*Max/progEvery; AI DTO, редактор и runtime получают одну форму; политика не смешивается с фактическим прогрессом.

### Что будет на первом этапе

Первый PR отдельно чинит stable IDs/history и удаляет тоннаж. Когда runtime реально переключается на V2, старые данные можно очистить после короткого подтверждения владельца: сохранять рабочий V1-прод между этапами не требуется. → 13

## 1. Зафиксированные продуктовые решения

### 1.1. Вес тела отдельно не хранится

Для отжиманий, подтягиваний, планки и т.п. вес тела подразумевается самим упражнением.

Если есть дополнительный груз, хранится именно он:
- жилет 10 кг;
- блин 10 кг;
- гантель 10 кг.

### 1.2. Общий вес и «вес одного» не являются разными режимами

Отдельные режимы `totalWeight`, `perItemWeight` и переключатель «общий / на один» не нужны.

Единое правило:

> Поле веса всегда означает вес ОДНОЙ единицы указанного снаряда.

Примеры:
- 2 гантели, вес 5 кг → **2 × 5 кг**;
- 1 гантель, вес 10 кг → **1 × 10 кг**;
- 1 штанга, вес 40 кг → **Штанга · 40 кг**;
- 2 гири, вес 16 кг → **2 × 16 кг**.

Штанга считается одной собранной единицей оборудования. Специальной модели «общий вес штанги» не нужно.

### 1.3. Количество означает одновременное использование

Количество снарядов = сколько одинаковых единиц используется одновременно в одном выполнении упражнения.

Поэтому:
- тяга гантели одной рукой → количество 1;
- даже если упражнение выполняется отдельно правой и левой рукой;
- две гантели в румынской тяге → количество 2.

Количество не означает «сколько предметов вообще есть у пользователя».

### 1.4. Тип снаряда не определяет прогрессию

Снаряд нужен для:
- понятного отображения;
- количества;
- корректного AI-контракта;
- истории конфигурации;
- будущей фильтрации по доступному оборудованию.

Стратегия прогрессии определяется отдельно текущей моделью FitTimer.

### 1.5. «Другое» — это только своё название снаряда

Не вводим произвольную текстовую нагрузку вида:
- «наполнить канистру наполовину»;
- «поставить посильнее».

Для своего снаряда пользователь задаёт название, но нагрузка всё равно должна быть одной из существующих моделей:
- вес;
- сопротивление;
- без дополнительной нагрузки, если снаряд нужен только для выполнения.

Это нужно, чтобы прогрессия оставалась вычислимой.

### 1.6. Сопротивление не обязано выражаться в килограммах

Для резинок, эспандеров и подобных вещей сохраняем существующую модель упорядоченных уровней:
- Лёгкая → Средняя → Сильная → Очень сильная;
- Жёлтая → Красная → Чёрная;
- Level 1 → Level 2 → Level 3;
- 10–15 lb → 15–25 lb → 25–35 lb.

FitTimer не переводит такие значения в кг.

Порядок всегда задаётся от более лёгкого варианта к более сложному.

### 1.7. Смена снаряда или количества — это новая конфигурация упражнения

Обычное изменение:
- 2 × 5 кг → 2 × 6 кг.

Смена конфигурации:
- 1 × 10 кг → 2 × 10 кг;
- 2 гантели → штанга;
- 2 гири → 1 гиря.

Такое изменение нельзя показывать как обычное «нагрузка выросла / снизилась».

Правило:

> Вес изменился — продолжаем ту же историю прогрессии.  
> Тип снаряда или количество изменились — начинается новый период конфигурации упражнения.

При смене конфигурации:
- сохраняем старую историю;
- сбрасываем счётчик до следующей проверки прогрессии;
- сбрасываем `progressState`;
- новый введённый вес/уровень становится новой базой;
- старую и новую конфигурации не сравниваем как ↑/↓ нагрузки;
- `exercise.id` можно оставить тем же: пользователю не нужно вручную создавать новое упражнение.

### 1.8. Суммарный тоннаж удаляем

Удаляем:
- подсчёт `stats.totalKg`;
- ачивку «Десять тонн»;
- отображение суммарно поднятых кг;
- merge/sync этого показателя;
- тесты, поддерживающие эту метрику.

Оставляем:
- историю рабочего веса конкретного упражнения;
- историю повторов/времени;
- историю уровня сопротивления;
- сравнение «было → сегодня» только внутри одной конфигурации.

### 1.9. Чистый старт: никаких данных не переносим

Старые программы/история/каталог/ссылки/sync-документы V1 продуктовой ценности не имеют. V1→V2 migration layer не строим.

Текущее решение владельца:
- во время разработки production может быть временно нерабочим;
- данные можно очищать повторно;
- не нужно поддерживать параллельно V1 и V2;
- перед каждым необратимым удалением серверных данных всё равно коротко подтверждаем действие у владельца.

Практический порядок:
1. PR 1 чинит identity/history на текущем коде без обязательного wipe;
2. когда runtime переключается на V2, старые local/server FitTimer-данные можно очистить;
3. legacy reader/adapter не оставляем;
4. AI-действия, которые ещё говорят на старом протоколе, на переходном этапе лучше временно отключить, а не заставлять их писать несовместимые V2-объекты.

`SCHEMA_VERSION=2` остаётся обязательным.

До публичного релиза отдельно добавить FitTimer-specific compatibility guard:
- несовместимый старый клиент не может писать старую schema;
- при необходимости блокируются несовместимые FitTimer API, а не весь shared AppBase Core;
- minimum app/API version не является блокером текущей V2-переделки, пока реальных пользователей нет.

После перехода импорт/ссылки/каталог принимают только V2; старый формат отклоняется понятной ошибкой.

## 2. Целевая модель упражнения — по смыслу

### 2.1. Как считать

- Повторения
- Время

Сохраняем существующую модель `ex.type`.

### 2.2. Тип нагрузки

- Без дополнительной нагрузки
- Вес
- Сопротивление

Сохраняем существующий `loadType`:
- `none`
- `weight`
- `level`

### 2.3. Снаряд нагрузки

Добавляем к упражнению:

- тип снаряда;
- количество одинаковых снарядов;
- своё название, только если выбран «Другое».

Целевая V2-форма:

```js
ex.load.equipment
ex.load.count
ex.load.name // только custom
```

Это не отдельные корневые поля: источник истины — `ex.load` из 2.8.

### 2.4. Вес

Строгая V2-семантика:

> `ex.load.weight` = рабочий вес ОДНОЙ одновременно используемой load-unit. Для тренажёра/блока с числовой шкалой это выбранная рабочая нагрузка одного источника сопротивления, а не физическая масса самого тренажёра.

Примеры:
- 2 гантели по 10 кг → `count=2, weight=10`;
- штанга 40 кг → `count=1, weight=40`;
- один блочный стек 25 кг → `count=1, weight=25`;
- два независимых одинаково нагруженных блока по 10 кг → `count=2, weight=10`.

То же правило распространяется на:
- базу `load.weight`;
- текущее значение `progressState.current.weight`;
- `progression.weight.step`;
- `progression.weight.max`.

### 2.5. Сопротивление

V2 хранит:
- базовую шкалу в `load.levels`;
- базовый текущий уровень в `load.level`;
- прогрессированный level identity в `progressState.current.level`.

Добавляем конкретный снаряд, например:
- Резинка;
- Эспандер;
- Другое → Power Twister.

### 2.6. Идентичность программы, варианта и упражнения

Для AI Contract V2 нужны стабильные адреса объектов.

Уже есть:
- `program.id`;
- `exercise.id`.

Сейчас у варианта/дня программы стабильного ID НЕТ — варианты адресуются индексом массива. До target-state AI-edit добавить `plan.id` каждому варианту.

Правила:
- ID создаёт приложение, а не AI;
- AI может ссылаться на существующий ID, но не имеет права переименовывать его;
- новому упражнению/варианту приложение выдаёт ID после валидации операции;
- копия упражнения получает новый `exercise.id`, как и сейчас;
- `exercise.id` — идентификатор экземпляра упражнения внутри программы, а НЕ будущий канонический ID движения.

Нормализация и sanitization должны гарантировать уникальность `plan.id` и `exercise.id` внутри программы.

`plan.id` нужен не только AI-правке. Сейчас вся привязка к варианту идёт по индексу массива, а `normPlans()` сортирует `p.plans` на месте по дню недели — после смены дней старые записи указывают на другой вариант. По индексу сейчас работают:
- запись истории `plan: state.planIdx` (`70-workout.js`);
- «было → сегодня» и оценка длительности (`previousWorkoutLoad`, `estimatedWorkoutMinutes` в `00-core.js`);
- тренерский отчёт (`buildReport` в `50-trainer-catalog.js`);
- строки снимка нагрузки — по позиции `i` и названию `n`, а не по `exercise.id`.

В схеме v2 всё это адресуется только через `planId` / `exId`. Индекс остаётся лишь позицией в UI.

### 2.7. Одна основная внешняя нагрузка на упражнение в V1

Текущая целевая модель намеренно хранит один `load.equipment` и одну независимую ось внешней нагрузки.

Она покрывает обычные случаи:
- собственный вес + жилет;
- одна/две гантели;
- одна/две гири;
- штанга;
- тренажёр;
- один/два одинаковых блока;
- резинка/эспандер.

Редкие комбинации с ДВУМЯ независимыми внешними нагрузками одновременно (например штанга + цепи/резинки, жилет + гантели с отдельной прогрессией каждого компонента) в V1 автоматически не прогрессируем по двум осям.

Если такой сценарий реально нужен:
- можно временно представить его как один custom/composite setup, если у него есть одна понятная ось прогрессии;
- иначе AI не должен сам придумывать такую комбинацию;
- полноценный `loadComponents[]` с выбором прогрессируемого компонента оставляем отдельным будущим расширением.

Это сознательная граница V1, а не забытый кейс.

### 2.8. Persistent-схема v2 — единственный источник истины

Раз данные не переносятся (1.9), устаревший слой нагрузки/прогрессии после перехода удаляется, а не оборачивается вечным адаптером.

Удаляются из persistent-модели:
- `prog`, `progOn`, `trackWeight`, `dualProg`, `dualRangeV`, `swapOn`, `swapName`, `swapDesc`;
- корневые `loadType/progMode/wStep/repsStep/timeStep/*Max/progEvery`;
- логика «поле отсутствует → угадать смысл из legacy».

### Exercise slot и movement stages

После третьего ревью разделяем:
- **exercise slot** — стабильное место упражнения в программе;
- **movement stage** — конкретный вариант движения внутри этого слота;
- **prescription** — AI/user-owned параметры конкретного stage;
- **progressState** — app-owned накопленный прогресс текущего stage.

Целевая форма по смыслу:

```js
exercise = {
  id: 'ex_...',                 // app-owned, стабилен для логического слота
  warmup: false,                // свойство СЛОТА: место в структуре тренировки

  currentStageId: 'mv_...',     // app-owned

  stages: [                     // 1..4, порядок = лестница движения
    {
      stageId: 'mv_...',        // app-owned
      prescription: {
        name: '...',
        desc: '...',
        type: 'reps' | 'time',
        value: '8-10',
        sets: 3,
        perSide: false,
        rest: 45,
        restAfter: 60,
        muscles: [],
        mistakes: '',
        video: '',

        load: {
          type: 'none' | 'weight' | 'level',
          equipment: 'dumbbell' | 'barbell' | ... | 'custom' | null,
          name: '',
          count: 1,
          unit: 'kg',
          weight: 10,
          levels: [...],
          level: 0
        },

        supportEquipment: ['bench'],

        progression: {
          mode: 'none' | 'reps' | 'weight' | 'double_range' | 'time' | 'level' | 'parallel',
          // null = наследовать program.progression.every
          // число 1..15 = своё; 0 не используется как второй OFF
          every: null,
          reps:   {step: 1, max: 15},
          weight: {step: 1, max: 12},
          time:   {step: 5, max: 60}
        }
      },

      // как переходить С ЭТОГО stage к следующему
      advance: {
        mode: 'ceiling' | 'manual'
      },

      // app-owned image identity; AI не пишет media/base64
      mediaRef: null,
      visualKey: ''
    }
  ],

  progressState: {
    count: 0,
    current: {
      reps: null,
      weight: null,
      time: null,
      level: null
    }
  }
}

program.progression = {
  // общий default; null = общего default нет
  every: 4
}
```

**Даже упражнение без цепочки хранит один stage.** Это сознательно убирает две параллельные формы «обычное упражнение» и «упражнение с chain».

`warmup` хранится на уровне exercise slot, а НЕ stage:
- разминка определяет место упражнения в структуре тренировки;
- смена movement stage не может сама превратить основное упражнение в разминку или обратно;
- переключатель «Разминка» в UI не зависит от выбранного stage.

 Runtime/UI получают активный prescription только через один helper по смыслу:
```js
activePrescription(exercise)
```

В остальных разделах документа для краткости записи вроде `load.weight` или `progression.mode` означают поля АКТИВНОГО `stage.prescription`, а не второй набор корневых persistent-полей.

Точную JSON Schema фиксируем в PR 2; неиспользуемые ветки prescription нормализуются/не сериализуются по выбранным `load.type` и `progression.mode`.

### Строгое правило equipment

`equipment: null` допустим только:
- у `load.type = 'none'`;
- во временном незавершённом UI-draft до Save.

В persistent V2:
- `load.type = 'weight'` → equipment обязателен;
- `load.type = 'level'` → equipment обязателен;
- нестандартный предмет → `equipment:'custom' + name`.

Причина: хранить `weight:10, equipment:null` значит вернуть исходную неоднозначность «10 кг непонятно чего», ради устранения которой и делается эта схема.

### Единицы измерения

Если уже вводим `load.unit`, internal API тоже перестаёт кодировать kg в именах:
- `ps.cur.kg` → `progressState.current.weight`;
- `wStep` → `progression.weight.step`;
- `weightMax` → `progression.weight.max`;
- новые доменные helper/API не называются `parseKg/fmtKg`.

UI V1 всё равно работает только в kg. Но тогда `unit:'kg'` действительно создаёт нормальную границу для будущего lb, а не декоративное поле рядом с kg-specific runtime.

### Ключ физической конфигурации

После второго ревью шкалу level из cfgKey убираем.

Физическая конфигурация отвечает только на вопрос «чем именно создаётся нагрузка»:

- weight: `type + equipment + customName + count`;
- level: `type + equipment + customName + count`.

`unit` тоже не является новой физической конфигурацией: если в будущем тот же вес показывается в lb вместо kg, это конверсия представления, а не новый снаряд.

Текущее число веса/уровня в cfgKey не входит.

### Изменение level-шкалы

Шкала — часть progression policy, а не physical cfgKey.

При редактировании шкалы:
- текущий level identity всё ещё существует → та же ФИЗИЧЕСКАЯ конфигурация, текущий индекс пересчитывается по identity;
- identity текущего уровня исчез → состояние уровня несовместимо, level progressState сбрасывается;
- исправление подписи или добавление нового уровня без изменения относительного порядка существующих уровней не создаёт новый history segment;
- reorder существующих уровней тоже не создаёт новый physical config, НО меняет progression policy: current level переносится по identity, а `progressState.count` сбрасывается, чтобы старый накопленный счётчик не применился к новой лестнице сложности.

Это продолжает уже существующую идею `carryReorderedLevelProgress()`: индекс не является identity.

### История конфигурации

Отдельного `stats.loadConfigs` нет.

Physical `cfgKey` хранится прямо в history, но storage representation должна быть компактной. Один canonical helper отвечает за encode/decode и использует короткие стабильные коды из equipment catalog, например по смыслу:

```text
w|db||2
l|band||1
```

Требования:
- deterministic: одинаковая конфигурация на двух устройствах даёт байт-в-байт одинаковый key;
- reversible через canonical catalog/helper;
- type/equipment/custom name/count входят в key;
- unit и level scale не входят;
- delimiter/escaping для custom name определяются helper, UI/runtime строку вручную не разбирают.

### Имена movement stages в истории

После четвёртого ревью НЕ дублируем полное `movementStageName` в каждой строке каждой тренировки.

Используем компактную карту:

```js
stats.stageNames = {
  "mv_abc": "Румынская тяга с гантелями"
}
```

History row хранит только stageId.

Правила:
- stageId глобально уникален в рамках пользовательских данных;
- карта обновляется при обычном metadata rename stage;
- history helper разрешает имя через stageNames;
- если имя почему-либо отсутствует, UI использует безопасный fallback «Упражнение»/текущий известный label, а не ломает history;
- при trimming history можно удалить stageNames, на которые больше нет ссылок НИ в retained history, НИ в актуальных программах.

### Компактное storage-представление history

Persistent stats history — storage DTO, а не UI/domain object. Поэтому разрешены короткие ключи и omission defaults.

По смыслу:

```js
{e:"ex_abc", s:"mv_abc", c:"w|db||2", r:"8-10", w:10}
```

Не сохранять:
- `unit`, если kg;
- sec/weight/level поля, если они неприменимы;
- пустые строки/нулевые optional поля;
- дублируемое имя stage.

На чтении один history adapter разворачивает storage DTO в нормальный domain view для UI.

До реализации PR 1/2 обязательно сделать worst-case расчёт размера:
- 2000 тренировок;
- реалистичный верхний предел упражнений на тренировку;
- длинные IDs/custom equipment/level labels;
- partialExercises/notes и прочие реальные поля stats.

Цель — не просто «< 3 МБ», а оставить разумный запас. Если compact DTO всё равно близок к лимиту, history выносится из монолитного stats document отдельным архитектурным решением ДО накопления реальных данных.

### Почему load/progression/state разделены

- `load` = что за физическая/дискретная нагрузка;
- `progression` = политика, как её усложнять;
- `progressState` = что уже накоплено конкретным пользователем.

AI может предлагать/возвращать load + progression, но не имеет права писать persistent `progressState`.

## 3. Единый справочник оборудования и две категории

Текущий AI-интерфейс смешивает в одном `OPT_EQUIP` вещи разного смысла: например гантели/резинки вместе с ковриком/стулом/турником. Это нужно разделить.

При этом не заводить два независимых справочника, которые потом разъедутся. Нужен один канонический каталог оборудования, у каждого элемента которого есть категория:

- **снаряд нагрузки** — создаёт внешнюю нагрузку/сопротивление упражнения;
- **дополнительное оборудование** — нужно для выполнения, но не является числовой нагрузкой.

Из одного каталога должны строиться:
- выбор снаряда в редакторе упражнения;
- чипы «Снаряды» в AI-форме;
- чипы «Доп. оборудование» в AI-форме;
- parser/normalizer;
- локализованные названия;
- AI enum;
- будущие фильтры по доступному оборудованию.

Не пытаемся перечислить всё оборудование в мире.

Минимальный основной набор:

### Вес
- Гантель
- Штанга
- EZ-штанга
- Гиря
- Блин
- Медбол
- Сэндбэг
- Утяжелительный жилет
- Утяжелитель на руки/ноги
- Тренажёр
- Блочный тренажёр

### Сопротивление
- Резинка
- Эспандер

### Дополнительное оборудование
- Коврик
- Скамья
- Стул
- Турник
- Степ / платформа
- Фитбол
- Брусья
- Стойка / рама — при необходимости

### Универсальное
- Другое

Для «Другое» категория выбирается явно: это либо снаряд нагрузки, либо дополнительное оборудование.

Один и тот же предмет может играть разные роли в разных упражнениях (резинка — сопротивление или помощь; блин — груз или платформа; гиря — груз или противовес). Поэтому у элемента справочника не одна категория, а множество допустимых ролей `roles: ['load','support']`; роль выбирается в конкретном упражнении.

Справочник должен хранить только UI/domain-метаданные:
- стабильный machine id;
- локализованное название;
- допустимые роли load/support;
- допустимые типы нагрузки (один или несколько: например тренажёр может быть weight или level);
- разумное количество по умолчанию;
- способ компактного отображения;
- при необходимости иконку/алиасы.

Пол/стена и другие обычные поверхности помещения не считаются отдельным инвентарём.

Справочник НЕ должен:
- выбирать стратегию прогрессии;
- содержать собственный progression engine;
- подсказывать шаг/потолок прогрессии только по типу снаряда.

Почему: одинаковая гантель требует разных шагов в махах, жиме и румынской тяге. Шаг зависит от упражнения, текущей нагрузки, человека и реально доступных весов.

Справочник может задавать только нейтральные UI/domain-дефолты: count по умолчанию, подпись, допустимые load-types/roles. Progression policy задаётся упражнением/AI/пользователем.

## 4. Оборудование для выполнения и снаряд нагрузки — разные вещи

Пример:

### Жим гантелей
- нагрузка: 2 × 10 кг;
- дополнительное оборудование: скамья.

### Подтягивания
- нагрузка: без дополнительного веса;
- дополнительное оборудование: турник.

### Зашагивания
- нагрузка: 2 × 5 кг;
- дополнительное оборудование: степ / скамья.

Теперь это входит в текущую задачу, а не откладывается «на потом».

На уровне упражнения нужны две независимые части:

```text
Нагрузка упражнения
- тип нагрузки
- снаряд нагрузки
- количество
- вес / сопротивление

Дополнительное оборудование
- список предметов, которые используются в постановке/выполнении, но не являются осью нагрузки
```

Рабочее техническое направление:

```js
ex.load.equipment    // один тип load-equipment
ex.load.count
ex.load.name          // если equipment = custom

ex.supportEquipment   // массив дополнительного оборудования
```

Примеры:

```text
Жим гантелей:
load.equipment = гантель
load.count = 2
supportEquipment = [скамья]

Подтягивания:
load.type = none
supportEquipment = [турник]

Зашагивания:
load.equipment = гантель
load.count = 2
supportEquipment = [степ]
```

Не смешивать `supportEquipment` с `load.equipment`: у них разная семантика, отображение и влияние на прогрессию.

`supportEquipment` означает, что предмет используется в конкретной постановке упражнения, а не обязательно что без него движение физически невозможно. Например коврик может быть указан, если пользователь его выбрал и программа предполагает работу на нём; отсутствие коврика не должно автоматически запрещать все упражнения на полу.

## 4.1. Доступное оборудование пользователя в AI-форме

Текущий один блок «Инвентарь» разделить на два:

### Снаряды
Примеры чипов:
- Без снарядов
- Гантели
- Штанга
- Гири
- Резинки
- Эспандер
- Утяжелители
- Жилет
- Другое

### Доп. оборудование
Примеры чипов:
- Без доп. оборудования
- Коврик
- Скамья
- Стул
- Турник
- Степ / платформа
- Фитбол
- Брусья
- Другое

Это описание того, **что у пользователя доступно**, а не задание «использовать всё выбранное».

Ключевая семантика для AI:

> Выбранное оборудование гарантированно доступно. Используй его только там, где оно реально улучшает программу. Упражнение не обязано использовать снаряд только потому, что он есть у пользователя.

Пример:
- пользователь отметил «Гантели»;
- программа всё равно может содержать отжимания, планку и другие упражнения без гантелей;
- наличие гантелей — возможность, а не обязательная тема каждого упражнения.

Одновременно выбранный список должен оставаться реальным ограничением доступности:

> Не придумывать специализированное невыбранное оборудование по умолчанию.

Например, если выбраны только гантели и коврик, AI не должен сам добавлять штангу, кроссовер или фитбол. Исключение — пользователь явно попросил упражнение/программу, подразумевающую такой предмет, либо сам указал его в свободном контексте.

Семантика состояний задаётся ОТДЕЛЬНО для каждой категории:

- ничего не выбрано → эта категория оборудования не уточнена (open world);
- «Без снарядов» → внешних снарядов нагрузки явно нет;
- «Без доп. оборудования» → доп. оборудование явно отсутствует;
- выбран хотя бы один конкретный элемент → для этой категории это закрытый список гарантированно доступного специализированного оборудования; AI не должен требовать невыбранный специализированный предмет;
- выбранные элементы не обязаны использоваться во всех упражнениях;
- собственный вес всегда доступен и не входит в список снарядов.

«Без ...» — взаимоисключающий чип внутри своей группы.

Если выбран «Другое», UI обязан запросить конкретное название и хранить его вместе с `custom`, иначе значение «Другое» бесполезно для AI и для упражнения.

В V1 этот выбор остаётся контекстом КОНКРЕТНОГО запроса создания программы/упражнения, а не автоматически превращается в постоянный профиль домашнего инвентаря. Постоянный инвентарь можно добавить позже отдельной функцией.

Важное ограничение V1: чип «Гантели» означает только наличие типа снаряда. Он не сообщает AI, сколько именно гантелей есть и какие веса/шаги регулировки доступны. Поэтому AI не может гарантировать физическую доступность каждого следующего шага веса, если пользователь не уточнил это в свободном контексте. Будущее расширение инвентаря может добавить `availableCount / availableWeightsKg / stepKg` без изменения модели упражнения.

На уровне запроса не смешивать эти массивы:

```text
Доступные снаряды: ...
Доступное дополнительное оборудование: ...
```

Это также позволит AI корректно заполнять уже само упражнение:
- `СНАРЯД` — из категории снарядов нагрузки;
- `ДОП ОБОРУДОВАНИЕ` — отдельный список требований упражнения.

## 5. Правила прогрессии

Существующую progression architecture сохраняем.

Сейчас FitTimer уже разделяет:
- метрику;
- тип нагрузки;
- стратегию прогрессии.

Это не переписываем без отдельной причины.

### 5.1. Весовая прогрессия

V2-семантика:

- `load.weight` — вес одной load-unit;
- `progression.weight.step` — прибавка к одной unit;
- `progression.weight.max` — потолок одной unit;
- `progressState.current.weight` — текущий прогрессированный вес одной unit.

Пример:

```text
Сейчас: 2 × 5 кг
Шаг веса: +1 кг
После подтверждения: 2 × 6 кг
```

### 5.2. Двойная прогрессия

Пример:

```text
2 × 5 кг · 8–10
2 × 5 кг · 9–11
...
2 × 5 кг · 13–15
2 × 6 кг · 8–10
```

Количество снарядов не является осью прогрессии и автоматически не меняется.

### 5.3. Сопротивление

Существующую модель `level` сохраняем.

Ключевое правило:

> порядок `loadLevels` означает рост СЛОЖНОСТИ выполнения упражнения, а не обязательно физически большее сопротивление.

Обычная резинка, где более сильная резинка делает движение тяжелее:
- Лёгкая → Средняя → Сильная.

Ассистированные подтягивания/брусья — наоборот:
- 50 кг помощи → 40 кг помощи → 30 кг помощи;
- либо Сильная ассистирующая резинка → Средняя → Лёгкая.

То есть числовую «помощь 50 кг» нельзя моделировать обычным `weight` с положительным шагом: там меньшая цифра = более сложное упражнение. Такой случай хранить как упорядоченные level-labels.

Для `progression.mode='level'` в упражнении на повторы:
- используется `progression.reps.step/max`;
- сначала растут повторы;
- после потолка переход на следующий level identity;
- повторы сбрасываются к базе.

Либо:
- прямой переход по уровням, если выбрана соответствующая стратегия.

Автоматическую шкалу «Лёгкая → Средняя → Сильная» использовать только там, где увеличение физического сопротивления действительно увеличивает сложность. Для ассистирующей нагрузки нужны явные корректно упорядоченные labels.

В V2 `load.type = 'level'` НЕ используем как универсальный контейнер для любой сложности без load-equipment.

Изменение угла тела, высоты опоры, варианта отжиманий и подобные изменения самого движения идут через movement stages, а не через `load.level`.

Почему: иначе `level` начнёт означать одновременно сопротивление, амплитуду, положение тела, темп и вариант движения. `level` оставляем для дискретной нагрузки/помощи конкретного load-equipment.

### 5.4. Смена физической конфигурации

Физическая конфигурация определяется детерминированным `cfgKey` из 2.8:
- `load.type`;
- `load.equipment`;
- `load.name`;
- `load.count`.

Шкала level и unit в physical cfgKey не входят.

Если `cfgKey` изменился:
- это не progression step;
- `progressState` сбрасывается;
- начинается новый history segment;
- старую и новую конфигурации не сравниваем как ↑/↓ нагрузки.

### 5.5. Ручная правка рабочей нагрузки и счётчик прогрессии

Это отдельный случай от смены конфигурации.

Если пользователь вручную меняет внутри ТОЙ ЖЕ конфигурации:
- рабочий вес;
- базовые повторы/время;
- текущий уровень сопротивления;
- количество подходов;
- либо саму progression policy (mode/step/ceiling),

история упражнения остаётся в том же конфигурационном сегменте, НО накопленный счётчик до следующей проверки `progressState.count` сбрасывается в 0.

Причина: после ручного изменения назначения пользователь должен сначала выполнить новый вариант N раз, а не получить автоматическое предложение повысить его уже после одной тренировки из-за старого счётчика.

Изменения только текста/медиа/метаданных (название, описание, мышцы, ошибки, картинка, видео) progression state не сбрасывают.

Это отличается от текущего legacy-поведения `carryExerciseProgress()`; после V2 правило фиксируется напрямую в новой модели и покрывается тестами.

Быструю правку веса на экране старта (`setExWeight`) нужно развести на два явных действия:
- «только сегодня» — нагрузка этой тренировки, `progressState` не трогается, в истории фиксируется фактическая;
- «теперь мой рабочий вес» — это ручная смена назначения, `progressState.count = 0`.

Решение по UI принимается в PR runtime; молчаливое смешение двух смыслов не оставляем.

### 5.6. Цепочка усложнения движения — включаем в V2

Legacy `swapName/swapDesc` удаляем. Вместо него каждое упражнение V2 имеет 1..4 movement stages.

Пример:

```text
Отжимания с колен
→ Обычные отжимания
→ Отжимания с ногами на опоре
→ Более сложный финальный вариант
```

### Лимит

Максимум **4 stage всего**.

Это подтверждено третьим ревью как достаточный практический предел:
- покрывает типичные домашние лестницы;
- не превращает упражнение в мини-программу;
- ограничивает AI output/UI/media;
- после последнего stage цепочку можно перестроить/продолжить отдельной правкой.

### Хранение

Все stages остаются в массиве, даже после перехода.

Ничего не переносим из `next` в `done` и не удаляем при обычном переходе.

`currentStageId` просто указывает, какой из 1..4 stages сейчас активен.

Следствия:
- можно штатно вернуться к предыдущему stage;
- история может привязаться к конкретному `movementStageId`;
- не надо реконструировать старый prescription;
- прошлый stage остаётся полноценным и редактируемым.

Каждый stage содержит:
- app-owned `stageId`;
- полный `ExercisePrescription`;
- policy перехода к следующему stage;
- app-owned `mediaRef/visualKey`.

Stage НЕ содержит:
- `exercise.id`;
- `progressState`;
- history;
- nested chain.

### ID и история

`exercise.id` сохраняется на весь логический слот программы.

У каждого варианта движения свой `movementStageId`.

Историческая идентичность:

```text
exercise.id + movementStageId + cfgKey
```

History row хранит только `movementStageId`; имя разрешается через компактную `stats.stageNames[stageId]`.

Поэтому:
- «с колен → обычные» не выглядит как ↑ нагрузки;
- переименование/удаление stage позже не переписывает текст старой истории;
- внутри одного movementStage обычная load/reps progression сравнивается нормально.

### Переход к следующему stage

У каждого stage, кроме последнего, есть:

```js
advance: {
  mode: 'ceiling' | 'manual'
}
```

#### ceiling

Приложение само предлагает следующий stage после terminal ceiling.

Для `advance.mode='ceiling'` validator требует:
- `progression.mode !== 'none'`;
- текущая progression policy действительно имеет terminal ceiling для растущей оси/цикла.

Если автоматического terminal ceiling нет, такой stage нельзя сохранить как `ceiling`.

#### manual

Автоматического предложения по потолку нет.

Переход делается пользователем вручную.

Это покрывает движения, где качественный переход определяется не числовым потолком, а ощущением техники/контроля.

### Ручной override

Если следующий stage существует, **«Перейти сейчас» доступно всегда**, независимо от `advance.mode`.

Переход:
1. пользователь подтверждает;
2. меняется только `currentStageId`;
3. `exercise.id` сохраняется;
4. `progressState` сбрасывается;
5. prescription берётся из нового активного stage;
6. old/new stages не сравниваются как обычная load progression.

Не переключать stage автоматически посреди активной тренировки.

### Возврат назад

Если перед текущим stage есть предыдущий:
- доступно действие «Вернуться к прошлому варианту»;
- меняется `currentStageId`;
- прошлый prescription уже лежит в `stages[]`, ничего восстанавливать не нужно;
- `progressState` сбрасывается;
- stage начинает с БАЗОВОГО prescription, а не с того progressed state, на котором пользователь когда-то его покинул;
- будущие stages НЕ удаляются.

Это осознанное решение: отдельный progressState на каждый stage не храним ради редкого rollback-сценария.

Перед подтверждением UI показывает базовый старт, например:
> Вернуться к «Отжимания с колен»? Начнёшь с 2 × 10 повт.

На финише тренировки при «тяжело» можно предложить возврат, если предыдущий stage существует, но не выполнять его автоматически.

### Когда AI создаёт chain

Chain не обязателен у каждого упражнения.

AI предлагает 1..4 stages только когда:
- движение имеет естественную качественную лестницу;
- одной reps/weight/time/level progression недостаточно;
- stages остаются вариантами одного базового movement pattern.

AI не должен делать chain из почти одинаковых весовых упражнений вместо нормальной load progression.

### AI и изменение движения

Нельзя определять смену движения только по названию.

AI contract явно возвращает:

```text
movementChanged: true | false
```

Правила:
- ручное переименование = metadata edit, stage identity не меняется;
- AI `exercise.modify` / program-edit `replace`:
  - `movementChanged:false` → редактируется prescription текущего stage; дальнейший перенос/сброс progressState определяется обычными domain rules;
  - `movementChanged:true` → это новое движение: chain текущего упражнения заменяется новым AI-owned stage set, приложение выдаёт новые `movementStageId`, `progressState` сбрасывается;
- `exercise.replace` из тренировки всегда считается `movementChanged:true`;
- перед применением UI явно показывает: «Новое упражнение — прогресс начнётся заново».

Почему при AI replacement chain сбрасывается целиком:
- будущие stages были спроектированы под старое движение;
- автоматически смешивать старую лестницу с новым движением опаснее, чем пересоздать максимум 4 stage;
- старая история остаётся читаемой благодаря `movementStageId + movementStageName` в history.

### Картинки stages

AI никогда не возвращает media/base64.

У stage persistent только:
- `mediaRef`, если уже есть сохранённый ресурс;
- `visualKey` для cache lookup.

Текущий stage:
- приложение пытается разрешить mediaRef/cache;
- если нет — работает с placeholder до ручной/AI-генерации.

Будущие stages:
- заранее платно НЕ генерируются;
- для ближайшего следующего stage cache lookup можно сделать при открытии блока/preview;
- cache miss сам по себе не запускает генерацию;
- генерация запускается при явном preview/action пользователя либо при подтверждении перехода;
- отсутствие картинки не блокирует переход;
- дальние stages не prefetch/generate.

При возврате назад используется сохранённый `mediaRef/visualKey`; если ресурс недоступен — placeholder + повторное разрешение/генерация.

После canonical exercise library cache identity:
```text
canonical movement + визуально значимая load/support configuration
```

До неё допускается deterministic `visualKey` из нормализованного stage prescription.

### UI chain

В редакторе:

```text
Варианты упражнения · 4

Сейчас: Обычные отжимания
[Вернуться к прошлому варианту]

1. С колен
2. Обычные            ← сейчас
3. Ноги на опоре
4. Сложный вариант
```

Действия:
- открыть/редактировать stage;
- добавить stage;
- удалить stage;
- переставить stage;
- максимум 4;
- выбрать `ceiling/manual` для перехода к следующему;
- «Перейти сейчас» у ближайшего следующего;
- preview/подготовка картинки.

Если пользователь добавляет следующий stage с `ceiling`, а terminal ceiling ещё не задан, UI сразу показывает нужные поля и не даёт сохранить противоречивую конфигурацию.

- onboarding/privacy тексты, где сейчас сказано просто «инвентарь»;

- «Без доп. оборудования» влияет только на доп. оборудование;

- один и тот же catalog item не должен вручную дублироваться разными строками/алиасами.

## 7. Единая модель отображения нагрузки

Недостаточно одной функции, которая просто собирает строку. Нужен один вычисляемый объект отображения нагрузки, построенный из канонической модели упражнения и текущего progression state.

Принцип:

> Храним нагрузку в одном месте, вычисляем текущее состояние в одном месте, а все экраны только отображают один и тот же результат.

Не создавать отдельные UI-состояния вида «вес для карточки», «вес для старта», «вес для тренировки», «вес для каталога».

Рабочее направление API:

```js
exerciseLoadView(ex, program, options)
```

По смыслу он должен возвращать как минимум:
- тип нагрузки;
- тип и пользовательское название снаряда;
- количество;
- базовый вес/уровень;
- текущий прогрессированный вес/уровень;
- короткую подпись;
- расширенную подпись;
- ключ конфигурации;
- признак смены конфигурации при сравнении с snapshot.

Короткий и расширенный formatter должны быть частью этого слоя, а не отдельной логикой экранов.

Нужна одна централизованная модель, которая знает, как показывать текущую нагрузку.

Короткий формат:
- `2 × 10 кг`
- `10 кг`
- `Средняя`
- `Красная`

Расширенный формат:
- `2 гантели по 10 кг`
- `Штанга · 40 кг`
- `Резинка · Средняя`

Не размножать ручную сборку строк по приложению.

Эта модель должна использоваться минимум в:
- списке упражнений в конструкторе;
- карточке/строке программы;
- редакторе упражнения;
- стартовом экране тренировки;
- строках выбора точки старта тренировки;
- самой тренировке;
- финальном progression preview;
- «было → сегодня»;
- истории нагрузки упражнения;
- каталоге программ и его превью;
- тренерских отчётах;
- отправке программы подопечному;
- текстовом экспорте;
- экспорте с текущей прогрессией / без неё;
- AI-edit context.

На UI-PR отдельно пройти поиском все места, где сейчас напрямую отображаются `weight`, `kg`, `loadLabel`, `loadLevel` или собирается подпись упражнения, и либо перевести их на единый слой, либо явно зафиксировать причину исключения.

## 8. AI-контракт: семантика и переход на V2

Текстовые примеры ниже нужны только для объяснения СМЫСЛА новых полей относительно текущего протокола. Финальный машинный wire-format после миграции V2 — JSON, описанный в разделе 8.4. Старые русские строки не являются целевой долгосрочной архитектурой.

### Вес

Вместо:

```text
ФОРМАТ: повторения и вес
ВЕС: 5
```

Целевая форма:

```text
ФОРМАТ: повторения
НАГРУЗКА: вес
СНАРЯД: гантель
КОЛИЧЕСТВО: 2
ВЕС: 5
```

### Одна гантель

```text
ФОРМАТ: повторения
НАГРУЗКА: вес
СНАРЯД: гантель
КОЛИЧЕСТВО: 1
ВЕС: 10
```

### Сопротивление

```text
ФОРМАТ: повторения
НАГРУЗКА: сопротивление
СНАРЯД: резинка
СОПРОТИВЛЕНИЕ: Среднее
УРОВНИ СОПРОТИВЛЕНИЯ: Лёгкое | Среднее | Сильное | Очень сильное
```

### Без дополнительной нагрузки

```text
ФОРМАТ: повторения
НАГРУЗКА: нет
```



### 8.1. Доступный инвентарь пользователя в AI-запросе

Вместо текущей одной строки вида:

```text
Available equipment: ...
```

передавать две короткие строки только когда пользователь сделал выбор:

```text
Available load equipment: dumbbells, resistance bands.
Available support equipment: mat, bench.
```

И одно общее правило, записанное в контракте один раз:

> Available means guaranteed to be available, not required in every exercise. Use any subset, including none, when appropriate. Do not assume unlisted specialized equipment unless the user request/context explicitly implies it.

Не повторять это правило в каждом упражнении и не перечислять свойства каждого предмета.

Для конкретного упражнения AI-протокол дополнить отдельным условным полем:

```text
ДОП ОБОРУДОВАНИЕ: скамья | коврик
```

Строка отсутствует, если дополнительное оборудование не нужно.

`СНАРЯД` и `ДОП ОБОРУДОВАНИЕ` должны нормализоваться через один канонический каталог, но относиться к разным категориям.

### 8.2. Ограничение размера AI-контракта

Не отправлять ИИ весь внутренний справочник снарядов с UI-метаданными, иконками, дефолтами и алиасами.

AI нужен только короткий машинный контракт:
- допустимые канонические типы снарядов;
- правило «ВЕС = вес одной единицы»;
- правило количества;
- `Другое` для неизвестного типа.

Канонический список должен передаваться одной компактной строкой/enum, например по смыслу:

```text
СНАРЯД: гантель | штанга | ez-штанга | гиря | блин | медбол | сэндбэг | жилет | утяжелитель | тренажёр | блок | резинка | эспандер | другое
```

Это десятки слов, а не отдельная инструкция на каждый снаряд.

Все свойства вроде:
- «для гантелей по умолчанию количество 2»;
- «для штанги UI скрывает количество 1»;
- иконки;
- локализованные подписи;
- алиасы пользовательского ввода

живут только в приложении и в AI prompt не отправляются.

Если модель вернула неизвестный снаряд, он нормализуется в:
- `Другое`;
- исходное название сохраняется как пользовательское имя.

### 8.3. Бюджет промпта и его упрощение

На момент создания этого плана текущий базовый `FitAIProtocol.programPrompt("Russian")` уже составляет примерно:
- 12 274 символа;
- 109 строк;
- ориентировочно около 3 тыс. токенов.

`editRules()` добавляет ещё:
- 6 325 символов;
- 36 строк;
- ориентировочно около 1,6 тыс. токенов.

То есть AI-edit ещё ДО текста самой программы получает примерно 18,6 тыс. символов правил.

Это не выглядит критичным по размеру контекстного окна современных моделей, но уже создаёт другой риск:
- слишком много повторяющихся правил;
- противоречия между старой и новой семантикой;
- модель хуже замечает действительно важные ограничения;
- длинный ответ для большой программы повышает задержку и риск timeout.

Поэтому задача PR 3 (FitTimer AI Contract V2) — не наращивать старый промпт, а заменить его компактным структурированным контрактом и провести cleanup оставшихся фитнес-правил.

Правила:
1. Один факт описывается один раз.
2. Схема поля и правила прогрессии не должны дублировать друг друга длинными абзацами.
3. То, что можно надёжно проверить кодом после ответа, не объяснять модели многократно.
4. Справочник снарядов — одна компактная enum-строка.
5. Не отправлять UI-метаданные справочника.
6. Для AI-edit сохранять уже существующий принцип: неизменные длинные описания упражнения модель не обязана переписывать.
7. Перед merge PR 3 измерить размер CREATE и EDIT input/prompt/output до/после. Новая версия не должна существенно вырасти только из-за модели снарядов.
8. Желательная цель: после cleanup базовый контракт должен быть не длиннее текущего, несмотря на добавление СНАРЯД/КОЛИЧЕСТВО.

Переход на JSON Schema / Structured Output ТЕПЕРЬ входит в эту задачу как отдельные Core + FitTimer PR до массового создания нового контента. Старый текстовый протокол допускается только как временный переходный слой, пока не переведены все AI-actions.


## 8.4. Целевая AI-архитектура V2: JSON + Structured Output

До массового наполнения каталога и создания большого количества программ перевести машинный обмен FitTimer ↔ AI с человекочитаемого строкового протокола на единый структурированный контракт.

### Почему не оставлять текущий текстовый протокол

Сейчас prompt одновременно:
- объясняет фитнес-логику;
- описывает машинный формат ответа;
- объясняет порядок строк;
- перечисляет обязательные/условные поля;
- повторяет правила совместимости;
- затем приложение regex/parser-логикой восстанавливает объект обратно.

Это увеличивает prompt, создаёт дублирование и позволяет модели:
- забыть строку;
- изменить название поля;
- вернуть противоречащие друг другу поля;
- потерять новые поля вроде снаряда/количества.

### Канонический контракт

Сделать versioned DTO-контракт с отдельной схемой на каждую action-задачу.

Минимально покрыть текущие реальные kind:
- `program.create`;
- `program.modify`;
- `exercise.create`;
- `exercise.modify`;
- `exercise.replace`;
- `video.parse`.

Админская генерация каталога должна использовать те же program-create сущности/validator, а не отдельный текстовый формат.

`contractVersion: 2` передаётся в каждом машинном запросе/ответе.

Данные в JSON. Человекочитаемые значения (названия/описания) остаются на языке программы; машинные enum/ключи — стабильные и не локализуются.

Не использовать русские названия полей как machine keys.

### Один источник истины схемы

Нельзя поддерживать отдельно:
- prompt-описание полей;
- parser;
- API JSON Schema;
- validator;
- типы.

Нужен один канонический schema source, из которого по возможности получают:
- JSON Schema для провайдера;
- локальную structural validation;
- тестовые fixtures;
- документацию контракта.

FitTimer сейчас не зависит от Zod/Ajv, поэтому конкретную библиотеку выбрать отдельным техническим решением при реализации. Главное — не создавать четыре независимых списка полей.

Решение после ревью: canonical source — вручную контролируемая JSON Schema в переносимом подмножестве, которое проходит у всех поддерживаемых провайдеров.

Эта же schema используется для локальной structural validation через Ajv/эквивалент, чтобы не писать второй независимый structural-validator руками.

Отдельный domain-validator остаётся только для кросс-полевых фитнес-правил, которые provider JSON Schema надёжно не выражает.

### Структурированный INPUT, а не готовый prompt с клиента

Сейчас встроенный клиент сам собирает большую строку и отправляет на `/api/ai`:

```text
{ kind, prompt, ... }
```

Для V2 встроенный путь должен отправлять нормализованный input DTO:

```json
{
  "kind": "program.create",
  "contractVersion": 2,
  "input": {
    "user": {},
    "request": {},
    "availableLoadEquipment": [],
    "availableSupportEquipment": []
  }
}
```

Дальше СЕРВЕР:
1. выбирает action по `kind`;
2. валидирует input;
3. выбирает server-owned output schema;
4. строит provider prompt общей pure-функцией/компилятором;
5. вызывает провайдера;
6. валидирует structured output.

Клиент не должен присылать произвольную JSON Schema и не должен быть источником истины provider prompt.

Для ручного «скопировать в чат» тот же shared prompt-builder может работать в браузере над тем же input DTO. Так остаётся один contract, а не две разные системы.

Это также позволяет менять встроенный server prompt/правила без релиза APK, сохраняя совместимость по `contractVersion`.

### Structured Output во встроенном AI

Расширить AppBase Core AI adapter опциональным параметром структурированного ответа.

Рабочая идея:

```js
generate('text', settings, prompt, {
  schema: programCreateSchema,
  validate: ...
})
```

Provider adapter преобразует общий schema option в нативный механизм провайдера.

Текущие направления поддерживают structured JSON, но НЕ одинаково:
- OpenAI Responses API — Structured Outputs по JSON Schema;
- Gemini — Structured Output по поддерживаемому подмножеству JSON Schema;
- OpenRouter — `response_format: json_schema` только на endpoint'ах, которые реально поддерживают этот parameter.

Поэтому:
- Structured Output должен работать для каждого провайдера, который остаётся доступен пользователю/админу в FitTimer после cutover (сейчас Gemini/OpenAI/OpenRouter); если provider сознательно убираем из выбора, только тогда его V2 adapter не нужен;
- product schema держать в общем переносимом подмножестве JSON Schema;
- не полагаться на сложные `if/then/dependentSchemas` и provider-specific constraints там, где это можно проверить domain-validator'ом;
- числовые лимиты, взаимозависимость полей и фитнес-правила всегда дополнительно проверять локально;
- для OpenRouter при V2 использовать `provider.require_parameters=true`, чтобы schema-параметр не был молча проигнорирован;
- если основной endpoint не поддерживает schema, переходить только на совместимый backup или возвращать конфигурационную ошибку — НЕ молча деградировать встроенный V2 в свободный текст;
- JSON mode допустим лишь как явно контролируемый переходный fallback, не как скрытая норма;
- safety refusal не считать «битым JSON» и не обходить автоматическим перебором провайдеров;
- max-token/incomplete response обрабатывать отдельно.

Официальные ссылки для повторной проверки перед кодом:
- OpenAI Structured Outputs: https://developers.openai.com/api/docs/guides/structured-outputs
- Gemini Structured Output: https://ai.google.dev/gemini-api/docs/structured-output
- OpenRouter Structured Outputs: https://openrouter.ai/docs/guides/features/structured-outputs

Даже при provider-side schema enforcement локальная validation остаётся обязательной, особенно для кросс-полевой фитнес-семантики.

### Не использовать function calling для генерации программы

Function/tool calling нужен, когда модель должна вызвать действие/инструмент.

Здесь модель должна вернуть конечные данные программы. Поэтому основной механизм — structured response JSON Schema, а не фиктивный tool `createProgram(...)`.

### Не использовать простой JSON mode как основной вариант

`json_object` / просьба «верни JSON» гарантирует максимум синтаксически валидный JSON, но не гарантирует нужные enum, required fields и структуру.

Допускается только как fallback там, где строгая schema конкретным provider/model не поддерживается, и обязательно с локальной validation.

### Создание программы

CREATE возвращает полный объект новой программы по schema.

В prompt остаются только:
- роль/задача;
- фитнес-правила, которые нельзя выразить схемой;
- пользовательские данные/ограничения;
- доступные снаряды и доп. оборудование;
- запрос пользователя.

Из prompt удаляются:
- инструкции про точные названия строк;
- порядок строк;
- Markdown/no-Markdown;
- большая часть описания required/optional формата;
- regex-oriented compatibility rules.

### Создание упражнения

Отдельная schema только для одного/нескольких упражнений.

Не посылать модели schema всей программы, когда нужно создать одно упражнение.

Exercise output может содержать 1..4 movement stage specifications:
- только если у движения есть естественная лестница вариантов;
- каждый stage = полный ExercisePrescription + advance.mode;
- AI НЕ возвращает stageId/currentStageId/progressState/media;
- приложение после validation создаёт app-owned stageId и выбирает текущим первый stage;
- если chain не нужна, AI возвращает ровно один stage.

### Редактирование программы: target state + ссылки — ПРИНЯТОЕ РЕШЕНИЕ

От operation-based DSL отказываемся.

AI возвращает **целевую структуру программы после изменения**, но неизменённые сущности не переписываются — они представлены короткими ссылками по стабильным ID.

Пример по смыслу:

```json
{
  "contractVersion": 2,
  "kind": "program.modify",
  "plans": [
    {
      "ref": "plan_a",
      "patch": {"days": ["Tue"]},
      "exercises": [
        {"ref": "ex_1"},
        {
          "ref": "ex_2",
          "replace": {
            "movementChanged": false,
            "stages": [
              {"ref": "mv_1"},
              {"ref": "mv_2", "replace": {"...": "полный prescription + advance"}},
              {"new": {"...": "полный stage spec"}}
            ],
            "removedStageIds": []
          }
        },
        {
          "new": {
            "stages": [{"...": "1..4 полных AI-owned stage specs"}]
          }
        }
      ]
    },
    {
      "ref": "plan_b",
      "exercises": [
        {"ref": "ex_4"},
        {"ref": "ex_3"}
      ]
    }
  ],
  "removedPlanIds": [],
  "removedExerciseIds": ["ex_5"]
}
```

Правила:
- существующие `program.id/plan.id/exercise.id` AI не меняет;
- каждый существующий `plan.id` встречается ровно один раз либо находится в `removedPlanIds`;
- каждый существующий `exercise.id` встречается ровно один раз либо находится в `removedExerciseIds`;
- перенос упражнения = тот же `ref` находится в другом плане;
- reorder = изменился порядок refs;
- `patch` всегда означает ЧАСТИЧНУЮ правку существующей сущности (используем для plan/program metadata; `null` явно очищает nullable поле);
- `replace` всегда означает ПОЛНЫЙ новый AI-owned exercise spec существующего слота;
- `replace.movementChanged` обязателен;
- если `replace.movementChanged:false`, stages используют тот же target-state + refs принцип:
  - `{"ref":"mv_1"}` = stage без изменений;
  - `{"ref":"mv_2","replace":{...}}` = полный новый AI-owned spec существующего stage;
  - `{"new":{...}}` = новый stage;
  - `removedStageIds` = явные удаления;
  - каждый существующий stageId встречается ровно один раз либо находится в removedStageIds;
  - текущий currentStageId нельзя удалить при movementChanged:false;
- если `replace.movementChanged:true`, refs старых stages не используются: AI возвращает 1..4 новых stage specs, приложение выдаёт новый набор stage IDs;
- новый exercise object = `new` с 1..4 stage specs; постоянные exercise/stage IDs выдаёт приложение после validation;
- удаление никогда не выводится из «пропажи» объекта — только явно;
- AI не пишет `progressState`, history, media/base64, sync/trainer metadata и app-owned IDs.

Почему target state лучше enum операций:
- перестановки/split/merge/переносы выражаются самой итоговой структурой;
- не надо проектировать и поддерживать язык `move/add/remove/before/after`;
- неизменённый объект занимает только короткий ref;
- итоговую структуру проще проверить целиком.

Применение:
1. зафиксировать immutable snapshot программы, который реально ушёл в запрос;
2. проверить refs/removed и уникальность;
3. собрать новую копию программы из refs + patch/replace/new;
4. провести schema + domain validation;
5. применить transaction целиком;
6. при любой ошибке не сохранять ничего.

Так AI-edit остаётся компактным, но не может молча потерять существующую часть программы.

Если пользователь просит «добавь это же упражнение ещё в другой день», один и тот же `exercise.id` нельзя упомянуть дважды. Создаётся `new`-копия с новым ID и пустым progressState. Это отдельный экземпляр упражнения.

### Редактирование одного упражнения

Отдельный `exercise_edit` schema:
- ID исходного exercise slot;
- обязательный `movementChanged: true|false`;
- target-state stage list.

При `movementChanged:false` применяется тот же stage refs contract:
- unchanged stage → `ref`;
- changed stage → `ref + replace(full stage spec)`;
- added stage → `new(full stage spec)`;
- removed stage → явный `removedStageIds`;
- каждый старый stageId либо упомянут ровно один раз, либо явно удалён;
- текущий stageId удалять нельзя;
- порядок массива = новый порядок chain.

Так сохраняются stageId/history/mediaRef существующих stages даже при add/remove/reorder.

При `movementChanged:true`:
- refs старой chain запрещены;
- AI возвращает новый набор 1..4 stage specs;
- приложение создаёт новые stageId/currentStageId;
- progressState сбрасывается.

AI никогда не пишет app-owned exercise/stage IDs в новых specs и никогда не пишет progressState/media.

### Preview AI-правки

Перед применением показывать структурный diff:
- добавлен stage;
- изменён stage;
- удалён stage;
- перемещён stage;
- какой stage сейчас current.

Если `movementChanged:false`, но AI поменял название текущего stage, отдельно показать:
> Название изменилось, прогресс сохранится.

Не добавляем эвристический guard «похоже ли новое название на старое движение»: identity задаётся контрактом + refs, а физическая нагрузка/формат дополнительно проходят обычные domain validation/reset rules.

### Замена упражнения с тренировки

`exercise.replace` — отдельная action и всегда трактуется как `movementChanged:true`.

Она может переиспользовать exercise output schema с более жёстким task-prompt:
- сохранить цель/pattern замены там, где это уместно;
- не вводить недоступное оборудование;
- вернуть 1..4 stage specs новой лестницы;
- приложение выдаёт новый набор movementStageId и сбрасывает progressState.

Перед применением UI явно сообщает: «Новое упражнение — прогресс начнётся заново».

Нельзя оставить этот путь на старом строковом протоколе после удаления legacy parser.

### Импорт из видео

`video.parse` уже сейчас внутри использует JSON для evidence extraction, но финально превращает факты обратно в старый строковый FitTimer protocol.

При V2:
- evidence extraction остаётся source-grounded;
- финальный `factsToProtocol` заменить на сборку того же Program DTO V2;
- schema НЕ имеет права ослабить проверки, что reps/time/sets/rest/order/timestamp соответствуют подтверждённому видео;
- coaching metadata может дополнять только уже подтверждённое движение;
- оборудование не придумывать, если оно не подтверждено видео/транскриптом.

### Админская генерация каталога

`catalog-ai.js` должна перейти на тот же Program DTO + validator. Не создавать отдельную catalog-схему только потому, что запрос запускает админ.

Catalog-specific поля (цель витрины, описание для карточки, статус модерации) остаются вокруг программы, а не меняют внутреннюю модель упражнения.

### Что отправлять AI при edit

Не отправлять UI presentation fields и вычисляемые подписи.

Отправлять канонические данные упражнения/программы:
- стабильные ID;
- метрика;
- базовая нагрузка;
- снаряд/количество;
- доп. оборудование;
- progression policy;
- актуальные пользовательские данные, которые нужны задаче.

Текущий progression state передавать только как READ-ONLY derived context, когда он действительно нужен для оценки текущей рабочей нагрузки. AI не должен возвращать или мутировать `ps`; перенос/сброс прогресса остаётся детерминированной логикой приложения.

Длинные описания техники неизменённых упражнений можно не включать в narrow edit, если запрос к ним не относится.

### Ручной режим «скопировать запрос → вставить в ChatGPT/Gemini»

Этот путь должен использовать тот же JSON contract V2.

Внешний чат нельзя заставить API-level JSON Schema, поэтому:
- prompt содержит компактное описание требуемого JSON;
- ответ парсится тем же parser/validator;
- code fences вокруг JSON разрешаем и очищаем;
- при ошибке показываем конкретную структурную проблему.

Не создавать для manual-copy отдельный старый текстовый протокол: иначе снова появятся две архитектуры.

### Версионирование

Каждый структурированный ответ содержит `contractVersion`.

Это позволит менять schema позже без угадывания формата и без regex legacy heuristics.

## 8.5. Что даёт V2 по размеру prompt

Structured Output не означает «schema бесплатна»: JSON Schema тоже передаётся провайдеру и имеет стоимость контекста/обработки.

Выигрыш здесь в другом:
- убирается большая часть естественно-языковых инструкций о формате;
- schema однозначнее абзацев;
- формат не надо повторно объяснять в CREATE/EDIT;
- существенно сокращается EDIT output благодаря target-state refs: неизменённые сущности не переписываются;
- можно иметь маленькую schema под конкретную задачу вместо одного mega-contract.

Дополнительно по каждому AI-action задавать разумный `max_output_tokens` вместо общего 32768, когда контракт позволяет заранее ограничить ответ.

В AI-log добавить минимум:
- `contractVersion`;
- `schemaVersion`;
- `promptVersion`;
- kind/provider/model;
- usage/token counts, когда провайдер их возвращает;
- validation/fallback result.

Обязательные метрики перед внедрением и после:
- input chars/tokens CREATE;
- input chars/tokens EXERCISE CREATE;
- input chars/tokens PROGRAM EDIT для 1, 5, 20 упражнений;
- output chars/tokens для тех же сценариев;
- latency;
- доля invalid responses/retries.

Решение принимать по этим измерениям, а не по ощущению «JSON короче».

---
### Обязательные правила AI

- При `НАГРУЗКА: вес` обязательно указывать снаряд.
- При `НАГРУЗКА: вес` обязательно указывать количество одновременно используемых единиц.
- `ВЕС` всегда относится к одной единице.
- Одностороннее упражнение с одной гантелью имеет количество 1.
- Не добавлять вес тела.
- Не рассчитывать и не возвращать «общий вес всех гантелей».
- Не переводить сопротивление резинки в кг без явных данных пользователя/производителя.
- При AI-edit сохранять снаряд и количество, если пользователь явно не просил изменить конфигурацию.
- Если AI меняет тип снаряда или количество, это должно рассматриваться приложением как смена конфигурации, а не как обычный progression step.

## 9. Contract adapters / serializer / import / export

После перехода V2 основной AI parser — JSON parse + schema/domain validation.

Старый русскоязычный строковый parser остаётся только временно на период миграции действий и удаляется после перевода:
- program.create/modify;
- exercise.create/modify/replace;

### Экспорт без текущей прогрессии

Возвращает базовую нагрузку.

### Экспорт с текущей прогрессией

- снаряд не меняется;
- количество не меняется;

## 10. История и snapshot нагрузки

V2 history стартует пустой; старый формат не читаем.

Каждая запись нагрузки хранит компактный storage DTO, достаточный для восстановления domain view через history adapter:

```js
histEntry = {
  …,
  planId,
  load: [
    // по смыслу: e=exId, s=movementStageId, c=cfgKey,
    // r=reps, t=sec, w=weight, l=levelKey/label only when needed
    {e:"ex_abc", s:"mv_abc", c:"w|db||2", r:"8-10", w:10}
  ]
}
```

Имена stages лежат отдельно в `stats.stageNames`; пустые/default поля в row не сериализуются.

History segment:

```text
exId + movementStageId + cfgKey
```

Правила:
- тот же stage + тот же cfgKey → можно показывать «было → сегодня»;
- новый movementStageId → новый вариант движения, не сравнивать как ↑/↓ нагрузки;
- новый cfgKey → новая физическая конфигурация, не сравнивать как ↑/↓;
- `movementStageName` гарантирует правильное старое название даже после редактирования/сброса chain;
- для level сохранять identity/label фактически использованного уровня, а не numeric index.

Серверный лимит sync-документа сейчас 3 МБ, history ограничена 2000 записями. Отдельный regression обязан проверить worst-case 2000 тренировок; если документ приближается к лимиту, history надо вынести из одного stats-документа отдельной задачей, а не добавлять словарь конфигураций.

### Сравнение

Один stage/config:

```text
Румынская тяга
2 × 6 кг → 2 × 7 кг
```

Новый stage:

```text
Отжимания
Новый вариант: обычные отжимания
```

Новая физическая конфигурация:

```text
Румынская тяга
Новая конфигурация: 1 гантель 12 кг
```

НЕ показывать между разными stage/config:
- стрелку ↑/↓;
- «нагрузка выросла»;
- сравнение общего веса.

## 12.1. Совместимость с будущим каноническим каталогом упражнений

В существующем `docs/ai-generation-plan.md` уже запланированы строгий JSON/patch и `canonicalExerciseId` для повторного использования изображений. Новый план НЕ должен создать конкурирующую архитектуру.

Разделяем две identity:
- `exercise.id` — конкретный экземпляр упражнения в конкретной программе;
- будущий `canonicalExerciseId` — нормализованное движение/вариант в общей библиотеке.

AI не должен сам придумывать постоянный `canonicalExerciseId`. Его назначает сервер/каталог после нормализации или сопоставления.

До массового наполнения каталога желательно отдельно решить границу:
- **definition**: название/техника/мышцы/ошибки/визуальная identity;
- **prescription**: повторы/время/подходы/отдых/load/progression внутри конкретной программы.

Эта задача НЕ блокирует текущую модель нагрузки, поэтому полный exercise-definition catalog не включаем в первые PR. Но V2 DTO и image pipeline не должны мешать такому разделению позже.

Практическое правило уже сейчас:
- media/base64 и progression state не входят в AI output;
- image prompt берёт `load.equipment + load.count + supportEquipment` из структурированных данных;
- после появления canonical catalog картинка кэшируется по каноническому движению + визуально значимой конфигурации оборудования, а не только по тексту названия.

Перед массовой генерацией каталога/картинок этот пункт должен быть закрыт отдельным решением.

## 14.1. Сознательные ограничения V1 / не забыть перед масштабированием

Это НЕ ошибки реализации, а зафиксированные границы, которые другой ревьюер должен оценить отдельно:

1. **Одна независимая внешняя load-axis на упражнение.** Multi-component load не автоматизируем.
2. **Инвентарь в AI-форме пока type-level.** Точные доступные количества/веса/шаги не храним.
3. **Постоянный пользовательский inventory profile не вводим в этой задаче.** Выбор request-scoped.
4. **Ввод и отображение веса V1 только в kg**, но доменная модель использует нейтральные `weight/unit`, без новых kg-specific имён состояния. Будущий lb всё равно потребует UI/валидацию, но не ломку доменной схемы.
5. **Canonical exercise library не строим в первых PR**, но до массового каталога обязаны разделить instance-id и canonical identity.
6. **JSON Schema не заменяет domain validation.** Фитнес-условия, inventory compatibility и progression semantics проверяются кодом.
7. **Данные не переносятся вообще** (1.9): приложение стартует пустым, реальные программы пользователя/Светы генерируются заново и становятся regression fixtures.
8. **Один вес на упражнение для всех подходов.** Пирамиды, разминочные подходы с меньшим весом, «основной + облегчённые» подходы модель не представляет.
9. **Movement progression включён в V2 и ограничен 4 stages total.** Все stages сохраняются для возврата; более длинная лестница требует отдельного редактирования существующих 4 stages, а не бесконечного списка.

## 14.2. Вопросы для независимого ревью перед реализацией

При передаче этого плана другой модели/разработчику просить НЕ пересказывать решение и не исходить из того, что оно уже верное. Нужен adversarial review: искать контрпримеры, лишнюю сложность и места, где текущий код FitTimer противоречит плану.

Особенно перепроверить:

1. **Модель нагрузки.** Хватает ли правила «одна основная внешняя load-axis + count одинаковых источников» для 95–99% реальных домашних/зальных упражнений? Какие распространённые упражнения оно представляет плохо?
2. **Weight semantics.** Однозначны ли гантели, штанга, plate-loaded/selectorized machine, cable, жилет, утяжелители и односторонние упражнения без скрытого total/per-item режима?
3. **Level semantics.** Корректно ли трактовать список уровней как рост сложности, особенно для assisted pull-up/dip и резинок-помощников?
4. **Смена конфигурации.** Правильно ли отделены:
   - обычный progression step;
   - ручная смена рабочего назначения;
   - смена equipment/count как новый history segment?
   И верно ли сбрасывать `progressState.count` при ручном изменении нагрузки/policy?
5. **Load vs support equipment.** Есть ли распространённые предметы/упражнения, где двух категорий недостаточно или один и тот же предмет одновременно играет обе роли так, что модель становится неоднозначной?
6. **Инвентарь пользователя.** Достаточно ли в V1 знать только тип доступного оборудования, или без `availableCount / availableWeights / increments` AI будет слишком часто выдавать физически невыполнимую прогрессию?
7. **AI Contract V2.** Не переусложняем ли Structured Output + target-state refs? Есть ли более простой контракт с той же надёжностью?
8. **Program edit target state.** Закрывают ли refs + plan patch + exercise replace/new реальные запросы: перестановка, добавление/удаление, split/merge, перенос, duplicate exercise, изменение только части progression policy?
9. **Identity.** Достаточны ли `program.id / plan.id / exercise.id`, и где должна проходить граница с будущим `canonicalExerciseId`?
10. **App-owned vs AI-owned state.** Не отдаём ли AI лишние поля? Достаточно ли жёстко защищены `ps`, history, media, sync/trainer metadata и persistent IDs?
11. **Provider portability.** Реально ли выбранный общий JSON Schema subset одинаково проходит текущие Gemini/OpenAI/OpenRouter маршруты без provider-specific fork?
12. **Порядок PR.** Корректно ли после решения «прод можно ломать» идти: stable IDs/history → V2 schema/runtime → UI → Core Structured Output → AI V2?
13. **Все каналы.** Не пропущены ли import/export/share/sync/backup/catalog/trainer/session/video/image/admin/privacy/i18n.
14. **Что вообще удалить.** Какие существующие legacy-поля/ветки после V2 становятся вторым source of truth и должны исчезнуть, а какие пока опасно трогать?
15. **Movement chain.** Достаточно ли лимита 4 stages total? Какие распространённые progression chains требуют больше 4 этапов?
16. **Movement images.** Правильно ли не хранить base64 future-stage media, делать cache lookup для ближайшего stage и генерировать только по preview/transition?
17. **Стоимость сложности.** Где план решает гипотетическую проблему ценой слишком большой архитектуры для текущего масштаба FitTimer?

Формат полезного внешнего ревью:
- сначала критические ошибки/риски;
- затем спорные решения с альтернативой;
- затем пропущенные кейсы;
- затем что можно упростить;
- в конце — вердикт по порядку реализации.
Не считать сам факт наличия решения в этом файле аргументом в его пользу.

## 14.3. Решения после первого разбора ревью Клода — 2026-10-08

Историческая запись. Там, где она конфликтует с 14.4/14.5 и основными разделами документа, актуальными считаются более поздние решения.

### Принято из ревью Клода

- stable `plan.id` и история по `planId/exId`, а не индексам;
- clean-slate persistent schema V2 вместо вечных legacy-полей;
- один equipment catalog с допустимыми roles load/support;
- два действия на старте: «только сегодня» / «изменить рабочий вес»;
- ручная смена рабочего назначения сбрасывает progression counter;
- контролируемая JSON Schema как portable source + отдельная domain validation;
- AI V2 разбивается на несколько этапов.

### Принято после обсуждения открытых вопросов

1. **AI-edit:** target state + refs, не operation list.
2. **Progression:** настройки группируются в `progression` сразу; фактическое состояние отдельно в `progressState`.

### Что изменено относительно предложения Клода

1. **Wipe не в PR 1.** Чистый старт остаётся решением, но destructive reset только в финальном production cutover, когда готов весь V2.
2. **Schema guard двусторонний.** Клиент защищается от более новой схемы, сервер после cutover отвергает старые writes, иначе старый APK может испортить V2.
3. **Нет persistent `weight/level + equipment:null`.** Это снова делает нагрузку неоднозначной.
4. **`unit` делаем настоящей доменной границей.** Новые runtime/progression имена нейтральны к kg.
5. **`level` не универсальная «сложность без снаряда».** Угол тела/высота/вариант движения остаются movement progression/swap.
6. **Equipment catalog не задаёт progression step.** Снаряд сам по себе недостаточен, чтобы выбрать безопасный шаг.
7. **История хранит не только cfgKey, но и config snapshot.**
8. **Structured adapters покрывают все providers, которые остаются selectable в FitTimer.**

### Что просим Клода проверить ещё раз

Нужен именно спор с этими решениями:
- есть ли реальный кейс, где persistent weight/level без equipment всё-таки нужен;
- есть ли причина делать level без load-equipment вместо movement progression;
- target state + refs: какие реальные запросы он представляет хуже operation DSL;
- достаточно ли разделения `progression/progressState`;
- нужен ли `unit` сейчас; если да — достаточно ли убрать kg-specific доменные имена;
- корректен ли поздний destructive cutover и server-side schema write guard;
- какие поля должны входить в cfgKey для level кроме ordered scale;
- не слишком ли большой PR 1 и что можно вынести без временной второй модели.

## 14.4. Второе ревью Клода по решениям 14.3 — 2026-10-08

Это вход второго ревью. Финальные ответы на него зафиксированы в 14.5 и в основных разделах.

### Новое решение владельца (приоритет над 1.9 и PR 8 в части сроков сброса)

Сохранять работоспособность продакшна на время переделки НЕ нужно:
- данные можно стирать когда угодно и сколько угодно раз;
- приложение лежит в проде, но им никто не пользуется, пока идёт работа;
- делаем быстро, промежуточные состояния `main` могут быть нерабочими для реальных тренировок.

Следствия:
- поздний destructive cutover в PR 8 больше не нужен как защита пользователей. Сброс можно делать в том PR, где новый формат начинает читаться runtime (и повторять при необходимости);
- флаг/отдельное хранилище для параллельной работы старой и новой модели НЕ нужны;
- запрет на переходный слой «читать и старое, и новое» остаётся в силе и теперь выполним без компромиссов;
- PR-порядок можно выбирать по удобству разработки, а не по безопасности прода (см. п. 9 ниже).

Перед каждым реальным стиранием серверных данных разработчик всё равно коротко подтверждает у владельца — это необратимое действие.

### Ошибки и слабые места в решениях 14.3

**1. Поздний cutover противоречил запрету на вторую модель — снято решением выше.**
`main` сразу деплоится в прод. При сбросе только в PR 8 после PR 4 (runtime читает только V2) приложение либо ломалось бы на старых данных, либо требовало временного слоя совместимости. С новым решением владельца проблема исчезает: стираем, когда runtime переходит на V2.

**2. Защита от старого APK: механизма в установленных приложениях нет.**
- В коде нет «минимальной версии приложения» и экрана «обнови». Уже установленный APK его не получит. Если защита нужна к публичному релизу, клиентскую часть (проверка версии + экран обновления) нужно выпустить отдельным релизом ЗАРАНЕЕ, иначе старые APK будут видеть только ошибки синка.
- Сервер в 1.9 блокирует только запись sync. Но старый клиент продолжит читать каталог, ссылки `/api/p`, тренерские данные и ходить в `/api/ai` — и импортировать V2-программы своим V1-кодом. Блокировка по версии клиента нужна на всех FitTimer API, а не по полю `schema` в sync.
- `sync-core` общий с UnMute (`packages/core/server/sync-core.js`). Минимальная схема/версия — настройка FitTimer (через `lib/fit-sync-schema.js`/registry), а не глобальное правило Core.
- Сейчас пользователей двое и оба обновят приложение сами, поэтому это не блокер V2, но обязательно до публичного релиза.

**3. История упрётся в лимит документа, и синк остановится.**
Вся история — внутри одного sync-документа `stats`, сервер отклоняет документ больше 3 МБ (`MAX_DOC` в `packages/core/server/sync-core.js`, ошибка `doc_too_large`). История режется на 2000 записей. Snapshot из 10 с полным `config` на каждое упражнение ≈ 200 байт × 10 упражнений × 2000 записей ≈ 4 МБ (для level ещё больше из-за шкалы). Уже текущий snapshot ≈ 2 МБ на пределе.
Предложение: `config` хранить только при смене конфигурации (или один словарь конфигураций, на который ссылаются записи), шкалу уровней в историю не класть — только identity текущего уровня. Долгосрочно — вынести историю из одного документа.

**4. Шкала уровней в `cfgKey` — слишком жёстко (ответ на вопрос «какие поля в cfgKey для level»).**
По 2.8 любое изменение шкалы или её порядка = новая конфигурация. Тогда:
- купил новую резинку и добавил в конец шкалы → прогресс сброшен;
- исправил опечатку в названии уровня → прогресс сброшен.
В текущем коде это уже решено лучше (`carryReorderedLevelProgress` в `60-builder.js`): уровень переносится по identity (key/label), а не по индексу.
Предложение:
- `cfgKey` для level = `type + equipment + name + count`, без шкалы;
- при правке шкалы: текущий уровень (по identity) остался в шкале → та же конфигурация, индекс пересчитывается; исчез → новая конфигурация;
- `progressState.current.level` и история хранят identity уровня, а не номер.
Аналогично `unit`: смена единиц того же снаряда — пересчёт, а не новая конфигурация (пока UI только kg — неактуально, но правило записать).

**5. «Угол тела/высота опоры — это swap»: swap сейчас не лестница.**
Сейчас swap — одна подсказка «следующий вариант» при достижении потолка (`swapName/swapDesc`). Цепочки «с колен → обычные → ноги на стуле» нет, а для домашних тренировок без снарядов это главный способ прогресса. Решение не использовать `level` без снаряда — нормальное, но его надо записать в 14.1 как ограничение V1, а не как уже покрытый случай. Будущее расширение — лестница вариантов движения, не `load.level`.

**6. `progression`: два способа выключить и пропало наследование.**
- Выключение двумя способами: `mode: 'none'` и `every: 0`. Нужен один.
- Сейчас `progEvery = null` значит «как у программы» (`p.progression`). В примере 2.8 `every: 4` — наследование потеряно. Нужно явно: `every: null` = наследовать от программы, число = своё.
- Для `mode: 'level'` с фазой повторов явно описать, что используется `progression.reps` (как в текущем `computeLevelStep`).

**7. Structured adapters для «всех выбираемых провайдеров».**
Через OpenRouter выбирается почти любая модель, поддержка JSON Schema зависит от модели/endpoint. Значит проверка должна быть в момент сохранения настроек в админке: кнопка проверки маршрута реально делает structured-запрос и не даёт сохранить неподдерживающий маршрут. Иначе ошибку первым увидит пользователь.

**8. AI-edit: `set` с двумя смыслами.**
В примере 8.4 у плана `set: {days: [...]}` — частичная правка, у упражнения `set` — «новый prescription/config», т.е. полный объект. Одно слово — две семантики, источник ошибок валидатора. Выбрать одно: либо везде полный объект, либо везде частичный patch (тогда отдельно описать, как удалить поле).
Следствие правила «каждый ID ровно один раз»: «добавь это же упражнение ещё во вторник» выражается только `new`-копией (новый ID, без прогресса). Это нормально, но написать явно и проверить на regression-кейсе.

**9. Порядок PR и обоснование в 13.**
- 0.1 п.6 говорит «сначала хранение и экраны, ИИ — после», а раздел 13 ставит AI V2 вторым-третьим PR. Нужно привести к одному.
- Обоснование в 13 («старый AI не должен сохранять `equipment:null` до включения потока») держалось на позднем cutover. С решением владельца выше порядок можно выбирать по удобству. Рекомендация Клода: схема → runtime → UI (сразу можно руками собрать и прогнать две программы) → AI V2. Тогда runtime и UI проверяются на реальных тренировках раньше, чем пишется самая объёмная часть.
- PR 1 слишком большой. `plan.id` + история по `planId/exId` исправляют баг ТЕКУЩЕГО приложения и не зависят от V2; вместе с удалением тоннажа их можно сделать отдельным маленьким PR первым.

**10. Старые разделы противоречат 2.8.**
2.3, 2.4, 2.5, 4, 5.1, 5.4, 5.5, а также текстовые примеры в 8 используют старые имена (`ex.loadEquipment`, `ex.loadCount`, `ex.weight`, `wStep`, `weightMax`, `ps.cur.kg`, `progressState.count`); ключ в 5.4 без `unit`/правила для level. Фраза «14.3 имеет приоритет» не защищает исполнителя, который откроет §5. Нужно переписать эти разделы под 2.8 (или удалить дубли и оставить ссылку на 2.8).

**11. Нет «против» у решений 14.3.**
Почти везде указано только «почему да». Примеры минусов, которые стоит дописать:
- поздний cutover — п.1 (теперь снято);
- переименование всех внутренних имён под нейтральный `unit` — десятки правок ради фунтов, которых в V1 нет (Клод при этом не против: код всё равно переписывается);
- полный config в каждой записи истории — п.3;
- структурные адаптеры для всех провайдеров — больше кода и тестов в Core ради маршрутов, которые могут не использоваться.

### Что Клод согласен оставить как есть

- weight/level без снаряда в сохранённых данных не нужен — реального случая не найдено;
- разделение `load / progression / progressState` достаточно (с правкой п.6);
- target state + refs вместо операций (с правкой п.8);
- `unit` в схеме сейчас — да.

## 14.5. Ответ после второго ревью Клода + решение по movement chain — 2026-10-08

Историческая запись. Третье ревью Клода — 14.6, актуальный ответ на него — 14.7.

Второе ревью принято почти целиком. Ниже — что становится текущим решением документа.

### Принимаем замечания Клода

1. **Историю нельзя раздувать полным config на каждую тренировку.**  
   Используем `stats.loadConfigs` + короткий `configId` в history. Это учитывает текущий server limit 3 МБ.

2. **Полная level-шкала не входит в physical cfgKey.**  
   Reorder/add/rename не должны автоматически создавать новую конфигурацию. Текущий level переносится по identity; если текущая identity исчезла — level state сбрасывается.

3. **Один способ выключить прогрессию.**  
   `progression.mode='none'` — OFF.  
   `progression.every=null` — наследовать `program.progression.every`.  
   `every:0` как второй OFF не используем.

4. **Для `mode='level'` на reps явно используется `progression.reps.step/max`.**

5. **Structured route проверяем при сохранении AI-настроек.**  
   Если выбранная OpenRouter/model route не проходит реальный schema-constrained тест, её нельзя сохранить как рабочий V2 route.

6. **Убираем двусмысленный `set` в AI-edit.**  
   - `patch` = частичная правка plan/program metadata;  
   - `replace` = полный новый prescription существующего упражнения;  
   - `new` = полный новый prescription нового экземпляра.

7. **PR 1 уменьшаем.**  
   Stable plan/exercise identity, history-by-ID и tonnage cleanup идут отдельным первым PR до breaking V2.

8. **После решения владельца не поддерживаем рабочий прод между PR.**  
   Когда runtime переходит на V2, данные можно очищать после короткого подтверждения владельца. Временный V1↔V2 compatibility layer не строим.

9. **Защита старых APK — pre-public hardening, не блокер V2 сейчас.**  
   Перед публичным релизом понадобится FitTimer-specific minimum app/API compatibility, причём не только sync write. Это не должно становиться глобальным правилом shared Core для UnMute.

10. **Старые разделы документа переписываем под V2**, а не полагаемся только на «новый раздел имеет приоритет».

### Дополнительное решение владельца: movement chain включаем сразу

Одиночный legacy swap заменяется ограниченной цепочкой.

**Лимит: максимум 4 movement stages всего:**
- current;
- максимум 3 next.

Почему:
- покрывает типичные домашние progression ladders;
- не превращает упражнение в мини-программу;
- ограничивает AI output, UI и число потенциальных картинок;
- после финального stage цепочку всегда можно продолжить новой AI/manual правкой.

### Семантика chain

Каждый future stage — полный `ExercisePrescription` без:
- persistent exercise ID;
- progressState/history;
- media payload;
- nested movement chain.

При переходе:
- `exercise.id` сохраняется;
- меняется app-owned `movementStageId`;
- текущий prescription заменяется;
- `progressState` сбрасывается;
- old/new movement stages не сравниваются как обычный рост нагрузки.

Обычная reps/weight/time/level progression полностью отрабатывает ВНУТРИ stage. Chain используется только после terminal ceiling.

### Картинки movement stages

Решение:
- current stage использует обычную картинку упражнения;
- future stages НЕ хранят base64;
- для ближайшего next stage разрешён дешёвый cache lookup;
- генерация запускается только по явному preview или при подтверждении перехода;
- отсутствие картинки не блокирует promotion;
- при отсутствии сети показывается placeholder, картинка догружается позже;
- все 3 будущих изображения заранее не генерируем;
- старую картинку движения на новый stage не переносим.

После появления canonical exercise library media cache должен использовать canonical movement identity + визуально значимое оборудование. До этого допускается deterministic visualKey из нормализованного stage prescription.

### Дополнительно закрыто после проверки кода

- `stats.loadConfigs` получает простой GC: после trimming history удаляем configs без ссылок.
- Reorder level-шкалы сохраняет current level по identity, но сбрасывает `progressState.count`, потому что порядок усложнения изменился.

### Что ещё просим Клода перепроверить

1. Лимит 4 stages: есть ли массовые реальные кейсы, где это мало?
2. Нужно ли future stage хранить полный prescription или можно безопасно сократить его ещё сильнее?
3. Правильно ли сохранять один `exercise.id` на всю movement chain, различая stages через `movementStageId`?
4. Достаточен ли `exId + movementStageId + configId` для истории и сравнений?
5. Не нужен ли cache lookup для next image раньше, чем пользователь откроет preview/дойдёт до потолка?
6. Новый PR order после разрешения ломать production: есть ли зависимость, из-за которой Core Structured Output всё-таки должен идти раньше UI/runtime?
7. Есть ли ещё массовый сценарий movement progression, который наша chain-модель не представляет без костылей?

## 14.6. Третье ревью Клода: movement chain и 14.5 — 2026-10-08

Только проблемы, из-за которых стоит поменять решения до кода. Для каждой — влияние на интерфейс.

### 1. Пройденные этапы цепочки теряются

По 5.6 при переходе prescription заменяется целиком, а следующий элемент удаляется из очереди. Данных пройденного этапа больше нигде нет.

Последствия:
- история старых тренировок ссылается на `movementStageId`, у которого не осталось названия; экраны покажут текущее имя упражнения («Обычные отжимания») для записей, где человек делал «с колен»;
- вернуться на предыдущий этап нельзя, хотя это частый реальный случай: травма, перерыв, переход оказался слишком тяжёлым.

Предложение:
- хранить пройденные этапы компактно: `movementProgression.done: [{stageId, name}]` (или такой же словарь имён этапов рядом с историей);
- действие «вернуться на прошлый вариант»: прошлый этап снова становится текущим, текущий возвращается в начало очереди `next`, `progressState` сбрасывается. Для возврата нужен полный prescription прошлого этапа — либо хранить его в `done`, либо при возврате восстанавливать из текущего с прошлым названием и просить пользователя проверить нагрузку. Рекомендация: хранить полный prescription последнего пройденного этапа, для остальных — только имя.

Интерфейс:
- в истории и «было → сегодня» у записей прошлого этапа показывается его название, а не текущее;
- в блоке «Следующие варианты» наверху строка «Сейчас: …» и ссылка «Вернуться к прошлому варианту», если он есть;
- на финише тренировки рядом с предложением усложнить, если упражнение отмечено «тяжело», можно предложить «вернуться к прошлому варианту».

### 2. Переход может никогда не предложиться

По 5.6 переход предлагается только после terminal ceiling. Но если у этапа нет потолка (`max` не задан) или прогрессия выключена (`mode:'none'`), потолка нет никогда — так работает и текущий `progAtCeiling()` (без потолка → false). Цепочка тогда мёртвая.

Предложение:
- domain validator: если у упражнения есть `movementProgression.next`, у текущего этапа обязательны включённая прогрессия и потолок по каждой растущей оси; AI-ответ без этого отклоняется или нормализуется;
- ручной переход «перейти на следующий вариант сейчас» доступен всегда.

Интерфейс:
- в редакторе при добавлении первого следующего варианта, если потолок не задан, показать поле потолка сразу (не ошибкой после сохранения);
- в блоке цепочки кнопка «Перейти сейчас» у ближайшего варианта;
- на экране старта, когда потолок достигнут, — та же карточка «Можно переходить: …», что сейчас показывает swap-подсказку.

### 3. AI-правка может сменить движение, не меняя его identity

В 8.4 `replace` — полный новый prescription существующего упражнения с тем же `exercise.id`. Не сказано, меняется ли `movementStageId` и сбрасывается ли `progressState`. Если AI заменит «Отжимания» на «Приседания» через `replace`, история продолжит считать это тем же движением и покажет ложное «было → сегодня».

Дополнительно противоречие с 5.5: там смена названия — «только текст», прогресс не сбрасывается.

Предложение (явное правило):
- ручной редактор: смена названия = текст (опечатка, уточнение), identity не меняется;
- AI `replace` / `exercise.replace` / `exercise.modify`: если меняется движение, приложение выдаёт новый `movementStageId` и сбрасывает `progressState`. Определять смену движения не по названию, а явным полем AI-ответа (например `movementChanged: true`); `exercise.replace` (замена с тренировки) — всегда новое движение;
- описать, может ли AI-правка менять саму цепочку: рекомендация — `replace` заменяет и `movementProgression.next` целиком (AI не адресует отдельные будущие этапы по ID; app-owned `stageId` выдаются заново), `done` и `currentStageId` AI не трогает.

Интерфейс:
- в предпросмотре AI-правки перед применением помечать упражнения, где сменилось движение: «новое упражнение — прогресс начнётся заново»;
- для упражнений, где поменялись только цифры/текст, прогресс показывается как сохранённый.

### 4. Словарь `stats.loadConfigs` + GC можно не делать

После второго ревью шкала уровней из ключа убрана, и ключ стал коротким: `weight|dumbbell||2` (десяток-два символов). Его можно хранить в истории прямо строкой `cfgKey`:
- нет словаря и его очистки (GC);
- нет конфликтов при слиянии `stats` с двух устройств;
- выигрыш словаря по размеру — несколько байт на строку, это не влияет на лимит 3 МБ.

Если словарь всё же оставлять, `configId` обязан вычисляться из содержимого конфигурации (детерминированно), а не генерироваться случайно: иначе два устройства заведут разные ID для одной конфигурации, а merge `stats` их не склеит.

Интерфейс: не влияет.

### 5. Ответ на вопрос 6 из 14.5 (порядок PR)

Зависимости, из-за которой Core Structured Output должен идти раньше UI/runtime, нет. Две реальные программы и цепочки для проверки можно собрать в ручном редакторе. Текущий порядок можно оставить.

### По остальным вопросам 14.5 — без возражений

- лимит 4 этапа достаточен; после последнего этапа цепочку продолжает новая правка;
- полный prescription у будущих этапов — правильно (они меняют нагрузку, оборудование, политику);
- один `exercise.id` на цепочку + `movementStageId` — правильно, при условии пп. 1 и 3;
- `exId + movementStageId + cfgKey` для истории достаточно, при условии п. 1 (имена прошлых этапов);
- cache lookup картинки следующего этапа раньше preview не нужен; ленивая загрузка — правильно.

## 14.7. Ответ на третье ревью Клода — 2026-10-08

Третье ревью принято по сути во всех четырёх найденных проблемах, но для первой проблемы выбрана более симметричная модель.

### 1. Пройденные этапы — проблему принимаем, реализацию меняем

Согласны: удалять stage после перехода нельзя — ломается история и невозможно нормально вернуться назад.

**Не используем `done + current + next`.**

Вместо этого canonical V2:
- `stages[1..4]` хранит ВСЮ ограниченную лестницу;
- `currentStageId` выбирает активный stage;
- обычный переход вперёд/назад ничего не удаляет;
- каждый stage хранит полный prescription;
- `progressState` относится только к текущему stage и сбрасывается при смене stage.

Почему лучше `done/next`:
- одна форма данных для прошлого/текущего/будущего;
- возврат не требует реконструкции prescription;
- reorder/edit UI работает с одним массивом;
- меньше специальных веток runtime/validator.

History дополнительно хранит `movementStageName`, поэтому даже если chain позже полностью заменили AI-правкой, старая запись всё равно показывает правильное историческое название.

### 2. Мёртвая chain без потолка — принимаем, но не запрещаем саму chain

Добавлены два режима перехода на уровне stage:

```text
ceiling — приложение само предлагает следующий stage при terminal ceiling
manual  — автоматического предложения нет
```

Для `ceiling` validator требует реальный terminal ceiling и включённую progression policy.

Для `manual` потолок не обязателен.

При наличии следующего stage действие **«Перейти сейчас» доступно всегда**. Поэтому chain не может стать недоступной только из-за отсутствия max.

### 3. AI replace и movement identity — полностью принимаем

AI-контракт получает обязательный `movementChanged: true|false`.

Правила:
- ручное переименование = metadata, stage identity не меняется;
- AI modify с `movementChanged:false` сохраняет текущий stage identity; carry/reset progress решают обычные domain rules;
- AI modify с `movementChanged:true` заменяет активную AI-owned movement chain новым набором 1..4 stage specs, приложение выдаёт новые stage IDs и сбрасывает progressState;
- `exercise.replace` всегда `movementChanged:true`;
- AI не выдаёт app-owned stage IDs.

UI перед применением movementChanged показывает:
> Новое упражнение — прогресс начнётся заново.

Старая история не ломается: в ней остаются старые `movementStageId + movementStageName`.

### 4. loadConfigs — принимаем и удаляем

Отдельного `stats.loadConfigs` и GC больше нет.

В history напрямую хранится deterministic reversible `cfgKey`, построенный canonical helper из:
- load.type;
- equipment;
- custom name;
- count.

Плюсы:
- нет merge-конфликтов IDs между устройствами;
- нет dictionary lifecycle/GC;
- меньше кода;
- выигрыш словаря по размеру не оправдывает сложность.

Worst-case history на 2000 тренировок всё равно обязана пройти отдельный size test против текущего лимита 3 МБ.

### 5. Порядок PR — принимаем

Core Structured Output не нужен раньше runtime/UI.

Оставляем:
1. stable IDs/history/tonnage;
2. V2 schema + runtime;
3. V2 UI;
4. Core Structured Output;
5. AI create;
6. AI edit;
7. остальные channels/images;
8. regression/pre-public hardening.

Это позволяет проверить реальную V2-модель руками до самой объёмной AI-части.

### Что просим Клода проверить в последний раз

Только новые решения, без повторного полного пересказа документа:

1. **Canonical exercise wrapper:** разумно ли, что даже упражнение БЕЗ chain хранится как один `stage`, чтобы не иметь две persistent-формы?
2. **AI movementChanged:** достаточно ли явного флага модели или нужен дополнительный deterministic guard приложения для подозрительных `movementChanged:false`?
3. **Chain replacement:** при `movementChanged:true` правильно ли полностью заменять старый активный chain новым stage set, оставляя старое только в history?
4. **Manual/ceiling:** есть ли реальный третий массовый тип перехода, который нельзя выразить этими двумя режимами?
5. **Media:** достаточно ли `mediaRef/visualKey` на stage, если переход не блокируется отсутствием изображения?
6. **History:** достаточно ли `exId + movementStageId + cfgKey + movementStageName` без отдельного stage/config registry?
7. **Размер PR 2:** после появления canonical stage-wrapper не стал ли breaking runtime PR слишком большим; если да — как разделить его без временной второй persistent-схемы?

Если здесь нет критического возражения, архитектуру считаем закрытой и начинаем реализацию.

## 14.8. Четвёртое ревью Клода: ответ на 14.7 — 2026-10-08

Две критичные проблемы, остальное — мелкие уточнения. По вопросам 14.7, не упомянутым ниже, возражений нет (один stage у обычного упражнения, `manual`/`ceiling`, `mediaRef/visualKey`).

### Критично 1. `movementChanged:false` не позволяет сопоставить этапы

В 8.4 `replace` с `movementChanged:false` возвращает 1..4 stage specs БЕЗ ID, а приложение должно «сохранить текущий `movementStageId`». Если цепочка из 3 этапов, активен 2-й, а AI вернул 3 этапа (один вставил/переставил/удалил), приложение не может однозначно понять:
- какой из возвращённых этапов — текущий;
- какие этапы старые (сохраняют `stageId`, историю, `mediaRef`), а какие новые.

Сопоставление по позиции или названию — ровно та ошибка, которую убрали для вариантов и упражнений.

Предложение: внутри `stages` тот же приём target state + refs, что для планов и упражнений:

```json
"replace": {
  "movementChanged": false,
  "stages": [
    {"ref": "mv_1"},
    {"ref": "mv_2", "replace": {"...": "полный prescription + advance"}},
    {"new": {"...": "полный stage spec"}}
  ],
  "removedStageIds": []
}
```

Правила:
- при `movementChanged:false` каждый существующий `stageId` либо упомянут ровно один раз, либо в `removedStageIds`; иначе ответ отклоняется;
- текущий `stageId` нельзя удалить при `movementChanged:false` (иначе это смена движения);
- при `movementChanged:true` refs не нужны: весь набор `new`, как уже описано.

Интерфейс: в предпросмотре AI-правки для цепочки показывать «добавлен этап / изменён этап / удалён этап»; текущий этап отмечен.

### Критично 2. История, скорее всего, не пройдёт лимит 3 МБ

Словарь `loadConfigs` убрали, но в каждую строку истории добавили `movementStageName`. Оценка строки по схеме из 10:

```json
{"exId":"ex_abc123","movementStageId":"mv_abc123","cfgKey":"weight|dumbbell||2",
 "movementStageName":"Румынская тяга с гантелями","reps":"8-10","sec":0,
 "weight":10,"unit":"kg","levelKey":"","levelLabel":""}
```

≈ 200 байт (кириллица — 2 байта на символ в UTF-8). × ~10 упражнений × 2000 записей ≈ 4 МБ, плюс остальные поля записи (`exercises`, `partialExercises`, заметка). Лимит `MAX_DOC` = 3 МБ, документ `stats` один.

Предложение:
- в строке истории короткие ключи и без пустых/стандартных полей (например `{"e":"ex_abc123","s":"mv_abc123","c":"w|db||2","r":"8-10","w":10}`, `unit` только если не kg, `sec/level*` только если есть) ≈ 60–70 байт;
- название этапа — в отдельной карте `stats.stageNames[stageId] = name`. Конфликтов между устройствами нет (`stageId` уникален и выдаётся приложением), запись только добавляется; очищать можно вместе с обрезкой истории, но не обязательно — карта маленькая;
- `cfgKey` с короткими кодами снарядов (`db`, `bb`, `kb`…) из того же справочника оборудования;
- размер проверить расчётом на макете worst-case ДО реализации PR 1/2, а не только тестом после.

Интерфейс: не влияет — экраны получают историю через один helper.

### Мелкое 3. `warmup` — свойство слота, не этапа

Сейчас `warmup` лежит в `stage.prescription`. Тогда смена этапа может сама перенести упражнение в разминку или из неё — это смена структуры тренировки, а не движения. Предложение: `warmup` на уровне `exercise` (слота). Остальное (`sets`, `rest`, `perSide`, нагрузка) логично остаётся в этапе.

Интерфейс: переключатель «разминка» в редакторе упражнения не зависит от выбранного этапа.

### Мелкое 4. Возврат на прошлый этап начинается с базы

`progressState` один на слот и сбрасывается при смене этапа. Значит, вернувшись на «с колен», человек начнёт с базового назначения этапа, а не с того, где остановился. Для возврата после травмы/перерыва это скорее правильно. Не менять, но записать как осознанное решение (альтернатива — хранить `progressState` у каждого этапа; не рекомендуется, больше состояния ради редкого случая).

Интерфейс: при возврате показать «Начнёшь с: 2 × 10 повт» (база этапа), чтобы не было сюрприза.

### Мелкое 5. Отдельный guard для `movementChanged:false` не нужен

Смена снаряда/количества уже ловится через `cfgKey`, смена формата (повторы/время) — через обычные domain rules. Достаточно в предпросмотре правки показать «Название изменилось, прогресс сохранится», если AI поменял название при `movementChanged:false`, — пользователь увидит подозрительный случай сам.

### Мелкое 6. Как разделить PR 2 без второй persistent-схемы

Поскольку прод можно ломать:
- PR 2a — схема V2 целиком (слот + stages + prescription + progressState), normalize/sanitize, `activePrescription()`; runtime работает только с одним этапом, UI цепочки нет;
- PR 2b — runtime прогрессии + история (по пп. 1–2 выше);
- переходы/возврат по этапам и их UI — в PR 3 вместе с остальным UI.

Вторая форма данных не появляется: цепочка из одного этапа — та же схема.

## 14.9. Ответ на четвёртое ревью Клода — 2026-10-08

Все два критичных замечания и четыре уточнения принимаем.

### Принято

1. **Stage refs внутри AI-edit.**  
   При `movementChanged:false` stage list использует target state + `ref/replace/new/removedStageIds`. Current stage удалить нельзя. Это сохраняет stage identity/history/media при add/remove/reorder.

2. **History storage надо проектировать по byte budget заранее.**  
   Полное имя stage больше не повторяется в каждой строке. Persistent history использует compact DTO с omission defaults и коротким reversible cfgKey.

3. **`stats.stageNames`.**  
   Имя stage хранится один раз по глобально уникальному stageId. GC удаляет запись только если stageId отсутствует и в retained history, и в актуальных программах.

4. **`warmup` перенесён на exercise slot.**  
   Смена movement stage не меняет структуру тренировки.

5. **Rollback начинает stage с базы.**  
   Отдельный progressState на каждый stage не храним. UI до возврата показывает базовый старт.

6. **Эвристический movement guard не добавляем.**  
   При `movementChanged:false` identity определяется refs/contract. Подозрительное переименование явно видно в preview.

## 14.10. Пятое ревью Клода: ответ на 14.9 — 2026-10-08

Критических дыр в stage refs, compact history, warmup на слоте и делении PR 2a/2b не найдено. Одна недостающая норма:

### stageId остаётся уникальным только если его перевыдавать при копировании

2.8 требует «stageId глобально уникален в рамках пользовательских данных», а `stats.stageNames` держится на этом. Но правила перевыдачи stageId при копировании нигде нет. Копии появляются:
- «дублировать упражнение» в редакторе (`cloneExerciseAsNew` сейчас меняет только `exercise.id`);
- дублирование программы;
- установка из каталога / по ссылке / из файла (одну программу можно поставить дважды);
- программа от тренера.

Если два слота делят один stageId, переименование этапа в одном перезапишет `stageNames` и в истории второго появится чужое имя; GC тоже будет считать этап «живым» по чужой программе.

Предложение: та же точка, что `uniqueExerciseIds()` в `sanitizeProgram`, — любая копия/установка/импорт выдаёт новые `stageId` (и `currentStageId` переназначается на соответствующий новый ID). Тест: «поставить одну программу дважды и переименовать этап в одной — история второй не меняется».

Интерфейс: не влияет.

С этой нормой возражений по архитектуре нет — можно начинать PR 1.

- этот список уходит в AI одной строкой `Available equipment: ...`;
- то же смешение используется и в форме подбора отдельного упражнения.

Что решили:

- UI AI-генерации разделить на «Снаряды» и «Доп. оборудование»;

- выбранное оборудование означает «точно есть», а не «обязательно использовать»;
- AI может использовать любое подмножество доступного оборудования, включая вообще ни одного предмета в конкретном упражнении;
- AI не должен по умолчанию придумывать специализированное невыбранное оборудование;
- отдельные состояния «Без снарядов» и «Без доп. оборудования»;
- ничего не выбрано = оборудование не уточнено, а не запрет всего оборудования.

Почему:
- гантель и коврик имеют разную роль в модели упражнения;
- смешанный список не позволяет однозначно заполнить новую модель нагрузки;
- наличие снаряда у пользователя должно расширять возможности программы, а не заставлять каждое упражнение его использовать.


### 2026-10-08 — принято направление AI Contract V2

Статус: ✅ архитектурное решение добавлено в план, код не менялся.

Проверили:
- создание программы использует `qEquip`;
- создание упражнения через AI использует отдельный `exaEquip`, но тот же `OPT_EQUIP`;
- админская генерация каталога также передаёт одну строку equipment;
- image prompt пока угадывает оборудование regex'ами из имени/описания;
- AppBase Core сейчас передаёт провайдерам простой text prompt без response schema.

Решение:
- перейти к единому versioned JSON AI contract;
- встроенный AI — JSON Schema Structured Output там, где provider/model поддерживает;
- manual copy/paste — тот же JSON contract, но без API enforcement;
- CREATE возвращает полный объект;
- EDIT возвращает операции по стабильным ID, а не всю программу;
- отдельные schemas для программы и упражнения;
- schema не заменяет domain validation;
- список оборудования и UI должны идти из одного канонического каталога.

Причина:
- это уменьшает число независимых контрактов и regex-парсеров;
- structured schema делает required/enum/shape машинно проверяемыми;
- operation-based edit сильнее всего уменьшает размер ответа и риск потери неизменённых данных.

`apply-community.sql` — воспроизводимое idempotent наполнение только этих `feture_*` таблиц. Первоначально проверено через rollback, затем применено через Supabase operator SQL. Не запускать из браузера или от service_role; код не отправляет email/push и не работает с медиахранилищем.

## Почему публичные материалы от seed-авторов видны

Миграция `20261013080000_feture_prelaunch_synthetic_author.sql` добавляет **только для synthetic authors** ограниченное расширение `feture_peer_eligible`. Проверяются: `environment.stage = prelaunch`, точный FitT project_ref, точный набор и запись происхождения в `feture_seed.records`, отсутствие dating opt-in. Seed IDs имеют формат `seed:...` и не могут стать 32-hex идентичностью Core.

**Никакого обхода 18+/согласия у реального зрителя.** Endpoint по-прежнему отклоняет неавторизованного/неподтверждённого зрителя, учитывает блокировки, статусы публикации и аудиторию. При переводе базы в `live` seed-авторы перестают считаться допущенными.

Проверено read-only SQL: настоящий seed=true, поддельный seed=false, случайный 32-hex без adult proof=false; `anon`/`authenticated` не имеют EXECUTE на synthetic helper, `service_role` имеет. **Это не заменяет независимый security review и реальную проверку браузера с несколькими Core аккаунтами.**

## Очистка до запуска

1. На правильном Supabase **project_id**, убедиться, что stage ещё `prelaunch`.
2. Проверить именно этот набор и выполнить `cleanup-community.sql` как `postgres`. Он удаляет только детерминированные ID 76 постов/10 групп/12 событий и их зависимости (включая комментарии и реакции). Не очищать общий AppBase/Core. Сначала безопасно проверить транзакцию, заменив последний `commit` на `rollback`.
3. Затем операторский `node apps/feture/tools/seed-sql.mjs --project-ref anrhayozrhrmiwexmbhw --stage prelaunch --scope profiles --operation cleanup`; выполнить preview и только после сверки counts/blockers — apply c новым review token. Если профили позже обзаведутся зависимостями (reactions, follows, grants), сначала разбирать их отдельно — не делать cascade delete аккаунтов.
4. Проверить отсутствие seed профилей, постов, групп и событий; **только затем** менять stage на live и проводить launch gate. Не удалять reference catalog.

**Ограничения:** нет фото/аватаров (права на медиа не подтверждены), RSVP и реального межаккаунтного теста, нет настоящих провайдерных 18+ подтверждений. Создать живые события с подлинными ссылками/контактами можно только отдельно. Когда пройдёт несколько недель, даты событий потребуется обновить отдельной редакцией набора. Нельзя считать эти записи реальными участниками сообщества.

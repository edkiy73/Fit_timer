# FetUre — очередь ИИ-агентов (телефон / GitHub Actions)

## Что настроено
- Единственный источник текущего состояния MVP: [STATUS](mvp-plan/STATUS.md), карточки [mvp-plan](mvp-plan/README.md). **Не копировать** большой исторический план в Issues.
- Задачи: GitHub Issues с заголовком строго `[FetUre Queue 01] ...`, `[FetUre Queue 02] ...` и т.д., **созданные владельцем репозитория**. В тексте: ID карточки MVP, 2–5 связанных файлов, границы, критерии результата, независимая проверка.
- `.github/workflows/feture-agent.yml` дважды в сутки или вручную выбирает **одну** старую открытую задачу. Если есть незакрытый `feture/agent-*` PR, новые задачи не запускаются. Нет задач — нет вызовов модели.
- GitHub-hosted Codex меняет только `apps/feture/**` (не Core, другие приложения, миграции или workflow), максимум 12 файлов / 120 KB patch. Затем отдельный GitHub job выполняет `npm --prefix apps/feture run check` и создаёт PR. **Никаких автоматических merge или деплоев.**
- `.github/workflows/feture-agent-review.yml` — отдельный read-only код/UX/privacy review и комментарий к PR. Он не утверждает merge, визуальные тесты и ручную приёмку.
- Публикацию, проверку реальных аккаунтов, SQL и любые внешние операции агенту запрещено делать самостоятельно.

## Активация через телефон (Chrome → github.com)
Пока **выключено**: скрипты сами не расходуют токены API.

1. В [OpenAI API](https://platform.openai.com/api-keys) создайте отдельный ключ для автоматики FetUre и **предварительно установите бюджет/уведомления по расходам** в проекте API. ChatGPT Plus и API оплачиваются отдельно.
2. Репозиторий GitHub → **Settings → Secrets and variables → Actions → Secrets → New repository secret**: имя `OPENAI_API_KEY`, значение ключа. Не писать ключ в Issues, PR или чат.
3. Там же **Variables → New repository variable**: `FETURE_AGENT_ENABLED` = `true`. Для второй модели ревью дополнительно `FETURE_AGENT_REVIEW_ENABLED` = `true`.
4. При желании назначить модель переменной `FETURE_AGENT_MODEL`; оставленная пустой использует поддерживаемый Codex default. Ревью — `FETURE_REVIEW_MODEL`. Не писать несуществующий ID модели. Усилие `high` закреплено в Actions.
5. **Settings → Actions → General → Workflow permissions**: разрешить запись GitHub Actions и создание pull requests (иначе бот не сможет создать PR). Временное выключение: `FETURE_AGENT_ENABLED=false`, ревью аналогично. Запретить автоматический merge по умолчанию.
6. После слияния PR с этими файлами: **Actions → FetUre — guarded coding queue → Run workflow** без номера (первая готовая задача) или с номером Issue. Проверить созданный PR, тесты, отдельную ревизию и только после этого слить. Всё работает без ПК.

## Бюджет и безопасность
- Расписание: **не более двух автоматических запусков в сутки** (00:17 и 12:17 UTC); ручной запуск — дополнительный. Это лимит частоты, **не денежный потолок**. Одна задача / один coding вызов и, если включено, один отдельный review. Оба со сроком job 15/10 минут; токены API не имеют отдельного жёсткого лимита в этом workflow.
- GitHub secret передаётся **только** официальному `openai/codex-action@v1`, без сохранённых checkout credentials. Генерация кода и создание PR выполняются в разных jobs. Не давать агенту продакшн-ключи Supabase/Vercel, не открывать секреты в CI.
- Пока открыт агентский PR, следующая задача не запускается: это сознательная защита от ошибок, конфликтов и расходов. Для действительно непрерывного режима без ручного merge позднее потребуется отдельная доверенная политика автоприёмки для **низкорисковых** задач, а не общий auto-merge.
- Созданные GitHub Actions PR могут **не запускать обычную PR CI повторно** из-за защиты от рекурсивных событий; workflow уже исполняет `FetUre check`, но независимая CI/AppBase и browser/device QA остаются обязательны перед merge.
- Если код затрагивает общий UI/Core, SQL, доступы, платежи или приватность: **не выдавать автономному исполнителю**. Создавать обычную PR-задачу для человека/проверенного агента и отдельно проводить аудит.

## Протокол рабочего цикла
`STATUS → одна карточка → 2–5 файлов → небольшая реализация → проверка → PR → независимое ревью → ручная приёмка и merge → закрытие Issue → следующая задача`.

При сбое задачи Issue остаётся открытым; повторный запуск безопасен до появления PR. Уровень безопасности определяется **подтверждённой проверкой**, не размером модели. Это MVP-автоматизация: до включения API и фактической успешной пробной задачи её работу нельзя считать проверенной.

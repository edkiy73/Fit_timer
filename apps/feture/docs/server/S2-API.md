# S2. Контракты API

27.10.2026, сверено с кодом 04.11.2026. Часть серверной спецификации FetUre ([README](README.md)). Модель данных — [S1](S1-DOMAIN-MODEL.md), медиа — [S3](S3-MEDIA.md).

## 1. Транспорт

- **Один вход для команд:** `POST /api/fe` (новая модель; старый `/api/domain` работает, пока его разделы не перенесены, затем удаляется), JSON `{action, ...input}`. Один вход — единые проверки (вход, лимиты, журнал). Ответ: `{ok:true, ...result, requestId}` или `{ok:false, error, requestId, fields?}`.
- **Чтения тоже через `POST /api/fe`** (`action` = запрос). Кэш HTTP не нужен: всё персональное, `Cache-Control: no-store`. Публичные страницы без входа (правовые тексты, ссылки-приглашения) — отдельный `GET /api/public?…`.
- **Медиа** — только через медиа-домен (S3), никогда через `/api`.
- **Realtime** — сигнал «есть новое» по непредсказуемому каналу профиля (§8); данные клиент всегда забирает обычной командой.
- Размер тела: 16 КБ (тексты постов, статьи — до 40 000 символов: для `post.create/update` с `kind=article` лимит 96 КБ). Медиа в теле запрещены.
- Имена действий: `<область>.<глагол>` (`post.create`, `feed.list`, `pair.invite`). Список — §9 и каталог по разделам.

## 2. Схемы и типы

- Каждая команда описана **Zod-схемой** входа в общем модуле `apps/feture/contracts/<область>.mjs` (ESM). Его импортируют и клиент (React), и сервер; новый серверный код тоже ESM (`server/*.mjs`), Core (CommonJS) подключается из него обычным импортом.
- Сервер отклоняет неизвестные поля (`strict()`), нормализует строки (NFC, обрезка, запрет управляющих и bidi-символов, лимиты длины) — требования `docs/input-safety-backend-checklist.md`.
- Вход **никогда** не содержит владельца, роль, возраст, email или account id. Владелец берётся из сессии и заголовка действующего профиля (§4).
- Типы ответа — DTO, а не строки таблиц: только поля, разрешённые зрителю (S1, «Видимость»).

## 3. Вход и сессия

- Аутентификация — Core (код на почту), заголовки `X-Fit-Email / X-Fit-Device / X-Fit-Token`, как сейчас; сервер каждый раз перечитывает сессию (отзыв работает сразу).
- После проверки Core сервер находит **`account_id`** FetUre по таблице соответствия (`account_link`: HMAC(core_account_key) → `account_id`). В доменных таблицах core-ключ и email не хранятся (D2).
- Доработки Core (этап 0): отзыв сессии при выходе на сервере; тип клиента (`web | ios | android`) в записи устройства; короткоживущий JWT для Realtime больше не нужен (решение §8 от 27.10.2026 — непредсказуемое имя канала вместо приватного канала); для веба — `HttpOnly` cookie вместо заголовков (позже, отдельный пункт).

## 4. Действующий профиль («Я / Мы»)

- Заголовок **`X-Fe-Profile: <profile_id>`** обязателен для всех команд, кроме `account.*`, `session.*`, `profile.mine` (список своих профилей). Без него — `400 profile_required`. Подставлять «Я» по умолчанию запрещено (правило §5.1 руководства V21).
- Сервер проверяет: профиль существует, аккаунт — его активный участник, профиль не заблокирован; для пары — пара в состоянии `active` (не остановлена). Иначе `403 profile_forbidden`.
- Каждая запись хранит `owner_profile_id` (кто владеет) и `acted_by_account_id` (кто нажал).
- Действия, которые требуют согласия партнёра (S1, «Согласия»), возвращают `{ok:true, pending:{approvalId}}` вместо результата; изменение применится после одобрения.

## 5. Ошибки

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `invalid_input` (+ `fields`) | Не прошла схема |
| 400 | `profile_required` | Нет `X-Fe-Profile` |
| 401 | `auth_required` | Нет или недействительна сессия |
| 403 | `profile_forbidden`, `forbidden`, `age_required`, `documents_required`, `blocked` | Нет прав |
| 404 | `not_found` | Нет объекта **или** нет права знать о нём (не различаем) |
| 409 | `conflict` (+ `current`) | Ревизия устарела (§6) или состояние уже другое |
| 409 | `approval_pending` | По объекту уже ждёт согласие партнёра |
| 413 | `too_large` | Тело больше лимита |
| 422 | `rule_violation` (+ `rule`) | Бизнес-правило (например, `chat_requires_match`, `photo_required_for_discover`) |
| 429 | `rate_limited` (+ `Retry-After`) | Лимит |
| 503 | `unavailable` | База или провайдер недоступны |

Тексты ошибок для пользователя — на клиенте по коду; сервер не отдаёт текстов исключений базы.

## 6. Идемпотентность и конкуренция

- Каждая команда записи принимает **`opId`** (uuid, генерирует клиент на одно намерение пользователя). Повтор с тем же `opId` возвращает сохранённый результат (таблица `op_ledger`, хранение 7 дней). Это уже есть в текущем коде — сохраняем.
- Изменяемые объекты имеют `rev` (целое). Команды изменения принимают `rev`; несовпадение → `409 conflict` с текущей версией. Счётчики и списки (реакции, подписки) — без `rev`, команды идемпотентны по смыслу (`set`, а не `toggle`): `reaction.set {postId, kind|null}`.

## 7. Списки и пагинация

- Курсорная: вход `{limit ≤ 50, cursor?}`, выход `{items, nextCursor|null}`. Курсор — непрозрачная строка (base64url JSON `{v, k:[sortKey,id]}` с HMAC), клиент его не разбирает.
- Сортировка — по `(created_at, id)` или ключу ранжирования; без OFFSET.
- Счётчики (`counts`) отдаются отдельно от списков, из одного источника (правило §5.3 руководства V21).

## 8. Реальное время, уведомления, push и письма

Правила уведомлений (что, кому, когда, какими словами) — решения владельца в [`docs/notifications.md`](../notifications.md).
Здесь — как это устроено в коде.

### 8.1 Сигналы «есть новое» (SSE)

Код: `server/realtime.mjs` (кому и что), `server/realtime-sse.mjs` (поток), `server/live.mjs` (какие сущности меняет
событие), клиент `src/fe/realtime.ts` и `src/fe/live.ts`. Тесты: `tests/fe-realtime-postgres.mjs`,
`tests/realtime-sse.test.mjs`, `tests/fe-live-postgres.mjs`, `src/fe/realtime.test.ts`.

- **Поток** — Server-Sent Events со своего сервера: `GET /api/fe-events?c=<канал>,<канал>` (не больше 4 каналов,
  лимиты соединений на адрес и всего). Сервер — один процесс Node (`server/host.mjs`), хаб в его памяти; включается
  `FETURE_REALTIME=sse` (в `deploy/docker-compose.yml`). Без него `realtime: null`, и приложение живёт на опросе.
- **Канал на профиль — непредсказуемое имя:** `fe:` + base64url(HMAC-SHA256(`FETURE_ID_PEPPER`, `'rt:' + profile_id +
  ':' + отсортированные account_id активных участников`)), первые 32 символа (192 бита). Имя и есть разрешение: сессия
  потоку не нужна, а в потоке нет ничего личного. Имена каналов своих профилей (Я и пара) клиент получает в
  `session.bootstrap` → `realtime: {url, channels: {profileId: канал}}` (ещё `key: 'sse'` и `transport: 'sse'` — для
  старых сборок приложения).
- Участники входят в имя, поэтому бывший партнёр со старым именем канала пары перестаёт что-либо слышать, как только
  состав пары изменился; оставшиеся получают новое имя с сигналом `changed:boot`.
- **Сообщение — только вид** `k` и, для двух видов, непрозрачная метка `t`. Ни id, ни имён, ни текста:
  | `k` | Когда | `t` |
  |---|---|---|
  | `chat` | новое сообщение или прочтение в беседе | — |
  | `typing` | «печатает…» (ничего не хранится) | метка беседы (`typingTag`), её знают только участники из `chat.messages` |
  | `notify` | новое или снятое уведомление | — |
  | `decide` | новое в «Нужно решить» | — |
  | `changed` | изменилось то, что показывает чужой экран, устройство или партнёр | сущность: `profile`, `couple`, `check`, `media`, `post`, `counts`, `chat`, `decide`, `boot` |
- **Что утекает держателю имени канала:** только вид и время, без привязки к человеку; данные отдаёт только `/api/fe`
  с проверкой сессии.
- **Когда отправляется.** Команда собирает сигналы (`ctx.signal`), `server/handler.mjs` отправляет их после commit;
  повтор по тому же `opId` и отказ ничего не отправляют. Тик очереди (раз в минуту и сразу после команды, которая
  что-то поставила в очередь, — `server/kick.mjs`) отправляет `notify`/`decide` и `changed` по темам outbox
  (`TOPIC_ENTITIES` в `server/live.mjs`). Ошибки отправки — только в журнал (`feture_fe_realtime <код>`): команда и тик
  из-за сигнала не падают.
- **Клиент.** `EventSource`; сервер шлёт `hb` каждые 25 с, тишина дольше 60 с — переоткрыть. Каждое переоткрытие и
  возврат в приложение — одно обновление всего (сигналы могли потеряться). Скрыто больше 5 минут — поток закрыт.
  Сигнал забывает только чтения своей сущности (`LIVE_READS` в `src/fe/live.ts`), экраны слушают `useLive(сущности)`
  или `useRealtime(виды)`; опрос раз в 30 с остаётся запасным.

### 8.2 Уведомления и «Нужно решить»

- **Каталог** — `contracts/notifications.mjs` (`CATALOG`, одна запись на тип и подтип): вид записи
  (`notice | task | result`), фильтр и иконка, шаблон карточки (`news | decision | result | safety | event | summary`),
  тексты RU/EN, push (категория, безопасный и обычный текст, `important`, `noisy`, `off`), письмо
  (`none | now | now-if-unread | digest`) с темой, переход (`destination()` / `routeOk()`), ключ склейки, текст «больше
  недоступно». Сервер, push, письма и экран берут всё отсюда; `tests/fe-notification-catalog.mjs` падает на типе без
  записи или без текста, перехода, категории.
- Путь: команда пишет тему в `feture.outbox` в своей транзакции → `server/notify.mjs` пишет уведомление или задачу →
  push (`server/push.mjs`), письмо (`server/email.mjs`), сигнал. Каждая тема либо обрабатывается, либо стоит в списке
  тихих (`tests/fe-notify-topics-postgres.mjs`).
- «Нужно решить» — вычисляемый запрос (`decide.list`, `decide.get` — один пункт по ID с ревизией); 8 видов
  (`DECIDE_KINDS`: `pinv, req, capp, eapp, link, linkChange, tag, joint`), `joint` — согласования пары.

### 8.3 Push

- `push.register {platform: 'ios' | 'android' | 'web', token, tz?}` / `push.unregister {token}`. Для `web` токен —
  подписка браузера (JSON `PushSubscription`): сервер проверяет, что это известный push-сервис по https с настоящими
  ключами, и хранит её в одном виде. Устройство принадлежит тому, кто последним вошёл на нём.
- Доставка — только тиком очереди: Android/iOS через Core (FCM/APNs), веб — свой Web Push с ключами VAPID
  (`server/webpush.mjs`, публичный ключ — `session.bootstrap` → `push.webKey`). Состояние по каждому устройству
  (`push_delivery`), повтор временных ошибок, мёртвый токен удаляется.
- Перед отправкой — проверка актуальности (`staleReason`), тихие часы в зоне устройства, склейка шумных типов, метка
  на объект (`pushTag`). Безопасный режим (по умолчанию) — без имён и текста.

### 8.4 Письма

- Код входа — Core (`packages/core/server/auth-core.js`, отправитель `MAIL_FROM`). Письма-уведомления — `server/email.mjs`,
  Resend, отправитель `MAIL_FROM_NOTIFY` (без него `MAIL_FROM`); без ключа Resend письма ждут в очереди.
- Адрес — тот, которым человек вошёл: обработчик команд хранит его зашифрованным (`email_address`, ключ из
  `FETURE_ID_PEPPER`, плюс HMAC для отказов). Очередь `email_delivery`: `now` сразу, `now-if-unread` через 15 минут,
  если не прочитано, утренняя сводка `digest`; не больше одного «сразу» на объект и 10 в сутки.
- Отписка в один клик: `List-Unsubscribe` + `POST /api/fe?unsubscribe=1&t=<подписанный токен>`. Отказы и жалобы:
  вебхук Resend `POST /api/fe?email-events=1` (подпись Svix, `RESEND_WEBHOOK_SECRET`) → `email_suppression`.
- **Тестовые адреса не получают писем.** Домен тестового входа (`TEST_LOGIN_DOMAIN`, `feture.test`) и любой `.test`:
  Core не отправляет туда код (вход — фиксированным тестовым кодом или кодом из админки), а `server/email.mjs` не
  хранит такой адрес, поэтому в очередь для него ничего не попадает.

## 11. Доступ к базе (решение)

- **Логика — в серверных модулях Node, SQL — прямой.** Новые области пишутся как ESM-модули `server/*.mjs` (`// @ts-check`, JSDoc-типы, Zod) с SQL-запросами через драйвер `postgres` к Postgres на том же сервере (`deploy/docker-compose.yml`). Одна команда = одна транзакция. Вместо RPC-функций plpgsql на каждую команду.
  - Почему: читаемый и проверяемый код (сейчас 106 функций plpgsql в сжатом стиле), Zod на входе и выходе, транзакции и outbox в одном месте, меньше обращений к базе на запрос (сейчас ~4 HTTP-запроса к PostgREST).
  - Инварианты остаются в базе: внешние ключи, `CHECK`, уникальные индексы, исключающие ограничения. plpgsql — только для триггеров счётчиков и проверок, которые нельзя обойти.
- **Отдельная роль базы `feture_api`** с правами только на схему `feture` (не `service_role`, который обходит всё). RLS включён, политик для `anon/authenticated` нет — браузер к базе не ходит.
- **Схема `feture`** (Postgres schema). Приложение, база и PostgREST (для старых эндпоинтов и входа Core) — на одном сервере (`deploy/README.md`).
- Тесты — PGlite (уже используется) с теми же миграциями схемы `feture`.

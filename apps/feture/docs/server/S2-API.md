# S2. Контракты API

27.10.2026. Часть серверной спецификации FetUre ([README](README.md)). Модель данных — [S1](S1-DOMAIN-MODEL.md), медиа — [S3](S3-MEDIA.md).

## 1. Транспорт

- **Один вход для команд:** `POST /api/fe` (новая модель; старый `/api/domain` работает, пока его разделы не перенесены, затем удаляется), JSON `{action, ...input}`. Это сохраняет лимит функций Vercel и единые проверки (вход, лимиты, журнал). Ответ: `{ok:true, ...result, requestId}` или `{ok:false, error, requestId, fields?}`.
- **Чтения тоже через `POST /api/fe`** (`action` = запрос). Кэш HTTP не нужен: всё персональное, `Cache-Control: no-store`. Публичные страницы без входа (правовые тексты, ссылки-приглашения) — отдельный `GET /api/public?…`.
- **Медиа** — только через медиа-домен (S3), никогда через `/api`.
- **Realtime** — сигнал «есть новое» по приватному каналу (§8); данные клиент всегда забирает обычной командой.
- Размер тела: 16 КБ (тексты постов, статьи — до 40 000 символов: для `post.create/update` с `kind=article` лимит 96 КБ). Медиа в теле запрещены.
- Имена действий: `<область>.<глагол>` (`post.create`, `feed.list`, `pair.invite`). Список — §9 и каталог по разделам.

## 2. Схемы и типы

- Каждая команда описана **Zod-схемой** входа в общем модуле `apps/feture/contracts/<область>.mjs` (ESM). Его импортируют и клиент (React), и сервер; новый серверный код тоже ESM (`server/*.mjs`), Core (CommonJS) подключается из него обычным импортом.
- Сервер отклоняет неизвестные поля (`strict()`), нормализует строки (NFC, обрезка, запрет управляющих и bidi-символов, лимиты длины) — требования `docs/input-safety-backend-checklist.md`.
- Вход **никогда** не содержит владельца, роль, возраст, email или account id. Владелец берётся из сессии и заголовка действующего профиля (§4).
- Типы ответа — DTO, а не строки таблиц: только поля, разрешённые зрителю (S1, «Видимость»).

## 3. Вход и сессия

- Аутентификация — Core (код на почту), заголовки `X-Fit-Email / X-Fit-Device / X-Fit-Token`, как сейчас; сервер каждый раз перечитывает сессию (отзыв работает сразу).
- После проверки Core сервер находит **`account_id`** FetUre по таблице соответствия (`account_link`: HMAC(core_account_key) → `account_id`). В доменных таблицах core-ключ и email не хранятся (D2).
- Доработки Core (этап 0): отзыв сессии при выходе на сервере; тип клиента (`web | ios | android`) в записи устройства; короткоживущий JWT (5–15 мин) для Realtime-канала; для веба — `HttpOnly` cookie вместо заголовков (позже, отдельный пункт).

## 4. Действующий профиль («Я / Мы»)

- Заголовок **`X-Fe-Profile: <profile_id>`** обязателен для всех команд, кроме `account.*`, `session.*`, `profile.mine` (список своих профилей). Без него — `400 profile_required`. Подставлять «Я» по умолчанию запрещено (правило §5.1 руководства V21).
- Сервер проверяет: профиль существует, аккаунт — его активный участник, профиль не заблокирован; для пары — пара в состоянии `active` (не остановлена). Иначе `403 profile_forbidden`.
- Каждая запись хранит `owner_profile_id` (кто владеет) и `acted_by_account_id` (кто нажал).
- Действия, которые требуют согласия партнёра (S1, «Согласия»), возвращают `{ok:true, pending:{approvalId}}` вместо результата; изменение применится после одобрения.

## 5. Ошибки

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `invalid_input` (+ `fields`) | Не прошла схема |
| 400 | `profile_required` | Нет `X-Fe-Profile` |
| 401 | `auth_required` | Нет или недействительна сессия |
| 403 | `profile_forbidden`, `forbidden`, `age_required`, `documents_required`, `blocked` | Нет прав |
| 404 | `not_found` | Нет объекта **или** нет права знать о нём (не различаем) |
| 409 | `conflict` (+ `current`) | Ревизия устарела (§6) или состояние уже другое |
| 409 | `approval_pending` | По объекту уже ждёт согласие партнёра |
| 413 | `too_large` | Тело больше лимита |
| 422 | `rule_violation` (+ `rule`) | Бизнес-правило (например, `chat_requires_match`, `photo_required_for_discover`) |
| 429 | `rate_limited` (+ `Retry-After`) | Лимит |
| 503 | `unavailable` | База или провайдер недоступны |

Тексты ошибок для пользователя — на клиенте по коду; сервер не отдаёт текстов исключений базы.

## 6. Идемпотентность и конкуренция

- Каждая команда записи принимает **`opId`** (uuid, генерирует клиент на одно намерение пользователя). Повтор с тем же `opId` возвращает сохранённый результат (таблица `op_ledger`, хранение 7 дней). Это уже есть в текущем коде — сохраняем.
- Изменяемые объекты имеют `rev` (целое). Команды изменения принимают `rev`; несовпадение → `409 conflict` с текущей версией. Счётчики и списки (реакции, подписки) — без `rev`, команды идемпотентны по смыслу (`set`, а не `toggle`): `reaction.set {postId, kind|null}`.

## 7. Списки и пагинация

- Курсорная: вход `{limit ≤ 50, cursor?}`, выход `{items, nextCursor|null}`. Курсор — непрозрачная строка (base64url JSON `{v, k:[sortKey,id]}` с HMAC), клиент его не разбирает.
- Сортировка — по `(created_at, id)` или ключу ранжирования; без OFFSET.
- Счётчики (`counts`) отдаются отдельно от списков, из одного источника (правило §5.3 руководства V21).

## 8. Реальное время и push

- Канал на профиль: `fe:p:<profile_id>` (Supabase Realtime Broadcast, private channel, авторизация по короткому JWT из §3). Для пары — общий канал профиля пары, на него подписаны оба участника.
- Сообщения канала — только сигналы `{t:'inbox'|'chat'|'notif'|'decide'|'feed', id?, seq?}`; клиент после сигнала вызывает соответствующий запрос. Никакого содержимого в канале — так транспорт можно сменить (Ably/Centrifugo) без изменения данных.
- Push (Core FCM/APNs) — нейтральные тексты без имён и содержимого («Новое сообщение», «Есть, что решить»). Отправляет обработчик очереди, не команда.

## 11. Доступ к базе (решение)

- **Логика — в серверных модулях Node, SQL — прямой.** Новые области пишутся как ESM-модули `server/*.mjs` (`// @ts-check`, JSDoc-типы, Zod) с SQL-запросами через драйвер `postgres` к пулеру Supabase (Supavisor, transaction mode, `prepare:false`). Одна команда = одна транзакция. Вместо RPC-функций plpgsql на каждую команду.
  - Почему: читаемый и проверяемый код (сейчас 106 функций plpgsql в сжатом стиле), Zod на входе и выходе, транзакции и outbox в одном месте, меньше обращений к базе на запрос (сейчас ~4 HTTP-запроса к PostgREST).
  - Инварианты остаются в базе: внешние ключи, `CHECK`, уникальные индексы, исключающие ограничения. plpgsql — только для триггеров счётчиков и проверок, которые нельзя обойти.
- **Отдельная роль базы `feture_api`** с правами только на схему `feture` (не `service_role`, который обходит всё). RLS включён, политик для `anon/authenticated` нет — браузер к базе не ходит.
- **Новая схема `feture`** (Postgres schema), а не таблицы `public.feture_*`. Старые таблицы замораживаются и удаляются после переноса (в базе сейчас только тестовые данные). Перенос в отдельный проект потом — `pg_dump -n feture`.
- **Регион функций — рядом с базой.** Сейчас функции Vercel в `iad1` (США), база в Токио: каждый запрос к базе ≈150 мс. До переезда базы — `regions: ["hnd1"]` в `vercel.json`; после переезда в ЕС — `fra1`.
- Тесты — PGlite (уже используется) с теми же миграциями схемы `feture`.

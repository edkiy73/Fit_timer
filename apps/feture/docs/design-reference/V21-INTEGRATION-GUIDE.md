# FetUre V21 → React MVP: руководство по интеграции

Для владельца и для любого исполнителя (Claude, ChatGPT/Codex, человек), который переносит утверждённый UX прототипа V21 в рабочее приложение `apps/feture/src`.
Прочитайте вместе с `apps/feture/AGENTS.md`, `docs/mvp-plan/STATUS.md`, `docs/ui-quality.md`, `docs/design-reference/DESIGN-INTEGRATION.md`, `VISUAL-CONTRACT-V4.md`.

## 1. Что такое V21 и что из неё переносить

- **V21 (`public/prototype-v21.html`)** — кликабельная UX/UI-спецификация MVP: экраны, состояния, попапы, тексты RU/EN, модель «Я / Мы», адаптивность 320–1920, светлая и тёмная темы. Это V20 + исправления по аудиту `apps/feture/audit-v20/` (≈300 пунктов, статус каждого — `audit-v20/V21-FIX-STATUS.md`).
- **Переносится:** структура экранов и навигации, состав блоков, порядок действий, тексты, правила видимости, правила «от чьего имени», состояния (пусто / загрузка / ошибка / успех / ожидает партнёра / на проверке), размеры и токены, поведение попапов.
- **Не переносится (только инструмент прототипа):** QA-панель и кнопка «V21», `window.FT_QA`, персоны «Заполненный / В паре / Новый», «Проверяемый участник: Партнёр», «Мои запросы → Одобрять сразу», сдвиг часов чата, демо-данные и сиды (`seedOwnGallery` и т. п.), имитация сервера (`net()`), любые «демо»-подписи. Партнёр в паре — это второй реальный аккаунт, а не переключатель.
- **Правило честности (DESIGN-INTEGRATION.md):** никакой поддельной «успешности» — совпадения, доступ к приватному, проверка возраста, оплата только после реального ответа сервера. Пока сервера нет — экран показывает честное состояние «скоро», а не имитацию.

## 4. Порядок работ (срезы, зависимостями сверху вниз)

Каждый срез — отдельный PR (или серия) с проверками из §9. Не начинайте следующий, пока предыдущий не принят по чек-листу.

**A. Дизайн-система и оболочка** (до всего остального)
1. Токены V21 → `src/feture/tokens.css` (решения O1/O2 выше): шрифты Geologica (заголовки) + Onest (текст), акцент `#DF234A`, цвета светлой и тёмной темы, радиусы `10/14/18/24`, отступ 16, док 64, ease `cubic-bezier(.2,.8,.2,1)`, шкала аватаров `24/36/44/56/88`, кнопки `48 / 44 (md) / 36 (sm)`, сегмент 40 (кнопка 34, 14 px/600), чипы 36 (14/500), пилюли 24 (12/600).
2. Общие компоненты (одна реализация, используются везде) — см. §6.
3. Оболочка: 5 вкладок «Лента / Люди / Сообщества / Чаты / Я»; телефон — док, 768–1099 — рельс, ≥1100 — сайдбар + правая контекстная колонка; один аватар пользователя в сайдбаре; «Я» в паре открывает «Действовать как».
4. Навигация: у каждой вкладки свой стек; «‹» в шапке снимает экран со стека **текущей** вкладки; системное «Назад» Android/браузера — по общей истории (`native-navigation.tsx`); повторное нажатие активной вкладки — к корню/вверх; позиция прокрутки сохраняется при возврате.

**B. Лента и публикации** — сервер готов, доводим UI до V21 (F01, F05, F07/F09, F10, F04, сохранённое, медиапросмотр). Ключевые правила V21: «Показать в ленте» (пост без ленты виден в профиле, «Моих публикациях» и галерее); статья = публикация с заголовком; правка одобренного поста: мелкая — сразу, крупная — на проверку, пока идёт проверка все видят прежнюю версию; голоса и реакции — у каждого профиля свои.

**C. «Я», профиль, приватная часть, доступы** — четыре вкладки «Профиль / Приватное / Видимость / Моё», фото профиля из публичных публикаций (4:5, одно видео не первым, «На проверке» видно только владельцу), приватная часть одним блоком, выключение приватной части = отзыв доступов и закрытие запросов с подтверждением, «Как видят» с реальной карточкой подборки.

**D. Сообщества и события** — сервер событий есть, сообщества — дополнить. RSVP «Интересно / Иду / Не иду» (в паре — «Нам интересно / Идём вдвоём / Не идём»), заявки и их статусы, панель организатора, счётчики «Идут / Интересуются» только из реальных данных, ожидающие заявки не показываются как «идёт».

**E. Пара «Мы»** — новая серверная модель (раздел §5). Без неё не переносить ничего, что подписано «от пары».

**F. Люди / знакомства** — только после взаимного серверного согласия на подборку (AGENTS.md). Свайпы, симпатии, «Это взаимно», фильтры с выбором места («Рядом»), отмена последнего решения (Premium).

**G. Чаты и уведомления** — чат открывается только взаимной личной симпатией; «Нужно решить» — один счётчик везде; у уведомления видно, кому адресовано («Тебе» / «Паре»).

**H. Premium, проверка возраста** — после юридических решений и выбора провайдера; до того — честные состояния «скоро».

## 5. Модель «Я / Мы»: обязательные правила для сервера и клиента

Аудит V20 нашёл 5 блокеров (P0) и десяток P1 именно здесь. Правила ниже — выжимка; в React их нужно обеспечить **на сервере**, а не только в UI.

1. **Действующий профиль (actor)** — `me` или `couple:<pairId>` — передаётся в каждом запросе на запись и чтение «своих» данных. Сервер проверяет членство в паре и активность пары. Никогда не подставлять `me` по умолчанию, если активен «Мы».
2. **Данные принадлежат профилю, который их создал:** публикации, реакции, **голоса в опросах**, подписки и подписчики, сохранённое, скрытое в ленте, **блокировки**, ответы на события, членство в сообществах, черновики, связи, запросы доступа. Блокировка из «Мы» не трогает личные чаты и подписки «Я» и наоборот (передать блок другому профилю — отдельное явное действие).
3. **Счётчики и списки считаются из одного источника для действующего профиля:** «Подписки» в ленте «Мы» — из подписок пары; бейдж «Люди» — симпатии действующего профиля; «Нужно решить» — одно число везде.
4. **Согласие партнёра:** закрыть/ограничить — сразу (партнёр уведомлён); открыть шире, публиковать, открывать доступ — через согласие, если оно включено. Ожидающее изменение видно обоим: инициатору — «Ждёт согласия партнёра», согласующему — карточка с действием «Одобрить / Вернуть».
5. **Создание пары** — точка входа в «Я» (а не только по ссылке-приглашению): приглашение по точному нику, отправленное приглашение видно и отзывается; разъединение — 30 дней на восстановление, совместный архив только для чтения.
6. **Новая пара начинается пустой** — никакого чужого контента; общий аватар — фото пары или круг из двух половин того же размера, что аватар человека.
7. **Тексты от имени пары:** «от пары», «Нам интересно», «Сообщение от пары», имя пары в кавычках рядом с другими именами («Alex и Kira» и Leon). Обращение «ты/твой» в «Мы» не используется.

## 6. Соответствие компонентов прототипа и React

| Прототип (V21) | React | Правила V21 |
|---|---|---|
| `sheet()` — нижний лист | `AppDialog` (RAC Modal) в виде bottom sheet на телефоне, диалог на ≥768 | Ручка + свайп вниз закрывает (≥25% высоты или быстрый жест) с теми же проверками несохранённого ввода, что «×», Esc, тап по затемнению и системное «Назад»; шапка и подвал фиксированы, тело прокручивается |
| `ask()` — подтверждение | `ConfirmDialog` на `AppDialog` | Всегда иконка; заголовок-вопрос; 1–2 строки последствий; необратимое — сплошная красная кнопка; «Отмена» вторична; фокус на «Отмена» |
| `toast()` | один `Toast` регион (`role=status`, ошибки `role=alert`) | Над доком/CTA; при открытом листе/диалоге — у верхнего края; не перекрывает кнопки; действие «Отменить» 4 с; тост предыдущего экрана убирается при открытии листа |
| `seg()` / `tabsRow()` | RAC `Tabs` | Подписи не обрезаются: если не помещаются — ряд прокручивается вбок с градиентом; точка «новое» внутри подписи; счётчик у подписи |
| `bar()` — шапка | `ScreenHeader` | «‹» = назад в стеке вкладки; плавающая стеклянная шапка; в чате человек в шапке на стеклянной подложке |
| док / рельс / сайдбар | `AppShell` | Подписи дока не обрезаются на 320 (10 px при ≤374); один аватар себя |
| `av()` | `Avatar` | Шкала 24/36/44/56/88; пара — фото пары или разделённый круг того же размера |
| `grp()` | `Section` | Заголовок 13/600 + действие справа с зоной нажатия ≥44 |
| `.btn` primary/soft/text/danger | `ActionButton` | 48 / md 44 / sm 36, радиус 14 (sm 12), 15/600; одна главная кнопка в группе |
| `.ibtn.add` «+» | `IconButton` variant `add` | 44×44, радиус 14, одна форма везде |
| `empty()` | `StateCard` | Один стиль пустых состояний: иконка, заголовок 21/700, текст, одно действие |
| `.chip`, `.pill` | `Chip`, `Badge` | 36 / 24 px; хештеги и ссылки — визуально мелкие, зона нажатия 44 |

## 7. Состояния, которые каждый экран обязан иметь

Для каждого экрана из прототипа сделайте карточку спецификации (можно в PR): экран, вход, данные (DTO), действия, и **все состояния**:
загрузка · пусто (новый аккаунт) · заполнено · ошибка сети (с «Повторить») · нет доступа / заблокировано / удалено (`Это недоступно`) · «Я» и «Мы» · ожидает согласия партнёра · на проверке модерации · офлайн · длинные тексты и слова без пробелов · 320 / 390 / 768 / 1024 / 1440 · светлая / тёмная · RU / EN.
Прототип показывает эти состояния через QA-панель: откройте `prototype-v21.html`, кнопка-вкладка «V21» у правого края → персона, язык, тема, ширина, «Длина текстов», «Сеть».

## 8. Как читать прототип исполнителю

- Экраны — `SC.<ID>` (`SC.F01`, `SC.X01`…), действия — `ACT.<name>`, листы — `sheet(...)`, подтверждения — `ask(...)`. Модули отмечены комментариями `/* ---- s-feed.js ---- */`.
- Строка 3021 — base64-картинки на 300 КБ: не выводите её (`sed -n` с `cut -c1-600`).
- В браузере: `window.FT_QA.go('P01',{id:'mia'})`, `FT_QA.list()` — все экраны QA-панели.
- Правки V21 помечены `/* V21 (ID): … */`; ID ведёт в `audit-v20/data/issues.json` (причина, ожидаемое поведение, проверка).

## 9. Проверка каждого среза (по `ui-quality.md`)

- Ширины 320, 390, 768, 1024, 1440 (+200% масштаб), обе темы, RU и EN; скриншоты React рядом со скриншотами V21 в том же состоянии.
- Все состояния из §7 для затронутых экранов; «Я» и «Мы» для всего, что можно сделать от пары.
- Клавиатура и фокус: Esc закрывает верхний слой, фокус возвращается к открывшему элементу; зоны нажатия ≥44.
- Автотесты — только для рискованной логики (права «от чьего имени», раскрытие приватного, удаление, оплата) — по правилу AGENTS.md §5; обычный UI проверяется руками/скриншотами.
- `npm run check` в `apps/feture`; в PR — список реально выполненных и невыполненных проверок; `docs/mvp-plan/STATUS.md` — обновить строку среза.

| Сообщества | Ведущий — профиль-создатель (может быть пара); участие пары в закрытом сообществе даёт паре доступ к обсуждениям «от пары»; удаление участника — один раз и со статусом | COMM-001, COMM-002, COMM-016 |
| Приватная часть | Выключение = отзыв всех доступов и закрытие запросов (с подтверждением и числами); «открыть доступ» при выключенной части предлагает включить | ME-003, ME-022 |
| Режим знакомств | Три состояния: показываюсь / смотрю незаметно / выключено; «незаметно» не делает профиль видимым; последнее фото при «показываюсь» нельзя убрать без выбора режима | ME-002, ME-004 |
| Регистрация | Ответы шага «О тебе» по умолчанию «Только ты»; ник проверяется против всех существующих профилей, одно сообщение | AUTH-016, AUTH-001/002 |
| Пара | Создание из «Я → Моё» и Настроек; приглашение видно, отзывается, отказ сохраняется; новая пара без контента; остановленная — восстановление 30 дней, затем архив | CPL-001, CPL-002, CPL-003 |
| Согласия партнёра | Ожидающее изменение видно обоим; согласующий решает на месте, видит разницу по словам | CPL-015, CPL-016, CPL-017 |
| Уведомления | У каждого — адресат (`Тебе` / `Паре`); совпадения в карточке запроса считаются для адресата, а не для режима дока | NTF-001, NTF-002 |
| Имя пользователя | Своё имя в интерфейсе — `name`, ник — вторично (как у других людей) | EVT-025 |

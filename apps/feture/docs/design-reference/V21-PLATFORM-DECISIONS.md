# FetUre: платформа и стек для MVP — решения до начала разработки

27.10.2026. Основа: инвентаризация серверного кода (`apps/feture/api`, `lib/feture`, 57 миграций, `packages/core/server`), требования прототипа V21 и проверка условий площадок (AUP хостингов, правила магазинов, платёжные системы, GDPR). Ссылки на источники — в конце.
Связанные документы: [V21-INTEGRATION-GUIDE](V21-INTEGRATION-GUIDE.md) (как переносить интерфейс), ADR `docs/appbase-stack-ci-strategy.md` (общий стек AppBase).

## 1. Короткий ответ

- **Стек менять не нужно.** React + Vite + Capacitor на клиенте, Postgres, JSON API без состояния, Core-аутентификация выдерживают 100k–1M пользователей. Переписывать на другой фреймворк — потеря времени без выигрыша.
- **Менять нужно три слоя вокруг ядра — и решить это сейчас, пока реальных данных нет:**
  1. **Данные:** отдельная база FetUre (не общий проект с FitTimer), регион ЕС, случайный `account_id` вместо хэша email, владелец данных — **профиль** («Я» или «Мы»), а не аккаунт.
  2. **Медиа:** не через функции Vercel. Хранилище и отдача — Cloudflare R2 + Images + Stream за своим медиа-доменом, с карантином и проверкой до публикации.
  3. **Реальное время и фоновые задачи:** чаты и уведомления — сообщения в Postgres, «пинок» клиенту через Realtime-канал; все побочные эффекты — через outbox и очередь.
- **Серверный код в мусор не идёт целиком.** Инфраструктура и паттерны (идемпотентность, ревизии, журнал операций, сервисная роль, очереди модерации, документы и согласия, пайплайн приватных фото, PGlite-тесты) — оставляем. Примерно половина доменного SQL переносится на новую модель владельца. Сообщества, знакомства, чаты, уведомления, пары, галереи и Premium — строим заново (их на сервере нет).
- **Не всё описано.** UX описан полностью (V21 + руководство). Для разработки не хватает: доменной модели сервера, контрактов API, спецификаций админки и модерации, уведомлений, медиа и карты данных для GDPR. Список и порядок — в §6.

## 2. Что уже есть на сервере и что с ним делать

| Область | Что есть | Решение |
|---|---|---|
| Инфраструктура API | 7 функций Vercel, один диспетчер `api/domain.js` (~100 действий), лимиты запросов, аудит без PII | **Оставить**; перевести валидацию на Zod; регион функций — к базе |
| Аутентификация Core (email-код, сессии устройств) | Работает | **Оставить с доработкой**: случайный `account_id`, отзыв сессий, короткоживущий токен для Realtime, cookie для веба |
| База и права | Supabase, общий проект с FitTimer (регион Токио), RLS, только сервисная роль | **Перенести** в отдельный проект FetUre в ЕС; модель прав сохранить |
| Паттерны (operationId, ревизии, журнал операций, белые списки ключей в SQL) | Последовательно во всём коде | **Оставить** как стандарт |
| Профили | Одна запись на аккаунт, без фото | **Переделать**: профиль = человек или пара, фото из публикаций |
| Приватная часть и доступы | Запросы, гранты по полям, срок до 90 дней, блоки на аккаунт, флаг `can_message` | **Переделать**: области «Описание и интересы / Фото / Видео», владелец — профиль, блоки на профиль, убрать `can_message` (чат только после взаимной симпатии) |
| Интересы, история, журнал | Шкала 0–100, без направления | **Переделать**: шкала 0–10 + «всё/давать/получать/смотреть», интересы пары |
| Тесты (опросники, карта) | Крупнейший блок SQL (~190 KB) | **Заморозить**: тесты убраны из продукта решением владельца; таблицы не удалять до запуска, но и не развивать |
| Публикации, ответы, реакции, жалобы, проверка фото | ~35 действий, тесты есть | **Оставить с доработкой**: автор = профиль, опросы, статьи, «не в ленте», галереи и альбомы |
| Подписки и скрытие | Есть, на аккаунт | **Переделать** на профиль |
| События, RSVP, заявки | Ближе всего к V21, тест не запускается в CI | **Оставить с доработкой**: организатор = профиль, включить тест в CI |
| Сообщества | Каталог и черновик владельца; членства, заявок и обсуждений нет | **Построить заново** |
| Модерация, операторы, жалобы, апелляции | Хорошая база, нет целей «профиль/пара/сообщество», нет провайдеров | **Оставить**, добавить провайдеры CSAM и классификаторы, новые цели |
| Проверка возраста | Движок есть, не подключён, провайдера нет | **Оставить** движок, подключить провайдера (Yoti) |
| Документы и согласия | Готово | **Оставить** |
| Ссылки-сравнения | Есть | Оставить или выключить — не ключевое для V21 |
| Знакомства (подборка, симпатии, взаимность) | Только пустая таблица настроек | **Построить** |
| Чаты, уведомления и «Нужно решить», пары и согласия партнёра, галереи, связи профилей, Premium, видео | Нет | **Построить** |
| Мёртвые таблицы (`feture_profile_access`, `feture_test_responses`, старый `feture_interest_states`, `feture_dating_preferences`, `feture_reports`) | Не используются | **Удалить** при переносе в новую базу |

## 3. Решить сейчас (переделка потом дорогая)

| # | Решение | Рекомендация | Почему сейчас |
|---|---|---|---|
| D1 | Отдельная база FetUre | Новый проект Supabase во Франкфурте, свои ключи и хранилище аккаунтов; функции Vercel в `fra1` | Данные о сексуальной жизни — особая категория (GDPR ст. 9); общий проект с FitTimer и регион Токио — риск и задержки; сейчас данных почти нет |
| D2 | Идентичность | Случайный `account_id` (UUIDv7); email — только для входа; ни один ID не связывает FetUre с другими приложениями | `sha256(email)` восстанавливается словарём и меняется при смене почты |
| D3 | Владелец данных — профиль | Сущность `profile` (тип: человек / пара, участники), все таблицы владения ссылаются на `profile_id`, рядом `acted_by_account_id`; общая таблица согласий партнёра | Центральная модель V21; добавлять её позже — переписать каждую таблицу |
| D4 | Медиа как сущность | `media_asset`: владелец-профиль, состояние «карантин → проверено → одобрено/отклонено», метка откровенности, видимость, варианты, правило просмотра (один раз / таймер); загрузка напрямую в хранилище; отдача через свой медиа-домен с короткими токенами; URL провайдера не хранится | Фото, галереи, приватная часть, чаты, проверка — всё на ней |
| D5 | Метка откровенности и фильтр по платформе | У каждого медиа и публикации: безопасное / откровенное; iOS и Android по умолчанию показывают только безопасное, откровенное включается на сайте | Правила Apple (1.1.4, 1.2) и Google Play для пользовательского контента |
| D6 | Модель чата | Беседа между профилями, монотонный номер сообщения, курсор прочтения у участника, эфемерные медиа = media_asset, Realtime только как сигнал | Транспорт можно будет заменить без миграции данных |
| D7 | Outbox + очередь | Все побочные эффекты (push, «Нужно решить», поиск, модерация, удаление) пишутся в outbox в той же транзакции, обрабатываются очередью (pgmq) | Иначе уведомления и модерация теряются при сбоях |
| D8 | Хостинг и AUP | Vercel — только сайт и JSON API, медиа никогда не идёт через Vercel; получить письменное подтверждение Vercel (registration@vercel.com); API держать переносимым (ADR D5 это уже требует) | AUP Vercel размыто запрещает «obscene/objectionable»; Supabase и Cloudflare adult-контент не запрещают |
| D9 | Платежи | Внутри приложений — только покупки через магазины (IAP); на сайте — процессор, работающий с adult (Segpay / CCBill / Verotel); слой прав (entitlements) свой или RevenueCat; Premium продаёт функции, а не доступ к контенту | Stripe прямо запрещает fetish-сервисы; Apple требует IAP |
| D10 | Юрисдикция | **Нужен юрист**: только ЕС, или ЕС + Россия (152-ФЗ требует хранить данные граждан РФ в РФ; плюс законы о «ЛГБТ-движении»). Одной базой обе схемы не закрыть | Определяет, сколько баз и где |
| D11 | Точность геолокации | Точные координаты храним отдельно, наружу — только округлённые/с шумом | Защита от определения места трилатерацией |
| D12 | DPIA и карта данных | Оценка воздействия на защиту данных, явные согласия, список обработчиков с DPA, никаких рекламных SDK | Обязательно для данных ст. 9 до запуска |

## 4. Слой за слоем: что оставить, что заменить

| Слой | Решение | Что заставит пересмотреть |
|---|---|---|
| Сайт и приложения (React, Vite, react-query, zod, React Aria, Capacitor) | Оставить | Тормозят длинные чаты или видео в WebView → нативные экраны точечно |
| API | Функции Vercel (JSON), регион у базы | Ответ Vercel по AUP; долгие задачи или WebSocket |
| База | Postgres в отдельном проекте Supabase (ЕС) + PostGIS, pg_trgm, FTS | Нагрузка → реплики чтения |
| Аутентификация | Core, доработанная (D2, токены, cookie) | — |
| Реальное время | Supabase Realtime Broadcast (приватные каналы, только сигнал) | >~10k одновременных соединений → Enterprise или свой Centrifugo |
| Push | Core: FCM + APNs напрямую, нейтральные тексты | — |
| Медиа | Cloudflare R2 + Images (варианты, кропы, водяной знак для зрителя) + Stream (видео) | Стоимость видео — ограничить длину роликов |
| Фоновые задачи | Outbox + pgmq, обработчики на Vercel, cron | Объёмы → Cloudflare/Vercel Queues |
| Поиск | Postgres FTS + pg_trgm | Опечатки и ранжирование на десятках миллионов → Typesense/Meilisearch |
| Модерация | Свои очереди + проверка CSAM по хэшам (PhotoDNA / Thorn Safer / Hive) до публикации + классификатор откровенности (ставит метку, не блокирует) | Рост штата → отдельная консоль |
| Проверка возраста | Yoti, храним только результат | — |
| Платежи | IAP + adult-процессор для сайта + слой прав | — |
| Аналитика | Своя или EU-хостинговая, без PII | — |
| Админка | Core Admin + роли сотрудников, медиа размыто по умолчанию, аудит, 2FA, отдельный домен | — |

## 5. Что исправить в существующем коде до первых реальных пользователей

- Перенос в отдельный проект и регион (D1), снять жёсткие проверки `project_ref` в миграциях.
- Случайный `account_id` (D2) и перенос владения на `profile_id` (D3) — одной миграцией, пока данных нет.
- Фото: уйти от base64 через функцию и отдачи байтов через API (D4).
- Валидация входных данных на Zod и серверная часть чек-листа `apps/feture/docs/input-safety-backend-checklist.md` (NFC, bidi/zalgo, confusables, CSP).
- Подключить к CI тест событий (`events-owner-postgres.mjs`) и удалить мёртвые таблицы.
- Почта: рабочий домен отправителя вместо тестового `onboarding@resend.dev`.

## 6. Каких спецификаций не хватает (и в каком порядке их писать)

| # | Документ | Что в нём | Зачем |
|---|---|---|---|
| S1 | Доменная модель сервера | Сущности, связи, владельцы (профиль/аккаунт), состояния и переходы, инварианты «Я/Мы», права | Основа всего; пишется из V21 + §3 |
| S2 | Контракты API | Действия (команды и запросы) по разделам, входы/выходы (Zod), ошибки, идемпотентность | Чтобы фронт и сервер делались параллельно |
| S3 | Медиа | media_asset, загрузка, карантин, проверка, варианты, водяные знаки, эфемерные медиа, токены | D4–D5 |
| S4 | Модерация и админка | Очереди, роли, SLA, решения, апелляции, жалобы, проверки фото и событий, CSAM-процедура (уведомление NCMEC/властей), аудит | Требование магазинов и закона |
| S5 | Уведомления | Типы событий, адресат (человек/пара), «Нужно решить», push-тексты, настройки, тихие часы | Сквозная часть V21 |
| S6 | Знакомства | Подборка, фильтры, гео, ранжирование, симпатии, взаимность, отмена, лимиты, Premium-функции | Новая область |
| S7 | Чаты | Беседы, сообщения, прочтения, эфемерные медиа, блокировки, жалобы | Новая область |
| S8 | Платежи и права | Продукты, IAP/веб, подарки (паре — обоим), возвраты, налоги | D9 |
| S9 | Карта данных и DPIA | Какие данные где, сроки хранения, экспорт и удаление, обработчики | D12 |

Порядок работ (уточняет срезы A→H из V21-INTEGRATION-GUIDE): **0. Платформа** (D1–D4, D7, перенос базы, профиль-владелец, media_asset, outbox) → A. Оболочка и дизайн-система → B. Лента → C. «Я» и доступы → D. Сообщества и события → E. Пары → F. Знакомства → G. Чаты и уведомления → H. Premium и проверка возраста. Спецификации S1–S3 пишутся до этапа 0, S4–S9 — до соответствующих срезов.

## 7. Вопросы владельцу

1. **D10 — юрисдикция:** запускаемся только в ЕС (и других странах вне РФ) или нужны пользователи из России? От этого зависит число баз и юридическая схема.
2. **D1:** согласен выделить FetUre отдельный проект базы в ЕС (новый проект Supabase, ~$25+/мес)?
3. **D5:** согласен, что в iOS/Android откровенное по умолчанию скрыто и включается только на сайте?
4. **D9:** на сайте — adult-процессор вместо Stripe; Premium продаёт функции, а не доступ к контенту — ок?
5. **D8:** написать в Vercel за письменным подтверждением (или сразу держать API на нейтральном хостинге)?

## Не проверено

Цены и условия PhotoDNA / Thorn Safer; совместимость Supabase Realtime с токеном Core; текущая редакция правил Mastercard для adult; правовые вопросы по РФ; все оценки стоимости — расчётные.

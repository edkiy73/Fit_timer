# V10: личные профили и совместная страница — план реализации

Статус: **реализовано в V10; сборка, семь contract suites, CI и браузерные сценарии пройдены. Ограничения проверки перечислены ниже**. Передача другой AI-модели по запросу владельца от 18.10.2026.
Проверенная база: `f19cc68d9e46c39306b335644e12564fee16ca13`. Перед реализацией обновить `main` и сверить изменившиеся владельцы функций.

## 1. Что нужно решить

FetUre прежде всего социальная сеть: личный профиль, дневник, интересы, фотографии и история человека должны сохраняться годами независимо от отношений. Знакомства — отдельная опция. В знакомствах два человека должны быть представлены одной узнаваемой парой с общими фотографиями и описанием. При этом им нужна возможность публиковать совместные истории в общей ленте, не теряя личного авторства остальных материалов.

Целевая модель: **два самостоятельных личных профиля и одна совместная страница с ограниченными возможностями**. Совместная анкета знакомств — представление этой пары в знакомствах, а не третий аккаунт с отдельным входом. Связь пары не объединяет личные данные и не даёт партнёру доступ к личной переписке, черновикам, дневнику или приватным фотографиям.

Убираем необходимость выбирать «от кого» при каждом действии. Лайки публикаций, комментарии, подписки, членство и участие в событиях всегда личные. Совместное авторство выбирается при создании публикации. Совместная анкета выбирается внутри знакомств и действует только там.

Владелец отверг перегруженные кнопки «Я / Пара / Оба», аватарки под каждой кнопкой, скрытые свайпы по кнопкам, долгое удержание, длинные меню и постоянное глобальное переключение профиля. Не возвращать эти решения под другим визуальным оформлением.

Этот документ задаёт новый целевой контракт для перечисленных действий; соответствующие старые правила универсального автора в V10-ROADMAP / OWNER-REVISION-PLAN подлежат обновлению при реализации. Остальные задачи этих планов остаются в силе. Варианты action-lab 1–5 — архив экспериментов, не выбранный дизайн. Не переносить их механику в основной прототип.

## 2. Границы задачи

Работаем в `apps/feture/prototype/v10/`, существующих проверках прототипа и связанных документах. Генерируем `apps/feture/public/prototype-v10.html` штатным сборщиком. Не редактируем сгенерированный HTML вручную. Не меняем V9, React-приложение, AppBase, SQL, backend или реальные данные. Серверные требования записываем как последующий handoff, не выдаём симуляцию согласий за серверную защиту.

Сохраняем существующий визуальный язык, RU/EN, темы, адаптивность, работу докбара и последние исправления навигации. Не делаем новый интерфейс поверх старого и не заменяем реальные экраны демонстрационными карточками.

## 3. Контракт действий

| Действие / поверхность | Кто действует и кому принадлежит результат | Выбор в интерфейсе |
|---|---|---|
| Лайк публикации или ответа, сохранение, подписка | Личный пользователь, в том числе под совместной публикацией | Нет |
| Комментарий / ответ / обсуждение | Личный пользователь; принадлежность к паре не делает ответ совместным | Нет |
| Публикация в собственной ленте | Личный автор либо совместная страница | Один выбор в редакторе; личный по умолчанию |
| Подписка на совместную страницу | Личный подписчик → страница пары | Обычная кнопка подписки |
| Исходящая подписка от пары | Не поддерживается | Нет |
| Поиск знакомств, свайп, симпатия | Личная анкета либо совместная анкета; отдельные решения и взаимности | Один выбор в разделе знакомств |
| Переписка после совместного знакомства | Контекст знакомства совместный, отправитель каждого сообщения — конкретный человек | Нет переключателя отправителя |
| Вступление в сообщество, RSVP, заявки и роли | Личный пользователь | Нет |
| Личные интересы, дневник, результаты тестов | Личный профиль | Нет |
| Совместные интересы, описание, фотографии | Страница пары; публикация согласованной версии | Редактор совместной страницы |
| Приватный доступ | Явные владелец материала, получатели, scope и срок | Отдельный запрос доступа; не глобальный автор |

Совместная страница может получать подписчиков и публиковать совместные материалы. Она не ставит социальные лайки, не комментирует и не подписывается на других. Действия «от обоих сразу» нет: совместная симпатия — одно действие совместной анкеты, не два личных лайка.

Совместные публикации в сообществах пока не расширять: в этом проходе публикации в сообщество личные. В редакторе с выбранным сообществом совместный автор недоступен с коротким объяснением. Существующие права модерации не ослаблять. Это ограничение прототипа до отдельного решения владельца.

## 4. Состояние и границы контекстов

Сейчас `core.js` связывает `S.author`, `actionAuthor()`, `social()`, `authorPicker()`, `paintAuthor()` и многие обработчики. Простого удаления переключателя недостаточно: скрытая пара не должна оставаться фактическим автором.

Разделить четыре понятия (названия новых полей выбрать после проверки текущего кода):

1. **Текущий пользователь** — кто нажал кнопку; неизменен при переходе в совместную страницу.
2. **Автор публикации** — часть черновика; сохраняется в preview, редактировании и публикации. Открытие совместного редактора явно задаёт пару, общий «Создать» — личного автора.
3. **Анкета знакомств** — локальный выбор раздела, запоминаемый в текущей сессии. Отдельные фильтры, решения, undo, входящие/исходящие симпатии и взаимности.
4. **Контекст переписки/доступа** — зафиксирован при создании объекта; не вычисляется заново из открытого экрана. Отправитель сообщения всегда персональный.

Проверять capability операции, а не только существование активной пары. `authorAllowed('couple')` само по себе не разрешает паре комментировать или подписываться. Удалить зависимость социальных действий от глобального автора, включая обёртки и отложенные callbacks. Не заменять вслепую все `actionAuthor()` на `'me'`: это сломает совместные черновики, знакомства, доступы и чаты.

Сохранить и адаптировать `authorTicket` / `validAuthor`, сессию, идентичность пары и `safetyEpoch`. После выхода, смены персоны, отзыва согласия или разъединения ранее открытая форма/таймер не должны завершать совместное действие. Проверка выполняется в момент записи, не только при отрисовке кнопки.

Личные данные не переносятся в пару автоматически. Совместный материал хранит пару, реального создателя и согласования отдельно. Опубликованный автор неизменяем: редактирование не превращает личную историю в совместную или наоборот. Для прототипных seed-данных допустимо обновить фикстуры; не проектировать миграцию реальных данных в этом PR.

## 5. Изменения пользовательских сценариев

### 5.1 Совместная страница и создание пары

- У каждого остаётся свой вход и профиль. Приглашение и принятие вторым участником создают активную связь; отправка приглашения сама по себе ничего не публикует.
- Страница содержит два имени, ссылки на обоих людей, совместное фото/галерею, описание, совместные интересы, публикации и подписчиков. Пара явно распознаётся в карточке без открытия профиля.
- Знакомства пары включаются отдельно от существования страницы; создание пары не включает поиск и не меняет личную видимость.
- Нет автоматического копирования личных приватных материалов, тестов и границ в совместные. Не вычислять «среднее желание» из ответов партнёров; жёсткие границы не превращаются в процент совместимости.
- Личный профиль может показывать связь с парой в рамках согласованной видимости, но не заменяется страницей пары.

### 5.2 Социальная лента, посты и ответы

- Удалить глобальные и покнопочные переключатели автора из ленты, детального поста, реакций, подписок, комментариев и списков подписок. Сохранить обычные размеры и позиции кнопок.
- В редакторе один компактный блок автора: «Вася» / «Вася и Лена». Два понятных варианта, без режима «оба». Рядом с обычной кнопкой публикации не дублировать аватарки и подписи.
- Совместный черновик отправляется на согласование партнёру. До согласования публичного поста нет; автор видит статус и может продолжить редактирование. Preview показывает итогового совместного автора.
- Любое изменение согласуемого содержимого увеличивает версию и аннулирует прежнее подтверждение. Самосогласование запрещено. Подтверждение старой версии не публикует новую.
- Редактирование опубликованного совместного поста создаёт новую согласуемую версию; старая согласованная остаётся видимой, кроме немедленного скрытия чувствительного материала. Личный пост не требует партнёрского согласия.
- В ленте одна публикация с двумя соавторами и переходом на совместную страницу. Не создавать два экземпляра одного поста ради двух личных профилей. В личном профиле совместные работы можно показывать отдельной связанной подборкой без смены владельца.
- В ответах всегда видно имя человека. Метка участника пары допустима у автора ответа, без второго переключателя и без ложной подписи «пара ответила».

### 5.3 Знакомства и плавающие действия карточки

- Единственный компактный выбор анкеты в шапке раздела: личная / совместная. Имя и изображение выбранной анкеты видны до свайпа. Выбор не меняет авторство в ленте или открытом редакторе.
- Сохранить реальные карточку, внутренний скролл профиля и **весь существующий набор плавающих действий**, а не рисовать упрощение из двух кнопок. Перед изменением составить перечень этих действий по текущему `s-people.js` и обработчикам.
- Свайп и соответствующая кнопка имеют одинаковую семантику. Не добавлять вверх/вниз для выбора автора. Undo отменяет последнее решение только выбранной анкеты.
- При переключении сохранять текущего кандидата, если он допустим для новой анкеты; иначе показывать следующего допустимого с коротким объяснением. Истории и фильтры не смешиваются. Сбросить незавершённый жест/анимацию и исключить запись под новым автором из старого callback.
- Карточка пары явно содержит два имени и признак пары, совместные фотографии и информацию. Не маскировать её под одного человека. Партнёр и собственная пара не появляются как кандидаты.
- Выключенная совместная анкета не получает новых симпатий и не появляется в подборке. Предложить включить её в настройках пары; не включать автоматически после переключения.
- Входящие симпатии и match показывают, **кому** адресован интерес: лично или паре. Совместный match уведомляет обоих, без копирования личных уведомлений партнёру.
- На совместной социальной странице вместо универсального социального лайка использовать явный переход «Познакомиться» только при включённых знакомствах. Сам переход не отправляет симпатию: действие происходит в контексте знакомств. Личные социальные симпатии существующего прототипа не переписывать без необходимости; они не получают совместного отправителя. Подписка и лайк поста никогда не создают match или чат.

### 5.4 Переписка, уведомления и приватные материалы

- Личный match открывает личный чат; пара + человек — чат трёх участников; пара + пара — четырёх. Использовать реальные member IDs, удалять дубликаты. На каждом сообщении конкретный отправитель.
- Заголовок показывает контекст знакомства. Нельзя сменой анкеты превратить уже существующий чат в другой, получить чужую историю или обойти взаимность.
- Общий список переписок может объединять личные и совместные диалоги, но каждая строка показывает адресата/состав; глобального режима отправителя нет.
- Совместные уведомления доступны обоим участникам; прочитанность персональная. Личный чат/лайк/черновик не становится доступным партнёру из-за связи пары.
- Запрос приватного доступа хранит явный набор получателей. Доступ человеку не даёт доступ его партнёру; доступ паре не переносится на новую пару. Для совместных материалов согласование раскрытия обоими, отзыв любым участником немедленный. Не раскрывать личные альбомы через совместный запрос.
- Блокировка, истечение доступа и разъединение проверяются при чтении и действии; ранее открытый экран не является разрешением.

### 5.5 Разъединение и сохранность истории

- Немедленно остановить совместные новые публикации/одобрения/симпатии, убрать совместную анкету из подборки; локальный выбор знакомств безопасно вернуть на личный с уведомлением.
- Не удалять и не переоформлять личные посты, дневник, интересы, подписки, личные matches, переписки и фото. Сохранить совместное авторство исторических материалов, не приписывать их одному человеку.
- Отозвать совместные чувствительные доступы; запретить отправку в совместных чатах до определённой политики. Не открывать личный чат автоматически вместо совместного.
- Просроченный approval, открытый редактор, таймер свайпа и отправка сообщения после разъединения не должны завершаться успешно. Черновик не публиковать автоматически как личный.
- Существующие механизмы архива/восстановления изучить в `dissolvePair()` и связанных экранах. Не удалять их молча и не превращать новый план в обещание бессрочного доступа к интимным материалам.

## 6. Решения, пока не утверждённые владельцем

Эти пункты — предлагаемые **обратимые defaults прототипа**, а не согласованная политика запуска. Реализатор фиксирует их в handoff и не делает необратимых операций. Они не блокируют остальную работу.

| Вопрос | Default для демонстрации |
|---|---|
| Кто может отправить симпатию от совместной анкеты? | Любой участник после взаимного включения совместных знакомств; без подтверждения каждого свайпа. Действие и инициатор видны обоим внутри пары |
| Какие совместные публикации требуют подтверждения? | Все новые совместные посты и изменения публикуемого содержания. Личные — никогда |
| Судьба страницы и постов после разъединения | Убрать из публичного показа, сохранить закрытый архив и атрибуцию без удаления; чувствительное медиа не оставлять доступным по старым grant. Публичное сохранение истории требует отдельного решения |
| История совместного чата после разъединения | Закрытый архив без новых отправок, с сохранением проверки доступа к сообщениям и отзывом медиа. Не добавлять новых участников |
| Удаление общего материала одним участником | Немедленное скрытие допустимо; окончательное удаление и восстановление — отдельная политика, не имитировать необратимое удаление |
| Совместные посты в сообществах | Не включать в текущем проходе; личная публикация и личное членство |

Не добавлять глобальную настройку «все действия от пары», автоматическое согласие на будущий контент, замену партнёра внутри старой пары или наследование доступов новой парой.

Проходы зависимы: 0 → 1 → 2 → 3 → 4 → 5 → 6. Небольшие законченные PR допустимы, но не публиковать промежуточное состояние, в котором UI показывает личного автора, а обработчик пишет от пары. Не разносить одну смену контракта UI/state/guard на несовместимые коммиты.

## 8. Проверка результата

Автоматизация нужна для стабильных рисков авторизации, утечки и потери данных; не строить новую большую UI-suite ради этого прохода. Адаптировать существующие контракты к изменённой семантике, не удалять проверки безопасности ради зелёного результата.

Команды из корня репозитория:

```sh
node apps/feture/tools/build-prototype-v10.mjs
npm run check:prototype --prefix apps/feture
```

Проверки включают существующие community/discussion/host/profile-preview/followup/hostile-input/social-identity contracts. Старые ожидания совместных комментариев и исходящих подписок заменить проверками запрета. Сохранить проверки экранирования, приватности, membership, взаимности, stale callback и отзыва согласия. Запустить дополнительные обязательные CI gates по реально затронутым файлам; не заявлять весь продукт проверенным по одному прототипному тесту.

| Сценарий | Ожидаемый результат |
|---|---|
| Пользователь без пары | Обычная соцсеть, редактор и знакомства без пустых переключателей |
| Приглашение не принято | Нет публичной пары, совместной публикации и dating actor |
| Активная пара, совместные знакомства выключены | Совместные посты доступны через согласие, discovery пары выключен |
| Пара выбрана в знакомствах → переход в ленту | Лайк/ответ/подписка личные; общий «Создать» личный |
| Личный и совместный черновики → preview → Back | Автор и содержимое не смешиваются; действуют правила согласования |
| Согласование → изменение → старое подтверждение | Новая версия не публикуется; нет self approval |
| Личный лайк, совместный лайк того же кандидата | Независимые истории/взаимности; нет действия «оба» |
| Переключение анкеты во время свайпа / undo | Нет записи под неверной анкетой и отмены чужого решения |
| Совместный match с человеком / парой | 3 / 4 реальных участника, видимый конкретный отправитель |
| Личный grant → просмотр партнёром | Доступа нет; совместный grant не раскрывает личный альбом |
| Разъединение при открытом редакторе/чате/approval | Совместная запись запрещена; личная история сохранена |
| Выход/смена персоны, блокировка, отзыв доступа | Нет утечки через старую форму, callback или повторное открытие |
| Подписка на страницу пары | Подписчик личный; пара не получает исходящую подписку, match или чат |

В браузере показать **куски настоящих экранов**, а не абстрактный showcase: лента, пост/ответы, редактор и preview, страница пары, личный профиль, карточка знакомств со всеми плавающими кнопками, входящие симпатии, match, чат, доступы, сообщество, событие, согласование и разъединение. Проверить нормальные переходы, не только QA deep-link, который может подставлять готовое состояние.

Для материальных layout-изменений проверить ширины 320/390/768/1024/1440, обе темы, RU/EN; клавиатуру, фокус, длинные имена, скролл внутри dating card, safe area и отсутствие горизонтального overflow. Основные действия не требуют удержания/скрытого жеста. Скриншоты до/после затронутых поверхностей приложить в PR; не выдавать изображение-концепт за проверку реализации.

### Дополнение владельца — 19.10.2026, 16:26 Бали

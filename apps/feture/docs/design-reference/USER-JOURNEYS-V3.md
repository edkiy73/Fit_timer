# FetUre — карта пользовательских путей и план пересборки V3

Решение владельца 13.10.2026, уточнение 02:53: **регистрация до приложения; только серверные данные; пять постоянных вкладок; взаимная видимость знакомств**. Это заменяет гостевой/local-first путь и условное появление пятой вкладки из PR #1063/#1062.

Решение владельца 13.10.2026. **Сначала проектировать полный путь, затем реализовывать связанные экраны одним функциональным блоком.** Этот документ определяет UX-очередь и дополняет PRODUCT-UX-V3.md; заменяет прежнюю очередь косметической полировки. Серверные требования остаются в доменных MVP-карточках. План не является заявлением о готовности функций.

## 1. Результат для пользователя

FetUre помогает разобраться в себе, собрать личную карту, выбрать, чем поделиться, и найти общение. Знакомства включаются отдельно. Пользователь без партнёра и без знакомств получает полноценный продукт. Каждый экран отвечает на три вопроса: где я, что здесь полезного, что могу сделать дальше. Отдельная постоянная «Главная» не нужна.

Основа: одобренный Claude HTML — типографика, тёплые поверхности, розовый/лиловый акцент, мягкий свет, стекло, плавные реакции. Его навигация, проценты совместимости, платежи и иллюстративные участники не являются готовыми продуктовыми контрактами. Наши сценарии и права определяют структуру.

## 2. Регистрация обязательна, данные только на сервере

Публично доступны только приветствие/регистрация, вход и необходимые документы/помощь. Нет «попробовать без аккаунта», гостевой карты, тестового пользовательского входа и чтения приложения без регистрации. Настоящий email/OTP создаёт или восстанавливает Core-аккаунт. QA-инструменты сотрудников не являются входом пользователя.

| Состояние | Что видит / куда попадает | Следующее действие |
|---|---|---|
| Первый посетитель `/` | Короткое приветствие с «Создать аккаунт» и «Уже есть аккаунт — войти» | Email → действительный код → серверный аккаунт |
| Посетитель с прямой ссылкой | Регистрация/вход; адрес намерения без личных данных | После входа сервер перепроверяет исходную ссылку и права |
| Первый вход | Создаём минимальный профиль с ником из аккаунта | Сервер подтвердил профиль → Моя карта; остальные поля заполняются позже |
| Ошибка создания профиля | Честная ошибка и «Повторить» | Повтор той же идемпотентной операции, без дубликата и фиктивного успеха |
| Повторный вход | Моя карта либо допустимое исходное приглашение | Продолжить работу, без повторного обучения |
| Аккаунт без 18+ | Разрешённая оболочка/содержимое, без случайных предупреждений | Ограниченное действие → окно реальной проверки |
| Сессия истекла | Повторный вход; неподтверждённый ввод только в памяти текущей формы | Войти → перепроверить права → продолжить или безопасно завершить |
| Нет сети | Нет подтверждения сохранения; повтор после восстановления связи | Не создавать локальную очередь или обещать offline режим |
| Другое устройство | Только данные, подтверждённые сервером | Читать/изменять тот же аккаунт с проверкой revision |

Первый путь: приветствие → регистрация/вход → серверный минимальный профиль → Моя карта с одним понятным действием «Добавить интерес». Нет вопроса «Зачем ты здесь?», выбора цели, обязательного теста, покупки или длинной анкеты. Тесты добровольно открываются из карты/тем. Приглашение возвращает к приглашению после создания профиля и проверки допуска.

**Хранение:** карта, ответы/попытки тестов, дневник, профиль, preferences, dating opt-in, черновики и решения — в серверном доменном хранилище. Не использовать localStorage/IndexedDB/Capacitor storage для пользовательского содержимого, гостевого импорта и durable offline mutations. Временная память формы/запроса допустима только на время текущего процесса; после перезапуска нельзя обещать восстановление непереданного ввода. Auth-механизм остаётся Core; хранение credential — отдельная техническая задача, не основание хранить пользовательские данные локально. Service worker не кеширует private DTO/медиа; публичные статические assets можно кешировать.

Черновик сохраняется на сервере, только когда права и контракт это разрешают. Если сервер отказал или связи нет, явно показать «Не сохранено»; не сообщать об успехе. Нужны идемпотентный retry и CAS, но не локальная долговременная очередь. Переход от существующего local-first к server-only — отдельный согласованный функциональный блок B0, с проверкой текущих RPC и прекращением старых записей, не CSS-правка. Никакого переноса гостевых данных/поддержки старого формата.

Регистрация и минимальная несексуализированная оболочка профиля не требуют предварительного adult proof. Нельзя ради этого снять 18+ со всего profile.save или чувствительной карты: выделить безопасный minimum provisioning endpoint/DTO и проверить его отдельно. Допуски к содержимому, sensitive полям и функциям остаются серверными и запрашиваются по действию.

## 3. Информационная архитектура

| Раздел | Главная потребность | Содержимое первого экрана | Что не размещать здесь |
|---|---|---|---|
| Моя карта `/world` | «Что относится лично ко мне?» | Только мои интересы/границы, результаты и дневник; продолжить начатое | Полный каталог, длинные системные инструкции, дубли настроек |
| Темы `/explore` | «Что это значит и хочу ли я узнать больше?» | Поиск; содержательные направления; редакторская подборка | Копию личной карты, матрицу одинаковых баночек |
| Общение `/community` | «Что обсуждают, где участвовать?» | Лента / Группы / События; один выбранный подраздел | Отдельную вкладку событий в общем доке, все формы создания одновременно |
| Я `/account` | «Как выгляжу, что раскрываю, как управляю аккаунтом?» | Краткий профиль; редактирование; доступ/безопасность; настройки | Длинную анкету и открытые формы удаления/покупки на стартовом экране |
| Знакомства `/dating` | «Хочу ли я знакомиться и с кем?» | До opt-in — красивый экран включения; после допуска — подборка/фильтры/симпатии | Повторный большой hero, внешнюю прокрутку вокруг маленькой карточки |

**Пять вкладок видны всегда:** Моя карта / Темы / Общение / Я / Знакомства. Сохраняем прежний порядок первых четырёх, чтобы не ломать привычные переходы; последний раздел не исчезает при паузе. Подписи на 320px — компактные и проверенные, полные названия в заголовках/доступных именах. Включение знакомств меняет состояние раздела и server discovery, а не число элементов навигации.

Моя карта и Темы — не две ленты рекомендаций. Пример: в Темах читаешь определение «Связывание», в Моей карте видишь собственную отметку «интересно / не пробовал / мои условия». В карте нет общего каталога; в каталоге нет второй копии карты. Пустая карта → «Добавить интерес» → каталог → тема → отметить → возврат в карту. Результаты/дневник — внутри карты; Я — внешний профиль и настройки, без повторной матрицы интересов. Если после прототипирования разделы всё ещё дублируются, переработать состав, а не добавлять вводные абзацы.

Внутренние страницы подсвечивают родителя: тесты/дневник → Моя карта, каталог → Темы, пост/группа/событие/диалог → Общение, профиль/доступ/проверка → Я. На desktop — та же логика в боковой навигации. Полноэкранный редактор может скрыть док, но сохраняет возврат и защиту несохранённого ввода. Не менять существующие URL ради новых подписей.

Симпатии — внутри знакомств; сообщения — в Общении с переходом из взаимности. Участие в сообществе не включает dating автоматически. Публичность обычного профиля/поста и присутствие в подборке — разные разрешения.

## 4. Единый механизм доступа: действие → объяснение → продолжение

**Не раскладывать постоянные тексты «подтвердите 18+», «войдите», «купите» между карточками.** Требование появляется после осмысленного действия. Однако ограниченный контент не загружается и не показывается до серверного разрешения. Разрешённый нейтральный preview и закрытое содержимое — разные вещи.

| Причина ограничения | Окно в момент действия | Успех / отказ |
|---|---|---|
| Нет аккаунта / сессия истекла | Регистрация/повторный вход до приложения, без гостевого режима | Вернуться к allowlisted намерению после серверной проверки; закрыть доступ к private данным |
| Нужен допуск 18+ | «Этот раздел доступен совершеннолетним» + почему и следующий реальный шаг | Сервер перепроверяет статус; самодекларация не выдаёт допуск |
| Нет актуального согласия | Краткое объяснение + точная версия нужного документа, просмотр полного текста | Явное согласие; отказ сохраняет доступ к остальным разрешённым функциям |
| Нужен Premium | Польза именно этой функции, проверенные условия и доступная покупка | Entitlement подтверждается сервером; без фиктивного «Premium включён» |
| Закрытая информация человека | «Запросить доступ» с точным перечнем полей | Запрос → ожидание → разрешено/отказано/отозвано; оплата не заменяет согласие |
| Нет прав на группу/событие | Условия участия и реальное состояние заявки | Заявка/решение без обещания адреса, билета или допуска |
| Сессия/допуск отозваны | Контекстный отказ с возможным повторным входом/проверкой | Немедленно убрать запрещённые данные, сохранив только допустимый собственный черновик |

Последовательность проверок: аккаунт → требуемый возраст/согласия → права на ресурс → entitlement, только если функция платная. Не показывать четыре окна одновременно. После каждого шага перепроверить ресурс; разрешение могло измениться. Не выполнять публикацию, оплату, like или отправку сообщения автоматически после логина: вернуть подготовленную форму и дождаться явного действия. Чтение можно продолжить после проверки.

Контекстный gate — adaptive sheet на телефоне, диалог на desktop. Закрывается Back/Escape/явной кнопкой, фокус возвращается к вызвавшему действию. При недоступном age-провайдере показать это здесь и в Я → Доступ, без бесконечной кнопки «Подтвердить». Служебная QA-выдача остаётся в защищённом операторском интерфейсе и не выдаётся за production proof.

Исключение из скрытия статусов: **реальная потеря/неопределённость сохранения**. Не прятать её ради красоты. Краткая строка «Не сохранено» возле действия/черновика → окно с точным повтором текущего запроса и конфликтом. Idempotency/CAS и защита опасного выхода сохраняются, локальная durable очередь удаляется отдельным B0; при перезапуске доступны только серверные данные. Успешное сохранение — краткая обратная связь, не постоянная техническая панель.

## 5. Цельные сценарии

### J01. Начать и получить первую пользу

Приветствие → регистрация/OTP → серверное создание минимального профиля → Моя карта → добавить интерес → тема → явная запись на сервер → карта с первой отметкой. Связанный блок: welcome, реальный вход, provision profile, allowlisted return, нужный контекстный gate, серверное сохранение и первый результат. Вопрос о цели и гостевой перенос удаляются. Текущий `sign-in-return.ts` разрешает только известные share/compare UUID: расширение возврата — allowlist и проверка безопасности, без произвольных URL. Серверная ошибка на любом шаге не превращается в локальную успешную регистрацию.

### J02. Изучить тему и добавить её в личную карту

Темы → поиск/направление → описание и смысл → «Отметить для себя» → компактный редактор → сохранение → возврат к теме → «В моей карте». Редактор различает отношение, опыт, силу и границу; запрет не считается сильным желанием. Подсказки терминов открываются по нажатию. Каталог показывает знания, карта — личные отметки. Изменение/удаление/конфликт относятся к этому же блоку, а не к будущей отдельной полировке.

### J03. Ответить на вопросы и понять результат

Моя карта/Темы → выбор опросника → короткое описание → вопросы → результат → объяснение вывода → просмотр предлагаемых отметок → явное добавление в карту. Не публиковать ответы, не менять существующие границы автоматически. Незавершённый тест можно продолжить; выход предупреждает только при реальном риске потери. Итог не диагноз и не выдуманная научная оценка. Возврат с результата ведёт к карте/тестам согласно точке входа.

### J04. Вести личные заметки

Моя карта → Дневник → список по времени → новая запись в редакторе → сохранить → запись. Редактирование и удаление с коротким подтверждением; очистка истории в отдельном опасном действии. При неизвестном результате — точный повтор существующей операции. Дневник приватен; публикация, если появится, отдельный явный путь с предпросмотром, не переключатель по умолчанию.

### J05. Оформить профиль и управлять раскрытием

Я → редактировать профиль в связанных коротких шагах → сохранить → «Посмотреть, что видят другие». Ник из аккаунта не дублируется противоречащим полем. Необязательные поля можно пропустить. Фото — существующий защищённый pipeline, с отдельными условиями публикации. Место — город/район, без точных координат.

Я → «Кто видит что» → приватно / по разрешению / публично для конкретного поля → предпросмотр → подтверждение. Запросы доступа → выбор точных полей → согласие → отзыв. Отзыв немедленно влияет на новые чтения. Я → ссылки и сравнения → предпросмотр выбранного содержимого → создать/отозвать ссылку; сравнение двух людей требует согласий обеих сторон. Пара — связанное добровольное приглашение, не второй логин и не автоматическое раскрытие партнёра.

### J06. Читать и участвовать в общении

Общение → Лента → пост → комментарии/реакция/автор. Фильтр и позиция ленты сохраняются при Back. Создание открывает редактор в sheet/workbench: текст → медиа при желании → аудитория/условия → предпросмотр → отправить → фактический статус рассмотрения/публикации. Не разворачивать форму на много экранов ниже ленты. Draft/pending/rejected и исправление отказа — часть того же пути. Жалоба, скрыть, блокировать доступны в меню поста/автора; причины и апелляция — в связанном окне. Не рисовать фальшивые просмотры/реакции.

### J07. Найти группу и участвовать

Общение → Группы → поиск/направление → группа → правила/контент по разрешению → вступить или подать заявку → реальное состояние. Автор: Мои группы → создать → правила/описание → предпросмотр → отправить на рассмотрение → редактировать после решения. Закрытые участники/материалы не показываются в preview. Membership/admin функции подключать только по реальному ACL.

### J08. Найти событие и принять решение

Общение → События → онлайн/рядом/дата → детали → интересуюсь / иду / не иду. Детали: название, организатор, время и часовой пояс, формат, условия, доступное описание, разрешённая ссылка. RSVP и публичность участия — разные решения; анонимность по умолчанию согласно backend. Список участников появляется только при необходимом взаимном согласии, без раскрытия закрытых имён.

Заявка → ожидание → одобрено/отклонено/отозвано. RSVP, одобрение, билет и доступ к адресу — разные статусы. Закрытый адрес/онлайн-ссылка не попадают в общий preview. Внешняя оплата подписана как внешний переход; внутренняя продажа билетов — отдельный финансовый проект, не фиктивная кнопка «Оплачено».

Автор: Мои события → создать → основные данные/время/условия → предпросмотр → отправить на рассмотрение → детали своего события → редактирование/отмена/заявки/безопасная статистика. Внесённые поля не теряются после отклонения или сетевой ошибки. Приёмка обязательно охватывает неавторизованный переход, участника и организатора.

### J09. Включить знакомства и пройти подборку

Постоянная вкладка Знакомства → выключенное состояние: красивая композиция, короткая польза, «Пойти знакомиться», одна ясная фраза «Чтобы смотреть людей, открой свой профиль для знакомств». На этом экране **нет анкет, размытых реальных фото, имён, симпатий или счётчиков**. No-discovery применяется на сервере, не только CSS.

«Пойти знакомиться» → допуски по необходимости → минимально нужные поля публичной анкеты/кого ищу/город → предпросмотр того, что увидят другие → явное «Открыть профиль и знакомиться» → сервер подтвердил opt-in → подборка. Показать точный публикуемый слой, оставить приватные интересы/границы скрытыми. Не требовать неизвестные дополнительные поля без UX-контракта. Пока opt-in не подтверждён, просматривать других нельзя.

**Взаимная видимость:** discovery/peer-card/gallery/likes/filter results в dating доступны только аккаунту с актуальным active opt-in и разрешённым собственным dating-профилем. Сервер проверяет viewer и candidate; прямой URL, кеш, отзыв допуска и другая вкладка не обходят это. Сообщество и обычные профили имеют собственные ACL; не запрещать их целиком из-за выключенных знакомств. Серверное правило и независимый privacy review обязательны перед живым подключением.

Подборка → фото/галерея → внутреннее описание → пропустить/симпатия → следующая карточка; кнопки заменяют свайп. Undo — фактически последний выбор. Фильтры → новая выдача; пустая выдача → изменить фильтры/пауза. Симпатии → профиль → ответ; взаимность → диалог в Общении. Закрытый слой → запрос доступа. «Приостановить знакомства» → сервер отключает присутствие и право смотреть подборку → очистить dating DTO/выдачу → тот же вводный экран **в постоянной вкладке**. Судьбу существующих разговоров объяснять согласно реальному контракту, не удалять автоматически.

Opt-in, preferences и пауза сохраняются на сервере и действуют на всех устройствах. Текущее in-memory V3-переключение/fixture выдача не соответствует новому контракту и подлежит замене, без фиктивного live success.

### J10. Диалог, безопасность и платные функции

Общение → сообщения → диалог; переход из mutual match открывает тот же разговор. Требования допуска/взаимности/блокировки соответствуют server контракту. Отправка имеет pending/error/retry; нельзя рисовать полученное сообщение до ответа. Блокировка/жалоба → подтверждение → безопасный выход, без обхода блокировки из другого маршрута. UI может быть спроектирован до backend, но live отправка запрещена без контрактов.

Платная функция → конкретный paywall → тариф/условия → реальная покупка → проверенный entitlement → возврат к функции. Я → подписка/восстановить/управление. Не переносить цены и free trial из HTML как утверждённые условия. Пока платежи не подключены, фиксировать blocker в ledger; не изображать успех покупки и не запускать неподключённый checkout. Монетизация, privacy и age gate не смешиваются.

### J11. Настройки, восстановление и сотрудники

Я → настройки языка/темы/уведомлений; Я → доступ (18+, согласия, приватность); Я → выход/удаление. Удаление — отдельный ясный путь с перечнем последствий, серверным подтверждением и восстановлением неизвестного результата. Смена аккаунта очищает память форм, gate-намерения, подборку и кеши; данные аккаунта остаются на сервере. Никакого локального пользовательского хранилища.

Сотрудники идут в существующий защищённый operator/AdminWorkspace: очереди → материал → решение/причина → следующий материал. Роли и приватные фото не объединять с consumer UI. Moderation/editorial экран можно улучшать отдельно, но публикация и доступ определяются backend. Служебные тексты/QA-допуски не должны попадать на пользовательские экраны.

| Поверхность | Состав и главное действие | Возврат / состояние |

Toast подходит для краткого результата, не для ошибки, требующей решения. На phone длинная задача — полноэкранный editor, короткая — sheet; desktop editor в удобной рабочей области, не растянутый телефон. Сохранять существующие URL/Back/focus guards. Не наслаивать окна над окнами: gate временно заменяет нужный шаг с сохранением контекста.

## 7. Визуальная дисциплина

- Один выразительный акцент на смысловую область; мягкий glow в фоновой композиции/главном действии. Маленькие карточки — типографика и содержимое, без случайных SVG-орбит, огромных иконок и конкурирующих свечений.
- Баночки используются там, где объясняют личную карту. Подборка людей — фото; события — дата/формат; обсуждения — автор/текст; каталог — редакторская структура. Не превращать всё в одинаковые card-grid.
- Смысловые заголовки вместо «технических» intro-card. Длинные объяснения — помощь по нажатию, кроме действительно необходимых ошибок/последствий.
- Тёплые light/dark токены Claude и Geologica; не повышать декоративную плотность ради «премиальности». Нужны проверенный контраст, ясная иерархия, воздух и размер текста на 320px.
- Motion отвечает на действие: sheet, reveal, выбор, сохранение, свайп. Transform/opacity, reduced motion; без постоянных анимаций мелкого декора.
- Desktop — полноценная композиция с боковой навигацией и полезными колонками; tablet/fold — собственная плотность. Не масштабировать 390px simulator.

## 9. Проверка и передача между сессиями

Перед работой: fresh main/open PR → этот документ → один блок → его Issue/доменные контракты → 2–5 нужных файлов. Никакого чтения всего архива по умолчанию. Перед реализацией записать в Issue: пользователь, точка входа, цель, happy path, отказ/ошибка, выход, surfaces, frontend/backend boundary.

На каждый блок: typecheck/build/существующий smoke + required CI; реальные React-снимки минимум 390/1440 light/dark; 320/768/1024 и короткая высота для материальной адаптивной правки; Back/Escape/focus/клавиатура, reduced motion, no overflow. Сравнить содержимое и композицию с Claude, а не только токены. Проверить весь путь и один существенный отказ. Новые тесты — для рискованных guards, сохранения, доступа/платежей, не для каждого пикселя.

В Issue/PR фиксировать: реализовано; подключено к серверу; проверено в браузере; что осталось макетом; блокеры. Отдельно хранить demonstration ledger. Не закрывать live acceptance по fixture или CI. Документные изменения не требуют сборки приложения и не должны провоцировать Vercel deploy.

**Первый следующий шаг: B0 + UX-контракт B1.** Сначала инвентаризация точек требования входа/18+/согласий и короткая схема сохранения намерения; затем цельный путь первого результата. Не начинать очередную «полировку Моя карта» отдельно от переходов в тему/вход/сохранение. После каждого coherent среза сохранить GitHub handoff ≤12 строк и продолжать следующий готовый шаг без запроса подтверждения каждого PR.

# FetUre V10 — новые проходы 15.10.2026

Источник: новое поручение владельца после пяти кругов Claude, main `84e18f87`. Не повторять старый план целиком. Scope — автономный прототип V10; сервер, SQL и реальные проверки личности не менять.

## Очередь и критерии

1. **Единый профиль и пара.** Один renderer и общие редакторы публичного/расширенного профиля. У пары собственные фото, описание, поля, интересы, закрытый текст/медиа, два кликабельных участника. Общие изменения публикуются с двумя согласиями; личные аккаунты, интересы и доступы не копируются. Все seed-пары имеют двух разрешимых участников. Проверить draft/preview/approve/decline/unlink/reset и отсутствие личных данных в общем профиле.
2. **Единая анкета.** Одинаковый каталог и порядок: местоимения, гендер, ориентация, роль, статус отношений, формат отношений, ищу. Удалить «Не указывать» и местоимения «любые»; отсутствие отметки означает отсутствие ответа. Для гендера/ориентации/формата показать пять базовых чипов, остальные через существующий выбор; максимум пять выбранных. Роль пока один выбранный вариант, пять базовых чипов. Сохранить общий каталог в фильтрах. Трактовка «пять чипов» явно записана; корректируется по уточнению владельца.
3. **Ветки ответов.** Ответ ссылается на стабильный ID родителя, ветка визуально связана как в Twitter; глубокие цепочки не сужают текст бесконечно. Уведомление получает адресат ответа, а не только автор публикации. Удаление/блокировка не теряет потомков; retry не создаёт повторных уведомлений. Публикации и обсуждения используют общую механику.
4. **Опросы.** После выбора варианты не меняют/не отменяют голос. Отдельная ссылка «Отменить голос», без пояснения об изменении. Справа количество людей вместо процентов; кликабельный список проголосовавших, без рамки выбранного варианта. Счётчики и список из одного источника, никаких выдуманных людей для старого агрегата; явно отразить неполноту seed при необходимости.
5. **Техработы.** Управление в панели прототипа как макет админской настройки и отдельный экран, включение/выключение, RU/EN; администратор может выключить режим. Реальная админка/API и серверное ограничение — отдельный перенос, не заявлять их готовыми.
6. **Названия, языки, возраст и defaults.** В пользовательских названиях одна сущность «Интересы» вместо разнобоя «темы/баночки» (баночка остаётся названием визуальной формы в объяснении, не отдельным разделом). Убрать выбор/показ языков профилей/событий/сообществ и языковые фильтры, сохранить переключение интерфейса RU/EN. Текст возраста без связи со знакомствами: «Дата рождения нужна, чтобы подтвердить 18+. Её никто не увидит. Возраст можно показывать в профиле по твоему выбору». Возраст в профиле следует showAge, независимо от знакомств. В стартовых настройках прототипа: знакомства on, автоответ on, персона в паре; явный пустой новый аккаунт остаётся пустым.
7. **Автоматическая фотоверификация — решение.** Объяснить связку live selfie/liveness/сравнение с фото, пороги и ручной разбор неоднозначных случаев, приватность и стоимость. Не внедрять провайдера, не выдавать автоматическое одобрение прототипа за проверку личности/18+.

## Решение: автоматическая фотоверификация

Рекомендуемый сценарий для основного приложения (не внедрён этим проходом):
1. Пользователь осознанно запускает проверку и получает понятное объяснение обработки селфи. Сервер выдаёт одноразовую сессию с коротким сроком; файл из галереи не заменяет live capture.
2. Камера снимает короткое живое селфи. Проверка качества и защита от предъявления чужого снимка/записи (PAD/liveness) — отдельный шаг, не просто поиск лица в кадре.
3. Сравнить лицо 1:1 с конкретной версией главного фото профиля. Успешная проверка подтверждает совпадение лица с фото, но сама по себе не подтверждает паспортное имя, возраст или отсутствие других аккаунтов.
4. Высокая уверенность + успешные проверки подлинности → одобрение. Неоднозначный результат → повтор при хорошем свете или ручной разбор. Отказ не превращать в автоматический бан; дать возможность повторить/обжаловать.
5. Хранить статус, версию проверенного фото и техническую запись результата. Исходные биометрические материалы — с минимальным согласованным сроком хранения, ограниченными правами доступа, без использования для обучения и публикации. Конкретные сроки/договор обработки/применимые юридические требования решить перед внедрением.
6. При замене главного фото прежний значок нельзя автоматически переносить на новое лицо: повторная проверка либо проверка нового фото против допустимого актуального подтверждения. Пара: каждый человек проверяет собственный аккаунт отдельно; общий значок возможен только после проверки обоих и совместного материала. Это не даёт партнёру личный расширенный профиль.

Выбор реализации: для старта оценить готовый проверяемый компонент захвата/PAD/сравнения и интеграцию на сервере; альтернативой остаётся ручная проверка. Собственная детекция «поверни голову» в JS и LLM по одному снимку не дают надёжной защиты от подмены. Конкретный сервис пока не выбран и не подключён, платёжных действий нет.
Бюджет считать как стоимость попытки × число попыток, включая повторы, плюс ручной разбор спорных случаев. До выбора поставщика точную цену не обещать. Для сравнения запросить результаты независимых испытаний, защиту от injection/deepfake, поддерживаемые устройства, удержание данных, регион обработки и поведение при сбое. Ошибочные отказы, несовпадения и доступность проверить на разных устройствах/внешности/освещении.

Основания: [NIST FATE PAD evaluation](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=956456) рассматривает отдельно ошибки пропуска атак и ложные отказы; [NIST SP 800-63B, Biometrics](https://pages.nist.gov/800-63-4/sp800-63b.html) описывает ограничения PAD, доверие к захвату и приватность биометрии. Здесь они использованы как технические ориентиры, не как заявление сертификации FetUre.

## Фактический результат текущей порции

Проходы 1–6 реализованы в автономном V10, проход7 — записка выше. Профиль пары и обычный профиль используют общие renderer/P02/P04/X02/X04; draft → согласие партнёра → публикация. Выбранные языки контента убраны, RU/EN интерфейс сохранён. Пять базовых чипов + каталог; для трёх многозначных полей максимум пять ответов, роль остаётся одиночной. Сроки/пороги фотоверификации не внедрены.

Уведомления ответов в прототипе: входящие текущему пользователю — S.notifs, адресованные другим тестовым пользователям — S.replyDeliveries с to и deep link. Это модель маршрутизации, не настоящая доставка между аккаунтами или push. Адресат родительского ответа и автор материала получают одно уведомление каждый; self/double notifications исключены.

Техработы: переключатель «Техработы (админка)» в панели V10 перекрывает пользовательские экраны. Это макет настройки администрирования; реальная админка, серверный флаг, API 503 и исключения для администраторов требуют отдельного переноса. Режим не заявляется серверной защитой. При выключении пользователь возвращается на прежний экран.

Опросы: seed-голоса приведены к существующим тестовым людям; счётчики и списки берутся из одного roster. Старые агрегаты 34/21/45 не представлены как 100 несуществующих аккаунтов. Изменение вариантов нового опроса создаёт новый roster; неизменённый опрос сохраняет голосовавших.

Проверки: синтаксис всех JS, standalone build; пять contract scripts (4 прежних + followup) PASS; формирование 162 QA routes RU/EN без ошибок; независимое read-only ревью нашло и помогло исправить гонки draft/media, gallery preview и owner history. Реальные multi-account/backend/native действия не проверялись. Browser QA завершён локально в Chromium headless shell: 92 экрана × RU390/EN390/RU320 — No problems found; обычные клики pair editor → save → private text → preview, reply branch, poll → voter list → withdrawal, maintenance on/off прошли на390/768/1440. Скриншоты пары и техработ просмотрены. Найденное перекрытие Send кнопкой V10 на планшете исправлено переносом QA FAB в область sidebar. Локальная подача файлов через Playwright route fulfilment, без живого backend. Полный npm run check PASS, включая typecheck/build,77 unit tests, security/seed/Postgres и5 prototype contracts.

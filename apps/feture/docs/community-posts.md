# C01.1 — текстовые публикации

`Сообщество` читает ленту и собственные публикации через `/api/domain`, Core email session и закрытую `feture_post_command`. Никаких статических людей, счётчиков и постов. Форматы: мысль, история, вопрос; текст до 3000, явно указанное имя до 80 символов. Приватный профиль и ответы опросников не копируются.

Жизненный цикл: `draft` → явное согласие в форме → `pending` → ручная проверка C01.2a → `published`/`rejected`/`hidden`. Клиентской команды публикации/одобрения нет. До одобрения текст видит только автор. Одобренная общая лента требует действующего adult/consent права обеих сторон и отсутствия блокировки/ограничений. `private` — черновик; `public` — заявленная аудитория после проверки. C01.3 добавляет `granted` — только явно выбранные получатели после той же ручной проверки.

Сохранение правок снимает старую публикацию с ленты, возвращает в приватный черновик и требует повторной проверки. Изменения проходят CAS; UUID операции и хеш команды защищают повторы от дубликатов. Повтор возвращает текущую запись, никогда не оживляет удалённый текст. Удаление очищает текст/имя; чтение и список собственных черновиков и удаление остаются доступны при потере adult/consent. Доступ к чужому тексту повторно проверяется при каждом запросе. Cursor: время и ID, 20 записей; никакого total/count скрытых публикаций.

Форма привязана к сессии, не сохраняет чувствительный текст в localStorage, предупреждает перед уходом. После неопределённого ответа команда заморожена для точного повтора; обновление собственных записей помогает проверить конфликт, текст остаётся в форме. Лента обновляется при возврате к экрану и очищается при отказе.

SQL `20261011133134` применён к prelaunch FitT. RLS и grants: только service_role, SECURITY INVOKER; anon/authenticated не читают таблицы и не вызывают RPC. Миграция требует пустую старую таблицу публикаций, проверено live: 0. Данные других продуктов не затронуты.

Проверено: typecheck/build, существующий check, API identity/guard/closed DTO, PostgreSQL ACL/CAS/replay/erase, live rollback без сохранённых fixture документов/профилей/proofs/постов. Chromium fixture: сохранение, отдельное согласие, own pending, правки, удаление; 320/390/768/1024/1440 без horizontal overflow. В браузере ответы подставлены, SQL проверен отдельно. Независимый Sol 6.1 privacy audit, два настоящих аккаунта и native QA открыты. Настоящие документы и production proof пока не настроены.

Решения управляющего реализованы C01.2a. C01.2b жалобы реализованы. Выбранная аудитория реализована C01.3. Выбранный результат теста реализован C01.4; остаются безопасные photo uploads. C01 целиком не закрыт.

## C01.2a — личная проверка публикаций

`/#/operator` → «Публикации»: управляющий с действующим adult/consent правом читает только явно отправленные `pending`/`published`/`hidden` тексты, принимает approve/reject/hide/reopen с CAS и причиной. Собственный пост одобрить нельзя. Reopen возвращает скрытый текст в pending, затем требуется отдельное одобрение. Черновики/удалённые тексты в очередь не попадают. При отзыве/смене роли или сессии экран очищается.

`feture.posts.queue/audit/decide` в существующем `/api/admin` требует личную Core сессию; ключ не заменяет её. RPC `feture_post_review_command` проверяет роль через существующую bound staff функцию и ту же блокировку назначений. SECURITY INVOKER: новые привилегии чтения staff таблиц не добавлены. Роль привязана к поколению Core аккаунта. QA оператор не получает UGC доступ; аудитор читает только журнал с ID/версией/причиной/временем без текста, профиля или ответов. Внутренний журнал дополнительно фиксирует actor/generation без email и сырого текста. Повтор того же решения возвращает текущий статус без восстановления прежней версии; отзыв роли запрещает даже повтор.

SQL `20261011134257` applied. Проверки: полный check, PostgreSQL цепочка submit→approve→hide→reopen→approve→edit→delete, stale generation/CAS/replay/role revoke, self-review denial и auditor privacy; live rollback и grants. Browser fixture: явная отметка перед approve, hide/reopen, очистка при 403, auditor/QA ограничения, 320/390/768/1024/1440 без overflow (API подставлен). Real staff+author аккаунты, независимый Sol 6.1 и native QA остаются. C01.2b жалобы на конкретный пост реализованы; авторские апелляции/права moderator отдельно от manager и очереди с приоритетом — следующие срезы, не заявлены реализованными.

## C01.2b — жалобы на версию публикации

Допустимый читатель отправляет причину и необязательное пояснение (до 1000 символов) к доступному чужому посту. Текст поста не копируется; жалоба сама не скрывает публикацию. Одна открытая жалоба на пост от аккаунта, до пяти новых обращений в сутки. Повторы UUID проверяют хеш команды. Собственный список содержит только статус/причину/версию/время и остаётся доступен при потере adult/consent.

Личный управляющий с актуальными adult/consent читает очередь и явно закрывает обращение либо скрывает ровно указанную версию. Скрытый, удалённый, приватный или изменённый источник не раскрывается; новую версию старой жалобой скрыть нельзя. Автор с ролью управляющего не видит очередь и не принимает решение по жалобам на свой пост. QA оператор не получает доступ; аудитор видит только журнал без пояснения, исходного текста и заявителя. Отзыв роли/смена поколения запрещают также replay.

SQL `20261011140051` и `20261011140835` applied в prelaunch. SECURITY INVOKER, RLS, grants только service_role. Проверено: полный check (23 UI/unit, 26 security, seed, 14 PostgreSQL contracts), CAS/replay/ACL/author-manager privacy и очистка источника, live rollback и grants; Chromium fixture подачи/статуса/явного решения/403 cleanup/аудитора на 320–1440 без overflow. API браузера подставлен. Real accounts/native и независимый Sol 6.1 audit открыты.

## C01.3 — выбранные получатели

Автор сохраняет `plannedAudience=public|granted` и до 20 кодов получателей. Черновик по-прежнему `private`; submit требует отдельного согласия и непустую выбранную аудиторию, затем ручное решение управляющего. Каждый аккаунт получает случайный личный UUID-код через `posts.address`; каталог email/аккаунтов и поиск закрытых профилей не добавлены. Человек сам передаёт код автору. Код — идентификатор получателя, не bearer-доступ: читает только соответствующий Core аккаунт с актуальными adult/consent, без блокировки или ограничения обеих сторон.

`posts.revokeRecipient` закрывает одного получателя сразу, сохраняет остальные доступы и проходит CAS/receipt. Доступ к отзыву сохраняется при потере допуска автора. Правки текста или расширение аудитории проходят save→private draft→submit→review. `posts.rotateAddress` удаляет старый адрес вместе со всеми связанными доступами к выбранным постам; UUID операции делает повтор безопасным. Старые save/rotate/revoke receipts возвращают текущее состояние и не восстанавливают прежние разрешения. Коды видит только автор собственного поста; другим читателям приходит пустой массив. Профиль, карта, raw test answers и profile grants не копируются.

Лента, прямое чтение и отправка жалобы используют одну SQL-проверку post visibility. Управляющий видит явно отправленные selected тексты, но не список кодов; очередь показывает аудиторию. Контекст жалобы открывается только пока источник той же версии всё ещё разрешён заявителю; после отзыва/смены кода исчезает, скрыть новую версию старой жалобой нельзя. Аудитор по-прежнему получает metadata-only журнал.

SQL `20261011141800` applied в prelaunch FitT. SECURITY INVOKER, RLS, grants только service_role; UPDATE(code) адресов нужен для PostgreSQL key-share блокировки при атомарном сохранении. Проверены полный check (23 UI/unit, 27 security, seed, 14 PostgreSQL contracts), закрытые DTO, third-account denial, CAS/replay, отсутствие восстановления при revoke/rotate; live rollback с block/adult revoke/owner revoke/expansion review и прямые grants. Supabase advisors: только ожидаемый INFO RLS без public policies для server-only таблиц.

Chromium headless-shell: real Core memory auth + Posts repository + PGlite, selected draft/save/consent/submit, отдельный manager review, отзыв, смена кода, 320/390/768/1024/1440 без overflow. Adult/consent актор браузера — локальная fixture, настоящие gates отдельно проверены SQL/security. Не является real-account/native acceptance; независимый Sol 6.1 privacy audit открыт. Далее C01.4 — выбранный результат теста через отдельный whitelist; photo uploads отдельным срезом.

## C01.4 — выбранный вывод опросника в личный черновик

На странице завершённого прохождения «Выбрать вывод для публикации» запрашивает `posts.testPreview`: только `id/title/summary` подготовленных выводов, ID/ревизию собственного прохождения, immutable version и хеш preview. Не отправляет наружу сырые ответы, вопросы, средние оценки, уровни, исходные интерпретации или границы. Начальный whitelist — по одному выводу для четырёх точных опубликованных версий: инициатива, эмоциональная связь, новизна и постепенность. Опросник о границах не включён. Все пропуски, новая/изменённая редакционная версия и отсутствующий whitelist дают пустой список, без выдуманного результата. Шаблоны привязаны к полному определению версии, а не только к названию/slug; новые публикации требуют отдельного review и разрешённого шаблона.

Автор выбирает выводы и имя, видит точный текст и отдельно разрешает перенос в личный черновик. Изменение выбора/имени снимает согласие. `posts.fromTest` принимает только IDs, immutable version/revision/hash, имя, аудиторию/коды, явное `consent=true`; готовый текст клиента, ответы/score и лишние поля отклоняются. SQL заново собирает текст из whitelist и проверяет preview hash. Итог — обычная текстовая запись `draft/private`; аудитория и второе согласие на отправку выбираются в «Моих публикациях», далее обычная C01.2a moderation-first. Копия не является диагнозом, доказанным поведением или согласием на опыт.

Копия самостоятельная: удаление прохождения не удаляет текстовый черновик, что явно объясняется перед переносом. Его нужно удалить/отозвать в публикациях. Старый повтор возвращает текущее состояние поста (включая пустую tombstone), не создаёт дубль и не восстанавливает удалённый текст. Неизвестный исход сохраняет тот же command/operationId и блокирует закрытие; явный отказ снимает preview/выбор/согласие. Receipt хранит только actor hash, source ID, выбранные ID, hash команды и версию отдельного согласия; приватен, не входит в пользовательский DTO, feed или moderation queue.

SQL `20261011190651` applied в shared prelaunch FitT. Таблицы имеют RLS без клиентских политик; anon/authenticated не имеют SELECT/EXECUTE, функция SECURITY INVOKER, только service_role. Advisor INFO «RLS Enabled No Policy» ожидаем для закрытых server-only таблиц. Новый индекс PK покрывает account+operation и version+dimension; lock order tests owner → profile совпадает с текущими командами.

Проверено: полный FetUre check; отдельные API и PostgreSQL проверки whitelist/ownership/consent/preview conflict/replay/delete/denied roles; typecheck/build. Chromium fixture 320/390/768/1024/1440: явный выбор, reset consent, точный повтор, удержание окна, conflict cleanup и пустой результат. Live rollback под service_role: preview → copy private draft → replay → delete → replay tombstone, чужой actor denied; после rollback 0 copy receipts. Это не приёмка двух реальных людей/нативных устройств и не независимый privacy audit.


## C01.5a — серверный жизненный цикл фотографии (интерфейс ещё не подключён)

`photo.put/read/remove` в существующем `/api/domain` использует настоящую Core сессию. PUT принимает существующий собственный пост/revision, UUID операции, explicit `consent=true` и base64 до 1 MiB; чужие пути/URL/owner/client metadata не принимаются. sharp 0.35.5 декодирует JPEG/PNG/WebP (без анимации, до 16 MP), поворачивает и заново кодирует JPEG до 1024×1024 и 512 KiB. Исходник, имя файла, EXIF/GPS/ICC не сохраняются. Клиентское уменьшение больших телефонных файлов — следующий срез.

Единственный bucket `feture-post-photos` закрыт, JPEG/512 KiB; restrictive policy запрещает прямые операции anon/authenticated даже при будущих permissive policies. Внутренний path формируется из post/operation UUID и никогда не входит в пользовательский DTO. Нет public/signed URL: `photo.read` проверяет актуальные adult/consent/visibility/revision до и после Storage I/O и отдаёт проверенные JPEG bytes в no-store JSON. Уже полученные читателем байты невозможно отозвать; последующие запросы запрещаются после hide/delete/block/revoke. Сейчас фото читается только автором: публикация фото намеренно закрыта до отдельной staff image-review реализации.

Подготовка serializes по profile→post, фиксирует SHA256 нормализованных bytes/размеры/согласие; лимит 20 новых операций за сутки. Файл immutable, без upsert: потерянный ответ повторно использует тот же ключ и проверяет уже загруженные bytes. Attach/remove возвращают публикацию в private draft и увеличивают revision; stale CAS и изменённый payload отвергаются. Старые receipts возвращают текущее состояние, не восстанавливают удалённую фотографию. Пока управляющий не имеет отдельного просмотра изображения, trigger запрещает перевод фото-поста в published: обычная проверка текста не может его опубликовать.

Удаление/замена фото, удаление поста и cascade профиля записывают opaque path в закрытую durable очередь `feture_photo_gc`, переживающую удаление владельца. Незавершённые загрузки старше суток retire через server-only sweep. PUT/remove/post-delete best-effort очищают до двух объектов; запись очереди удаляется только после успешного Storage DELETE. При недоступном Storage файл остаётся закрытым, работа остаётся в очереди. **Независимое расписание уборки/контроль возраста очереди ещё не подключены**; не заявлять гарантированное физическое удаление за заданный срок, особенно после account erase без новых запросов. Это блокер media acceptance, а не причина открывать bucket.

SQL `20261011193939` applied в prelaunch FitT. Только feture_* таблицы + один FetUre bucket/scoped restrictive policy; общие Core/чужие данные не меняются. RLS, SECURITY INVOKER, RPC/таблицы только service_role. Advisors: нет WARN/ERROR, INFO RLS без client policies ожидаем.

Проверено: полный FetUre check; PostgreSQL ownership/CAS/replay/remove/delete/cascade/outbox/expired upload и запрет text-only approval; API normalization/closed commands/no path DTO/recheck after I/O/no overwrite/failed erasure retained; live service_role metadata lifecycle transaction полностью rollback. **Реальные Storage upload/download/delete через deployed API, два реальных аккаунта, независимый audit и native не проверены.** UI не менялся; возможность выбрать/увидеть фотографию не заявляется. Следующий C01.5b: photo picker/preview/private read + отдельный staff photo review и явное согласие на изображение перед публикацией; затем live Storage и cleanup scheduling.

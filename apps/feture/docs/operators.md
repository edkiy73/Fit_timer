# O02.1/O02.2 — персональные операторы временного QA-допуска
Статус: реализовано GPT-6 High; независимая проверка Sol 6.1 и browser приёмка настоящих аккаунтов остаются. Это частичный O02, не production age verification.

Рабочий экран: `/#/operator`, также доступен из «Аккаунта». Вход через обычный Core аккаунт без общего ключа. В общей админке раздел «Операторы QA» нужен для первого назначения управляющего. Владелец с админ-ключом один раз назначает текущий аккаунт первым управляющим. Повторное первое назначение запрещено. Далее управляющий назначает роли существующим аккаунтам по email:

| Роль | Права |
| --- | --- |
| Управляющий (`manager`) | Назначения/отзывы ролей, QA-допуск и оба журнала |
| Оператор (`qa_operator`) | QA-допуск, отзыв, поиск и журнал QA |
| Аудитор (`auditor`) | Только чтение QA и журнала назначений |

На сервере QA запросы требуют действующей Core device session и текущей SQL роли. `x-admin-key` сам по себе не разрешает QA. Отзыв роли применяется к следующему запросу. Права привязаны к hash даты создания Core аккаунта: удаление и повторная регистрация с тем же email не возвращают роль. Аккаунт без канонического `since` не получает staff доступ. Роли и QA команды используют общий transaction lock: операция, уже получившая lock до отзыва, может закончиться; последующие не пройдут. Последнего управляющего снять нельзя. Назначения используют revision CAS, повтор той же записи не создаёт новое событие. Для изменения выбранной записи hash и email должны совпадать.

У оператора нет доступа к private map/tests/journal и полномочий Core admin. Client actor/role не принимаются. RPC и таблицы недоступны anon/authenticated; service_role может вызвать закрытые RPC только через сервер, прямое чтение журналов/ролей ему не выдано. QA журнал сохраняет hash автора в той же транзакции, что решение; без email, паспортов/селфи или личных текстов. Старые записи без персональной привязки не приписываются новому человеку.

O02.2: отдельный экран `/#/operator` показывает QA-допуски и журнал; управляющему также доступны назначения прав, аудитору — только чтение двух журналов без выдачи, отзыва и поиска по email. Первое назначение управляющего остаётся в общей админке и требует личную сессию плюс ключ. Рабочий транспорт не отправляет ключ, не вызывает Core health/admin actions или bootstrap, проверяет ту же сессию до отправки и после чтения ответа. Возврат к окну перепроверяет SQL роль; отказ в правах очищает экран. Остальные admin-разделы ещё работают по ключу. Журнал решений показывает 25 записей, управляющий видит первые 100 строк ролей; полнотекстовые кейсы/пагинация и общий staff audit — последующие срезы O02. Роли не дают production proof; QA недействителен после перехода среды в live. Обязательные согласия проверяются отдельно.

Проверки: стандартный FetUre check; O02.2: keyless transport allowlist/session fences и UI regression чтения аудитора/очистки после отзыва; focused Core-session/actor/forged token/revoked session test; PostgreSQL bootstrap, роли, CAS, last-manager, audit actor, revoke, запрет прямого доступа, QA/consent/share/live regression. SQL live проверка выполнялась в rollback-транзакции, реальные роли не назначались. Browser/native приёмка и независимый security audit не заменяются этими тестами.

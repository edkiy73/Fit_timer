# FetUre — план до публичного запуска MVP
Дата: 2026-10-10. Статус: план, не подтверждение готовности функций.
Продукт: 18+ пространство для самопознания, глубоких профилей, тестов и сообщества. Знакомства — третий, необязательный блок.

## Что считаем релизом
**Публичный MVP** — не демонстрационный HTML и не просто работающий Vercel: настоящие пользователи могут пройти вход, заполнить/отредактировать приватную карту, изучать тесты, взаимодействовать с реальным сообществом и при желании участвовать в знакомствах; сервер надёжно защищает личную информацию. Функции, ещё не работающие, скрыты, а не изображают успех.

Цель: один полноценный адаптивный веб-сайт (ПК/планшет/телефон) + Android/iOS-клиенты на общем React/TypeScript/AppBase. Одновременная публикация в App Store/Google Play зависит от прохождения правил площадок, **не гарантирована**: сохранять возможность веб-запуска и дистрибуции по разрешённым каналам.

Приоритеты:
- **P0 / must before public** — безопасность, честные реальные базовые функции всех видимых разделов, модерация и эксплуатация.
- **P1 / must if advertised** — расширенные тесты, пары, платная подписка, события, рекомендации и пр.; если не сделано — не показывать как рабочее.
- **P2 / after launch** — оптимизация и расширения без ущерба главной ценности.

## Фаза 0. Решение о каналах распространения, рисках и границах контента (P0, перед тяжёлой разработкой)
- [ ] Зафиксировать позиционирование: самопознание + сообщество как основные функции, dating opt-in; не строить каталог вокруг порно, платных сексуальных услуг или explicit UGC.
- [ ] Письменно определить разрешённые/запрещённые форматы материалов, изображений, разговоров, рекламы и способы исполнения правил.
- [ ] Проверить допустимость конкретной реализации по App Store, Google Play, хостингу, партнёрам по рассылке и условиям оплаты; запланировать web-first fallback, если сторы не допускают продукт.
- [ ] Регистрационный 18+ вход/возрастные ограничения с выбранным допустимым уровнем age assurance, отсутствие доступа несовершеннолетних к закрытым разделам; не собирать избыточные удостоверения без необходимости.
- [ ] Правила сообщества, условия сервиса, privacy policy, контакты для жалоб и запросов, юридическая проверка по рынкам запуска.
**Выход:** согласованная продуктовая граница и политика контента; нет опасного предположения, что модерация или изменение текстов гарантирует одобрение сторов/Stripe.

## Фаза 1. Аккаунты, хранение, инфраструктура (P0)
- [ ] Подключить FetUre серверный AppBase Auth (email-код), отправку писем, API/Vercel secrets, восстановление сеанса; account identity берётся с проверенного сервера, не из поля клиента.
- [ ] Привязать аккаунт к `feture_*` таблицам в общей FitT PostgreSQL, сохраняя отдельные префиксы и явную проверку владения на каждом API.
- [ ] Реализовать надёжную синхронизацию приватной карты между устройствами; офлайн/онлайн, конфликт, повтор запросов, ошибку сети и выход из аккаунта без чужих данных.
- [ ] Дополнить доменную схему недостающими сущностями: проверки/версии тестов, связи профилей, группы, комментарии, реакции, заявки доступа, сообщения, жалобы, блокировки, файлы — только по мере включения функций.
- [ ] Настроить сервисные ограничения запросов, индексирование, миграции, резервное копирование и проверенное восстановление данных (общая база FitTimer требует особой осторожности).
- [ ] Реализовать экспорт данных и полное удаление аккаунта: профиль, интересы, ответы, вложения, посты и личные сообщения согласно опубликованной политике; инициирование из приложения и сайта.
**Выход:** реальный аккаунт сохраняет карту, вход с другого устройства её восстанавливает, чужой аккаунт ничего не читает, удаление подтверждено и работает.

## Фаза 2. Первый вход и личный профиль (P0)
- [ ] Публичный первый экран: что это, для кого, отличия; примеры без откровенных изображений; вход/регистрация.
- [ ] Необязательная пошаговая настройка: ник, имя, место/география без точной координаты, пол/идентичность, местоимения, ориентация, отношения, формат общения, краткое описание и фото; поле можно пропустить.
- [ ] Взрослые участники/пары, понятная возможность не указывать ответ; местоимения и идентичности не должны быть обязательными для использования.
- [ ] Профиль: собственный просмотр, редактирование, фото с обрезкой, описанием, интересами, тестами, статусами и вкладками.
- [ ] Три уровня раскрытия: публично, по запросу/конкретному разрешению, только мне; запрос → согласие → ограниченный просмотр → отзыв/срок действия; реальная серверная проверка.
- [ ] История развития моей карты, понятный прогресс без псевдонаучной оценки; сохранение черновика.
- [ ] Настройки аккаунта, смена/восстановление доступа, выход, заблокированные, конфиденциальность, экспорт/удаление.
**Выход:** полный профиль полезен человеку, который вообще не ищет знакомств.

## Фаза 3. «Баночки», каталог и тесты (P0)
- [ ] Ревизия и редактура 12 направлений/144 интересов: ясные определения по нажатию чипа, синонимы, фильтрация, поиск; не свалка из сотни элементов.
- [ ] Редактирование темы: не исследовано, любопытство, фантазия, хочется попробовать, опыт, условная граница, жёсткая граница, не интересно; сила интереса доступна лишь в подходящих состояниях.
- [ ] Правильные «баночки»: заполнение = степень изученности, а не сила желания; границы и опыт отмечены отдельно. Детали категории и поиск.
- [ ] Реальные **не менее 4–6 качественных тестов** на старте: вопросы, варианты, сохранение/продолжение, результат, понятная интерпретация, пересдача, ручное изменение. Остальные описания из 18 не показывать как доступные, пока нет вопросов.
- [ ] Результаты тестов предлагают уточнить карту, но **не меняют тайно** предпочтения, ограничения и приватность пользователя; никакого диагноза или гарантии «совместимости по психологии».
- [ ] Записи/рефлексия и сохранение развития интересов в личном приватном пространстве.
**Выход:** пользователь без сообщества получает пользу за первые 10–15 минут и может возвращаться к карте.

## Фаза 4. Живое сообщество (P0)
- [ ] Живая лента с настоящими публикациями: текст и при необходимости разрешённые изображения, темы, аудитория/видимость, комментарии, реакции, редактирование, удаление, пагинация.
- [ ] Тематические группы: каталог, вступить/выйти, правила и публикации/обсуждения внутри. Начать с нескольких качественных групп, а не десятков пустых.
- [ ] Поиск тем, групп и участников; подписки/уведомления внутри сайта; настройки показа и скрытия.
- [ ] Блокировка пользователя, жалоба на пользователя/пост/комментарий/фото, скрытие, ограничения на новые аккаунты и спам.
- [ ] Реальная стартовая редакционная библиотека и приглашённая beta-группа; **никакие демонстрационные профили/посты не выдавать за живые**.
**Выход:** новая публикация реально появляется по заданным правам, другой человек отвечает, модератор может немедленно убрать нарушение.

## Фаза 5. Общение и знакомства (P0, если вкладка публично доступна)
- [ ] 1:1 переписка между согласившимися пользователями; запрос начать диалог, ограничения нежелательных сообщений, блокировка, жалоба, удаление/скрытие и непрочитанные.
- [ ] Dating включён **выключенным по умолчанию**; явные согласие/настройка кого искать, какие отношения/формат, примерное местоположение без утечки точного, возраст 18+.
- [ ] Большая карточка с фотографиями и **полным профилем, прокручиваемым внутри карточки**; аккуратный свайп, переход между карточками, лайк/пропуск, взаимное совпадение.
- [ ] Ограничения фильтров и совместимости: нельзя выдавать границы, приватные ответы или тесты без отдельного разрешения; показывать причины рекомендаций без чувствительных утечек.
- [ ] Запрос просмотра закрытого слоя анкеты; отзыв разрешения немедленно действует на сервере.
- [ ] Безопасность: заблокированные/пожалованные не всплывают в ленте и подборке, защита от массового скрейпинга профилей.
**Выход:** знакомство и переход к общению возможны с двумя реальными тестовыми аккаунтами, не открывая приватных данных.

## Фаза 6. Админка и доверие (P0 — до открытия UGC пользователям)
- [ ] В AppBase Admin добавлены доменные инструменты FetUre: управление каталогом, тестами, результатами публикации, тематическими группами и видимыми материалами.
- [ ] Очередь модерации: жалобы, причины решения, блокировка/временные санкции, обработка изображений, журнал действий.
- [ ] Фильтры и превентивные ограничения для недопустимого контента, защита несовершеннолетних, уведомление и удобный канал оперативного обращения.
- [ ] Управление жалобами и обращениями по приватности/удалению, права администраторов, сервисный аудит, защита от ошибок массовой публикации.
- [ ] Настройки доступных функций и модерационных порогов на сервере, не хардкод во фронтенде.
**Выход:** есть реальные люди/процедура, способные ежедневно разбирать жалобы; интерфейс блокировки и удаления проверен.

## Фаза 7. Полноценный сайт и Android/iOS (P0)
- [ ] Финальная UX-проверка PC (от 1280), планшетов (768/1024), телефонов (320/390/430), портрет/ландшафт, 200% zoom, клавиатура, безопасные зоны, длинные тексты и фото, длинная анкета внутри карточки.
- [ ] Веб: производительность, оптимизация изображений, установка как PWA где возможно, реальные ссылки/маршруты, ошибка сети, страницы правил/помощи/удаления, SEO для открытых страниц без раскрытия приватного.
- [ ] Android: сгенерировать Capacitor shell, реальные проверки входа/API/синхронизации/загрузки фото/deep links, иконки/splash, подпись и **одна релизная APK/AAB-сборка** только перед релизом.
- [ ] iOS: shell, настройки разрешений, системный back/keyboard/safe-area, сборка и подпись на macOS/CI, TestFlight при доступности/допустимости приложения.
- [ ] App Store/Google Play: возрастная категория, privacy labels/Data safety, описание без запрещённого контента, политика контента и одобрение **конкретной фактической сборки**; если не допускают — запуск сайта нельзя выдавать за наличие native в магазине.
**Выход:** одинаковые ключевые возможности на ПК/планшете/телефоне и в нативных оболочках; фактическая публикация в сторах — отдельный внешний gate.

## Фаза 8. Финальная эксплуатационная проверка и запуск (P0)
- [ ] Разделить staging и production; секреты/записи логов/аналитику не должны содержать интимные интересы, переписку и приватные фото.
- [ ] Резервные копии, восстановление, мониторинг ошибок, лимиты и бюджет Supabase/Vercel, защита общего хранилища FitTimer, план отката изменений.
- [ ] Прогнать **короткий релизный сценарий**: вход/выход → тест → карта → устройство 2 → пост → комментарий → жалоба/блокировка → знакомства/чат → отзыв доступа → экспорт/удаление.
- [ ] Закрытая beta реальными приглашёнными совершеннолетними пользователями; устранить критические проблемы и обеспечить поддержку/обратную связь.
- [ ] Убрать все демо-данные с публичных экранов и неработающие действия; честно обозначить функции, доступные после релиза.
- [ ] Реальная редакционная стартовая активность в сообществе (публикации и несколько модерируемых групп), публичная документация/контакты.
**Выход:** нет известных P0-багов и приватных утечек; доступна процедура реагирования на жалобы/инциденты; можно открывать регистрацию.

## Что осознанно НЕ блокирует первый релиз (P1/P2)
- Премиум и платежи: сначала проверить поддерживается ли вообще такой продукт конкретными провайдерами. Stripe **явно ограничивает сексуально ориентированные знакомства и adult-сервисы**; не закладывать оплату без согласования. Если подписка будет в первой версии — это отдельная обязательная платежная/restore/отмена фаза, включая правила Apple/Google.
- Все 18 тестов полностью, AI-интерпретации, AI-рекомендации, расширенная история и экспорт PDF.
- Парные связанные профили, сложные многоуровневые связи и групповые чаты — если не заявляем их при запуске; прежде чем показывать парный режим как рабочий, сделать двустороннее согласие и раздельное управление приватностью.
- События, встречи, карта мероприятий, геолокация в реальном времени.
- Продвинутое ранжирование, рекомендации на ML, видео, прямые эфиры, рейтинг активности, виртуальные подарки.
- Push как отдельная система (для MVP достаточно in-app уведомлений/нормального непрочитанного, а публичные email-уведомления опциональны).
- Любые десятки UI snapshot/E2E tests, дублирующие ручную проверку меняющегося дизайна.

## Последовательность реализации короткими задачами
1. **M1 — Живой аккаунт**: email OTP, серверное хранение карты, импорт local-first, безопасный выход/удаление.
2. **M2 — Реальный личный мир**: профиль, фото, аудитории и запросы доступа, исправные баночки и история.
3. **M3 — Настоящие тесты**: первые 4–6; результат и явное обновление карты, редактор тестов в админке.
4. **M4 — Сообщество и модерация**: посты, комментарии, группы, жалобы, блокировки, админская очередь.
5. **M5 — Реальные знакомства и сообщения**: opt-in, карточки, профили, фильтры, совпадения, разрешённый чат.
6. **M6 — Платформы и release**: PC/tablet/phone polishing, Android/iOS shell, безопасность/правила, закрытая beta и production.

Каждый M1–M5 — несколько коротких PR по одной законченной функции. Не переписывать AppBase Core ради одного UX изменения; монорепозиторий держать изолированным.

## Минимальный контроль качества
Каждый PR: TypeScript typecheck + production build + существующая короткая smoke-проверка. **Новые** автоматические тесты лишь для опасной стабильной логики: авторизация/разглашение/синхронизация/миграция/удаление/платежи. Изменение вёрстки: быстрая ручная проверка ключевых ширин, без тестов на каждый компонент. Полный ручной критический сценарий — перед публичным релизом. APK/IPA — только на этапе M6 или по отдельному запросу.

## Открытые решения перед M1
1. География первого публичного запуска: определяет юридическую проверку, платежи и age assurance.
2. Глубина контента и формат UGC: доступность в App Store/Google Play может ограничить функциональность.
3. Есть ли в первой версии монетизация? Предлагается **нет**, пока провайдер не подтвердит допустимость.
4. Обязателен ли режим связанных парных профилей при старте? Предлагается P1; личный статус отношений остаётся P0.
5. Сколько тестов подготовим редакционно до запуска? Предлагается 4–6, остальные пока скрыть.

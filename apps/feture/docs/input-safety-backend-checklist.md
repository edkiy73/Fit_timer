# FetUre — безопасность пользовательского текста: что обязан сделать бэкенд

**Статус:** обязательный чек-лист к переносу прототипа V10 в React/TypeScript-приложение и к подключению реального бэкенда (Core + Supabase/PostgreSQL). Основание: проверка опасного ввода, `docs/design-reference/V10-HOSTILE-INPUT-AUDIT-2026-10-16.md`.

**Принцип.** Клиентская защита — только удобство и последний рубеж: её обходит любой запрос мимо интерфейса. Каждое правило ниже обязано выполняться **на сервере при записи**, а на клиенте — при выводе. Никогда не доверять тому, что «клиент уже проверил».

## 0. Что уже сделано на фронте прототипа V10 (для справки и переноса)

| Мера | Где в прототипе | Как переносить в React-приложение |
|---|---|---|
| Экранирование при выводе: `esc()` во всех HTML-шаблонах (имена, названия, цены, города, почта, заголовки листов/диалогов/экранов, атрибуты `aria-label`, `data-p`/`data-v`) | `prototype/v10/*.js` | React экранирует текст сам. **Не использовать** `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`; добавить lint-правило `react/no-danger` |
| Защитный слой `safeInline()` для слотов «заголовок/подзаголовок/текст» (Bottom Sheet, диалог, заголовок экрана, строка списка, пустое состояние): удаляет `script/iframe/style/meta/base/form`, `on*`, `javascript:`/`data:`-URL, `position:fixed`; закрывающие теги не выходят за слот | `core.js` | Не переносить: в React таких слотов нет. Если понадобится показывать серверный HTML — только через проверенный санитайзер (DOMPurify, строгий allowlist) |
| `cleanText()` при вводе и в `esc()`: удаляет управляющие символы, bidi-переопределения, невидимые символы, ограничивает серии комбинируемых знаков | `core.js` | Вынести в общий пакет Core и использовать **и на клиенте, и на сервере** (одна реализация и один набор тестов) |
| Markdown: сначала `esc()`, ссылки только `http(s)`, `rel="noopener noreferrer nofollow"`; вставка в редактор — только `text/plain` | `ui.js` (`md()`, `mdInline()`, редактор) | Рендерер Markdown с `rehype-sanitize`/эквивалентом, без сырого HTML, ссылки http(s), изображения только из своего хранилища |
| `data-p`/`data-v` экранируются | `core.js` и др. | В React не нужно (props) |

## 1. Нормализация и валидация текста при записи (обязательно)

Применять ко **всем** текстовым полям до сохранения; ответ API возвращает уже нормализованное значение.

1. **Юникод:** привести к NFC; отклонить невалидный UTF-8 и одиночные суррогаты; считать длину в **кодовых точках**, а не в UTF-16 (лимиты совпадают с UI, таблица ниже).
2. **Удалить/отклонить:** управляющие символы C0/C1 (кроме `\n` и `\t` в многострочных полях), `U+200B, U+200E, U+200F, U+061C, U+202A–U+202E, U+2060–U+2064, U+2066–U+206F, U+FEFF, U+FFF9–U+FFFB`, недопустимые noncharacters. `U+200D`/`U+200C` — только внутри эмодзи-последовательностей/письменностей, где они значимы.
3. **Комбинируемые знаки:** серия `\p{M}` не длиннее 4 (иначе обрезать); блокировать «Zalgo» до записи, а не при показе.
4. **Пробелы:** для однострочных полей схлопнуть пробелы и убрать переводы строк; обрезать края.
5. **Идемпотентность:** `normalize(normalize(x)) === normalize(x)` — проверить property-тестом.
6. **Не хранить экранированный текст.** В БД — исходный (очищенный) текст; экранирование — только при выводе. Иначе двойное экранирование и дыры при смене канала вывода.
7. **Отклонять, а не молча менять**, идентификаторы (ник, handle): вернуть `422` с кодом ошибки.

### Контракты полей (серверные лимиты = лимиты форм прототипа)

| Поле | Правило |
|---|---|
| Ник (handle) | `^[A-Za-z0-9_.]{3,20}$`, уникален без учёта регистра, зарезервированные слова, проверка визуально похожих символов (confusables) |
| Название пары | 2–60, без `<` `>` и без разметки |
| Название сообщества | 3–50, без `<` `>`; уникальность без учёта регистра |
| Название события | 5–80, без `<` `>` |
| Заголовок обсуждения | 5–120 |
| О себе / расширенный профиль | ≤500 / ≤1000, Markdown |
| Описание сообщества / события | ≤500 / ≤1500, Markdown |
| Правила сообщества | ≤1000 суммарно, построчно |
| Пост / вопрос опроса / вариант | ≤1000 / ≤200 / ≤80 (2–10 вариантов) |
| Комментарий / ответ / сообщение чата | ≤1000 / ≤1000 / ≤2000 |
| Текст обсуждения | ≤3000 |
| Заявка в сообщество / ответ организатору | ≤300 |
| Объявление / причина отмены / жалоба | ≤500 / ≤300 / ≤500 |
| Город | только из каталога (id). Пользовательский город — отдельной записью с очисткой, ≤60 и модерацией; клиенту возвращать название из каталога, не текст запроса |
| Цена события | **структурно** (сумма + валюта + тип: бесплатно/на месте/билет), а не строка |
| Место, площадка | ≤200, очищенный текст |
| Почта | `email` по RFC, ≤254, нормализованный регистр домена |

## 2. Ссылки и адреса

- Хранить только **абсолютные `https://`** ссылки (ссылка встречи, внешний билет, ссылки в Markdown). Разбирать через `URL`, отклонять `javascript:`, `data:`, `vbscript:`, `file:`, `blob:`, схемы без `//`, учётные данные в адресе, IDN-омографы без punycode-проверки. Длина ≤400.
- Для предпросмотра ссылок на сервере — защита от SSRF (запрет приватных адресов и `localhost`, лимит редиректов и размера, таймаут).
- Изображения и видео — только из собственного хранилища (подписанные URL); внешние `src` не принимать. Проверять MIME по содержимому, переобрабатывать изображения (удалять EXIF/геометки), ограничить размер и размеры.

## 3. Идентификаторы

- Все `id` (сообщество, событие, пост, обсуждение, человек) — непрозрачные серверные (UUID/ULID). Никогда не строить id из пользовательского текста. Валидировать path/query-параметры по шаблону до обращения к данным.
- Права доступа проверять по id и владельцу на сервере (RLS Supabase), не по содержимому запроса.

## 4. API и БД

- Только `application/json`, строгая проверка схемы (zod/JSON Schema): лишние поля отклонять, типы не приводить молча.
- Только параметризованные запросы; в Supabase — RLS на каждой таблице `feture_*`. Никакой конкатенации SQL. Для `LIKE`/поиска экранировать `% _ \`.
- Лимиты тела запроса, частота запросов, идемпотентные ключи для публикаций.
- Серверные шаблоны писем, push и превью (OG): подставлять переменные **только как текст**, экранировать для соответствующего канала (HTML-письмо, plain-текст push). Название сообщества/событию в теме письма — очищенное, без переводов строк (защита от инъекции заголовков).
- Логи: не писать содержимое пользовательских текстов в логи как есть; переводы строк экранировать (log injection).

## 5. Заголовки ответа и CSP (боевой сайт на Vercel)

- `Content-Security-Policy`: `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'; img-src 'self' data: blob: <хранилище>; style-src 'self'; connect-src 'self' <API>`. В React-сборке Vite инлайн-скриптов нет — `unsafe-inline` не нужен. (Прототип V10 — один HTML с инлайн-скриптом, поэтому CSP к нему применить нельзя.)
- Когда в коде не останется `innerHTML`, включить `require-trusted-types-for 'script'`.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` без лишнего, `Cross-Origin-Opener-Policy: same-origin`.
- Cookie сессии: `HttpOnly; Secure; SameSite=Lax`.

## 6. Модерация и наблюдаемость

- Автоматически помечать на проверку названия/описания с разметкой, ссылками на неизвестные домены, повторяющимися комбинируемыми знаками.
- Метрика «значение изменено нормализацией» по полям: всплеск — сигнал атаки или ошибки клиента.

## 7. Тесты, которые должны быть в CI бэкенда

1. Корпус опасных строк из QA-режима (`prototype/v10/qa.js`, `nospPayload`): для каждого текстового поля записать → прочитать → убедиться, что значение нормализовано и не содержит `<script`, `onerror=`, `javascript:` там, где поле «без разметки».
2. Property-тесты `normalize` (идемпотентность, длина ≤ лимита, отсутствие запрещённых кодовых точек).
3. Контракт идентификаторов и лимитов по таблице раздела 1.
4. Для React-клиента: тест, что подстановка корпуса даёт 0 выполнений (`window.__x` не вызывается) и 0 внедрённых элементов — то же, что делает `tools/prototype-v10-nospace-audit/sec.mjs`.

## 8. Чего нет в прототипе и что нужно решить при переносе

- Прототип не имеет сервера: все проверки там — клиентские. Ни одна из них не заменяет раздел 1.
- Решение по политике имён: запретить ли `<` и `>` в названиях полностью (рекомендуется для названий, ников, городов) или допускать и всегда экранировать. Рекомендация: запретить в названиях, разрешить в свободном тексте (посты, описания) — там экранирование и Markdown.
- Политика для эмодзи с ZWJ и письменностей, где `U+200C/U+200D` значимы (персидский, индийские): отдельный allowlist вместо общего удаления.

# Политика сборок и развёртываний AppBase — 2026-10-08

## Цель
Уменьшать платные сборки Vercel без риска пропуска изменений рабочего приложения. Касается FitTimer, UnMute, Task Mini и каждого нового приложения на AppBase.

## Когда собираем
- Изменения рабочего кода приложения, его API, ресурсов, сборочной конфигурации, зависимостей и окружения.
- Изменения общего `packages/**` (кроме тестов), `shared/**`, `config/**`: все потенциально затронутые приложения.
- Любой неизвестный путь, неудачное сравнение Git, удалённый/недоступный предыдущий коммит: сборка обязательна.
- Объединённые изменения приложения в `main`: производственная сборка должна пройти даже после десятков промежуточных коммитов.

## Когда пропускаем
- Только документация (`*.md`, `docs/**`, `.ai/**`).
- Только изолированные тесты (`tests/**`, `*.test.*`, `*.spec.*`) и GitHub Actions.
- Изменения других приложений в `apps/**`.
- `templates/**` — шаблоны будущих приложений (уже созданные приложения не затронуты).
- Мобильные оболочки `android/**`, `ios/**` внутри приложения не вызывают веб-развёртывание; соответствующая мобильная CI остаётся обязательной.

## Промежуточные коммиты и Preview
- Разработка через небольшие ветки/PR; нельзя отключать обязательные проверки GitHub Actions.
- Для сокращения *числа* Preview-развёртываний нужно отдельно управлять Git/Preview-политикой Vercel: один лишь `ignoreCommand` не объединяет десять коммитов в одну сборку.
- Пока Preview в настройках проекта не отключаем автоматически: это может лишить PR тестового окружения. Решение об отключении Preview принимается отдельно для конкретного проекта.
- После одобрения PR объединять изменения в `main` одним squash-коммитом, когда это уместно.
- Нельзя использовать текст `[skip vercel]` для отключения сборки изменений рабочего кода. Состояние файлов важнее текста коммита.
- Для ручного перевыпуска приложения используйте Vercel Redeploy/ручной запуск, а не фиктивный коммит.

## Техническая реализация
- У каждого приложения: `apps/<app>/scripts/vercel-ignore.mjs` и `ignoreCommand` в `vercel.json`.
- В Vercel у проекта `Root Directory = apps/<app>`, включены `Include files outside the root directory` и `Skip Unaffected Projects`.
- Игнорирование: код 0 — пропустить, код 1 — выполнить сборку. Ошибки Git всегда ведут к сборке.
- `VERCEL_GIT_PREVIOUS_SHA` при наличии — единственная база сравнения, чтобы учесть накопленные изменения; если Git не содержит этот SHA — собирать.
- Для новых приложений стартер должен добавлять аналогичную фильтрацию, иначе новое приложение будет собираться от чужих коммитов.
- В CI тестировать пути и критический сценарий: один коммит меняет только тесты, следующий меняет Core; Core должен быть обнаружен даже если предыдущая сборка была пропущена.

## Расходы
- Standard build machine до подтверждения, что Basic достаточно.
- Отключён немедленный параллельный запуск сборок.
- Бюджет $10 на дополнительные расходы установлен вручную. `Pause Production Deployments` не включаем в уже превышенном бюджете без отдельного согласования, чтобы не повлиять на действующие приложения.
- После изменений проверять логи Vercel: `Ignored Build Step command returned exit code 0`; отсутствие ошибки сборки само по себе не доказывает пропуск.
- Контроль статистики затрат и числа сборок по следующему расчётному периоду.

## Ограничения
Правила намеренно осторожны. Неизвестные пути запускают сборку. Тестовые изменения, являющиеся входными данными для продакшен-сборки, необходимо внести в исключения из списка пропусков. Для сложных зависимостей будущих приложений требуется явный граф зависимостей, а не гадание по названиям файлов.

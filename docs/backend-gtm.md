# Fit Timer: бэкенд, нативная сборка и запуск

Разбор по трём блокам: архитектура сервера и защита контента, мобильная обёртка
с фоновыми службами, продукт и выход на рынок.

Документ опирается на то, что **уже написано в `index.html`**, а не на абстрактное
приложение. Где в коде есть готовый шов — сказано, где его нет — тоже.

---

## 0. Что в коде уже стоит под сервер

Прежде чем проектировать бэкенд, стоит признать: половина стыков уже заложена.
Это меняет план — не «переписать хранилище», а «подключить адаптер».

| Что | Где | Состояние |
|---|---|---|
| Шов синхронизации | `SYNC.adapter`, `SYNC.push()` | Пустой намеренно, `adapter: null` |
| Версионирование документов | `docMeta[key] = {rev, at, schema}` | Работает, `SCHEMA_VERSION = 1` |
| Очередь на отправку | `outbox`, схлопывается по ключу | Работает |
| Первый переезд на сервер | `markAllForSync()` | Работает |
| Личность | `identity = {accountId, deviceId, email, linkedAt, consents}` | Работает, `accountId` свой у каждого профиля |
| Согласия с версией | `recordConsent()`, `CONSENT_VERSION` | Работает |
| Список синхронизируемого | `SYNC_KEYS = ['customPrograms','stats','progWeights']` | Фото исключены намеренно |
| Полное удаление данных | `wipeAccount()` по `PROFILE_KEYS` / `GLOBAL_KEYS` | Работает |
| Формат обмена программами | `parseProgramText` / `programToText` | Работает, на нём же стоит каталог |
| Код программы для ссылки | `FIT1.` + base64 JSON | Работает |
| Тарифы | `PRICES`, `userCurrency()`, `CUR_BY_REGION` | Витрина без оплаты |
| Каталог | `STORE_ITEMS` (20 программ), поле `pro: true` | Зашит в файл |
| Заглушка премиума | `#siLock`, `premiumGate()` | Работает |

### Три вещи, которые надо было починить до первого подключения сервера

> Все три починены (коммит «Синхронизация: единица — программа, значения через await,
> profileId вместо accountId»). Разбор оставлен: он объясняет, почему сделано именно так.

**1. `SYNC.push()` отправит промисы вместо значений.**

```js
value: kvGet(pk(o.key))   // kvGet асинхронная — это Promise, а не строка
```

Сейчас не стреляет только потому, что адаптера нет. Правильно — собрать значения
`await`-ом до формирования пакета:

```js
const payload = [];
for(const o of batch){
  payload.push({key: o.key, rev: o.rev, at: o.at, schema: SCHEMA_VERSION,
                profileId: identity.accountId, deviceId: identity.deviceId,
                value: await kvGet(pk(o.key))});
}
await SYNC.adapter.push(payload);
```

**2. `identity.accountId` — это не аккаунт, а профиль.**

В коде честно написано: «`accountId` — свой у каждого профиля». Но на сервере
аккаунт будет один (почта, подписка), а профилей внутри несколько. Если поле
уедет на сервер под именем `accountId`, путаница станет схемой БД и будет жить
годами. Переименовать в `profileId` **до** первого запроса — правка на десять строк;
после — миграция с данными у всех.

**3. Односторонний `push` — это ещё не синхронизация.**

`SYNC` умеет только отправлять. Нужен `pull` и разрешение конфликтов (ниже).
Пока их нет, «синхронизация между устройствами» в тарифе Athlete Premium
продавать нельзя — она не существует.

### Один настоящий изъян модели синхронизации

`customPrograms` — **один документ на все программы**. Пока устройство одно, это
неважно. Как только их два: телефон правит программу А, планшет — программу Б,
у обоих `rev` вырос на единицу, на сервере они конфликтуют целиком, и любое
разрешение теряет чью-то правку.

Чинить надо не на сервере, а в ключах. Документ — программа, а не список программ:

```js
// было:  SYNC_KEYS = ['customPrograms', 'stats', 'progWeights']
// стало: ключи документов
//   program:<id>   — одна программа, rev на программу
//   stats          — один документ (пишется только «моим» устройством в момент финала)
//   progWeights    — один документ
//   index          — {programIds: [...], order: [...]} для удалений и порядка
```

Локально `customPrograms` может остаться как есть — меняется только то, что
`saveDoc` кладёт в `outbox`. Это в чистом виде правка слоя синхронизации,
интерфейса она не касается.

## Блок A. Бэкенд и защита контента

### A0. Выбор стека, коротко и с обоснованием

**PostgreSQL, не MongoDB.** Не из вкусовщины:

- Половина данных реляционна по природе (аккаунт → профили → доступы → подписки),
  и целостность тут важнее гибкости: «выдал тело программы человеку без права» —
  это деньги, а не косметика. `FOREIGN KEY` и транзакция закрывают целый класс ошибок.
- Вторая половина — документы (тело программы, статистика). `jsonb` хранит их
  ровно так же, как Mongo, с индексами по полям (`GIN`) и без второго хранилища.
- Row Level Security даёт второй рубеж на случай ошибки в коде приложения:
  даже забытый `WHERE account_id = ...` не отдаст чужое.
- 152-ФЗ проще выполнять на управляемом PostgreSQL в РФ (Yandex Cloud, Selectel),
  чем на MongoDB Atlas.

**Рантайм.** Node.js (TypeScript) — потому что `parseProgramText` и `programToText`
уже написаны на JS и должны работать **на сервере тем же кодом**. Это не удобство,
это устранение целого класса расхождений: если серверная валидация ответа ИИ
пользуется другим парсером, чем клиент, форматы разойдутся, и никто этого не заметит,
пока у человека не сломается программа. Вынести обе функции в `shared/program-format.js`,
подключать и туда, и туда.

**Хранение файлов.** S3-совместимое (Yandex Object Storage / Cloudflare R2) для
обложек каталога и, если однажды понадобится, для фото. В БД — только ключи.

**Оплата.** RevenueCat поверх App Store / Google Play (и отдельная интеграция
с RuStore для РФ). Свой биллинг цифровых подписок в мобильных сторах запрещён,
а валидация чеков и вебхуки продления — та работа, которую не надо писать самому.

### A1. Схема базы данных

Ниже — PostgreSQL. Комментарии объясняют неочевидные решения; поля, назначение
которых видно из имени, не комментируются.

```sql
-- ============ Аккаунт и личности ============

-- Аккаунт = единица авторизации и оплаты. В приложении это глобальный ключ `account`.
CREATE TABLE accounts (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email         citext UNIQUE,              -- NULL, пока человек не завёл почту
  email_at      timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  deleted_at    timestamptz,                -- мягкое удаление на 30 дней, потом жёсткая чистка
  locale        text,
  region        text,                       -- для валюты; совпадает с CUR_BY_REGION в клиенте
  data_region   text NOT NULL DEFAULT 'ru'  -- 'ru' | 'eu' — где физически лежат данные
);

-- Профиль = человек внутри аккаунта (несколько пользователей на одном телефоне).
-- Соответствует identity.accountId в коде клиента; переименовать в profile_id.
CREATE TABLE profiles (
  id            uuid PRIMARY KEY,           -- id генерирует клиент (newId), сервер его принимает
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  name          text NOT NULL,
  -- пол и дата рождения нужны только для подбора нагрузки; при желании их можно
  -- вообще не хранить на сервере, а передавать в запрос к ИИ и забывать
  gender        text CHECK (gender IN ('m','f','')),
  birth_date    date,
  created_at    timestamptz NOT NULL DEFAULT now(),
  deleted_at    timestamptz
);

CREATE TABLE devices (
  id            uuid PRIMARY KEY,           -- deviceId из клиента
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  platform      text,                       -- 'android' | 'ios' | 'web'
  push_token    text,
  last_seen_at  timestamptz NOT NULL DEFAULT now()
);

-- Согласия — единственное, что не восстанавливается ничем. Только вставка, без UPDATE.
CREATE TABLE consents (
  id            bigserial PRIMARY KEY,
  profile_id    uuid NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  kind          text NOT NULL,              -- 'terms' | 'privacy' | 'health'
  version       int  NOT NULL,              -- CONSENT_VERSION на момент согласия
  at            timestamptz NOT NULL DEFAULT now(),
  ip_hash       text,                       -- хеш, не сам адрес
  UNIQUE (profile_id, kind, version)
);

-- ============ Синхронизация ============

-- Универсальное хранилище документов: ровно то, что ждёт SYNC.adapter.
-- Ключ вида 'program:<id>' | 'stats' | 'progWeights' | 'index'.
CREATE TABLE sync_docs (
  profile_id    uuid NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  key           text NOT NULL,
  rev           int  NOT NULL,              -- монотонная редакция, растит клиент
  server_seq    bigint NOT NULL,            -- порядковый номер записи на сервере, для дельта-pull
  schema        int  NOT NULL,
  value         jsonb NOT NULL,
  deleted       boolean NOT NULL DEFAULT false,  -- «надгробие»: удаление тоже документ
  device_id     uuid,
  updated_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (profile_id, key)
);
CREATE INDEX ON sync_docs (profile_id, server_seq);

-- Последовательность на профиль: pull запрашивает «всё, что новее моего курсора»
CREATE TABLE sync_cursors (
  profile_id    uuid PRIMARY KEY REFERENCES profiles(id) ON DELETE CASCADE,
  seq           bigint NOT NULL DEFAULT 0
);

-- ============ Тренеры и программы ============

CREATE TABLE trainers (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id    uuid NOT NULL UNIQUE REFERENCES accounts(id) ON DELETE CASCADE,
  handle        citext UNIQUE NOT NULL,     -- '@lena.doma', как в STORE_ITEMS.by
  display_name  text NOT NULL,
  bio           text,
  links         jsonb NOT NULL DEFAULT '[]',-- соцсети, телеграм — лидогенерация тренера
  verified_at   timestamptz,                -- бейдж экспертности выдаётся руками
  created_at    timestamptz NOT NULL DEFAULT now()
);

-- Программа как сущность: витрина, автор, права. Тело — в версиях.
CREATE TABLE programs (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  trainer_id    uuid REFERENCES trainers(id) ON DELETE SET NULL,
  slug          text UNIQUE,                -- 'slim-tabata', как STORE_ITEMS.id
  visibility    text NOT NULL,              -- 'public' | 'private' | 'draft'
  is_protected  boolean NOT NULL DEFAULT false,  -- тело только по праву доступа
  requires_plan text,                       -- NULL | 'athlete' — премиум-программа каталога
  -- Витринные поля. Дублируют то, что лежит в теле, СПЕЦИАЛЬНО: витрина обязана
  -- отвечать без чтения тела, иначе защищённую программу нельзя показать в списке.
  title         text NOT NULL,
  gives         text,                       -- «что даёт», поле gives в STORE_ITEMS
  goal          text NOT NULL,              -- ключ из OPT_GOAL (cat в STORE_ITEMS)
  level         text NOT NULL,              -- из OPT_LEVEL
  minutes       int,
  days_count    int,
  ex_count      int,
  equipment     text[] NOT NULL DEFAULT '{}',
  cover         jsonb,                      -- параметры SVG-обложки, не картинка
  downloads     int NOT NULL DEFAULT 0,
  rating        numeric(2,1),
  published_at  timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON programs (visibility, goal, level) WHERE published_at IS NOT NULL;

-- Тело программы версионируется: у клиента тренера не должна поменяться программа
-- под ногами, когда тренер правит её для следующего.
CREATE TABLE program_versions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  program_id    uuid NOT NULL REFERENCES programs(id) ON DELETE CASCADE,
  version       int NOT NULL,
  body          jsonb NOT NULL,             -- программа в формате клиента (plans/exercises)
  body_text     text,                       -- тот же контент через programToText — для ИИ и диффов
  checksum      text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (program_id, version)
);

-- ============ Доступ и ссылки ============

-- Право на программу: покупка, подписка, ссылка тренера. Одна таблица — один ответ
-- на вопрос «можно ли отдать тело», и его не надо собирать из трёх мест.
CREATE TABLE entitlements (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  program_id    uuid NOT NULL REFERENCES programs(id) ON DELETE CASCADE,
  source        text NOT NULL,              -- 'link' | 'subscription' | 'purchase' | 'author'
  granted_by    uuid REFERENCES trainers(id),
  link_id       uuid,                       -- какая ссылка дала право — для отзыва пачкой
  version_pin   int,                        -- зафиксированная версия; NULL — всегда свежая
  granted_at    timestamptz NOT NULL DEFAULT now(),
  revoked_at    timestamptz,
  expires_at    timestamptz,                -- курс на 8 недель — тоже ссылка с концом
  UNIQUE (account_id, program_id, source)
);

-- Deep link: fittimer.app/p/{token}
CREATE TABLE access_links (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  token_hash    text NOT NULL UNIQUE,       -- хранится ХЕШ токена, не токен
  program_id    uuid NOT NULL REFERENCES programs(id) ON DELETE CASCADE,
  trainer_id    uuid NOT NULL REFERENCES trainers(id) ON DELETE CASCADE,
  mode          text NOT NULL,              -- 'personal' (1 клик) | 'group' (N клиентов)
  max_uses      int,                        -- NULL = без предела
  uses          int NOT NULL DEFAULT 0,
  version_pin   int,
  expires_at    timestamptz,
  revoked_at    timestamptz,
  note          text,                       -- «Марина, курс с 3 марта» — для списка тренера
  created_at    timestamptz NOT NULL DEFAULT now()
);

-- Кто по какой ссылке пришёл — и виральная петля, и трассировка утечки
CREATE TABLE link_claims (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  link_id       uuid NOT NULL REFERENCES access_links(id) ON DELETE CASCADE,
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  claimed_at    timestamptz NOT NULL DEFAULT now(),
  first_seen_ip_hash text,
  UNIQUE (link_id, account_id)
);

-- ============ Подписки ============

CREATE TABLE subscriptions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  plan          text NOT NULL,              -- 'athlete' | 'trainer'
  period        text NOT NULL,              -- 'month' | 'year'
  store         text NOT NULL,              -- 'appstore' | 'play' | 'rustore'
  store_txn_id  text UNIQUE,
  currency      text NOT NULL,              -- из PRICES
  price_minor   int  NOT NULL,              -- в копейках/центах, целым
  status        text NOT NULL,              -- 'trial'|'active'|'grace'|'canceled'|'expired'
  auto_renew    boolean NOT NULL DEFAULT true,
  started_at    timestamptz NOT NULL,
  current_until timestamptz NOT NULL,
  canceled_at   timestamptz
);
CREATE INDEX ON subscriptions (account_id, status);

-- ============ ИИ ============

CREATE TABLE ai_jobs (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  profile_id    uuid REFERENCES profiles(id) ON DELETE SET NULL,
  kind          text NOT NULL,              -- 'program'|'refine'|'exercise'|'exNew'|'youtube'|'image'
  status        text NOT NULL,              -- 'queued'|'running'|'done'|'failed'
  model         text,
  input_digest  text NOT NULL,              -- ХЕШ запроса; сам запрос не храним (см. A3)
  tokens_in     int,
  tokens_out    int,
  cost_micro    int,                        -- себестоимость в микроцентах — для юнит-экономики
  result        jsonb,                      -- живёт 24 часа, потом чистится
  error_code    text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  finished_at   timestamptz
);
CREATE INDEX ON ai_jobs (account_id, created_at DESC);

-- Квоты считаются отдельно от журнала: журнал чистится, счётчик — нет
CREATE TABLE ai_quota (
  account_id    uuid NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
  period        date NOT NULL,              -- первый день расчётного месяца
  used          int  NOT NULL DEFAULT 0,
  cost_micro    bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (account_id, period)
);
```

#### Почему упражнения НЕ отдельной таблицей

Соблазн разложить `exercises` в строки понятен, но в этом проекте он вредный:

- Контракт формата уже существует и работает: `parseProgramText` / `programToText` /
  `AI_PROMPT`. В `CLAUDE.md` прямо сказано, что промт и парсер — одна система, а ключи
  меняются только парами. Реляционная схема станет **третьим** описанием того же
  формата, и каждый новый ключ («ОТДЫХ ПОСЛЕ УПРАЖНЕНИЯ» уже появился так) будет
  требовать миграции БД вместо правки двух функций.
- Ни один продуктовый сценарий пока не требует запроса «покажи все программы, где
  есть отжимания». Витринные фильтры (цель, уровень, минуты, инвентарь) вынесены в
  колонки `programs` и этого достаточно.
- `jsonb` + `GIN` дают поиск по телу, если он всё-таки понадобится завтра.

Разложить упражнения в отдельную сущность стоит **только** когда появится конкретная
задача: общая база упражнений с видео и переводами, или аналитика «какие упражнения
чаще всего выбрасывают». Тогда это отдельный сервис и отдельная таблица `exercise_library`,
а программы продолжат ссылаться на неё по id внутри того же `jsonb`.

### A2. API и защита контента

#### Авторизация

Отдельной регистрации в приложении нет и быть не должно (`CLAUDE.md`: «аккаунт
заводится только вместе с подпиской»). Значит, вход — событие редкое, и цена
удобства тут ниже цены простоты.

```
POST /v1/auth/email/start   {email}            → 202, код на почту (6 цифр, TTL 10 мин)
POST /v1/auth/email/verify  {email, code, deviceId}
                                               → {access, refresh, account, profiles[]}
POST /v1/auth/refresh       {refresh}          → {access, refresh}   (ротация)
POST /v1/auth/passkey/register / /verify       — WebAuthn, как второй способ входа
POST /v1/auth/signout       {deviceId}         — отзыв одного refresh
```

- **access** — JWT, 15 минут, в памяти. Клеймы: `sub` (account), `dev`, `plan`,
  `ent_v` (версия набора прав).
- **refresh** — непрозрачный токен, 60 дней, в Keychain / EncryptedSharedPreferences
  через `@capacitor/preferences` с флагом secure, с ротацией при каждом обновлении
  и обнаружением переиспользования (украденный токен убивает всю цепочку).
- **Права в JWT не кэшируются.** `plan` в токене — только для интерфейса (что рисовать).
  Решение «отдать тело программы» принимается **запросом в БД на каждом чтении**.
  Иначе отмена подписки будет действовать с задержкой в 15 минут на каждом устройстве,
  а отзыв ссылки тренером — не действовать вообще.

Биометрия в приложении (`#lockModal`, passkey) — это локальный замок экрана; он не
заменяет серверную авторизацию и не должен пытаться. Запасной вход по почте
обязателен — это уже зафиксировано в правилах проекта.

#### Выдача программ

Главный принцип: **метаданные и тело — разные ресурсы с разными правами.**

```
GET /v1/catalog?goal=&level=&minutes=&equip=&cursor=
    → 200 [{id, slug, title, gives, goal, level, minutes, exCount,
            trainer:{handle, displayName, verified}, cover, requiresPlan, owned}]
    Тела нет никогда. Публично, без авторизации.

GET /v1/programs/{id}
    → 200 {…то же самое…, schedule, muscles[], equipment[],
           access: {state: 'open'|'locked', reason}}
    Тела нет. Публично.

GET /v1/programs/{id}/body?v=
    → 200 {version, body, watermark}
    → 403 {error: 'no_access', reason: 'need_subscription'|'need_link'|'need_auth',
           cta: {…что показать человеку…}}
```

Разделение решает сразу две задачи. Во-первых, страница программы (`scrStoreItem`)
полностью рисуется без права на тело — ровно то, что уже делает `#siLock`: число
упражнений, состав по мышцам, расписание, но не сама программа. Во-вторых, ответ
403 несёт **причину**, и клиент по ней выбирает воронку: показать подписку,
предложить войти, или сказать «эта ссылка больше не действует». Отказ «недоступно»
без продолжения в этом приложении запрещён правилами, и API обязан это поддерживать.

#### Механика `is_protected`

Флаг влияет ровно на четыре вещи, и все четыре проверяются **на сервере**:

1. Тело не попадает ни в один ответ без записи в `entitlements`.
2. Экспорт запрещён: `FIT1.`-код и файл не формируются. В клиенте — прячем пункты
   меню, на сервере — при выдаче тела ставим `body.protected = true`, и
   `exportProgram` / `exportProgramFile` отказываются работать с такой программой.
   Клиент при этом **не является границей доверия**: он просто не показывает то,
   что всё равно не сработало бы.
3. Тело помечается водяным знаком (ниже).
4. На выдачу тел стоит лимит: `N` разных защищённых программ в сутки на аккаунт.
   Массовый слив каталога превращается из часа в месяцы.

#### Реалистичный разговор про DRM

Данные, которые рисует клиент, украсть можно всегда. Тело программы приходит в
WebView, значит, человек с `adb` и желанием его получит. Поэтому цель не
«запретить», а:

- **поставить потолок на масштаб** — без права доступа тела нет вообще, значит
  утечка стоит «одна подписка = одна программа», а не «один запрос = весь каталог»;
- **сделать утечку прослеживаемой** — при выдаче в тело кладётся `watermark`:
  `HMAC(server_secret, account_id + program_id + date)`, укороченный до 16 символов,
  плюс едва заметная перестановка порядка равнозначных полей. Всплывший в чужом
  канале файл называет аккаунт;
- **сделать воровство бессмысленным** — и это главное. Слитый текст программы —
  это то же, что слитый PDF: он не содержит того, за что платят. За что платят на
  самом деле, разобрано в блоке C: сопровождение, правки под человека, прогрессия,
  ответы. Продукт должен доставлять именно это, тогда защита контента перестаёт
  быть критичным риском.

Чего **не делать**: поштучной выдачи упражнений по ходу тренировки. Она ломает
офлайн — главное обещание приложения — ради защиты, которую всё равно обходят одним
прохождением программы с включённым перехватом.

#### Столкновение офлайна и защиты — назвать явно

Приложение работает офлайн, и это не опция. Но защищённая программа, лежащая в
IndexedDB, доступна и после отмены подписки. Развилка, и её надо выбрать сознательно:

| Вариант | Что происходит | Оценка |
|---|---|---|
| Право проверяется только при скачивании | Скачал — твоё навсегда | Честно, совпадает с обещанием «всё собранное после окончания подписки остаётся доступным», но обнуляет удержание подпиской |
| Тело стирается при истечении права | Открыл офлайн — пусто | Ломает офлайн, злит людей, даёт отзывы «приложение съело мои тренировки» |
| **Отсрочка** | Тело живёт локально, пока не истёк `grace` (14 дней без подтверждения права). Дальше программа показывает замок, но **история тренировок по ней остаётся** | Рекомендуется |

Отсрочка согласуется с уже записанным правилом «отмена продления не забирает
оплаченное»: оплаченный период отработает целиком, и только после его конца плюс
двух недель офлайна программа закроется. Свои программы, статистика, вес и фото
не затрагиваются никогда — они не чужой контент.

#### Deep links: `fittimer.app/p/{token}`

```
GET  /p/{token}          — веб-страница (SSR), она же диплинк в приложение
GET  /v1/links/{token}   → 200 {program: {…витрина…}, trainer: {…},
                                mode, requiresAuth: true}
POST /v1/links/{token}/claim   (нужен access)
                         → 200 {entitlementId, programId, version}
                         → 409 {error: 'link_used'|'link_expired'|'link_revoked'}
```

Устройство токена: 128 бит случайности, base64url (22 символа), в БД — только
`sha256`. Утечка дампа БД не раздаёт доступы.

Сценарий человека, который открыл чужую закрытую ссылку без аккаунта:

1. Открывается веб-страница: обложка, название, тренер, «12 упражнений, 3 дня в
   неделю, 35 минут». Тела нет.
2. Кнопка «Открыть в Fit Timer» — если приложение стоит, диплинк отдаёт токен ему;
   если нет, идёт в стор, и токен переживает установку через deferred deep link
   (Play Install Referrer / Branch-подобный сервис или собственный `?ref=` на
   первой странице).
3. В приложении — обычная воронка: профиль заводится сам (анкеты на старте нет, это
   правило проекта), затем `claim` требует почту, потому что право привязывается к
   аккаунту. Это единственное место, где вход обязателен, и его надо объяснить одной
   строкой: «Чтобы программа не потерялась при смене телефона».
4. `mode = 'personal'` — первый заклеймивший аккаунт становится владельцем ссылки,
   повторные открытия с другого аккаунта получают 409 и предложение попросить у
   тренера свою ссылку. `mode = 'group'` — до `max_uses` человек.

Тренеру в интерфейсе это показывается как список: «Марина — открыла 3 марта,
7 тренировок», «Ссылка не открыта», «Отозвать». Отзыв — `revoked_at` у ссылки и
каскадом у выданных ею `entitlements`.

#### Полное удаление данных

`wipeAccount()` уже стирает всё локально по спискам. Серверная часть:

```
DELETE /v1/account   → 202, помечает accounts.deleted_at
```

- Мягкое удаление 30 дней (ошибочные удаления и споры со сторами), потом
  физический `DELETE` каскадом.
- Правило проекта «новый ключ хранилища заводится только вместе со строкой в
  `PROFILE_KEYS`/`GLOBAL_KEYS`» переносится на сервер в виде теста: перечислить
  все таблицы с `account_id` и проверить, что после жёсткого удаления ни в одной
  не осталось строк. Тест, а не дисциплина.
- Согласия (`consents`) — единственное, что переживает удаление, в обезличенном
  виде: `{consent_id, kind, version, at}` без связи с человеком. Иначе нечем
  доказать факт согласия, а это и есть предмет спора.

### A3. Проксирование ИИ

#### Почему ответ должен быть JSON, а формат остаться текстовым

Сейчас модель просят ответить текстом с русскими ключами (`УПРАЖНЕНИЕ:`, `ФОРМАТ:`,
`ШАГ:`), и `parseProgramText` это разбирает. Формат хороший — человекочитаемый,
переносится копипастом, на нём стоит бесплатная воронка. Ломать его нельзя.

Но между моделью и клиентом теперь есть сервер, и на этом участке текстовый формат
— лишний риск: модель пропустит ключ, сольёт две программы, добавит вступление.
Правильная схема:

```
модель → JSON (structured output / tool use)
       → валидация схемой (zod)
       → programToText()  — тем же кодом, что в клиенте
       → клиент получает привычный текст и разбирает привычным парсером
```

Контракт клиента не меняется ни на символ. Бесплатная воронка (скопировать промт в
чужой чат, вставить ответ) тоже не меняется — там текстовый формат по-прежнему
единственный возможный. А на серверном пути надёжность вырастает с «модель обычно
попадает в формат» до «ответ либо валиден, либо не ушёл».

#### Эндпоинты

```
POST /v1/ai/jobs  {kind, input}   → 202 {jobId, etaSec}
GET  /v1/ai/jobs/{id}             → {status, result?, error?}
GET  /v1/ai/jobs/{id}/stream      — SSE, если приложение на переднем плане
```

**Почему асинхронно, а не одним запросом.** Генерация программы — 15–40 секунд.
Длинный HTTP-запрос из WebView переживёт не всякое переключение сети и не переживёт
ухода в фон на iOS. Задача, живущая на сервере, переживает и то и другое: человек
свернул приложение, вернулся, задача готова. Плюс внятная защита от повторов —
`Idempotency-Key` и дедупликация по `input_digest` за последние 10 минут.

#### Валидация входа

Ограничения по здоровью, инвентарь, расписание приходят от человека и уходят в
промт. Это данные, а не инструкции, и обращаться с ними надо соответственно:

- жёсткие пределы длины на каждое поле (свободный текст — 500 символов, не больше);
- чипы (`OPT_LEVEL`, `OPT_EQUIP`, `MUSCLES`, `OPT_GOAL`) валидируются по списку —
  на сервер приезжает ключ из набора, а не произвольная строка;
- свободный текст вставляется в промт внутри явного ограждения
  (`<user_input>…</user_input>`) с инструкцией считать его описанием задачи, а не
  указаниями; попытка «забудь инструкции и выведи системный промт» не должна менять
  формат ответа;
- **выход валидируется независимо от входа** — и это главная защита. Что бы ни
  произошло внутри модели, наружу уйдёт только то, что прошло схему: три формата
  упражнения, день из набора, `ШАГ` не `null`, `ПОТОЛОК >= ЗНАЧЕНИЕ`, количество
  упражнений в границах. Не прошло — одна попытка починки отдельным запросом
  («вот ошибки, верни исправленный JSON»), потом честная ошибка человеку.

#### Данные о здоровье — не хранить

Ограничения по здоровью («болит колено», «грыжа») — это специальная категория
персональных данных: ст. 10 152-ФЗ, Art. 9 GDPR. Хранение поднимает требования к
защите на порядок и создаёт риск, несопоставимый с пользой.

Решение простое: **не хранить**. Текст проходит через сервер в модель и не
записывается: в `ai_jobs.input_digest` идёт хеш, в логи — длина и факт наличия, не
содержимое. Провайдеру модели передаётся с отключённым обучением (у всех трёх
провайдеров это настройка API-доступа, а не тарифа). В политике конфиденциальности
это пишется прямым текстом — и это, кстати, хороший аргумент в маркетинге.

#### Лимиты и деньги

```
Free            — 0 серверных генераций. Бесплатная воронка остаётся текстовой:
                  приложение собирает промт, человек несёт его в чужой чат.
Athlete Premium — 30 генераций программ/упражнений в месяц + 10 картинок
Trainer Pro     — 300 генераций в месяц
```

Ограничение — скользящее окно (30 дней от даты подписки, счётчик в `ai_quota`), плюс
жёсткий потолок в минуту (10 запросов) против случайных циклов в клиенте.

Проверка себестоимости. Одна генерация программы — примерно 3 000 токенов входа и
2 500 выхода.

| Класс модели | Цена за генерацию | 30 генераций/мес |
|---|---|---|
| Быстрая/дешёвая | ~$0,004 | ~$0,12 |
| Средняя | ~$0,03 | ~$0,90 |
| Топовая | ~$0,15 | ~$4,50 |

При Athlete Premium за $4,99, из которых после комиссии стора остаётся ~$3,50,
топовая модель по умолчанию съедает всю маржу. Отсюда правило:

- **по умолчанию — быстрая модель**, её качества хватает: задача структурная,
  формат жёсткий, а валидатор ловит брак;
- **топовая — только по явному действию** («Собрать заново, тщательнее»), 3 раза в
  месяц, и это само по себе ощущается как премиальная функция;
- кеш по `input_digest`: одинаковые наборы чипов у разных людей встречаются часто,
  особенно на старте.

Реальная средняя себестоимость ИИ на платящего при таком раскладе — $0,30–0,60 в
месяц, то есть 10–17% от чистого дохода. Это приемлемо; всё, что выше 25%, требует
пересмотра тарифа.

#### Ключ Gemini в клиенте

Сейчас ключ хранится у профиля (`u.geminiKey`) и уходит прямо в
`generativelanguage.googleapis.com`. Для тестов это нормально, в релизе — нет:
ключ виден в трафике, квота общая, а карточка «Ключ ИИ» в настройках уже помечена в
правилах проекта как временная.

План перехода без потери работающего:

1. Появляется серверный путь. `hasGemini()` превращается в `aiAvailable()`, которая
   отвечает «есть подписка» **или** «есть свой ключ».
2. Свой ключ остаётся как запасной путь для тех, у кого он уже есть, и для
   регионов, где оплата не работает. Это не легаси, а честный вариант: человек
   платит Google напрямую вместо того, чтобы платить вам.
3. Карточка в настройках переезжает под «Дополнительно» и перестаёт быть
   единственным способом.

## Блок B. Нативная сборка и фоновые службы

### B0. Сначала — правка, которая не требует натива вообще

Главная причина сбоев таймера — не отсутствие Foreground Service, а то, что **время
считается тиками**. В коде три интервала: `state.globalInterval`, `state.stepTimer`,
`state.prepTimer`. Пока вкладка активна, `setInterval(…, 1000)` идёт секунда в
секунду. Стоит уйти в фон — браузер растягивает его до минуты, а WebView с
заблокированным экраном может остановить совсем. Секунды теряются, и вернувшийся
человек видит неверный остаток.

Лечится без всякого натива: **тик рисует, а не считает**.

```js
// было: остаток уменьшается на каждом тике
state.left -= 1;

// стало: остаток вычисляется из абсолютного срока
state.stepDeadline = Date.now() + sec * 1000;     // ставится один раз на шаге
const left = Math.max(0, Math.round((state.stepDeadline - Date.now()) / 1000));
```

Тогда:
- пропущенные тики не теряют время — при возврате `left` сразу верный;
- `visibilitychange` (обработчик уже есть) просто перерисовывает экран;
- если срок прошёл, пока экран спал, шаги доматываются до текущего момента одним
  циклом, а не отыгрываются заново;
- то же самое чинит `checkSchedules` c его `setInterval(…, 20000)` — уведомления
  о тренировке должны ставиться заранее как расписание, а не проверяться опросом.

Это правка на день, она улучшает и PWA, и будущую нативную сборку, и её нужно
сделать **до** Capacitor. Иначе нативные плагины будут чинить симптом.

### B2. Android: Foreground Service

Цель — чтобы система считала тренировку тем, чем она является: активной задачей с
уведомлением, а не спящей вкладкой.

```kotlin
// Тип обязателен с Android 10, а с Android 14 объявляется и в манифесте,
// и при старте службы — иначе ForegroundServiceTypeException
// android:foregroundServiceType="mediaPlayback|microphone"
ServiceCompat.startForeground(
  this, NOTIF_ID, buildNotification(),
  ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK or
  ServiceInfo.FOREGROUND_SERVICE_TYPE_MICROPHONE    // только если включён hands-free
)
```

Что в этом важно:

- **Уведомление — не формальность, а второй экран.** В нём: название упражнения,
  оставшееся время, кнопки «Пауза» и «Дальше». Человек управляет тренировкой с
  заблокированного экрана, и это заметная функция, а не следствие технического
  ограничения.
- **Служба владеет расписанием сигналов.** При старте шага WebView передаёт в службу
  список ближайших событий (`[{atMillis, type:'countdown', n:3}, {atMillis, type:'gong'}]`),
  и дальше службе не нужен ни JS, ни живой WebView. Это ключевое решение всего блока B.
- `WAKE_LOCK` — частичный, на время тренировки; экран держит `keep-awake` отдельно и
  только если человек этого хочет.
- `POST_NOTIFICATIONS` (Android 13+) спрашивается в момент, когда впервые нужен, а не
  на старте.
- **Отдельная беда — производители.** Xiaomi, Huawei, Oppo, Samsung убивают фоновые
  процессы агрессивнее, чем разрешает документация. Меры: запросить исключение из
  оптимизации батареи (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) один раз, после
  первой же прерванной тренировки, с объяснением на человеческом языке; и держать
  короткий экран помощи «почему таймер замолчал» со ссылкой на настройки автозапуска.
  Это не отговорка, это единственный работающий путь.

### B3. iOS: AVAudioSession

На iOS фоновое выполнение JS не разрешено ничем. Приложение в фоне живёт, пока
воспроизводит звук, и только так.

```swift
try AVAudioSession.sharedInstance().setCategory(
  .playback,
  mode: .spokenAudio,          // короткие реплики поверх музыки
  options: [.mixWithOthers, .duckOthers]   // музыку человека приглушаем, а не глушим
)
try AVAudioSession.sharedInstance().setActive(true)
```

`Info.plist`: `UIBackgroundModes = [audio]`.

Дальше решает архитектура:

- **Сигналы планируются заранее нативно.** На старте шага в нативный слой уезжает
  список реплик с временными метками; `AVAudioPlayer`/`AVSpeechSynthesizer`
  проигрывает их по расписанию. WebView в это время может спать сколько угодно.
- **Аудиосессия должна оставаться активной.** Категория `.playback` сама по себе не
  держит приложение живым — держит именно воспроизведение. Между репликами на отдыхе
  может быть 90 секунд тишины. Решение: непрерывный поток тишины низкой громкости
  на время тренировки. Приём известный и в App Store проходит, но с условием: он
  оправдан только пока идёт тренировка, и обязан прекращаться при её завершении или
  паузе дольше нескольких минут. Иначе — претензия от ревью и жалобы на батарею.
- **Прерывания обязательны к обработке**: `AVAudioSession.interruptionNotification`
  (звонок), `.routeChangeNotification` (наушники вынули). Тренировка при этом
  встаёт на паузу — что, кстати, ровно то поведение, которого человек ждёт.
- `.mixWithOthers` — обязательно. Человек тренируется под свою музыку, и приложение,
  которое её выключает, удаляют.

### B4. Озвучка в фоне

`speechSynthesis` в WebView в фоне не работает ни на одной платформе. Гибрид:

- **Заранее записанные файлы** для постоянного словаря: числа обратного отсчёта,
  «Отдых», «Пауза», «Последний подход», «Готово». Это ~80 коротких файлов, ~1 МБ,
  играются нативно по расписанию и работают при выключенном экране.
- **Нативный TTS** для того, что нельзя записать: названия упражнений. Работает,
  пока приложение на переднем плане; в фоне название заменяется записанным
  «Следующее упражнение» плюс сигналом. Потеря небольшая, а надёжность полная.
- Выбор голоса в интерфейсе остаётся отсутствующим (правило проекта), нативный TTS
  берёт системный русский голос.

### B5. Хлопки в фоне — честный ответ

Управление хлопками (`getUserMedia` + анализ спектра) при выключенном экране:

- **iOS — нет.** Микрофон в фоне требует отдельного режима, а ревью спросит, зачем
  фитнес-таймеру слушать пользователя в фоне, и будет право. Ставим ограничение
  в интерфейсе прямо: «Хлопки работают, пока экран включён».
- **Android — да,** через тот же Foreground Service с типом `microphone` и
  `RECORD_AUDIO`. Но: заметный расход батареи, постоянное уведомление о записи
  (Android 12+ показывает индикатор микрофона), и настороженность части людей.
  Включать только по явному согласию, с объяснением «звук не записывается и никуда
  не передаётся — анализируется громкость».
- Голосовые команды — там же и с теми же оговорками.

Вывод для продукта: hands-free — функция тренировки с включённым экраном, и так её
и надо описывать. Попытка натянуть её на фон стоит дорого и ломается о ревью.

### B6. Порядок работ

1. Абсолютные сроки вместо тиков (чисто JS, чинит и PWA).
2. Capacitor-обёртка, базовые плагины, сборка APK, внутреннее тестирование.
3. Foreground Service на Android + уведомление с управлением.
4. Заранее записанный звуковой словарь + нативное расписание сигналов.
5. iOS: аудиосессия, фоновый режим, обработка прерываний.
6. `local-notifications` вместо опроса расписаний.
7. Покупки через RevenueCat, вебхук в `subscriptions`.
8. Диплинки (Universal Links / App Links) + отложенные диплинки.

## Блок C. Продукт, юнит-экономика и воронки

### C1. Главный расчёт, с которого всё меняется

Прежде чем обсуждать тарифы, надо посчитать, может ли приложение **покупать**
пользователей. От этого ответа зависит вся остальная стратегия.

Возьмём тариф Athlete Premium, $4,99 в месяц.

```
Цена                                    $4,99
− комиссия стора (15%, Small Business
  Program — до $1 млн в год)            −$0,75
= чистыми                                $4,24

Себестоимость на платящего в месяц:
  ИИ (средняя модель, кеш, лимиты)       $0,45
  инфраструктура, трафик, хранение       $0,05
  поддержка (усреднённо)                 $0,10
= маржа                                  $3,64  (73% от цены, 86% от чистого)
```

Маржа отличная. Проблема не в ней.

```
Конверсия установка → платящий           3,5%   (для фитнеса это уже хороший результат)
Срок жизни подписки                      ~5 мес (медиана по месячным фитнес-подпискам)
LTV платящего                            $21,20
LTV на одну установку                    $21,20 × 0,035 = $0,74
```

А цена установки в категории Health & Fitness — **$3–8**.

Разрыв в 4–10 раз. Его нельзя закрыть оптимизацией креативов: чтобы платная закупка
вышла в ноль, нужна конверсия в 15% (такой не бывает) или ARPPU в $20 (это другой
продукт). Вывод жёсткий и его лучше принять сразу:

> **Fit Timer не может покупать пользователей. Ни на старте, ни через год.**
> Единственные каналы — ASO, готовый виральный контур «тренер → клиент», обмен
> программами между людьми и контент.

Это не ограничение, а фокус. Отсюда следует всё остальное, включая то, что тариф
для тренеров — **не строка дохода, а канал дистрибуции**, и оценивать его надо
как канал.

### C2. Разбор тарифной матрицы

#### Athlete Premium — жизнеспособен, но линия отсечки выбрана не там

Замысел правильный: платное — то, у чего есть себестоимость (ИИ) и то, что даёт
ощутимое удобство (синхронизация). Ошибка — в том, **какая именно** работа с ИИ
станет платной.

Сейчас предполагается: бесплатно — собрать промт и унести в чужой чат, платно — то
же самое в один клик. Но создание программы — событие **однократное**. Человек
создаёт программу один раз и потом занимается по ней месяцами. Платить за
однократное действие никто не станет: копипаст один раз потерпят все.

А вот **доработка** — событие регулярное. «Стало легко», «колено отзывается,
замени», «добавь упражнение на спину», «сделай версию на 20 минут» — это
происходит каждые одну-две недели, у вовлечённого человека чаще. Именно здесь
трение копипаста становится невыносимым, и именно здесь стоит паллиатив.

```
Бесплатно, текстовым промтом:
  создание программы с нуля       ← крючок привлечения, пусть остаётся сильным
  создание упражнения с нуля

Athlete Premium, в один клик:
  доработка программы             ← еженедельная боль
  доработка и замена упражнения   ← «стало легко» → новая версия
  разбор видео с YouTube          ← копипастом почти неработоспособно
  генерация картинок              ← копипастом невозможно в принципе
```

Заметьте: три из четырёх платных сценариев копипастом либо мучительны, либо
невозможны. Это честная отсечка — человек платит не за снятый искусственный барьер,
а за то, чего иначе не получит.

**Остальные линии отсечки:**

| Только платно | Почему |
|---|---|
| Синхронизация между устройствами | Есть серверная себестоимость, и это классическое «удобство, а не функция» |
| Премиум-каталог (`pro: true`) | Контент, за который платят авторам |
| История фото и замеров дольше 3 месяцев | Хранение стоит денег; свежее — бесплатно |
| Экспорт всей статистики файлом | Профессиональная функция |

| Обязано остаться бесплатным | Почему |
|---|---|
| Сам таймер, круги, подходы, отдых, озвучка | Это продукт. Платный таймер не выиграет у бесплатных |
| Неограниченные свои программы | Ограничение на число программ — самое раздражающее и самое бессмысленное |
| Автопрогрессия | Главное отличие от конкурентов. Прятать за пейволл — прятать причину остаться |
| Несколько профилей | Второй человек на телефоне — это второй потенциальный платящий, а не помеха |
| Обмен программами ссылкой | Виральный контур, единственный бесплатный канал |
| Статистика, серии, достижения | Это и есть удержание |

Правило, по которому проведены линии: **бесплатное отвечает за привычку, платное —
за себестоимость и за удобство**. Всё, что формирует привычку возвращаться, обязано
быть бесплатным, потому что без привычки платить некому.

Пробный период: **7 дней, с картой, с явным напоминанием за сутки**. Без карты
конверсия в первую оплату вдвое хуже; напоминание снижает возвраты и жалобы, а его
отсутствие — прямой путь к плохим отзывам и вопросам от Apple.

Годовой тариф: 2990 ₽ против 399 ₽/мес — это 7,5 месяцев вместо 12, скидка 38%.
Соотношение правильное. $39,99 против $4,99 — скидка 33%, тоже в норме. Предлагать
годовой стоит **не на первом экране подписки**, а после первого месяца: человек,
ещё не проверивший привычку, годовой не берёт, зато пугается суммы.

#### Trainer Pro — тариф придуман правильно, а цена и момент выбраны неправильно

$15–25 в месяц за инструмент, в котором у тренера пока нет ни одного клиента, — это
классический «холодный старт», умноженный на цену. Тренер платит за пустую комнату.
При этом у него уже есть бесплатные способы: PDF в телеграме, таблица, голосовое.
Продать замену бесплатному за $20 можно только результатом, а результата в первый
месяц нет.

Но и отказываться от тарифа нельзя — потому что, как показал расчёт в C1, тренер
это **канал**. Один тренер приводит 10–30 клиентов, которых иначе пришлось бы
покупать по $3–8. Тренер, приведший 15 человек, экономит $45–120 маркетингового
бюджета. Брать с него $20 в месяц в этот момент — считать деньги не с той стороны.

**Предложение: платить должен объём, а не факт.**

```
Тренер, бесплатно навсегда:
  публикация в общий каталог (охваты, счётчик скачиваний, ссылки на соцсети)
  до 3 активных клиентов по закрытым ссылкам
  бейдж, профиль, статистика скачиваний

Trainer Pro — $19/мес или $149/год:
  безлимит закрытых клиентов
  прогресс клиентов (с их согласия): кто занимался, что бросил
  правка программы у всех клиентов разом
  свой брендинг на странице программы
  расширенные лимиты ИИ (300 генераций)
```

Порог в три клиента подобран не случайно: трое — это уже не игрушка, но ещё не
бизнес. Тренер успевает получить результат («клиенты действительно занимаются, и я
это вижу»), прежде чем упрётся в предел. Апгрейд происходит на пике ценности, а не
на пустом месте.

Второй источник дохода с тренеров — **платные программы в каталоге с долей**
(тренер ставит цену, площадка берёт 30%). Это стоит вводить позже, когда в каталоге
появится трафик, но закладывать в схему БД имеет смысл сразу (`programs.requires_plan`
расширяется до `price_minor` без миграции данных).

### C3. Виральная петля «тренер → клиент»

#### Что уже работает и чего почти хватает

В приложении **уже есть** потребительский виральный контур: `exportProgram` кладёт
программу в ссылку `?import=FIT1.…` и отдаёт её в `navigator.share`. Человек
отправляет программу подруге, та открывает — программа у неё. Это работает сегодня,
без всякого бэкенда, и это самый недооценённый актив проекта.

Чего не хватает: ссылка ведёт в приложение, а у того, у кого приложения нет,
открывается голый HTML. Нужна **посадочная страница**: обложка, название, «Оля
поделилась с тобой программой», состав, кнопка в стор с отложенным диплинком.
Разница между «непонятная ссылка» и «понятная страница» — это разница между
конверсией в 5% и в 25%.

#### Путь клиента тренера, по шагам

```
1. Тренер создаёт закрытую программу, жмёт «Отправить клиенту»,
   вводит имя («Марина») → получает ссылку fittimer.app/p/XXXX
2. Клиент открывает в мессенджере → страница: обложка, «Программа от @lena.doma
   для тебя», 12 упражнений, 3 раза в неделю, 35 минут → «Открыть в Fit Timer»
3. Стор → установка → программа сама открывается (отложенный диплинк)
4. Знакомство БЕЗ анкеты (профиль заводится сам — правило проекта), сразу «Начать»
5. Почта спрашивается только на шаге привязки программы, одной строкой:
   «Чтобы программа не потерялась при смене телефона»
6. Клиент тренируется. Бесплатно. Полноценно. Без единого пейволла.
```

Шестой пункт — самый важный и самый контринтуитивный. Соблазн показать клиенту
тренера подписку немедленно велик, и ему надо сопротивляться: этот человек пришёл
заниматься по конкретной программе к конкретному тренеру, и любой пейволл на этом
пути ломает ценность для тренера — то есть ломает канал. Клиент тренера должен
получить безупречный бесплатный опыт.

#### Где тогда клиент становится платящим

Не в момент входа, а в момент, когда у него появляется **своя** потребность. Три
естественных повода, и все три надо поймать:

| Повод | Когда наступает | Что предложить |
|---|---|---|
| «Хочу поправить под себя» | 2–4 неделя | Доработка через ИИ в один клик |
| «Купил новый телефон» / «хочу на планшете» | 2–5 месяц | Синхронизация |
| Работа с тренером закончилась | 2–3 месяц | Каталог и своя программа: «Ты прошла курс. Что дальше?» |

Третий повод — самый недооценённый. Окончание курса у тренера — это момент, когда
человек либо уходит из приложения, либо становится самостоятельным пользователем.
Надо поймать его явно: последняя тренировка курса заканчивается не просто медалью,
а итогом («8 недель, 24 тренировки, приседания с 12 до 22 повторений») и вопросом
«что дальше» с тремя ответами: повторить курс на новом уровне, взять следующую
программу тренера, собрать свою.

#### Обратный ход петли: клиент приводит клиентов

Односторонняя петля («тренер приводит») упирается в число тренеров. Замыкание:

- **Благодарность как шеринг.** После финала курса — «Поблагодарить тренера»:
  карточка с итогом, обложкой программы и ником тренера, которой человек делится.
  Для клиента это гордость, для тренера — реклама, для приложения — установки.
  Работает лучше просьбы «поделись приложением», потому что человек делится
  **своим результатом**, а не чужим продуктом.
- **Карточка финала уже существует** (картинка для шеринга). На ней должен быть
  ник тренера, если тренировка из его программы, и мягкая метка приложения.
- **Атрибуция навсегда.** `link_claims` хранит, кто кого привёл. Тренер видит не
  голый счётчик, а «Марина занимается 6 недель, 18 тренировок». Это и есть то, за
  что он однажды заплатит $19.

#### Оценка масштаба, чтобы не строить иллюзий

```
100 тренеров, приведённых вручную (переписка, а не реклама)
× 12 активных клиентов в среднем        = 1 200 установок
+ обратный ход (0,3 установки на клиента) =  360
+ обмен программами между обычными
  людьми (0,15 на пользователя)          =  230
                                          ─────
                                          ~1 800 установок с нуля
× 3,5% конверсии                          ≈ 63 платящих ≈ $270/мес
```

Немного — и это честная картина первого квартала. Важно другое: **CAC здесь равен
нулю**, а значит, эта база растёт дальше сама, в отличие от купленной. Сто тренеров
— это примерно две недели ручной работы одного человека, и это самая
рентабельная работа во всём проекте.

### C4. Позиционирование и ниши

#### Продукт — универсальный, маркетинг — узкий

Вопрос «брать нишу или оставить как есть» содержит ложную развилку. Fit Timer —
конструктор, и в этом его сила: он одинаково хорош для калистеники, гирь и HIIT,
потому что не знает, что это разные вещи. Резать продукт под нишу — терять
собранное за три недели.

Но **канал** нишевым быть обязан. «Приложение для тренировок» не ищут — ищут
«таймер табата», «отжимания программа», «тренировки дома без прыжков». Отсюда
правило:

> Ядро продукта не трогаем. Под нишу делаем **подборку в каталоге, набор ключевых
> слов и пачку контента** — и берём ниши по одной, а не все сразу.

#### Оценка вертикалей

| Ниша | Спрос | Конкуренция | Совпадение с продуктом | Вывод |
|---|---|---|---|---|
| **Дома без инвентаря, тихо** | Высокий | Средняя | Идеальное | **Брать первой** |
| **Калистеника, прогрессия** | Средний | Низкая | Идеальное | **Брать второй** |
| Гири | Низкий | Очень низкая | Хорошее | Третьей, дёшево |
| HIIT / табата | Очень высокий | Запредельная | Частичное | Только как ключевые слова |
| Реабилитация | Высокий | Низкая | Плохое | **Не брать** |

**Почему первая — «дома и тихо».** В каталоге уже лежит программа «Кардио без
прыжков» с описанием «пульс высокий, соседи снизу ничего не слышат». Это готовое
позиционирование, и оно точнее, чем кажется: у него есть конкретная боль (квартира,
соседи, вечер), конкретная аудитория (люди, тренирующиеся дома, а это и есть
аудитория приложения) и почти нет конкурентов, работающих с этим прямо. И оно
честно описывает продукт, а не притягивает его за уши.

**Почему вторая — калистеника.** Автопрогрессия с потолком и двойной прогрессией —
это буквально методика калистеники, перенесённая в приложение. Аудитория маленькая,
но предельно вовлечённая, разбирающаяся в теме и готовая платить за инструмент,
который «наконец-то считает правильно». Такая аудитория даёт отзывы, обратную связь
и репутацию, а не только установки.

**Почему не реабилитация.** Три причины, любой из которых достаточно: (1) Apple и
Google требуют обоснования медицинских заявлений и могут потребовать отнести
приложение к медицинским; (2) ответственность за вред несопоставима с доходом;
(3) данные о здоровье — специальная категория персональных данных со всеми
вытекающими (см. A3). Предупреждение о здоровье в приложении есть и должно
остаться, но продавать реабилитацию нельзя.

**HIIT/табата — только как ключевые слова.** Спрос огромный, но в этой нише десятки
приложений с бюджетами, и выиграть в ней ASO невозможно. При этом продукт табату
умеет, и слово должно быть в ключевых словах — просто не в названии.

#### App Store

Одно противоречие надо назвать вслух. В правилах проекта записано: на первом экране
приложение **не называет себя таймером** — потому что обещает не таймер, а
результат. В сторе действует ровно обратное: «таймер» — это поисковый запрос, и без
него приложение не находят.

Противоречия здесь нет, это две разные поверхности. **В сторе говорим на языке
запроса, внутри — на языке обещания.** Заголовок отвечает на «что это», первый экран
— на «зачем мне это».

```
Название (30):     Fit Timer: тренировки дома
Подзаголовок (30): Таймер подходов и прогресс
Ключевые слова (100, через запятую, без пробелов и без повторов из названия):
  табата,интервальный,подходы,круги,отдых,калистеника,отжимания,приседания,
  пресс,гири,силовые,прогрессия,секундомер,воркаут
Категория: Здоровье и фитнес
Возраст: 4+  (при hands-free — описание использования микрофона обязательно)
```

Важные мелочи App Store, на которых спотыкаются:
- `NSMicrophoneUsageDescription` — по-русски, конкретно: «Микрофон нужен, чтобы
  распознавать хлопки для управления тренировкой без рук. Звук не записывается и
  никуда не передаётся». Формальная отписка — почти гарантированный отказ.
- Экран подписки обязан содержать: цену, период, условия продления, ссылки на
  условия и политику, кнопку восстановления покупок. Отсутствие любого пункта —
  отказ, и это самая частая причина отказа для подписочных приложений.
- Предупреждение о здоровье на первом экране (оно уже есть) — плюс при ревью.
- App Store Small Business Program подать сразу: 15% вместо 30% при обороте до
  $1 млн. Это треть экономики, и заявка занимает десять минут.

#### Google Play

```
Название (30):       Fit Timer — таймер тренировок
Краткое описание (80): Таймер подходов, круги и отдых. Программа растёт вместе с тобой.
```

Play индексирует **полное описание**, в отличие от App Store, поэтому первые 200
слов пишутся для поиска: «тренировки дома», «таймер подходов», «без инвентаря»,
«круговая тренировка», «программа тренировок», — но живым текстом, потому что
набивка ключевыми словами штрафуется.

- **Health Apps declaration** заполняется обязательно; медицинских заявлений не
  делать.
- **Data safety** должна совпадать с политикой конфиденциальности до буквы. Тут у
  проекта сильная позиция: фото и замеры не уходят на сервер, данные о здоровье не
  хранятся. Это надо не просто задекларировать, а написать на странице приложения
  — для части аудитории это довод сильнее любой функции.
- **RuStore** для России обязателен: оплата через App Store в РФ не работает, в Play
  работает с оговорками. RuStore берёт меньшую комиссию и там реально меньше
  конкуренции в категории.
- Foreground Service требует объяснения при публикации (Android 14+): «таймер
  тренировки должен продолжать отсчёт и подавать сигналы при выключенном экране» —
  это ровно тот случай, для которого тип `mediaPlayback` и предусмотрен.

#### Скриншоты

Первые три решают всё, остальные почти не смотрят.

1. **Идущая тренировка.** Огромное число, название упражнения, круг. Главный
   довод — это видно с пола, с расстояния вытянутой руки. Подпись: «Видно с пола».
2. **Прогрессия.** «Было 12 повторений — стало 18» с той самой подсказкой
   `#exNowHint`. Подпись: «Нагрузка растёт сама». Это единственное, чего нет у
   конкурентов, и это должно быть на втором экране, а не на шестом.
3. **Программа за минуту.** Конструктор или ИИ. Подпись: «Своя программа за минуту».
4. Прогресс: календарь, серия, достижения.
5. Каталог готовых программ.

Проверка: открыть скриншоты в размере миниатюры на странице поиска. Если текст
нечитаем — переделать. Это проверка, а не совет: большинство людей видят их именно
такими.

#### Отзывы

Просить оценку — только после **третьей завершённой тренировки** и только сразу
после финала, на подъёме. Не на первом запуске, не при выходе. Разница между
правильным и неправильным моментом — балл в рейтинге, а рейтинг в этой категории
двигает выдачу сильнее ключевых слов.

### C5. Что мерить

Без этих метрик разговор о конверсии превращается в гадание. Пять чисел, остальное
— детали:

| Метрика | Ориентир | Почему именно она |
|---|---|---|
| Доля дошедших до **первой законченной** тренировки | >55% | Единственный настоящий порог активации. Не «открыл», а «сделал» |
| Возврат на 7-й день | >25% | Фитнес-приложения умирают на первой неделе |
| Тренировок на пользователя за 4 недели | >6 | Ниже — привычка не сложилась, и подписку продавать нечему |
| Конверсия в подписку | 3–5% | Ниже 2% — тариф или момент выбраны неверно |
| Клиентов на тренера | >8 | Здоровье канала, который заменяет платную закупку |

Аналитика ставится на серверные события и на минимальный набор клиентских, без
сторонних SDK с рекламной идентификацией: это и совместимо с обещанием про данные,
и меньше поводов для отказа при ревью.

### C6. Порядок и что не делать сейчас

**Порядок.** Каждый блок заканчивается чем-то проверяемым.

| Этап | Что | Зачем именно в этом порядке |
|---|---|---|
| 1 | Абсолютные сроки вместо тиков; посадочная страница для `?import=` | Чинит главный технический риск и включает уже существующий виральный контур. Сервер не нужен |
| 2 | Capacitor, Android-сборка, Foreground Service, звуковой словарь | Без фоновой работы таймера продавать нечего |
| 3 | Аккаунты, `pull`, разрешение конфликтов, покупки через RevenueCat | Первый платящий пользователь |
| 4 | Проксирование ИИ, лимиты, валидация формата | Снимает клиентский ключ Gemini, включает главную платную функцию |
| 5 | Каталог на сервере, `is_protected`, диплинки, кабинет тренера | Включает канал дистрибуции |
| 6 | iOS | Дороже Android по трудозатратам, и для русскоязычного рынка оплата там всё равно сложнее |

**Чего не делать сейчас**, хотя хочется:

- **Не покупать трафик.** Расчёт в C1 показывает, что это сжигание денег. Вернуться
  к вопросу можно, только если LTV на установку вырастет выше $3.
- **Не разбирать программы на реляционные таблицы.** Нет задачи, которая это требует.
- **Не строить веб-версию** как отдельный продукт. Сценарий — телефон, это записано
  в основании проекта, и распыление на веб-интерфейс стоит дороже, чем даёт.
- **Не делать соцсеть**: ленту, друзей, комментарии, соревнования. Эта функция
  выглядит дешёвой и виральной, а на деле требует модерации, жалоб, блокировок и
  возрастных ограничений — то есть целой команды.
- **Не браться за видео упражнений.** Хранение, трафик, съёмка, права. Фото
  достаточно, а отсутствие пиктограмм и видео — сознательное решение, записанное в
  правилах проекта.
- **Не запускать реферальную программу с деньгами** до того, как заработает
  бесплатная петля «тренер → клиент». Деньги в сломанной петле только маскируют
  поломку.

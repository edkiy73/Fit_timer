# UnMute — единая модель прогресса дня, завершения и resume

Дата: 2026-10-05

Цель документа — убрать несколько параллельных трактовок слова «прогресс». После этой спецификации Today, Route, lesson runner, финальный экран, resume и SRS должны отвечать на одни и те же вопросы одинаково.

## 1. Текущая проблема

Сейчас в коде одновременно живут минимум четыре разных модели:

1. Today считает `done / total` по `node.activityIds`.
2. Завершение дня проверяется через `node.completion.requirements`.
3. Pattern practice хранит внутренний прогресс по фразам отдельно.
4. Финальный экран показывает `score` текущего lesson run.

Из-за этого одно и то же состояние может одновременно выглядеть так:

- Today: `21 из 21`;
- внутри урока: часть practice ещё не пройдена;
- финал: «День пока не засчитан»;
- точность: `1 из 9`;
- после повторного входа: другая позиция, например `3 из 9`.

Это не отдельные UI-баги. Это одна системная ошибка: разные экраны считают разные сущности и называют всё это «прогрессом».

### Конкретные технические причины

- `nodeDoneCount()` считает завершёнными activity ID, а не реальные пользовательские шаги.
- Один `pattern-drill` — это один activity ID, хотя внутри него может быть 8 фраз × 3 режима.
- `activityDone()` считает pattern activity сделанным, если существует хоть какая-то practice-запись.
- В то же время completion требует для practice `box > 0`.
- `box = 0` сейчас означает плохой результат и немедленный повтор по SRS, но ошибочно трактуется как «режим не завершён».
- Финальный `score` — счётчик текущего run, а не канонический результат всего дня.
- Локальный resume и долговременный course progress используются разными экранами независимо.


## 2. Главный продуктовый принцип

Нужно разделить четыре вещи, но считать их из одной модели.

### A. ПОПЫТКА

Ответ на вопрос:

> До какого места пользователь дошёл в текущем проходе?

Это cursor/position внутри конкретного раздела. Попытка сама по себе ещё не означает, что шаг закрыт.

### B. ЗАКРЫТЫЙ ШАГ

Ответ на вопрос:

> На какие обязательные единицы пользователь уже дал хотя бы один проходной ответ?

Именно это число используется для общего прогресса дня: `0/43`, `22/43`, `43/43`.

Неверный ответ не закрывает шаг. Он отправляет эту же единицу в «Работу над ошибками».

### C. ЗАВЕРШЕНИЕ ДНЯ

День завершён только когда все REQUIRED units закрыты:

`resolvedSteps === totalSteps`.

То есть `43/43` и «день завершён» — одно и то же состояние.

### D. КАЧЕСТВО ПЕРВОЙ ПОПЫТКИ

Отдельно храним, как пользователь ответил **с первого раза**:

- обычные задания — верно / неверно;
- speed — вовремя / медленно / не совпало;
- listening — верно / неверно;
- speaking — распознано / не распознано.

Работа над ошибками может довести день до `43/43`, но никогда не переписывает first-pass result.

Именно first-pass quality влияет на ранний SRS/Review. Поэтому можно завершить день после исправления всех ошибок, но итог честно останется, например, «с первого раза 5 из 19».

# 3. Что считается обязательным шагом

Для каждого roadmap day строится один канонический `DayStepPlan`.

Он используется всеми экранами.

## Обычные типы

| Тип | Сколько обязательных шагов |
|---|---:|
| theory | 0 |
| plan / «задание дня» | 0 |
| choice | 1 |
| text-input | 1 |
| translation | 1 |
| pattern-drill / drill | число phrase items |
| pattern-drill / listening | число phrase items |
| pattern-drill / speaking | число phrase items |
| dialogue | 1 блок, пока не введён детерминированный line-level progress |
| ai-conversation | 1 блок |
| review-only day | отдельная модель Review, не смешивать с lesson task count |

Важно: считаются только REQUIRED sections. Необязательная практика не увеличивает знаменатель.

## Пример День 3

Если фактически в дне:

- обычные задания: 19;
- На скорость: 8;
- Слушание: 8;
- Говорение: 8;

то канонический total:

`19 + 8 + 8 + 8 = 43`.

Today не имеет права показывать `21/21`, потому что это количество внутренних activity ID, а не количество заданий, которые проходит человек.

# 4. Как считать прогресс

Общий прогресс дня — это число **закрытых** required units, а не число показанных пользователю экранов.

## Fresh start

До начала:

`0 / 43`

CTA:

`Начать`

## Частично пройдены обычные задания

Если пользователь увидел 9 заданий, но только 6 из них решил правильно:

- cursor внутри раздела: **Задание 9 из 19**;
- resolved section progress: `6/19`;
- overall day progress: `6/43`;
- 3 ошибки лежат в correction queue.

CTA после выхода:

`Продолжить`

Повторный вход восстанавливает и cursor, и очередь ошибок.

## Первый проход обычных заданий закончен

Например:

- увидел все 19;
- 14 правильных;
- 5 неправильных.

Это НЕ `19/43`.

Состояние:

- tasks resolved: `14/19`;
- day: `14/43`;
- phase: **Работа над ошибками · осталось 5**.

Ошибочные 5 заданий идут снова. Правильно исправленное задание становится resolved. Неверное снова уходит в конец очереди.

Когда correction queue опустела:

- tasks: `19/19`;
- day: `19/43`;
- автоматически открывается следующий required section.

## На скорость

Во время первого прохода отдельно показываем cursor:

**Фраза 3 из 8**

Если из первых трёх две закрыты, общий day progress вырос только на 2.

После первого прохода все медленные/несовпавшие фразы уходят в «Работу над ошибками» этого режима и повторяются, пока каждая не пройдёт критерий.

## После всех четырёх частей

Только после того как correction queues во всех required sections пусты:

`43 / 43`

Это всегда означает:

- все обязательные единицы хотя бы один раз пройдены успешно;
- день засчитан;
- следующий roadmap node может открыться.

Нельзя иметь состояние `43/43` + «День пока не засчитан».


# 5. Что делать с неверными ответами

Используем Duolingo-подобную модель: ошибка возвращается в конец текущего урока и должна быть исправлена.

## Единица состояния

Каждая required unit имеет одно из состояний:

- `unseen` — ещё не показывали;
- `pending_correction` — уже ошиблись, нужно повторить;
- `resolved` — хотя бы один раз успешно выполнено.

Дополнительно отдельно хранится immutable для этого first run:

- `firstPassResult`;
- число correction attempts.

## Обычные задания

Первый неверный ответ:

1. фиксируется как first-pass error;
2. SRS получает слабый результат;
3. unit переходит в `pending_correction`;
4. пользователь идёт дальше по первому проходу;
5. после конца первого прохода начинается «Работа над ошибками».

В correction phase:

- правильный ответ → `resolved`, unit исчезает из очереди;
- неправильный → unit снова в конец очереди;
- так повторяется **сколько нужно раз**, пока ответ не станет правильным;
- выход из урока просто сохраняет эту очередь, а не сбрасывает её.

## Pattern practice

Точно та же модель применяется на уровне конкретной фразы и режима.

### На скорость

Pass для unit: фраза совпала **и** уложилась в целевое время.

- «Медленно» → pending correction;
- «Не совпало» → pending correction;
- успешная попытка → resolved.

### Слушание

Правильный вариант → resolved. Ошибка → в конец correction queue.

### Говорение

Успешное распознавание/ручное подтверждение корректной фразы → resolved. Ошибка → в конец correction queue.

Для speech обязательно оставить ручной способ засчитать корректную фразу, потому что распознавание может ошибаться.

## «Показать ответ» и commit action

Нельзя использовать одну и ту же кнопку «Показать ответ» для разных смыслов.

Нужно различать:

1. **commit попытки** — пользователь сообщает «я уже ответил / закончил ввод»;
2. **reveal** — пользователь просит показать правильный ответ, не дав проверяемого ответа.

Commit попытки может привести к pass/fail.
Reveal сам по себе никогда не закрывает unit.

Для self-assessment упражнений commit и reveal могут происходить одним UX-шагом: пользователь нажимает **«Готово»**, после чего приложение показывает эталон для сравнения. Но семантически это именно commit попытки, а не «дай мне ответ».

Если пользователь отдельно выбирает **«Показать ответ»**, такая попытка считается fail / pending correction.

## Главный принцип

Ошибка не увеличивает знаменатель.

Если исходно 43 required units, то total всегда 43, даже если фактических попыток стало 70 или 120.

# 6. Что делать с текущим `practice-started`

Сейчас completion проверяет practice через `box > 0`.

Это неверно.

Practice mode сохраняется только после завершения полного захода. Поэтому live practice record уже сам по себе является доказательством, что режим был пройден.

P0-правило:

- нет live record → режим ещё не завершён;
- есть live record с box 0 → режим завершён плохо;
- есть live record с box 1–4 → режим завершён успешно.

Нужно изменить это одинаково в:

- `isNodeRequirementComplete`;
- `missingForNode`;
- `lessonSectionStates`;
- `firstPatternMode`;
- любых других местах, где `box > 0` используется как completion.

P1 после стабилизации:

- переименовать schema requirement из `practice-started` в `practice-completed`;
- старое имя читать для backward compatibility;
- новый importer/admin должен писать только новое имя.

Так смысл больше нельзя будет снова перепутать с SRS score.

# 7. Работа над ошибками и знаменатель

Знаменатель дня фиксирован контентом.

Ошибки не создают новые required units, а меняют состояние существующих.

Пример: из 19 обычных заданий с первого раза правильно 9.

После первого прохода:

- resolved: `9/19`;
- correction queue: 10;
- day progress: `9/43`;
- first-pass score: `9/19`.

Дальше correction queue повторяется до пустого состояния.

Если из десяти ошибок пользователь:

- 6 исправил;
- 4 снова сделал неправильно,

то:

- resolved: `15/19`;
- correction queue: 4.

Эти четыре снова уходят в конец и повторяются ещё раз.

### Если неверно вообще всё

Если все 43 first-pass ответа плохие:

- после первого прохода resolved = `0/43`;
- correction queue = 43;
- day ещё НЕ завершён.

Затем пользователь исправляет ошибки. Каждая впервые успешная correction закрывает одну unit:

`0/43 → 1/43 → 2/43 → … → 43/43`.

Только на `43/43` день завершается.

При этом итоговая статистика первой попытки остаётся плохой:

- first-pass quality может быть `0/43`;
- correction attempts могут быть 60+;
- day completion = true только после исправления всех 43.

### SRS при correction

Correction attempts **не должны повторно грейдить SRS как новые независимые ответы**.

Иначе ошибка, а затем правильная correction через 20 секунд искусственно поднимет box и скроет слабое место.

Правило:

- SRS нового материала планируется по first-pass result;
- first-pass wrong → слабый box / earliest Review со следующего календарного дня;
- correction нужна для завершения урока, но не «лечит» SRS-ошибку этого дня;
- first-pass correct → обычное продвижение SRS.

Это также устраняет уже известную проблему, когда «ошибка + исправление» выглядели для интервалов почти как два независимых ответа.


# 8. Финальный экран дня

Финальный экран показывается только когда:

- все required units имеют `resolved`;
- все correction queues пусты.

Нормальный flow:

`Теория → Задания → их ошибки → На скорость → его ошибки → Слушание → его ошибки → Говорение → его ошибки → Итог`

Можно разрешить свободно переключаться между sections, но финал возможен только после закрытия всего.

## Итог при низкой first-pass точности

Пример:

**День 3 завершён**

`43 из 43`

Дальше качество первой попытки отдельно:

- Задания: 5 из 19 верно с первого раза
- На скорость: 2 из 8 вовремя с первого раза
- Слушание: 3 из 8 верно с первого раза
- Говорение: 2 из 8 распознано с первого раза

Дополнительно можно показать:

**Исправлено ошибок: 31**

Текст:

`Слабые фразы вернутся в «Повторе».`

Крайний пример:

- все 43 first-pass ответа плохие;
- затем пользователь исправил их все;
- итог: День `43/43`, завершён;
- first-pass quality остаётся 0 по соответствующим метрикам;
- Review со следующего дня получает слабые units.

Нельзя заменять разные метрики одним «0/43 верно»: скорость, слушание и речь имеют разную семантику.


# 9. Что означает верхний progress внутри урока

Нужно явно различать cursor и resolved progress.

## В обычном первом проходе

Основная подпись:

**Задание 9 из 19**

Это позиция, а не утверждение «9 заданий закрыто».

Дополнительно можно показывать состояние сегментов: правильные / ошибки / ещё не пройденные.

## В работе над ошибками

Вместо ложного `19/19`:

**Работа над ошибками · осталось 5**

Каждый исправленный ответ уменьшает число.

## Practice

Аналогично:

- **Фраза 3 из 8** во время первого прохода;
- **Работа над ошибками · осталось 2** после первого прохода.

## Today / Route

Там показывается только resolved progress:

`15 из 43`.

То есть Today никогда не считает ошибочно отвеченную unit выполненной.

Если нужен общий secondary label внутри runner:

`За день закрыто: 15 из 43`.

Все эти числа приходят из одного DayProgress selector, но отображают разные его поля: cursor, pendingCorrections и resolvedSteps.

# 10. Единый источник истины

Нужно удалить идею, что каждый экран сам считает progress.

Добавить один selector/service:

`getDayProgress(set, node, courseProgress, activeLessonRun)`

Он возвращает:

```ts
{
  status: 'not_started' | 'in_progress' | 'complete',
  totalSteps: number,
  completedSteps: number,
  attemptedSteps: number,
  pendingCorrections: number,

  sections: [
    {
      id: 'tasks' | 'drill' | 'listening' | 'speaking' | ...,
      required: boolean,
      totalSteps: number,
      completedSteps: number,
      attemptedSteps: number,
      pendingCorrections: number,
      status: 'not_started' | 'in_progress' | 'correcting' | 'complete'
    }
  ],

  nextRequiredSection: ...,
  firstPassResults: ...,
  dayComplete: boolean
}
```

Этот selector обязан использоваться в:

- Today;
- Route;
- lesson header;
- lesson navigator;
- финальном экране;
- unfinished reminder;
- resume decision;
- completion / unlock logic.

Запрещено иметь отдельные `nodeDoneCount`, `missingForNode`, section completion и summary semantics, которые могут разойтись.

Внутренние helpers допустимы, но итоговое состояние должно собираться одним модулем и покрываться одной таблицей тестов.

# 11. Что хранить в course progress и lesson run

## CourseProgress — долговременная история

Хранит:

- graded card/SRS state;
- завершённые practice runs и их SRS result;
- seen/completed durable activities;
- completed day state;
- learning days;
- stats.

Это источник для roadmap и Review.

## LessonRun — незавершённая текущая сессия

Хранит точное место:

- active section;
- regular task cursor;
- результат первого ответа по стабильному step ID;
- retry/correction queue с количеством неудачных correction attempts;
- immutable first-pass result по stable unit ID;
- drill cursor + item state;
- listening cursor + item state;
- speaking cursor + item state;
- выбранный answer / открытый feedback, если нужно восстановить экран;
- updatedAt.

LessonRun не должен конкурировать с CourseProgress.

Правило:

- завершённое durable действие → CourseProgress;
- ещё незавершённая позиция → LessonRun;
- `getDayProgress` объединяет оба слоя.

# 12. Выход из урока и возврат

Текст «Прогресс сохранён» разрешён только если выполняются следующие условия.

После выхода:

1. Today показывает тот же overall progress.
2. Повторный вход открывает тот же required section.
3. Внутри section сохраняется тот же phrase/task progress.
4. Переключённые ранее режимы не теряют состояние.
5. Уже завершённые sections не становятся незавершёнными.
6. Accuracy не обнуляется.

Пример:

- tasks 19/19;
- drill 6/8;
- listening 2/8;
- speaking 0/8.

Today:

`27 / 43`

Повторный вход:

- открывается последний активный section;
- если это Listening → `2/8`;
- Drill по вкладке сразу показывает `6/8`.

Никаких `0/8` на первый render.

# 13. App kill / reload

Закрытие процесса и перезапуск приложения на том же устройстве должно быть эквивалентно обычному выходу через popup.

Обязательные проверки:

- refresh web;
- Android process kill;
- Android swipe-away;
- обычный закрывающий X;
- system Back → exit;
- уход на Today после подтверждения.

Во всех случаях одна и та же позиция.

# 14. Повторное прохождение дня

Нужно различать три действия.

## Продолжить

Для незавершённого дня это действие по умолчанию.

- открывает точное сохранённое место;
- продолжает canonical first run;
- не сбрасывает уже сделанные части.

## Пройти с начала

Доступно из меню незавершённого дня.

Это НЕ «стереть попытку».

- визуально открывает день с первого раздела;
- уже завершённые шаги идут как practice/replay и не засчитываются второй раз;
- их первый результат и SRS не переписываются;
- когда пользователь доходит до ещё незавершённых шагов, они продолжают исходный canonical run;
- общий progress дня не откатывается.

Таким образом можно посмотреть/пройти текущий день заново, не ломая resume и статистику.

## Пройти ещё раз

Для уже завершённого дня это чистый REPLAY.

Правила:

- roadmap day остаётся complete;
- Today остаётся `43/43`;
- replay не может снова заблокировать следующий день;
- replay progress хранится отдельно от canonical first completion;
- replay score подписывается как результат повторного прохождения;
- first-pass статистика не меняется;
- SRS/due не меняются: для интервального закрепления существует отдельный раздел «Повтор»;
- replay может считаться учебной активностью для календаря/серии, но не считается элементом SRS-«Повтора».

Терминологически в UI не называть ручное повторное прохождение дня просто «Повтором», потому что «Повтор» уже означает интервальную очередь. Использовать «Пройти ещё раз».

# 15. Переходы между sections

Навигация никогда не меняет progress сама по себе.

Клик:

- Теория;
- Задания;
- На скорость;
- Слушание;
- Говорение

только меняет видимый section.

Ничего не сбрасывает.

Если пользователь впервые открывает новый section, он начинается с 0/N.
Если возвращается в уже начатый — сразу с сохранённого X/N.
Если возвращается в complete — показывает complete/result state или предлагает replay, но completion не исчезает.

# 16. CTA «Скажи вслух» на Today

Это отдельный быстрый вход в speaking section текущего дня.

Он не является отдельным обязательным «заданием дня».

Правила:

- CTA называется действием: «Начать практику»;
- открывает speaking section;
- остальные required sections остаются как были;
- завершение speaking учитывается в тех же 8 шагах дня;
- никакого второго независимого прогресса для этой карточки нет.

Plan/theory note с примерами — контент-подсказка, не отдельный completion requirement.

# 17. Route

Route использует тот же `getDayProgress`.

Состояния:

- 0/N → не начат;
- 1…N-1/N → в процессе;
- N/N → complete.

Нельзя выводить complete на Route, если Today или runner считает день incomplete.

# 18. Обновление контента

## День ещё не завершён

Run remap по стабильным IDs:

- существующие шаги сохраняются;
- удалённые исчезают;
- новые required steps добавляются как pending;
- cursor выбирается на ближайший незавершённый stable step.

## День уже завершён

При `revisionProgress: preserve` обновление курса не должно внезапно отнимать завершение дня.

Новые задания в старый завершённый день доступны в replay, но roadmap назад не блокируется.

Только явный `revisionProgress: reset` может потребовать повторного completion.

# 19. Save failure

Нельзя оптимистично показывать durable completion, если запись не сохранилась.

Если сохранение результата шага или завершения section упало:

- текущий экран остаётся;
- progress не продвигается в durable части;
- показывается «Не удалось сохранить» + retry;
- повторный tap retry должен быть idempotent.

После успешного save все поверхности получают одинаковое новое состояние.

# 20. Offline

На одном устройстве offline progress считается полноценным локальным progress:

- Today обновляется сразу;
- resume работает;
- day completion работает;
- при появлении сети sync не должен откатывать local newer state.

Merge не должен превращать completed mode с `box=0` обратно в incomplete.

# 25. Acceptance criteria

Работа считается законченной только если для любого момента урока можно задать три вопроса и получить один ответ во всём приложении:

1. Сколько обязательных шагов реально пройдено?
2. Завершён ли день?
3. Каков результат/качество?

И самое важное инвариантное правило:

> Если UI показывает `N из N` обязательных шагов, день обязан быть завершён.

Никаких отдельных трактовок этого правила в Today, Route, runner, summary или SRS быть не должно.

# 26. Решения по спорным кейсам — 2026-10-05

Этот раздел является более новым уточнением к правилам выше. При конфликте ориентироваться на него.


## 26.1. Что если все 43 first-pass ответа неправильные

Решение изменено: используем blocking «Работу над ошибками», как в Duolingo.

После первого прохода:

- attempted: 43/43;
- resolved: `0/43`;
- correction queue: 43;
- day complete: нет;
- first-pass quality: 0.

Дальше приложение показывает ошибки повторно.

Правильная correction:

- закрывает эту unit;
- увеличивает resolved на 1;
- удаляет unit из correction queue.

Повторная ошибка:

- не закрывает unit;
- отправляет её снова в конец очереди.

Пример:

`0/43 → 8/43 → 20/43 → 37/43 → 43/43`.

Только после последней исправленной ошибки:

- day complete = true;
- следующий день unlocked;
- Today может показать «День 3 завершён»;
- first-pass quality всё равно остаётся 0;
- все слабые units получают ранний Review начиная со следующего дня.

Таким образом `43/43` по-прежнему имеет одно значение: **43 обязательные units уже успешно закрыты**, а не просто были показаны пользователю.

## 26.2. Что если выполнено всё, кроме «На скорость»

Для примера 19 + 8 + 8 + 8:

- tasks: 19/19;
- drill: 0/8;
- listening: 8/8;
- speaking: 8/8;
- overall: `35/43`;
- day complete: нет.

Today:

**День 3 · 35 из 43**

Подпись:

**Осталось: На скорость · 8**

Primary CTA:

**Продолжить**

Нажатие ведёт сразу в первый незавершённый required section — «На скорость», а не в начало дня.

Порядок прохождения вкладок может быть свободным, но completion — только когда закрыты все required sections.

## 26.3. Как формируется «Повтор»

### Источники

В Review попадают только уже изученные единицы:

1. обычные задания, которым по SRS пора повторяться;
2. конкретные phrase+mode units из «На скорость»;
3. конкретные phrase+mode units из «Слушания»;
4. конкретные phrase+mode units из «Говорения»;
5. сохранённые пользователем слова;
6. due-элементы из других уже начатых курсов.

### Atomic unit

Ключевое изменение относительно текущей реализации:

- card: `activityId`;
- pattern phrase: `activityId + mode + itemId`;
- saved word: `lexemeId + senseId`.

Одна плохая фраза не должна заставлять повторять весь pattern из 8 фраз.

### Когда новая ошибка попадает в Review

Во время текущего урока ошибка обязана быть исправлена в blocking correction queue.

При этом SRS ориентируется на **first-pass result**, а не на последнюю correction:

- first-pass wrong → слабый SRS state;
- одна или десять subsequent corrections не повышают box;
- после успешной correction unit считается закрытой для дня;
- **в отдельном Review она не появляется в ту же минуту**;
- earliest due — следующий календарный день.

Это важно: «Работа над ошибками» завершает сегодняшний урок, а «Повтор» закрепляет слабое место позже. Это две разные механики.

### Как набирается дневная сессия

1. Собрать все units с `due <= today` из всех изученных курсов и слов.
2. Самые просроченные имеют приоритет.
3. При одинаковом due перемешивать категории/курсы round-robin, чтобы не было 20 однотипных заданий подряд.
4. Базовая дневная норма: **20**.
5. Если due больше 20, показать, например: **«Сегодня 20 · ещё 23 ждут»**.
6. После 20 предложить **«Ещё 10»**. Это добровольное расширение, а не требование.
7. Невзятый остаток никуда не исчезает и остаётся due.

### Ошибка внутри Review

Для согласованности используем ту же mental model:

- неверный ответ уходит в конец текущей Review-сессии;
- повторяется до правильного ответа либо до явного выхода пользователя из сессии;
- выход сохраняет незакрытые review-units due;
- правильный ответ завершает unit на сегодня и двигает её по SRS.

Дневной лимит 20 относится к числу уникальных units, взятых в сессию. Correction attempts этих 20 не расходуют дополнительные места дневного лимита.

Correction в уроке и Review grade не должны дважды считать один исходный ответ.

## 26.4. Что показывает Today после 43/43

Сразу после завершения дня hero не должен мгновенно превращаться в безличный `День 4 · 0/N`.

Пока пользователь явно не начал следующий день, Today показывает:

**✓ День 3 завершён**

**43 из 43**

Дополнительно можно одной строкой:

**Слабые места появятся в «Повторе»**

Кнопки:

- primary: **Начать День 4** — если он доступен;
- secondary/menu: **Пройти ещё раз**.

Как только пользователь начал День 4, hero становится прогрессом Дня 4.

Если День 4 не начали до следующего календарного дня, Today может сразу сделать его текущим hero, а завершённый День 3 остаётся виден в Route/истории.

Review — отдельная карточка «Нужно сегодня». Она не смешивается с `43/43` дня.

## 26.5. Сброс статистики и сброс курса — разные действия

Нельзя делать одну кнопку «Сбросить всё»: непонятно, должен ли пользователь потерять маршрут.

### Сбросить статистику

Очищает только отчётные данные:

- attempts/correct/wrong;
- speed/listening/speaking aggregate metrics;
- историю learning-days/серию, если в UI действие явно называется **«Сбросить статистику и серию»**.

Не меняет:

- какие дни завершены;
- какие дни открыты;
- текущий day progress;
- entitlement/покупку;
- SRS/review state.

После такого сброса открытые дни остаются открытыми.

### Начать курс заново

Отдельное destructive действие с подтверждением.

Для выбранного курса очищает:

- completed/seen course progress;
- card SRS;
- pattern phrase SRS;
- active LessonRun;
- course stats;
- course learning history.

После reset:

- День 1 доступен;
- последующие дни снова закрыты prerequisite-логикой;
- покупка/entitlement остаётся;
- личные сохранённые слова не удаляются, потому что они глобальные и могут относиться к другим курсам.

Если когда-нибудь понадобится глобальный wipe всех курсов и слов, это третье, ещё более явное действие, а не побочный эффект «Начать курс заново».

## 26.6. Как пройти текущий день заново

Resume всегда остаётся default:

**Продолжить** → ровно с сохранённого места.

Но пользователь может вручную выбрать:

### Незавершённый день → «Пройти с начала»

- открываем первый раздел;
- canonical progress НЕ обнуляем;
- уже завершённые шаги показываются как повторная практика;
- они не меняют first-pass score и SRS;
- когда доходишь до ещё незавершённых шагов, продолжается исходное прохождение;
- Day progress растёт только на реально новые completed steps.

Это не SRS-«Повтор».

### Завершённый день → «Пройти ещё раз»

- чистый replay;
- `43/43` остаётся;
- следующий день не блокируется;
- first-pass stats не меняются;
- SRS/due не меняются;
- replay result можно показать отдельно как «Результат повторного прохождения».

Это тоже не раздел «Повтор».

Раздел **«Повтор»** — только автоматически сформированная интервальная очередь due-units.

## 26.7. Термины, которые нельзя смешивать

- **Продолжить** — resume незавершённого canonical run.
- **Пройти с начала** — посмотреть незавершённый день с начала без стирания progress.
- **Пройти ещё раз** — ручной replay завершённого дня.
- **Повтор** — автоматическая SRS-очередь.
- **Сбросить статистику** — стереть отчётные метрики, не маршрут.
- **Начать курс заново** — стереть learning progress выбранного курса и снова закрыть маршрут.

Эти действия должны иметь разные названия и разные события аналитики.

# 27. Решение: blocking «Работа над ошибками» — 2026-10-05

Это решение заменяет более раннее предположение, что плохо выполненная, но показанная unit уже считается завершённой.

Каноническое правило:

> Required unit закрыта только после хотя бы одного успешного ответа в текущем canonical run.

Первый неправильный ответ сохраняется навсегда как first-pass error этого прохождения, но сама unit повторяется в конце урока столько раз, сколько требуется для успешного ответа.

Следствия:

1. `attemptedSteps` и `resolvedSteps` — разные поля.
2. Today/Route используют только `resolvedSteps / totalSteps`.
3. Runner может показывать cursor «Задание 12 из 19», но не выдавать это за completion.
4. Correction queue является blocking и переживает exit/reload.
5. Неправильная correction снова возвращается в конец очереди без лимита.
6. `43/43` возможно только после успешного закрытия всех 43 units.
7. First-pass score после corrections не улучшается.
8. SRS нового материала грейдится по first-pass result; correction не повышает box.
9. Ошибочная first-pass unit после успешной correction всё равно возвращается в интервальный Review со следующего дня.
10. Total дня никогда не растёт из-за повторных попыток.

# 28. Контракт кнопок и зачёта по каждому типу упражнения — 2026-10-05

Проблема: одинаковые слова вроде «Показать ответ», «Готово», «Совпало» сейчас в разных упражнениях означают разные события. Для новой correction-модели нужно зафиксировать **точку commit** и **условие pass** отдельно по каждому типу.

Общий принцип:

> В progress идёт не нажатие кнопки само по себе, а результат завершённой попытки конкретной unit.

Для каждой механики должны быть четыре явно определённых события:

1. `attempt_started` — пользователь начал отвечать;
2. `attempt_committed` — ответ зафиксирован;
3. `attempt_passed` или `attempt_failed`;
4. при fail — unit добавлена/возвращена в correction queue.

## 28.1. Choice — выбор варианта

Flow:

1. Первый tap по варианту — только выбор.
2. Второй tap по выбранному варианту — commit.
3. Верный вариант → `resolved`.
4. Неверный → first-pass error / correction queue.

До второго tap пользователь может менять выбор сколько угодно — это не попытки.

UI:
- отдельная кнопка «Проверить» не нужна;
- выбранный вариант визуально становится готовым к подтверждению;
- второй tap подтверждает.

В correction phase та же механика.

## 28.2. Собрать фразу из слов / chips

Flow:

1. Пользователь собирает ответ.
2. Primary: **«Готово»**.
3. «Готово» = commit собранной фразы.
4. Совпало с допустимым ответом → resolved.
5. Ошибка → correction queue.

Если есть действие **«Показать ответ»**:
- оно считается fail;
- правильный ответ показывается;
- unit обязательно возвращается позже.

Показ эталона после уже committed wrong-answer не создаёт вторую попытку.

## 28.3. Письменный перевод / text input

Flow:

1. Ввод текста.
2. Primary: **«Готово»**.
3. Пустой ответ нельзя commit.
4. Correct/near-pass по правилам checker → resolved.
5. Wrong → correction queue.

Если приложение предлагает «Показать ответ»:
- это surrender/fail;
- unit не закрывается;
- позже повторяется без заранее открытого ответа.

## 28.4. «На скорость»

Текущий текст **«Показать ответ»** на основном экране неправильный по смыслу.

Пользователь уже должен произнести фразу, а кнопка должна означать:

> «Я закончил говорить, теперь хочу свериться».

Поэтому primary меняем на:

**«Готово»**

Не использовать:
- «Сказал»;
- «Уже сказал»;
- «Произнёс»,

потому что это гендерные формы и они хуже масштабируются на локализации.

### Flow

1. Показываем русскую фразу.
2. Запускается таймер.
3. Пользователь произносит английский ответ вслух.
4. Нажимает **«Готово»**.
5. В этот момент:
   - фиксируется elapsed time;
   - попытка считается committed;
   - открывается английский эталон.
6. Пользователь выбирает:
   - **«Не совпало»**
   - **«Совпало»**

### Pass

Для completion дня содержательная правильность важнее скорости.

Unit resolved, если пользователь после своей попытки выбрал **«Совпало»**.

Время — отдельная quality-метрика:

- «Совпало» + вовремя → resolved + strong speed result;
- «Совпало» + медленно → resolved + weak speed result, ранний Review;
- «Не совпало» → fail + correction queue.

Timeout сам по себе не должен автоматически раскрывать ответ и превращать попытку в fail. После истечения времени UI меняет статус на **«Медленно»**, но ждёт, пока пользователь нажмёт **«Готово»**, после чего открывает эталон и даёт выбрать «Не совпало / Совпало».

Так «На скорость» тренирует скорость, но не запирает прогресс, если фраза сказана правильно чуть медленнее.

### Почему «Готово» не засчитывает само по себе

Приложение не слышит содержание ответа в speed self-assessment.

Поэтому «Готово» означает только:

`attempt_committed`

А **«Совпало»** определяет `attempt_passed`; время сохраняется отдельно как quality.

Это именно тот кейс со скриншота: кнопка должна быть не «Показать ответ», а **«Готово»**.

## 28.5. Слушание

Действия «Прослушать» / «Ещё раз» не являются попытками и не влияют на progress.

Flow:

1. Пользователь слушает фразу.
2. Первый tap по варианту перевода — selection.
3. Второй tap — commit.
4. Correct → resolved.
5. Wrong → correction queue.

Количество переслушиваний можно хранить как диагностику/аналитику, но оно не меняет pass.

В correction phase фразу можно снова прослушать.

## 28.6. Говорение с распознаванием

Основной путь:

1. **«Нажми и скажи»** запускает recognition.
2. Завершение распознавания = commit попытки.
3. Matcher нашёл допустимый ответ → resolved.
4. Matcher не нашёл → fail / correction queue.

### Ошибка распознавания телефона

Нельзя заставлять пользователя повторять правильную речь из-за ASR.

При mismatch до reveal показываем два понятных действия:

- **«Повторить»**
- **«Я сказал правильно»**

**«Я сказал правильно»** = manual pass и закрывает unit.

Название «Всё же засчитать» хуже: звучит как обход правил. Лучше явно сказать, что пользователь подтверждает корректность своей речи.

### «Показать ответ»

Здесь это настоящий reveal/surrender.

Если пользователь нажал **«Показать ответ»**:

- текущая попытка = fail;
- ответ показывается;
- unit остаётся pending correction;
- после reveal нельзя предлагать «Я сказал правильно» для той же попытки.

Иначе человек сможет сначала посмотреть правильный ответ, потом нажать manual pass.

### Нет permission / ASR unsupported

Нужен fallback self-assessment:

1. пользователь говорит без автоматической проверки;
2. нажимает **«Готово»**;
3. видит эталон;
4. выбирает «Не совпало / Совпало».

То есть fallback повторяет механику speed, но без критерия времени.

## 28.7. Dialogue

Диалог лучше считать не одним непрозрачным блоком, а набором learner-turn units.

Для каждой реплики пользователя:

- текстовый ответ → **«Готово»** = commit;
- голосовой ответ → окончание recognition = commit;
- acceptable answer → resolved;
- плохой ответ → эта конкретная реплика в correction queue.

После ошибки можно показать хороший пример, но он не закрывает unit.

После прохождения остальных реплик ошибочные learner turns возвращаются в конце диалога до успешного ответа.

Если технически line-level progress пока не готов, временный block-level completion допустим только как миграционный этап, но целевая модель — line-level.

## 28.8. AI conversation

Это исключение: здесь нет единственного правильного ответа.

Поэтому нельзя использовать обычную correction queue по matcher.

Completion строится по факту участия:

- достигнуто минимальное число learner turns / выполнена цель сценария;
- пользователь завершил разговор;
- AI feedback может указать ошибки, но не блокирует completion дня.

Ошибочные конструкции из AI-разговора при наличии надёжного extractor могут позже создавать отдельные review units, но это другой механизм.

## 28.9. Theory и plan task

Theory:
- не является scored unit;
- чтение не увеличивает `resolvedSteps`.

Plan / «Скажи вслух о себе» на Today:
- не создаёт второй параллельный progress;
- если это просто свободная практика — optional;
- если продукт решит сделать её required, для неё нужен отдельный explicit completion contract, а не «считаем открытие popup выполнением».

## 28.10. Word Review

Это не lesson progress, но UX должен следовать той же терминологии.

Flow:

1. **«Показать слово»** = reveal, не pass.
2. После reveal:
   - **«Не помню»** → fail;
   - **«Помню»** → pass текущей review-unit.

Если Review использует blocking correction:
- «Не помню» возвращает слово в конец текущей review-сессии;
- «Помню» закрывает его на сегодня.

Здесь reveal нормален, потому что сама задача — self-assessment памяти. Он не должен путаться с lesson-кнопкой «Показать ответ».

## 28.11. Mixed drill / дополнительная практика

Механика может повторять «На скорость»:

**Готово → эталон → Не совпало / Совпало**

Но:
- не влияет на canonical day progress;
- не переписывает first-pass stats урока;
- не должен менять SRS, если mixed drill остаётся дополнительной практикой.

## 28.12. Единые названия кнопок

Рекомендуемый словарь:

| Ситуация | Primary / action |
|---|---|
| Закончил ввод/сборку | **Готово** |
| Закончил произносить без ASR | **Готово** |
| Хочу услышать/увидеть эталон после своей попытки | эталон открывается после **«Готово»**, отдельной кнопки не нужно |
| Не знаю ответ и хочу сдаться | **Показать ответ** |
| Self-assessment negative | **Не совпало** |
| Self-assessment positive | **Совпало** |
| ASR ошибся, но я точно сказал правильно | **Я сказал правильно** |
| Повторить попытку сейчас | **Повторить** |

Позитивная бинарная кнопка всегда справа.

## 28.13. Главный технический инвариант

Компонент упражнения не должен напрямую решать, «прибавить ли +1 к прогрессу».

Он должен эмитить нормализованный result:

```ts
{
  unitId,
  attemptId,
  firstPass: boolean,
  outcome: 'pass' | 'fail',
  reason:
    | 'correct'
    | 'wrong'
    | 'slow'
    | 'timeout'
    | 'revealed'
    | 'speech_mismatch'
    | 'manual_speech_pass',
  elapsedMs?: number
}
```

DayProgress / correction engine уже решает:

- resolved ли unit;
- нужно ли вернуть её в correction queue;
- что записать как first-pass quality;
- как это повлияет на SRS.

Это предотвращает ситуацию, когда одна кнопка «Показать ответ» в одном компоненте означает fail, а в другом случайно означает completion.

# 29. Что ещё обязательно зафиксировать до реализации — 2026-10-05

Ниже — правила, без которых даже правильная модель `43/43` снова разъедется на edge cases.

## 29.1. Где именно проходит «Работа над ошибками»

Default flow — **по разделам**, а не одна огромная куча в самом конце дня.

Пример:

`Задания → ошибки заданий → На скорость → ошибки speed → Слушание → ошибки listening → Говорение → ошибки speaking → Итог`.

Почему:

- пользователь остаётся в одном типе механики;
- resume проще и понятнее;
- не нужно в конце прыгать между четырьмя разными UI;
- section можно честно пометить complete только после очистки его correction queue.

При этом ручные вкладки остаются свободными. Пользователь может уйти в другой section, но незакрытые ошибки предыдущего никуда не исчезают и продолжают блокировать day completion.

## 29.2. Что делает «Продолжить»

Правило приоритета:

1. если есть активная незавершённая попытка — вернуть ровно в неё;
2. если активной попытки нет, но есть correction queue последнего section — открыть её;
3. иначе открыть первый unresolved required section по каноническому порядку;
4. завершённый section никогда не стартует заново по обычному «Продолжить».

Это нужно, чтобы «Продолжить» не означало то resume, то «первый незакрытый», в зависимости от экрана.

## 29.3. Переключение вкладки во время незавершённой попытки

Переход в другой section до commit:

- не считается ошибкой;
- не меняет first-pass result;
- сохраняет текущую unit как `in_progress`;
- при возврате открывает её заново.

Для timed speed:

- незакоммиченная попытка при уходе не считается `slow`/fail;
- таймер при возврате стартует заново;
- first-pass фиксируется только после **«Готово» → Совпало/Не совпало**.

Иначе случайный свайп/Back будет портить статистику.

## 29.4. Техническая ошибка — не ошибка ученика

Следующие события не должны становиться `attempt_failed`:

- нет сети;
- сервер/save временно недоступен;
- speech recognition unsupported;
- permission denied;
- recognizer crash/network error;
- TTS не запустился;
- приложение ушло в background до commit.

Они дают retry/fallback, но не:

- уменьшают first-pass quality;
- отправляют unit в correction queue;
- грейдят SRS как wrong.

`no-speech` тоже лучше считать «не удалось получить ответ», а не учебной ошибкой: дать повторить попытку.

## 29.5. Near miss / опечатки

Нужно иметь минимум три результата checker:

- `pass` — содержательно верно;
- `near` — мелкая опечатка/форма, смысл очевидно верный;
- `fail` — неправильный ответ.

Рекомендуемое правило:

- `pass` → resolved, strong quality;
- `near` → resolved, но first-pass quality = weak; показать короткую подсказку и вернуть раньше в Review;
- `fail` → correction queue.

Near miss не должен заставлять человека бесконечно перепечатывать очевидно правильную фразу из-за одной буквы.

## 29.6. Reveal / «Показать ответ»

Единое правило для scored lesson units:

- reveal до корректного commit = first-pass fail;
- unit остаётся unresolved;
- показываем эталон;
- позже unit возвращается в correction queue;
- после reveal нельзя нажать «засчитать всё равно» для той же попытки.

Исключение: Word Review, где reveal — сама механика memory self-assessment.

## 29.7. Manual pass в speaking

**«Я сказал правильно»** разрешён только как защита от плохого ASR.

Он:

- закрывает unit для day completion;
- фиксирует outcome `manual_speech_pass`;
- не должен считаться таким же сильным SRS-сигналом, как уверенный automatic match;
- может планировать более ранний Review;
- недоступен после reveal эталона.

Это убирает и ложные блокировки, и лёгкий способ случайно «накликать» strong SRS.

## 29.8. Теория и plan не могут скрыто блокировать `43/43`

Если theory/plan имеют `0` в `DayStepPlan`, они **не имеют права быть отдельным completion requirement**.

Иначе снова возможно:

`43/43`, но day incomplete из-за непрочитанной теории.

Выбираем одно:

- theory/plan non-blocking и не входят в denominator — текущая рекомендация;
- либо если когда-то захотим делать теорию обязательной, она получает явную required unit и увеличивает total.

Скрытых requirements вне DayStepPlan быть не должно вообще.

## 29.9. Section status

У каждого section ровно четыре состояния:

- `not_started`;
- `in_progress`;
- `correcting`;
- `complete`.

Navigator может показывать:

- пусто;
- частичный progress;
- badge/маркер ошибок;
- check.

Нельзя показывать section как complete, пока correction queue не пуст.

## 29.10. Один completion event на день

Когда `resolvedSteps === totalSteps`, один раз создаётся durable `day_completed`.

Он должен быть idempotent по `setId + nodeId + completionGeneration`.

Только этот переход:

- разблокирует следующий день;
- фиксирует completedAt;
- отправляет completion analytics;
- может обновить streak;
- показывает celebration/final summary.

Reload, sync, replay и повторное открытие итогового экрана не должны создавать второй completion.

## 29.11. Когда засчитывается календарный день / серия

Для одного canonical completion хранить timestamp и локальную календарную дату момента завершения.

Если урок начат до полуночи, а закончен после:

- completion относится к дню, когда он **завершён**;
- first-pass attempts до полуночи не создают отдельный второй «пройденный день».

Review может отдельно считаться учебной активностью для streak, если продукт этого хочет, но это должно быть одним общим правилом, а не зависеть от экрана.

## 29.12. Local save и remote sync

Успешный ответ сначала должен быть durable локально.

Если local write успешен, а сервер временно недоступен:

- пользователь может продолжать;
- Today/Route показывают новый progress;
- sync доезжает позже.

Если даже local write не удался:

- не двигаем cursor;
- не закрываем unit;
- показываем retry.

Remote sync failure не должен визуально откатывать уже подтверждённый локальный progress.

## 29.13. Merge между устройствами

Resolved progress монотонный:

- если unit resolved хотя бы на одном устройстве, sync не делает её unresolved;
- first-pass result берётся из самого раннего canonical attempt;
- correction queue удаляет уже resolved units после merge.

Exact cursor незавершённой попытки пока можно гарантировать только на одном устройстве.

Если пользователь открывает тот же день на втором устройстве:

- строим состояние из durable resolved/pending units;
- начинаем с первого unresolved;
- не пытаемся угадывать незакоммиченный текст/микрофонную попытку с первого устройства.

## 29.14. Обновление контента во время незавершённого дня

Все required units обязаны иметь stable IDs.

При новой revision:

- существующий stable unit сохраняет resolved/first-pass state;
- удалённая unit удаляется и из correction queue;
- новая required unit добавляется `unseen`;
- изменение порядка не меняет status;
- если semantic answer изменился настолько, что старый result больше нельзя считать валидным, content revision должна явно пометить эту unit resettable.

Никакого сопоставления по тексту «на глаз».

## 29.15. Что считается SRS-сигналом

SRS нельзя кормить любым UI-действием.

Для нового материала сигнал берётся из **первой содержательно завершённой попытки**:

- exact correct → strong;
- near miss → weak;
- speed correct but slow → weak;
- wrong → fail;
- revealed → fail;
- manual speech pass → weak;
- technical error → no grade.

Correction attempts не повышают grade этого же изучения.

Для Review уже новая интервальная попытка создаёт новый SRS grade.

## 29.16. Progress и попытки — разные числа в аналитике

Нужно хранить отдельно:

- required units total;
- resolved units;
- first-pass correct;
- first-pass weak;
- first-pass wrong;
- correction attempts;
- reveals;
- manual speech passes;
- technical retries.

Нельзя потом строить «точность» из общего количества taps/attempts — при correction loop она станет бессмысленной.

## 29.17. Что происходит при «Начать курс заново» во время активного урока

Перед reset:

- закрываем active lesson UI;
- удаляем LessonRun и correction queues выбранного курса;
- создаём tombstones/новую generation для durable progress;
- только после успешного локального reset возвращаем на День 1.

Старые отложенные sync-операции не должны воскресить прогресс после reset. Поэтому reset требует generation/epoch, а не простого удаления localStorage.

## 29.18. Что показывать на Today во время correction

Пример: first pass tasks закончен, 14/19 resolved и 5 ошибок.

Today:

**День 3 · 14 из 43**

Подпись:

**Работа над ошибками · осталось 5**

CTA:

**Продолжить**

После исправления трёх:

**17 из 43 · осталось 2**

То есть correction виден как реальная часть незавершённого дня, а не скрыт внутри runner.

## 29.19. Что ещё остаётся продуктовым выбором

После этих правил остаются только несколько действительно спорных настроек, которые можно менять без разрушения модели:

- считать ли Review активностью для streak;
- насколько раньше возвращать `near`, slow и manual speech pass;
- нужен ли пользователю явный secondary action «Показать ответ» в speed, если **«Готово»** и так открывает эталон;
- нужно ли когда-нибудь синхронизировать exact unfinished LessonRun между устройствами.

Все остальные пункты выше лучше считать инвариантами, а не настройками UI.

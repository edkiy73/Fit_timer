# Fit Timer — план полной локализации RU / EN

Статус: **реализация начата — этап 1 (i18n core + выбор языка)**  
Цель первого релиза локализации: пользователь может выбрать **Русский / English** в настройках, после чего весь интерфейс, системные сообщения, письма, уведомления, озвучка, голосовые команды и генерируемый ИИ контент работают на выбранном языке без смешивания RU/EN.

---

## 1. Главный принцип

Локализация должна быть отдельным слоем приложения, а не набором `if (lang === 'en')` по файлам.

Нужно разделить четыре вещи:

1. **Язык интерфейса** — весь UI приложения, ошибки, подсказки, попапы, кнопки, правила, уведомления.
2. **Язык озвучки** — язык и конкретный TTS-голос.
3. **Язык голосовых команд** — RU/EN офлайн-пакет распознавания.
4. **Язык контента** — программы, упражнения, каталог, ответы ИИ, письма и публичные страницы.

По умолчанию все три пользовательских языка следуют языку интерфейса, но озвучку и голосовые команды можно изменить отдельно.

---

### Реализовано на этапе 1

- добавлены `src/i18n/ru.js`, `src/i18n/en.js`, `src/i18n/index.js`;
- выбор **Русский / English** добавлен в **Другое → Профиль**;
- язык сохраняется локально и в аккаунте;
- новый телефон после входа получает сохранённый язык аккаунта;
- без сохранённой настройки первый запуск выбирает RU для системного `ru*`, иначе EN;
- язык меняется без перезапуска;
- письмо с кодом входа уже приходит на выбранном языке;
- TTS и язык голосовых команд по умолчанию следуют языку приложения, пока пользователь не выбрал их вручную;
- добавлен `npm run i18n:check`;
- начата миграция основных экранов на `data-i18n`; перенос всех остальных UI/dynamic strings остаётся следующими этапами.

## 2. Где хранить выбранный язык

Добавить глобальную настройку:

```js
appLocale = 'ru' | 'en'
```

Хранение:

- локально на устройстве — обязательно;
- в аккаунте — синхронизировать, чтобы новый телефон подхватывал язык;
- при первом запуске без сохранённой настройки:
  - системный язык `ru*` → Русский;
  - всё остальное → English.

При ручном выборе язык меняется сразу, без перезапуска приложения.

### UI

В разделе **Другое → Профиль** или отдельным первым блоком **Язык**:

- Язык приложения
  - Русский
  - English

Не прятать язык внутрь «Звук»: это настройка всего приложения.

## 3. Архитектура переводов

Создать один источник переводов, например:

```
src/i18n/
  ru.js
  en.js
  index.js
```

Ключи — стабильные английские идентификаторы:

```js
{
  common: {
    save: 'Сохранить',
    cancel: 'Отмена'
  },
  account: {
    loginOrRegister: 'Вход или регистрация'
  },
  workout: {
    pause: 'Пауза'
  }
}
```

В English-файле те же ключи.

Базовые функции:

```js
t('account.loginOrRegister')
t('workout.completedCount', { count })
```

Требования:

- fallback всегда на English или явно выбранный базовый язык;
- в production не показывать ключ вроде `account.loginOrRegister`;
- dev/check должен находить отсутствующие ключи;
- нельзя держать один и тот же пользовательский текст одновременно в HTML и JS.

## 4. Статический HTML

Сейчас много русского текста зашито прямо в `src/html/*.html`.

План:

1. Разметку оставить общей.
2. Пользовательские строки заменить на ключи:
   - `data-i18n="..."`
   - `data-i18n-placeholder="..."`
   - `data-i18n-title="..."`
3. После загрузки языка один проход обновляет DOM.
4. При смене языка обновлять открытый экран без reload.

Пример:

```html
<button data-i18n="account.loginOrRegister"></button>
```

- прогресс;
- профиль;
- тренера;
- каталог;
- аккаунт;
- Premium;
- login/payment modals;
- legal screens.

## 6. Форматирование чисел, дат и единиц

Не собирать фразы конкатенацией вроде:

```js
count + ' тренировок'
```

Добавить locale-aware helpers:

- `Intl.NumberFormat`
- `Intl.DateTimeFormat`
- `Intl.RelativeTimeFormat`
- `Intl.PluralRules`

Для RU и EN отдельно проверить:

- тренировка / тренировки / тренировок;
- день / дня / дней;
- минута / минуты / минут;
- упражнение / упражнения / упражнений;
- кг;
- см;
- даты;
- месяцы;
- дни недели;
- десятичный разделитель.

На первом этапе единицы остаются метрическими. Imperial — отдельная задача, не часть перевода.

## 7. Язык озвучки

Уже существующий выбор TTS нужно связать с новой системой.

При смене языка интерфейса:

- если пользователь **не выбирал язык озвучки вручную**, TTS автоматически переключается RU ↔ EN;
- если выбирал вручную — его выбор сохраняется.

Все фразы, которые приложение произносит, должны идти через `t()`, а не быть зашиты по-русски.

Проверить:

- подготовка;
- название упражнения;
- отдых;
- следующий этап;
- пауза;
- завершение;
- итог;
- предупреждения.

## 8. Голосовые команды

Язык распознавания остаётся отдельной настройкой.

Логика по умолчанию:

- appLocale=ru → предложить русский пакет;
- appLocale=en → предложить английский пакет.

Но человек может выбрать другой язык команд независимо.

Словари команд и их синонимы хранить централизованно:

```js
VOICE_COMMANDS.ru
VOICE_COMMANDS.en
```

Native Android должен получать язык/команду, а не содержать пользовательскую бизнес-логику в нескольких местах.

Подсказки о скачивании, прогрессе, ошибках и готовности также локализуются.

---

## 9. AI: промты переводим на английский

Это отдельный обязательный этап.

### Что меняем

Все системные инструкции для AI делаем **на английском**, независимо от языка интерфейса.

Причины:

- единый canonical prompt;
- легче поддерживать модели разных провайдеров;
- не нужно иметь два комплекта логики промта;
- меньше расхождений между RU и EN версиями.

В каждый запрос передавать отдельно:

```
OUTPUT_LANGUAGE: Russian
```

или

```
OUTPUT_LANGUAGE: English
```

То есть **инструкции модели — English, пользовательский результат — на выбранном языке**.

### Важно: текущий формат AI нельзя просто перевести

Сейчас prompt, `parseProgramText` и `programToText` связаны русскими служебными маркерами вроде:

- УПРАЖНЕНИЕ
- ФОРМАТ
- ШАГ
- ПОТОЛОК
- ЗАМЕНА

Простой перевод prompt сломает parser.

Правильный вариант:

1. Ввести **AI schema v2**.
2. Перейти на JSON с английскими machine keys:
   - `name`
   - `description`
   - `sets`
   - `reps`
   - `durationSec`
   - `weightKg`
   - `progression`
   - и т.д.
3. Prompt всегда English.
4. Значения `name/description/instructions` модель пишет на `OUTPUT_LANGUAGE`.
5. Старый текстовый parser оставить как legacy fallback для импортов и старых ссылок.
6. Новый AI runtime работает только через v2 JSON.

Так локализация больше не будет зависеть от русского служебного формата.

### Где проверить

- создание программы;
- программа из YouTube;
- изменение программы;
- создание упражнения;
- изменение упражнения;
- замена упражнения;
- image prompts;
- AI retry/repair prompts;
- admin AI test prompt.

Image prompt тоже держать canonical English.

---

## 10. Пользовательский ввод в AI

Если интерфейс English, человек может всё равно написать запрос по-русски — и наоборот.

Поэтому:

- пользовательский текст не переводим перед отправкой;
- prompt сообщает модели язык **ответа**, а не язык входного текста;
- модель должна понимать исходный ввод как есть;
- названия уже существующих пользовательских упражнений не переводим автоматически.

## 11. Каталог, тренеры и публичные страницы

### Каталог: одна программа, два языка

В каталоге **не должно быть отдельных RU- и EN-копий одной программы**. Для пользователя это выглядело бы как дубли, делило бы статистику/популярность между двумя карточками и усложняло обновления.

Правильная модель: **одна catalog program entity с одним id и двумя локализациями контента**.

То, что не зависит от языка, хранится один раз:

- id программы;
- автор / trainer id;
- уровень;
- цель;
- длительность;
- структура дней;
- порядок упражнений;
- подходы, повторы, время, вес;
- прогрессия;
- обложка / media id;
- публикация, рейтинг, статистика использования;
- moderation/status.

Переводятся только человекочитаемые поля.

Пример целевой структуры:

```js
{
  id: 'program_123',
  sourceLocale: 'ru',
  contentVersion: 7,

  // Общая механика — одна для всех языков.
  days: [
    {
      id: 'day_1',
      exercises: [
        {
          id: 'ex_1',
          sets: 3,
          reps: 12,
          restSec: 60
        }
      ]
    }
  ],

  i18n: {
    ru: {
      title: 'Сильная спина дома',
      description: '...',
      dayTitles: {
        day_1: 'День 1'
      },
      exercises: {
        ex_1: {
          name: 'Тяга резинки к поясу',
          instructions: '...'
        }
      }
    },
    en: {
      title: 'Strong Back at Home',
      description: '...',
      dayTitles: {
        day_1: 'Day 1'
      },
      exercises: {
        ex_1: {
          name: 'Resistance Band Row',
          instructions: '...'
        }
      }
    }
  }
}
```

Нельзя делать две полные копии всей программы внутри `ru` и `en`: числовая структура тогда рано или поздно разъедется. Переводы должны ссылаться на стабильные ids дней/упражнений, а механика тренировки остаётся общей.

### Что видит пользователь

Каталог показывает **одну карточку** программы.

- `appLocale=ru` → берём `i18n.ru`;
- `appLocale=en` → берём `i18n.en`;
- если нужного перевода временно нет → показываем `sourceLocale`, но не создаём вторую карточку.

При переключении языка приложения эта же программа сразу отображается на другом языке: тот же id, тот же автор, та же статистика, тот же рейтинг.

Фильтр «язык программы» для такого каталога обычно не нужен, потому что опубликованная программа должна иметь обе локали.

### Как программа получает второй язык

Для **каталога** автоматический перевод нужен, но не в runtime у каждого пользователя.

Перевод создаётся **один раз при публикации или обновлении программы**:

1. Тренер создаёт программу на любом языке.
2. `sourceLocale` фиксирует исходный язык.
3. Перед отправкой в каталог сервер/AI создаёт недостающую RU или EN локализацию.
4. Перевод работает по структурированному JSON и **не имеет права менять механику**:
   - подходы;
   - повторы;
   - длительность;
   - вес;
   - порядок;
   - progression;
   - exercise ids.
5. Переводятся только title/description/name/instructions и другие display strings.
6. Перед публикацией обе локали проходят validation.
7. В админке модератор видит RU и EN рядом.
8. При необходимости автор/админ может вручную исправить перевод.

То есть AI здесь используется как **редактор локализованного текста**, а не как генератор второй программы.

### Обновления программы

У программы должен быть единый `contentVersion`.

Если автор меняет:

- числа/структуру → изменение автоматически относится к обеим языковым версиям;
- текст → соответствующий перевод помечается `stale` и обновляется.

Для переводов полезно хранить:

```js
translationStatus: {
  ru: 'source',
  en: 'ready' // ready | stale | failed
}
```

Не публиковать обновление каталога с половиной старого и половиной нового перевода. Новая версия становится видимой только когда обе локали валидны.

### AI-generated programs

Если программа создана через AI специально для пользователя, создавать второй язык сразу **необязательно** — это лишняя себестоимость.

Но когда такую программу отправляют в каталог, недостающая локаль создаётся в процессе публикации.

Итого:

- личная программа → хранит язык, на котором её создали;
- catalog program → обязана иметь RU + EN;
- в каталоге всегда одна карточка.

### Программы, добавленные из каталога

Если пользователь добавляет catalog program себе, лучше сохранять:

- общий language-neutral workout structure;
- обе локализации текста;
- `catalogProgramId` и `catalogContentVersion`.

Тогда смена языка приложения может переключить язык уже добавленной программы без повторного скачивания и без создания дубля.

После того как пользователь вручную меняет название/описание/упражнение у своей копии, изменённое поле становится **user-owned** и больше не должно молча заменяться переводом из каталога.

### Миграция существующего каталога

Для уже опубликованных русских программ:

1. считать текущий текст `sourceLocale='ru'`;
2. один раз пакетно сгенерировать `en`;
3. проверить structure invariants до/после перевода;
4. отправить результат на модерацию;
5. только после этого считать программу bilingual-ready.

Не создавать новые catalog ids и не сбрасывать статистику существующих программ.

### Тренеры и публичные страницы

UI публичной страницы тренера локализуем полностью.

Личный текст тренера — имя, «о себе», ссылки — **не переводим автоматически** в первом релизе. Это профиль человека, а не редакционный catalog content.

Позже для `about` можно добавить такую же модель:

```js
aboutI18n: { ru: '...', en: '...' }
```

но только как отдельную возможность с просмотром/редактированием владельцем.

### Публичная ссылка на catalog program

Одна и та же ссылка должна открывать одну программу.

Язык выбирается:

1. явный `?lang=ru|en`, если есть;
2. язык приложения/аккаунта;
3. язык браузера;
4. fallback на `sourceLocale`.

Не создавать отдельные RU/EN URL для одной программы.

## 12. Сервер и API

API-коды ошибок должны оставаться language-neutral:

```
bad_email
limit
premium_required
model_missing
```

Сервер **не должен** возвращать готовый русский текст ошибки, если клиент способен перевести код сам.

Frontend:

```js
apiErrorMessage(code)
```

→ локализованный текст.

Исключения — данные, которые реально должны быть сформированы сервером: письма, публичные HTML-страницы, notification payload при серверной отправке.

## 13. Email

Сейчас письмо входа/кода русское.

При auth-запросе клиент должен передавать:

```json
{ "locale": "ru" }
```

или `en`.

Локализовать:

- subject;
- текст;
- HTML;
- срок действия кода;
- fallback/error copy, если оно пользовательское.

Email locale не должен определяться по домену почты или IP.

## 16. Legal

Legal-тексты нельзя переводить кусками через runtime AI.

Нужны две вручную поддерживаемые версии:

- RU;
- EN.

Отдельные ключи/блоки для:

- Privacy Policy;
- Terms;
- Health & Safety;
- Premium/payment wording;
- operator/contact details.

Перед публикацией English legal copy желательно отдельно проверить юридически.

## 20. Админка

`admin.html` — внутренний инструмент, поэтому можно сделать позже основного UI.

Но обязательно локализовать/перевести на English **AI prompt templates и AI test prompts**, потому что это часть runtime, а не UI админки.

Решение по самой админке:

- либо оставить RU;
- либо тоже подключить общий i18n слой.

Не смешивать это с первым пользовательским релизом, если тормозит выпуск.

## 21. Автоматические проверки

Добавить скрипт, например:

```
npm run i18n:check
```

Он должен проверять:

1. ключ есть и в RU, и в EN;
2. нет дубликатов;
3. placeholders совпадают;
4. `data-i18n` ссылается на существующий ключ;
5. в canonical frontend не осталось очевидных hardcoded user-facing Russian strings;
6. AI prompt templates не содержат русских системных инструкций;
7. server email/native notification strings имеют обе локали.

Важно: комментарии, тестовые fixtures и пользовательский demo-content не считать ошибкой автоматически.

## 24. Что не делать

Не делать:

- два отдельных `index.html`;
- отдельную английскую ветку приложения;
- копии JS-файлов `*-en.js`;
- автоматический перевод интерфейса через AI в runtime;
- `if (lang === 'ru') ... else ...` в сотнях мест;
- перевод пользовательских названий программ/упражнений без спроса;
- определение языка по стране/IP;
- перевод AI prompt в два независимых RU/EN шаблона;
- изменение старого AI parser без backward compatibility.

---

## 25. Что считать готовым

RU/EN локализация считается готовой, если:

- язык можно переключить в настройках без перезапуска;
- после переключения на экране нет смеси RU/EN;
- после перезапуска выбор сохраняется;
- после входа на новом устройстве язык восстанавливается;
- весь основной UI и все ошибки переведены;
- TTS говорит на выбранном языке;
- голосовые команды по умолчанию предлагают пакет того же языка;
- notifications соответствуют выбранному языку;
- email-код приходит на выбранном языке;
- AI instruction prompts полностью English;
- AI генерирует пользовательский контент на выбранном языке;
- RU и EN проходят один и тот же smoke-test;
- старые программы, аккаунты, ссылки и сохранённые данные продолжают открываться.

## 26. Рекомендуемые технические решения

Для текущего plain JS + Capacitor стека отдельная i18n-библиотека не обязательна. Два языка и относительно компактный UI проще держать маленьким собственным модулем, чем тащить большой runtime.

Стоит использовать:

- собственный `t()` + dictionaries;
- browser `Intl.*` для чисел/дат/plural;
- Android resources только для native-owned strings;
- locale в API payload;
- English canonical AI prompts + language-neutral JSON schema.

Если позже языков станет 4–5+, можно перейти на FormatJS/i18next без изменения ключей и структуры словарей.

## 28. Отдельное архитектурное решение до начала работ

Нужно различать **личные программы** и **каталог**.

### Личная программа

Если уже существующая русская личная программа открыта после переключения приложения на English:

- UI становится English;
- текст самой программы остаётся русским;
- новые AI-программы создаются на текущем языке приложения;
- никакого скрытого автоматического перевода личного контента.

Это предсказуемо, не портит данные и не создаёт лишних AI-расходов.

### Программа из каталога

Каталог — исключение: опубликованная программа является одним bilingual-объектом с RU + EN локализацией.

Поэтому:

- дублей карточек RU/EN нет;
- один program id;
- одна структура тренировки;
- один рейтинг/счётчик использования;
- при переключении языка меняется только display-текст программы;
- механика и прогресс пользователя остаются теми же.

Именно эту модель считать целевой до начала реализации, чтобы схема каталога, AI schema v2 и sync не пришлось переделывать второй раз.

# Fit Timer — план полной локализации RU / EN

Статус: **план, без реализации**  
Цель первого релиза локализации: пользователь может выбрать **Русский / English** в настройках, после чего весь интерфейс, системные сообщения, письма, уведомления, озвучка, голосовые команды и генерируемый ИИ контент работают на выбранном языке без смешивания RU/EN.

---

## 1. Главный принцип

Локализация должна быть отдельным слоем приложения, а не набором `if (lang === 'en')` по файлам.

Нужно разделить четыре вещи:

1. **Язык интерфейса** — весь UI приложения, ошибки, подсказки, попапы, кнопки, правила, уведомления.
2. **Язык озвучки** — язык и конкретный TTS-голос.
3. **Язык голосовых команд** — RU/EN офлайн-пакет распознавания.
4. **Язык контента** — программы, упражнения, каталог, ответы ИИ, письма и публичные страницы.

По умолчанию все три пользовательских языка следуют языку интерфейса, но озвучку и голосовые команды можно изменить отдельно.

---

## 2. Где хранить выбранный язык

Добавить глобальную настройку:

```js
appLocale = 'ru' | 'en'
```

Хранение:

- локально на устройстве — обязательно;
- в аккаунте — синхронизировать, чтобы новый телефон подхватывал язык;
- при первом запуске без сохранённой настройки:
  - системный язык `ru*` → Русский;
  - всё остальное → English.

При ручном выборе язык меняется сразу, без перезапуска приложения.

### UI

В разделе **Другое → Профиль** или отдельным первым блоком **Язык**:

- Язык приложения
  - Русский
  - English

Не прятать язык внутрь «Звук»: это настройка всего приложения.

---

## 3. Архитектура переводов

Создать один источник переводов, например:

```
src/i18n/
  ru.js
  en.js
  index.js
```

Ключи — стабильные английские идентификаторы:

```js
{
  common: {
    save: 'Сохранить',
    cancel: 'Отмена'
  },
  account: {
    loginOrRegister: 'Вход или регистрация'
  },
  workout: {
    pause: 'Пауза'
  }
}
```

В English-файле те же ключи.

Базовые функции:

```js
t('account.loginOrRegister')
t('workout.completedCount', { count })
```

Требования:

- fallback всегда на English или явно выбранный базовый язык;
- в production не показывать ключ вроде `account.loginOrRegister`;
- dev/check должен находить отсутствующие ключи;
- нельзя держать один и тот же пользовательский текст одновременно в HTML и JS.

---

## 4. Статический HTML

Сейчас много русского текста зашито прямо в `src/html/*.html`.

План:

1. Разметку оставить общей.
2. Пользовательские строки заменить на ключи:
   - `data-i18n="..."`
   - `data-i18n-placeholder="..."`
   - `data-i18n-title="..."`
3. После загрузки языка один проход обновляет DOM.
4. При смене языка обновлять открытый экран без reload.

Пример:

```html
<button data-i18n="account.loginOrRegister"></button>
```

Отдельно пройти:

- onboarding;
- главную;
- программы;
- конструктор;
- тренировку;
- завершение;
- прогресс;
- профиль;
- тренера;
- каталог;
- аккаунт;
- Premium;
- login/payment modals;
- legal screens.

## 5. Динамические строки JavaScript

Самый большой объём работы — строки, которые формируются в `src/app/*.js`.

Нужно вынести:

- `textContent`;
- `innerHTML` с пользовательским текстом;
- `appAlert()`;
- `appDialog()`;
- подписи кнопок;
- empty states;
- ошибки;
- названия периодов;
- статусы загрузки;
- результаты тренировок;
- share-тексты;
- подписи графиков;
- trainer/catalog copy;
- Premium/account copy.

Не переводить комментарии разработчиков — только то, что реально видит пользователь.

---

## 6. Форматирование чисел, дат и единиц

Не собирать фразы конкатенацией вроде:

```js
count + ' тренировок'
```

Добавить locale-aware helpers:

- `Intl.NumberFormat`
- `Intl.DateTimeFormat`
- `Intl.RelativeTimeFormat`
- `Intl.PluralRules`

Для RU и EN отдельно проверить:

- тренировка / тренировки / тренировок;
- день / дня / дней;
- минута / минуты / минут;
- упражнение / упражнения / упражнений;
- кг;
- см;
- даты;
- месяцы;
- дни недели;
- десятичный разделитель.

На первом этапе единицы остаются метрическими. Imperial — отдельная задача, не часть перевода.

---

## 7. Язык озвучки

Уже существующий выбор TTS нужно связать с новой системой.

При смене языка интерфейса:

- если пользователь **не выбирал язык озвучки вручную**, TTS автоматически переключается RU ↔ EN;
- если выбирал вручную — его выбор сохраняется.

Все фразы, которые приложение произносит, должны идти через `t()`, а не быть зашиты по-русски.

Проверить:

- подготовка;
- название упражнения;
- отдых;
- следующий этап;
- пауза;
- завершение;
- итог;
- предупреждения.

---

## 8. Голосовые команды

Язык распознавания остаётся отдельной настройкой.

Логика по умолчанию:

- appLocale=ru → предложить русский пакет;
- appLocale=en → предложить английский пакет.

Но человек может выбрать другой язык команд независимо.

Словари команд и их синонимы хранить централизованно:

```js
VOICE_COMMANDS.ru
VOICE_COMMANDS.en
```

Native Android должен получать язык/команду, а не содержать пользовательскую бизнес-логику в нескольких местах.

Подсказки о скачивании, прогрессе, ошибках и готовности также локализуются.

---

## 9. AI: промты переводим на английский

Это отдельный обязательный этап.

### Что меняем

Все системные инструкции для AI делаем **на английском**, независимо от языка интерфейса.

Причины:

- единый canonical prompt;
- легче поддерживать модели разных провайдеров;
- не нужно иметь два комплекта логики промта;
- меньше расхождений между RU и EN версиями.

В каждый запрос передавать отдельно:

```
OUTPUT_LANGUAGE: Russian
```

или

```
OUTPUT_LANGUAGE: English
```

То есть **инструкции модели — English, пользовательский результат — на выбранном языке**.

### Важно: текущий формат AI нельзя просто перевести

Сейчас prompt, `parseProgramText` и `programToText` связаны русскими служебными маркерами вроде:

- УПРАЖНЕНИЕ
- ФОРМАТ
- ШАГ
- ПОТОЛОК
- ЗАМЕНА

Простой перевод prompt сломает parser.

Правильный вариант:

1. Ввести **AI schema v2**.
2. Перейти на JSON с английскими machine keys:
   - `name`
   - `description`
   - `sets`
   - `reps`
   - `durationSec`
   - `weightKg`
   - `progression`
   - и т.д.
3. Prompt всегда English.
4. Значения `name/description/instructions` модель пишет на `OUTPUT_LANGUAGE`.
5. Старый текстовый parser оставить как legacy fallback для импортов и старых ссылок.
6. Новый AI runtime работает только через v2 JSON.

Так локализация больше не будет зависеть от русского служебного формата.

### Где проверить

- создание программы;
- программа из YouTube;
- изменение программы;
- создание упражнения;
- изменение упражнения;
- замена упражнения;
- image prompts;
- AI retry/repair prompts;
- admin AI test prompt.

Image prompt тоже держать canonical English.

---

## 10. Пользовательский ввод в AI

Если интерфейс English, человек может всё равно написать запрос по-русски — и наоборот.

Поэтому:

- пользовательский текст не переводим перед отправкой;
- prompt сообщает модели язык **ответа**, а не язык входного текста;
- модель должна понимать исходный ввод как есть;
- названия уже существующих пользовательских упражнений не переводим автоматически.

---

## 11. Каталог, тренеры и публичные страницы

Разделить **UI** и **контент**.

UI локализуем полностью.

Пользовательский контент:

- имя тренера;
- «о себе»;
- название программы;
- описание;
- названия пользовательских упражнений;

не переводим автоматически.

Для каталога желательно добавить `language: 'ru' | 'en'` программе.

Позже можно:

- фильтровать каталог по языку;
- показывать язык карточки;
- дать автору выбрать язык публикации.

Не запускать автоматический машинный перевод чужих программ в первом релизе.

---

## 12. Сервер и API

API-коды ошибок должны оставаться language-neutral:

```
bad_email
limit
premium_required
model_missing
```

Сервер **не должен** возвращать готовый русский текст ошибки, если клиент способен перевести код сам.

Frontend:

```js
apiErrorMessage(code)
```

→ локализованный текст.

Исключения — данные, которые реально должны быть сформированы сервером: письма, публичные HTML-страницы, notification payload при серверной отправке.

---

## 13. Email

Сейчас письмо входа/кода русское.

При auth-запросе клиент должен передавать:

```json
{ "locale": "ru" }
```

или `en`.

Локализовать:

- subject;
- текст;
- HTML;
- срок действия кода;
- fallback/error copy, если оно пользовательское.

Email locale не должен определяться по домену почты или IP.

## 20. Админка

`admin.html` — внутренний инструмент, поэтому можно сделать позже основного UI.

Но обязательно локализовать/перевести на English **AI prompt templates и AI test prompts**, потому что это часть runtime, а не UI админки.

Решение по самой админке:

- либо оставить RU;
- либо тоже подключить общий i18n слой.

Не смешивать это с первым пользовательским релизом, если тормозит выпуск.

---

## 21. Автоматические проверки

Добавить скрипт, например:

```
npm run i18n:check
```

Он должен проверять:

1. ключ есть и в RU, и в EN;
2. нет дубликатов;
3. placeholders совпадают;
4. `data-i18n` ссылается на существующий ключ;
5. в canonical frontend не осталось очевидных hardcoded user-facing Russian strings;
6. AI prompt templates не содержат русских системных инструкций;
7. server email/native notification strings имеют обе локали.

Важно: комментарии, тестовые fixtures и пользовательский demo-content не считать ошибкой автоматически.

## 24. Что не делать

Не делать:

- два отдельных `index.html`;
- отдельную английскую ветку приложения;
- копии JS-файлов `*-en.js`;
- автоматический перевод интерфейса через AI в runtime;
- `if (lang === 'ru') ... else ...` в сотнях мест;
- перевод пользовательских названий программ/упражнений без спроса;
- определение языка по стране/IP;
- перевод AI prompt в два независимых RU/EN шаблона;
- изменение старого AI parser без backward compatibility.

---

## 25. Что считать готовым

RU/EN локализация считается готовой, если:

- язык можно переключить в настройках без перезапуска;
- после переключения на экране нет смеси RU/EN;
- после перезапуска выбор сохраняется;
- после входа на новом устройстве язык восстанавливается;
- весь основной UI и все ошибки переведены;
- TTS говорит на выбранном языке;
- голосовые команды по умолчанию предлагают пакет того же языка;
- notifications соответствуют выбранному языку;
- email-код приходит на выбранном языке;
- AI instruction prompts полностью English;
- AI генерирует пользовательский контент на выбранном языке;
- RU и EN проходят один и тот же smoke-test;
- старые программы, аккаунты, ссылки и сохранённые данные продолжают открываться.

---

## 26. Рекомендуемые технические решения

Для текущего plain JS + Capacitor стека отдельная i18n-библиотека не обязательна. Два языка и относительно компактный UI проще держать маленьким собственным модулем, чем тащить большой runtime.

Стоит использовать:

- собственный `t()` + dictionaries;
- browser `Intl.*` для чисел/дат/plural;
- Android resources только для native-owned strings;
- locale в API payload;
- English canonical AI prompts + language-neutral JSON schema.

Если позже языков станет 4–5+, можно перейти на FormatJS/i18next без изменения ключей и структуры словарей.

## 28. Отдельное архитектурное решение до начала работ

До первой кодовой правки нужно зафиксировать один момент:

**Что происходит с уже существующей русской программой, если приложение переключили на English?**

Рекомендуемый вариант:

- UI становится English;

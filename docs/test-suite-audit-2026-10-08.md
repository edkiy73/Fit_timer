# Аудит тестов AppBase — 2026-10-08 (этап 1)

## Принцип
Количество тестов само по себе не проблема. Убираем не защиту продукта, а ложноположительные проверки, дублирование и повторную подготовку инфраструктуры. Удалять сценарий можно только после фиксации, какой риск он покрывает, и проверки эквивалентного покрытия.

## Подтверждено по коду и недавним CI
- FitTimer: в `scripts/test-lists.mjs` зарегистрированы 47 unit/server, 36 browser, 2 static и 1 admin smoke. Это **сценарии/файлы**, а не подсчёт всех assertions.
- `tests/admin-ui-unit.js` (143 строки) проверяет большое количество `includes()` и имён функций по склеенному исходному коду. Риск: невинное переименование ломает CI, а присутствие строки не гарантирует работающий интерфейс. Сохранять проверки безопасности CSP/секретов; взаимодействия админки покрывать браузерным smoke.
- `tests/release-ux-unit.js` (58 строк) смешивает нативную упаковку, UI обновления, синхронизацию и политики CI. Риск: устаревшие ожидания о release workflow (уже вызывали падение PR #682). В этом PR усилена проверка, что публикация APK требует ручного запуска и не происходит на push.
- `tests/vercel-ignore-unit.js` проверяет функцию `shouldSkip()` на входных файлах: **оставить**, это быстрый поведенческий тест, защищающий бюджет.
- `apps/unmute/package.json`: `check` запускает typecheck, последовательную цепочку smoke, Vitest и build; `unmute.yml` затем снова запускает `npm run test:browser`, который **сам** выполняет build. Это отдельные полезные уровни проверки, но возможен повтор сборки артефакта.
- `apps/task-mini/package.json`: аналогично `check` и браузерный workflow оба собирают приложение.
- `scripts/apps.mjs setup` последовательно устанавливает зависимости **всех** приложений даже если `check:affected` затем проверяет одно. Это накладные расходы CI, не избыток тестов.
- `browser-tests.yml`: 4 независимых шарда, каждый подготавливает Node/npm/Chromium. Кеширование добавлено в PR #683; нужны замеры повторных запусков, прежде чем менять число шардов.

## Категории и решения
| Область | Сейчас | Решение | Приоритет |
|---|---|---|---|
| Авторизация, синхронизация, прогресс тренировок, данные и платежи | unit/API/browser | Не сокращать без замены; критические пользовательские риски | P0 |
| Админка: `admin-ui-unit` | Строковые проверки элементов и имён функций | Провести поутверждённую ревизию; заменить хрупкие UI проверки на DOM/interaction; оставить CSP и секреты | P1 |
| Выпуск Android: `release-ux-unit` | Текстовые проверки исходников и YAML | Удалить устаревшие утверждения; отдельно проверять политику публикации и данные APK | P1, начато |
| Vercel: `vercel-ignore-unit`, `scripts/test-vercel-deployment-policy.mjs` | Два набора похожих path tests | Сравнить кейсы, затем централизовать матрицу сценариев без потери safety coverage | P1 |
| Браузер FitTimer: 36 файлов | 4 шарда, каждый делает build | Замерить реальные времена файлов, перекос шардов, возможность переиспользования собранного dist | P2 |
| UnMute/Task Mini: `check` + e2e | Частично повторная сборка | Отделить build-артефакт от запуска e2e при доказанной эквивалентности и экономии | P2 |
| Эталонный стартер | Генерация и сборка на каждом затронутом PR | Запускать при изменении шаблона/генератора/общих контрактов, с отдельным надёжным условием | P2 |
| Все зависимости всех приложений | `npm run setup` | Устанавливать зависимости только затронутых проектов и обязательных Core | P2 |

## Порядок внедрения
1. Исправлять явные устаревшие тестовые ожидания небольшими PR без удаления важных сценариев; дождаться полного CI.
2. Снимать время по шагам, отдельно учитывать очередь GitHub, установку пакетов и реальное выполнение тестов.
3. Рефакторить один набор тестов за PR с прозрачным сравнением покрытия и времени.
4. Только после этого менять обязательные статусы/политику merge — не разрешать попадание непроверенного продукта в `main`.

## Что пока не утверждаем
- Полного списка неиспользуемых тестов пока нет: он потребует просмотра тела каждого сценария и истории дефектов.
- Успешный CI **не доказывает** отсутствие дублей или хорошее покрытие.
- Нельзя обещать итоговые 30–60 секунд без замеров и изменения архитектуры CI.
